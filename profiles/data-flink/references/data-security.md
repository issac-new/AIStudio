# 数据安全域调研：法规标准与工程实践能力（实时数仓团队视角）

> 调研完成日期：2026-09-04 | 数据获取时间窗口：2024-03 至 2026-01 官方与一手来源
> 目标读者：Hermes data 团队（Flink / Paimon / Fluss / Dinky / MySQL / Redis 实时数仓技术栈）
> 主旨：给团队一张「法定义务 → 技术控制点 → 可固化 SOP」的映射表，让数据安全从合规文本变成 Flink 作业和 Paimon catalog 里可执行的配置。

## Executive Summary

**3 个决定性发现：**

1. **任务书里给的标准号有误，需先行纠偏**：GB/T 43698-2024 是《网络安全技术 软件供应链安全要求》，**不是**重要数据识别标准；真正对应「重要数据识别 + 数据分类分级」的国标是 **GB/T 43697-2024《数据安全技术 数据分类分级规则》**（2024-03-15 发布 / 2024-10-01 实施）。本报告正文按正确标准号展开，并在 §2.1 单独说明。
2. **网安法已完成首次大修，罚则大幅上调**：2025-10-28 十四届全国人大常委会第十八次会议通过《关于修改〈网络安全法〉的决定》（主席令第 61 号），**2026-01-01 已施行**——罚款上限从旧法最高 100 万元提至**1000 万元**，且新增「造成大量数据泄露」即触发 50–200 万的罚档。对数仓团队意味着：日志留存、数据分类分级、出境管控已不再是「建议」，而是高罚则下的硬义务。
3. **Paimon/Iceberg 的 Ranger 集成尚未成熟，权限下沉不能只靠 Ranger**：Paimon 1.4 官方文档明确其权限系统是**基于身份（IBAC）的文件型权限**，仅覆盖 filesystem/hive catalog，且官方 SECURITY.md 明确「row-level/column-level access control 不是 Paimon 的主 enforcement point」；Ranger 对 Paimon 无官方 plugin（apache/paimon#2990 仍是 open feature request），对 Iceberg 的原生 plugin 也未进入主线（apache/iceberg#3619 已以 not_planned 关闭）。团队要做细粒度权限，现实的路径是 **Paimon 内置 file-based privilege + Gravitino 统一元数据层推送 Ranger** 或 **REST Catalog 服务端行列级过滤** 三条线并行评估。

**其余为支撑细节：** 法规罚则矩阵（§1–2）、行业规范（§3）、国际框架（§4）、工程实践（§5）、落地 SOP（§6）。数据团队可直接执行的是 §6 的检查清单。

**层级关系标注**：§1–2 是法定义务（必须做），§3–4 是行业/国际最佳实践（应做，涉境外业务则部分为法定），§5 是技术手段（怎么做），§6 是工程固化（做到什么粒度）。递进关系，非并列。

## 1. 国内三法：核心义务与罚则

### 1.1 《中华人民共和国网络安全法》

| 属性 | 内容 |
|---|---|
| 文号 | 2016-11-07 十二届全国人大常委会第二十四次会议通过；2025-10-28 十四届全国人大常委会第十八次会议修正（主席令第 61 号） |
| 生效 | 原 2017-06-01 施行；修正后自 **2026-01-01** 施行 |
| 发布机构 | 全国人大常委会 |
| 罚则要点 | 见下表 |
| 对数据团队实际约束 | 等级保护定级、日志留存 ≥6 个月、CII 数据境内存储、事件报告 |

**核心义务**（数仓相关）：

- **网络运行安全**（2025 修正版第 23 条）：实行网络安全等级保护制度，制定内部安全管理制度、确定负责人、采取防范病毒与网络攻击的技术措施、采取监测记录网络运行状态与安全事件的技术措施、**按规定留存网络日志不少于 6 个月**、采取数据分类/重要数据备份和加密等措施。
- **关键信息基础设施（CII）**（2025 修正版第 35–40 条）：一旦被认定为 CII 运营者，个人信息和重要数据须境内存储，确需出境须通过安全评估；采购网络产品服务需安全审查。
- **AI 治理**（修正新增第 20 条）：国家支持 AI 基础理论与关键技术研发、推进训练数据资源与算力基建、完善伦理规范、加强风险监测评估与安全监管。对数仓团队意味着训练数据集的来源合规与质量追溯成为新的显性要求。

**罚则**（修正后第 61 条，2026-01-01 施行版本）：

| 情形 | 罚款幅度 | 直接责任人 |
|---|---|---|
| 不履行第 23/27 条安全保护义务 | 责令改正、警告，可处 1–5 万；拒不改正或有后果 5–50 万 | 1–10 万 |
| CII 运营者不履行第 35/36/38/40 条义务 | 警告，可处 5–10 万；拒不改正 10–100 万 | 1–10 万 |
| 造成大量数据泄露、CII 丧失局部功能等严重后果 | **50–200 万** | 5–20 万 |
| CII 丧失主要功能等特别严重后果 | **200–1000 万** | 20–100 万 |

### 1.2 《中华人民共和国数据安全法》（DSL）

| 属性 | 内容 |
|---|---|
| 文号 | 2021-06-10 十三届全国人大常委会第二十九次会议通过 |
| 生效 | 2021-09-01 |
| 发布机构 | 全国人大常委会 |
| 罚则要点 | 见下表 |
| 对数据团队实际约束 | 数据分类分级保护（第 21 条）、重要数据目录备案、风险评估、出境管控、数据交易中介义务 |

**核心义务**（数仓相关）：

- **数据分类分级保护制度**（第 21 条）：国家按数据在经济社会发展中的重要程度，以及遭篡改/破坏/泄露/非法获取/非法利用后对国家安全、公共利益、个人或组织合法权益的危害程度，对数据实行分类分级保护；**各地区、各部门确定本地区、本部门以及相关行业、领域的重要数据具体目录**，对列入目录的数据进行重点保护。这是所有下游分类分级工程工作的法律原点。
- **核心数据更严格保护**（第 21 条第 2 款）：关系国家安全、国民经济命脉、重要民生、重大公共利益等的数据属于国家核心数据，实行**更严格的管理制度**。
- **风险评估**（第 30 条）：重要数据处理者应当定期开展风险评估，并向有关主管部门报送风险评估报告。
- **出境管控**（第 31 条）：重要数据出境适用网安法及《数据出境安全评估办法》等规定。
- **数据交易**（第 33 条）：数据交易中介须要求数据提供方说明数据来源，审核交易双方身份并留存记录。

**罚则**（第 45 条）：

| 情形 | 罚款幅度 | 直接责任人 | 其他 |
|---|---|---|---|
| 不履行数据安全保护义务 | 责令改正、警告，可处 5–50 万 | 1–10 万 | 可责令暂停相关业务、停业整顿、吊销许可证/营业执照 |
| 不履行保护义务造成大量数据泄露等严重后果 | **50–200 万** | **10–100 万** | 同上 |
| 违反国家核心数据管理制度，危害国家主权、安全和发展利益 | **200–1000 万** | — | 责令暂停相关业务、停业整顿、吊销许可证/营业执照；构成犯罪追究刑责 |

### 1.3 《中华人民共和国个人信息保护法》（PIPL）

| 属性 | 内容 |
|---|---|
| 文号 | 2021-08-20 十三届全国人大常委会第三十次会议通过 |
| 生效 | 2021-11-01 |
| 发布机构 | 全国人大常委会 |
| 罚则要点 | 见下表（目前国内三法中顶格罚款最高） |
| 对数据团队实际约束 | 告知同意、敏感个人信息单独同意、PIA（个人信息保护影响评估）、跨境三条路径、个人权利响应 |

**核心义务**（数仓相关）：

- **处理合法性基础**（第 13 条）：取得个人同意、订立/履行合同所必需、履行法定职责或义务、应对公共卫生事件或紧急情况、公共利益实施新闻报道、处理已合法公开的信息、法律法规规定的其他情形。
- **告知同意**（第 14/17 条）：同意须在个人充分知情前提下自愿、明确作出；处理前须以显著方式、清晰易懂的语言真实、准确、完整告知处理者身份和联系方式、处理目的与方式、处理的个人信息种类与保存期限、个人行使权利的方式和程序。
- **敏感个人信息单独同意**（第 28–32 条）：生物识别、宗教信仰、特定身份、医疗健康、金融账户、行踪轨迹，以及**不满十四周岁未成年人的个人信息**，须有特定目的和充分必要性、严格保护措施，且取得单独同意。对数仓团队意味着：任何含身份证号、手机号、定位、健康、金融账户的字段进入 ODS 层即触发单独同意与加密存储义务。
- **个人信息保护影响评估（PIA）**（第 55/56 条）：处理敏感个人信息、利用个人信息进行自动化决策、委托处理/对外提供/公开披露、向境外提供、其他对个人权益有重大影响的处理活动，须事前进行影响评估并留存**处理情况记录 ≥3 年**。
- **个人权利响应**（第 44–50 条）：知情权、决定权、查阅复制权、可携带权、更正补充权、删除权、要求解释权，以及拒绝仅通过自动化决策方式作出决定的权力。
- **个人信息保护负责人**（第 52 条）：处理个人信息达到国家网信部门规定数量的处理者，须指定个人信息保护负责人。
- **合规审计**（第 54/64 条）：处理者须定期对其个人信息处理活动遵守法律、行政法规的情况进行合规审计。

**罚则**（第 66 条）：

| 情形 | 罚款幅度 | 直接责任人 | 其他 |
|---|---|---|---|
| 一般违法 | 责令改正、警告、没收违法所得；拒不改正处 **100 万以下**罚款 | — | 可责令暂停或终止提供服务 |
| 情节严重 | **5000 万以下或上一年度营业额 5% 以下**罚款 | **10–100 万**，可禁止一定期限内担任相关企业董监高和个人信息保护负责人 | 责令暂停相关业务或停业整顿、吊销相关业务许可或营业执照 |

## 2. 国内配套：国标与出境路径

### 2.1 ⚠️ 标准号纠偏：GB/T 43697-2024（非 43698）

**任务书原文写的是「GB/T 43698-2024 重要数据识别」，经查证有误：**

| 标准号 | 正确名称 | 发布/实施 | 说明 |
|---|---|---|---|
| **GB/T 43697-2024** | 《数据安全技术 数据分类分级规则》 | 2024-03-15 发布 / 2024-10-01 实施 | 含重要数据识别指南（附录 G 规范性）+ 核心数据定义 + 一般/重要/核心三级判定规则 |
| GB/T 43698-2024 | 《网络安全技术 软件供应链安全要求》 | 2024-04-25 发布 / 2024-11-01 实施 | 与数据分类分级无关，是软件供应链安全标准 |

**三角验证**：openstd.samr.gov.cn 官方平台（GB/T 43697 页面）+ 锦天城律所解读文章 + 长扬科技解读文章，三源一致。

**GB/T 43697-2024 关键内容**（对数仓团队）：

- **三级判定**：一般数据（未识别为核心/重要的其他数据）→ 重要数据（特定领域/群体/区域或达到一定精度规模，遭破坏可能直接危害国家安全、经济运行、社会稳定、公共健康和安全）→ 核心数据（对领域/群体/区域有较高覆盖度或较高精度、较大规模、一定深度，一旦非法使用或共享可能直接影响政治安全）。
- **附录 G《重要数据识别指南》（规范性）**：给出识别因素（影响国家政治/国土/军事/经济/文化/社会/科技/网络/生态/资源/核安全等）与识别流程。这是团队建立**重要数据清单**的直接依据。
- **行业差异化落地**：标准要求行业主管部门在国标框架下制定本行业细则（金融/工业/汽车见 §3）。
- **附录 J《动态更新场景参考》**：明确数据因汇聚融合、时效变化、加工处理方式变化时的**级别复核与变更机制**——这是数仓团队最容易忽略的点：数据被多次 JOIN/聚合后敏感度可能上升，须重新定级。

### 2.2 GB/T 35273-2020《信息安全技术 个人信息安全规范》

| 属性 | 内容 |
|---|---|
| 标准号 | GB/T 35273-2020，替代 GB/T 35273-2017 |
| 发布/实施 | 2020-03-06 发布 / 2020-10-01 实施 |
| 发布机构 | 国家市场监督管理总局、国家标准化管理委员会（TC260 归口） |
| 罚则要点 | 推荐性国标，无直接罚则；但作为 TC260 权威实践基准，在监管执法、认证、App 专项整治中作为**事实判据** |
| 对数据团队实际约束 | 告知同意的具体实现形态（单选/双选/单独同意）、最小必要、用户画像使用限制、个性化展示、第三方接入管理、汇聚融合限制 |

**关键变化**（2017 → 2020 版）：主体称谓从「个人信息控制者」改为「个人信息处理者」，与 PIPL 术语对齐；新增「多项业务功能的自主选择」「用户画像的使用限制」「个性化展示的使用」「基于不同业务目的所收集个人信息的汇聚融合」「第三方接入管理」「个人信息安全工程」「个人信息处理活动记录」；细化完善个人生物识别信息要求。

**工程落地要点**：这份标准是「怎么落地 PIPL 告知同意」最细的实践规范。对数仓团队，重点是「**汇聚融合限制**」——数仓天然是汇聚点，需确保融合后的数据若超出原告知目的，需重新告知同意或匿名化。

### 2.3 数据出境三条路径 + 豁免规则

| 路径 | 法规 | 发布/施行 | 关键门槛 |
|---|---|---|---|
| **① 数据出境安全评估** | 《数据出境安全评估办法》（国家网信办令第 11 号） | 2022-07-07 公布 / 2022-09-01 施行 | 触发条件（原 2022 版）：向境外提供重要数据；CII 运营者和处理 100 万人以上个人信息的数据处理者向境外提供个人信息；自上年 1 月 1 日起累计向境外提供 10 万人个人信息或 1 万人敏感个人信息 |
| **② 个人信息出境标准合同（SCC）** | 《个人信息出境标准合同办法》（国家网信办令第 13 号） | 2023-02-24 公布 / 2023-06-01 施行 | 未达①门槛时的合规通道；须备案 |
| **③ 个人信息保护认证** | 《关于实施个人信息保护认证的公告》（市场监管总局、国家网信办联合发布） | 2023-11-01 | 适合集团内跨境/多条业务线共用一套合规体系 |
| **豁免 + 放宽** | 《促进和规范数据跨境流动规定》（国家网信办令第 16 号） | 2024-03-22 公布并施行 | **调整关键门槛**：安全评估触发条件改为「自当年 1 月 1 日起累计向境外提供 100 万人以上个人信息（不含敏感）或 1 万人以上敏感个人信息」；新增 6 种豁免情形；自贸区负面清单机制；评估结果有效期 3 年（可延 3 年） |

**数仓团队实际约束**：

- **豁免判定是第一道检查**：《促进和规范数据跨境流动规定》第 5 条列出多种豁免情形，包括「为订立、履行个人作为一方当事人的合同所必需」（跨境购物/寄递/汇款/支付/开户/机票酒店预订/签证办理/考试服务）、「人力资源管理必需」「紧急情况为保护自然人生命健康和财产安全」等。团队应先判定是否落入豁免，再决定走哪条路径。
- **安全评估有效期与重评触发**：评估结果有效期 3 年；目的/方式/范围/种类变化、境外接收方所在国法规变化、实际控制权变化、保存期限延长等情形须**重新申报**。数仓团队在做跨地域同步链路改造时，须走「变更 → 重新评估」流程。
- **重要数据出境的独立通道**：重要数据**不在** SCC/认证路径内，只能走安全评估。识别出重要数据（见 §2.1）等于自动落入安全评估路径。

### 2.4 《中华人民共和国密码法》

| 属性 | 内容 |
|---|---|
| 文号 | 2019-10-26 十三届全国人大常委会第十四次会议通过 |
| 生效 | 2020-01-01 |
| 发布机构 | 全国人大常委会 |
| 罚则要点 | 见下 |
| 对数据团队实际约束 | 商用密码用于非国家秘密信息保护；商用密码须符合强制性国家标准；检测认证体系 |

**分类管理**：

- **核心密码 / 普通密码**：用于保护国家秘密信息，属国家秘密，由密码管理部门严格统一管理。数仓团队一般不涉及。
- **商用密码**：用于保护**非国家秘密**的信息。**数仓团队日常涉及的 TLS、KMS、字段级加密、透明加密（TDE）全部落在商用密码范畴**。

**核心义务**：

- 第 27 条：法律、行政法规和国家有关规定要求使用商用密码进行保护的关键信息基础设施，其运营者应当使用商用密码进行保护，**自行或委托商用密码检测机构开展商用密码应用安全性评估（密评）**；未通过评估的，须整改。
- 第 26 条：涉及国家安全、国计民生、社会公共利益的商用密码产品，应列入网络关键设备和网络安全专用产品目录，由具备资格的机构检测认证合格后方可销售或提供。
- 第 25 条：国家推进商用密码检测认证体系建设。

**罚则**（第 36–37 条）：违反第 27 条规定，由密码管理部门责令改正并警告；拒不改正或造成危害网络安全等后果的，处 10–100 万罚款，对直接负责的主管人员处 1–10 万罚款。违反第 26 条，由市场监管/密码管理部门责令停止销售或提供，没收违法产品和违法所得，并处违法所得 1–10 倍罚款；没有违法所得的，处 10–100 万罚款。

**实际约束**（对数仓团队）：

- KMS 选型须支持国密算法（SM2/SM3/SM4）以备密评；若系统被认定为 CII，**密评是强制项**。
- 字段级加密（如手机号、身份证号）应优先选 SM4-GCM 而非 AES（或两者并行），降低未来合规改造风险。
- 传输加密 TLS 应考虑支持国密 TLS（TLCP 协议）以备国产化/密评场景。

| 属性 | 内容 |
|---|---|
| 文号 | 国务院令第 790 号 |
| 通过/施行 | 2024-08-30 国务院第 40 次常务会议通过 / **2025-01-01 施行** |
| 发布机构 | 国务院 |
| 罚则要点 | 法律责任章节衔接《数安法》《个保法》处罚；不新设高于上位法的罚款 |

### 3.1 金融业

#### JR/T 0197-2020《金融数据安全 数据安全分级指南》

| 属性 | 内容 |
|---|---|
| 标准号 | JR/T 0197-2020 |
| 发布 | 中国人民银行 2020-09-23 发布 / 2020-11-01 实施（推荐性行业标准） |
| 罚则要点 | 推荐性，但央行对金融机构的数据安全检查以此为准据 |
| 对数据团队实际约束 | 5 级分类分级法、级别变更管理（汇聚融合/时效/加工方式变化须重新定级） |

**5 级定义**（对数仓团队映射）：

| 级别 | 判定 | 典型数据示例 | 数仓侧处理 |
|---|---|---|---|
| **5 级** | 重要数据；破坏后危害国家安全或对公众权益造成严重影响 | 大型金融机构关键业务数据、国家金融基础数据 | **物理隔离存储、加密+校验、严格权限审批**；一般数仓不承载 |
| **4 级** | 个人金融信息中的 **C3 类**（用户鉴别信息，如密码、密钥、生物特征模板）；破坏后对公众权益造成一般影响或对个人/企业造成严重影响 | 登录密码、交易密码、生物特征 | **加密存储 + 不进数据仓库明细层**；如必须，只存哈希值 |
| **3 级** | 个人金融信息中的 **C2 类**（可识别特定个人金融信息主体身份与金融状况的信息，如交易记录、账户余额）；破坏后对公众权益轻微影响或对个人/企业一般影响 | 交易流水、账户余额、征信报告 | **字段级加密或脱敏进入 ODS/DWD**；DWS 层聚合展示时脱敏 |
| **2 级** | 个人金融信息中的 **C1 类**（机构内部使用的个人金融信息）；破坏后对个人/企业轻微影响 | 内部标记的用户标识、渠道偏好 | 内部访问控制 |
| **1 级** | 公开数据 | 公开产品信息、市场公开数据 | 无特殊要求 |

**级别变更管理**（第 9 节，数仓团队最需要理解的点）：数据内容变化、时效变化、规模变化、使用场景变化、**汇聚融合**、国家/行业主管部门要求变化——任一情形都应触发级别变更评估。数仓中「汇聚融合」意味着：**同一字段在 ODS 层和 DWS 层的敏感级别可能不同**（如交易时间戳与身份证号 JOIN 后可唯一识别个人，聚合表敏感度上升），须重新定级。

## 4. 国际框架

### 4.1 GDPR（欧盟通用数据保护条例）

| 属性 | 内容 |
|---|---|
| 法规号 | Regulation (EU) 2016/679 |
| 生效 | 2016-04-27 通过 / **2018-05-25** 施行 |
| 发布机构 | 欧洲议会和欧盟理事会 |
| 罚则要点 | 两档：1000 万欧元或上一年度全球营业额 2%（较轻）；**2000 万欧元或上一年度全球营业额 4%**（较重，如违反数据主体权利、跨境传输规则） |
| 对数据团队实际约束 | 涉欧盟个人数据的处理活动：合法基础、数据主体权利、隐私设计（Privacy by Design）、DPIA、DPO 任命、跨境传输（SCC/BCR/Adequacy） |

**数仓团队关键要点**：

- **数据主体 8 项权利**：访问、更正、被遗忘（删除）、限制处理、可携带、反对、免受纯自动化决策约束。删除权（Right to be Forgotten）对数仓最具冲击力——需要支持**跨层（ODS/DWD/DWS）溯源删除**，而非只删源库。
- **记录处理活动（RoPA）**：处理者须保存处理活动记录，供监管机构检查。
- **跨境传输**：欧盟境内数据出境须基于 Adequacy 决定、适当保障措施（SCC/BCR）或特定情形的豁免。
- **72 小时泄露通报**：数据泄露后 72 小时内报告监管机构；高风险时还要通知数据主体。
- **DPO（数据保护官）**：大规模系统性监控或处理特殊类别数据时须任命。

### 4.2 ISO/IEC 27001:2022（信息安全管理体系）

| 属性 | 内容 |
|---|---|
| 标准号 | ISO/IEC 27001:2022（替代 2013 版） |
| 发布 | 2022-10 发布 |
| 发布机构 | ISO/IEC JTC 1/SC 27 |

### 4.3 ISO/IEC 27701:2025（隐私信息管理体系 PIMS）

| 属性 | 内容 |
|---|---|
| 标准号 | ISO/IEC 27701:2025（替代 2019 版） |
| 发布 | **2025-10-14** 发布 |
| 发布机构 | ISO/IEC JTC 1/SC 27 |
| 罚则要点 | 无罚则；认证性标准 |
| 对数据团队实际约束 | 2025 版是**里程碑式修订：不再要求先取得 ISO 27001 认证**，可独立认证 PIMS；转型期至 2027-10（认证机构）/2028-10（证书到期） |

**2025 版关键变化**：

- **独立认证路径**：2019 版是 27001 的「附加件」（Annex A/B 扩展），2025 版改为完整独立的管理体系标准，隐私可与 ISMS 分开建设。
- **控制集重构**：与 27001:2022 / 27002:2022 对齐，隐私控制按**功能**（而非域）分组。
- **新增内容**：AI 与云环境下的隐私治理、供应商隐私管理、**数据主体权利的运行化**（DPIA、数据主体权利请求响应、跨境传输影响评估）。
- **认证转型的现实意义**：如团队所在组织已有 27001 认证，可在过渡期内补齐隐私控制；如未做 27001，**2025 版允许从隐私单点切入**（适合数据平台型团队），后续再补 ISMS。

### 4.4 NIST Privacy Framework

| 属性 | 内容 |
|---|---|
| 标准号 | NIST Privacy Framework v1.0（2020-01）/ v1.1 IPD（CSWP 40，2025-04-14） |
| 发布机构 | 美国 NIST |
| 罚则要点 | 自愿性框架，无罚则 |

**结构**：Core（Identify-P / Govern-P / Control-P / Communicate-P / Protect-P 五大功能）+ Profiles（现状/目标差距）+ Tiers（Partial / Risk Informed / Repeatable / Adaptive 四级成熟度）。

### 4.5 SOC 2（AICPA Trust Services Criteria）

| 属性 | 内容 |
|---|---|
| 标准依据 | AICPA《2017 Trust Services Criteria（含 2022 年修订的 Points of Focus）》 |
| 发布机构 | 美国 AICPA / CIMA |
| 罚则要点 | 无政府罚则；但审计报告是 SaaS/云服务商用向客户交付的**市场准入凭证** |
| 对数据团队实际约束 | 五类信任服务标准：安全性（必选）、可用性、处理完整性、保密性、隐私；Type I（某时点）与 Type II（一段期间）两种审计报告形态 |

**数仓团队相关**：保密性（Confidentiality）与隐私（Privacy）两类 TSC 与数据安全直接相关——保密性要求对敏感数据加密、访问控制、传输加密、介质销毁；隐私要求对个人数据的通知、选择、收集、使用、保留、披露的合规控制。SOC 2 Type II 要求**在审计期内**持续提供控制有效性证据，这意味着日志、权限审批、变更记录要能被审计员随时抽查——对数仓团队的启示是：**权限变更、数据导出、脱敏规则变更须有留痕**。

## 5. 工程实践：从合规到技术控制

### 5.1 分类分级落地流程

参照 GB/T 43697-2024 + JR/T 0197-2020 的通用方法，落地到数仓可抽象为 **6 步**：

| 步骤 | 动作 | 产出 | 数仓团队角色 |
|---|---|---|---|
| 1. 数据资产盘点 | 梳理 MySQL/Redis/Paimon/Kafka 中的数据资产清单 | 数据资产目录（库/表/字段） | Dinky 里登记 Paimon catalog 资产 |
| 2. 业务属性分类 | 按「行业领域→业务条线→业务属性」三层分类 | 分类清单（如：用户域→交易子域→订单明细） | Flink 作业血缘分析辅助 |
| 3. 定级要素评估 | 对每张表/字段评估完整性/保密性/可用性破坏后的影响 | 初步级别（一般/重要/核心 或 1–5 级） | 敏感度扫描（列名/样本值模式识别）辅助人工 |
| 4. 级别判定与复核 | 参考行业目录与法规判定；考虑汇聚融合/时效/加工方式调整 | 定级清单（表级+字段级） | **Paimon 表 options 中加 `data.classification` 标签** |
| 5. 审核批准 | 数据安全负责人/最高决策组织审核 | 正式定级结论 | 定级结论落盘到元数据/权限系统 |
| 6. 变更管理 | 源数据/加工方式/汇聚融合变化时重新评估 | 变更记录 | Flink 作业上线/下线/加字段时触发重评流程 |

**关键工程实践**：定级不应一次性完成，而是**随管道演化持续维护**。建议把「新表上线必须带 classification 标签」固化为 CI 门禁，未打标的表禁止写入生产 catalog。

### 5.2 脱敏（静态 / 动态）

| 维度 | 静态脱敏（SDM） | 动态脱敏（DDM） |
|---|---|---|
| 时机 | ETL/离线批处理时落盘**已脱敏数据** | 查询/读取时按用户角色/策略实时脱敏 |
| 典型场景 | 测试环境数据集、数据共享给第三方、离线分析 | 生产环境 BI 查询、客服系统按角色查看 |
| 实现方式 | 批处理作业中用 UDF/Spark/Flink 函数对字段改写 | 数据库代理层（如 MySQL Proxy + 脱敏插件）、查询网关、视图层 |
| 优缺点 | 落盘后不可逆；但测试环境数据和真实数据存在偏差 | 灵活（同一数据按角色不同视图）；但代理层有性能开销 |

**数仓团队映射**：

- **Paimon/MySQL 明细表**：适合静态脱敏（ODS→DWD 过程中写入脱敏后的字段，或保留原字段+新增 `xxx_masked` 字段）。
- **BI/查询入口**（Dinky SQL 查询、Superset 等）：适合动态脱敏（按登录用户角色判断是否显示原值）。
- **Redis 缓存**：应避免缓存未脱敏敏感字段；若必须缓存，用**应用层脱敏后写入**而非依赖读取时脱敏。
- **跨环境同步**（生产 → 测试）：必须走静态脱敏管道，禁止直接 dump。

**常用脱敏算法**：遮盖（`138****5678`）、替换（用虚拟值）、哈希（单向，可关联）、加密（可逆，需 KMS）、泛化（年龄→年龄段）、扰动（加噪声，用于统计）。**PIPL 第 73 条定义「匿名化」是「无法识别且不能复原」，纯哈希/固定盐哈希不等于匿名化**——团队口径要统一，避免「脱敏=合规」的误解。

### 5.3 加密（KMS / 透明加密）

| 维度 | KMS（密钥管理服务） | 透明加密（TDE） |
|---|---|---|
| 粒度 | 字段级 / 文件级 / 对象级 | 存储介质级 / 文件系统级 / 表空间级 |
| 典型实现 | 云厂商 KMS（阿里云 KMS、AWS KMS）、Vault、自建国密 KMS | MySQL InnoDB TDE（keyring plugin）、HDFS TDE（encryption zone）、S3 SSE |
| 应用层耦合 | 需要应用代码显式调用加解密 | 应用无感知，存储引擎自动处理 |
| 性能 | 加密/解密在应用侧，对 CPU 有消耗 | 存储引擎侧处理，I/O 略有开销 |
| 审计 | 可记录每次加解密调用 | 依赖存储层日志 |

**数仓团队映射**：

- **Paimon/HDFS/S3**：用存储层加密（S3 SSE-KMS、HDFS encryption zone）；重要/核心数据建议端到端加密（应用写入前加密）。
- **MySQL**：开启 InnoDB 表空间加密（keyring_file 或 keyring_okv 插件，国密可选 keyring_kmip + 支持国密的 KMS）。
- **Redis**：传输加密（TLS）；存储层加密一般不用（性能代价大），敏感字段在应用侧加密后写入。
- **Flink 作业间通信**：Kafka 启用 SSL/SASL；Flink Web UI / REST 启用 HTTPS。
- **密钥管理**：主密钥与数据密钥分离（envelope encryption）；密钥轮换周期化；密钥访问有审计。

### 5.4 权限模型（RBAC / ABAC；Ranger 与 Paimon/Iceberg 集成现状）

#### RBAC vs ABAC

| 维度 | RBAC（基于角色） | ABAC（基于属性） |
|---|---|---|
| 判定逻辑 | 用户 → 角色 → 权限 | 用户属性 + 资源属性 + 环境属性 → 策略 |
| 典型实现 | Ranger 角色、Kafka ACL、K8s RBAC | OPA（Open Policy Agent）、Ranger 标签策略 |
| 适用场景 | 职责清晰、角色稳定（数据工程师/分析师/运维） | 数据量大、维度多（按部门/项目/敏感级别动态控制） |
| 数仓建议 | 基础层用 RBAC（Paimon 内置权限、MySQL GRANT） | 细粒度层引入 ABAC（按 classification 标签决定谁能查哪级表） |

**推荐实践**：RBAC 打底（谁能进数仓），ABAC 做细化（哪些敏感字段可见），两者组合而非互斥。

#### Apache Ranger 与 Paimon/Iceberg 的权限集成现状（关键工程事实）

这是本调研中**最需要基于真实社区状态**的判断，避免团队按过时博客文章踩坑：

**Paimon 侧**：

- Paimon **1.4 版官方文档**（paimon.apache.org/docs/1.4/maintenance/manage-privileges）明确：Paimon 提供基于 catalog 的权限系统，采用 **IBAC（identity-based access control）**，权限直接授予用户；当前仅支持 **file-based privilege system**，且仅对 `'metastore'='filesystem'` 或 `'metastore'='hive'` 的 catalog 生效。
- Paimon 官方 `SECURITY.md`（github.com/apache/paimon/blob/master/SECURITY.md）明确 Paimon 的安全威胁模型：**Paimon 不是用户级权限/行级/列级访问控制的主要 enforcement point**——它期望由查询引擎（Flink/Spark/Trino/StarRocks）或存储层（S3/HDFS ACL）或 REST Catalog 服务端来承担这些职责；Paimon 自身仅通过 REST Catalog 的 `authTableQuery` API **转发**服务端返回的 row filter 与 column masking 规则，但 **enforcement 在引擎或服务端**。
- **Ranger 对 Paimon 没有官方 plugin**：apache/paimon#2990「Integration with Apache Ranger to manage the privilege for paimon」截至检索日（2026-09-04）仍为 **open 的 feature request**，无合并实现。
- Paimon 1.4 新增 REST Catalog **Bearer Token 认证**（`token.provider='bear'`），可对接外部认证。

**Iceberg 侧**：

- apache/iceberg#3619（"Iceberg support ranger"）2021 年提出，2024-10-04 **以 not_planned 关闭**——Iceberg 官方没有原生 Ranger plugin。
- 业界实际做法（Apple batch-processing-gateway / Kyuubi 社区的 Spark Ranger plugin 经验，见 ApacheCon NA 2024 议题）：在 **Spark/Kyuubi 引擎层**注入 Ranger plugin，通过 Catalyst 优化器扩展拦截 Hive/Iceberg 表访问；Iceberg REST Catalog 路线的授权仍在演进中。
- **Gravitino**（apache/gravitino）提供「统一元数据层 + 权限推送到 Ranger」的路线：其 `HadoopSQL` Ranger service type 明确**覆盖 Hive/Iceberg/Paimon 三类 catalog**，把 Gravitino 内的授权写入 Ranger 策略。文档同时指出限制：Kyuubi authorization plugin 对 Paimon catalog **无法推送 update/delete**。
- Iceberg v3 规范增加了**列级权限（column-level access）与 row-level policy** 的元数据表达能力，但引擎侧 enforcement 仍是生态碎片化状态。

**给团队的落点结论**：

1. **短期（Paimon 生态内）**：启用 Paimon 内置 file-based privilege（`sys.init_file_based_privilege` + `sys.create_privileged_user` + `sys.grant_privilege_to_user`），对 catalog/database/table 做 IBAC 级别控制；接受其局限（**不阻止通过临时表路径或直接读文件系统绕过**），配合底层存储（HDFS ACL / S3 policy / OSS policy）做第二层兜底。
2. **中期（跨引擎/细粒度）**：若引入 Trino/StarRocks/Kyuubi 做查询引擎，优先评估 **Gravitino + Ranger（HadoopSQL service）** 路线，把 Hive/Iceberg/Paimon 的授权统一到 Ranger 策略中；对 Paimon 的 update/delete 推送限制要有预案（应用侧白名单或专门 service account）。
3. **长期（行列级）**：按 Paimon SECURITY.md 指引，把 row filter/column masking 逻辑放在 **REST Catalog 服务端**或查询引擎插件中实现，而非期望 Paimon library 自身承担。
4. **反模式警告**：不要按 2020–2023 年的旧博客尝试给 Paimon 装第三方 Ranger plugin——目前不存在可用的官方/成熟第三方实现，自研 plugin 的维护成本远高于 Gravitino/引擎层路线。

#### Flink 侧权限现状（补充）

- Flink 本身无统一权限模型，作业级权限通常由**提交入口**（Dinky、YARN队列、K8s RBAC、SQL Gateway session 认证）控制。
- Paimon catalog 的 file-based privilege 在 **Flink SQL 客户端**通过 `CREATE CATALOG ... ('user'=..., 'password'=...)` 传入，可在 Dinky 配置不同用户登录。
- 敏感字段在 Flink 作业中的可见性：建议通过**独立 service account + 最小权限 catalog 用户**限制每个作业只读它需要的库表，而非共用 root。

### 5.5 隐私计算（联邦学习 / 多方安全计算；FATE / SecretFlow）

| 维度 | 联邦学习（FL） | 多方安全计算（MPC） |
|---|---|---|
| 目标 | 数据不出本地，交换模型参数/梯度 | 数据不出本地，交换加密中间值协同计算任意函数 |
| 典型协议 | 纵向联邦（特征切分）、横向联邦（样本切分）、FedAvg | 秘密分享、混淆电路、同态加密辅助、PSI（隐私求交） |
| 性能 | 中（梯度/参数量较小） | 低（密码学开销大，适合 PSI/求和/求交等特定函数） |
| 典型框架 | FATE（微众银行）、TensorFlow Federated（Google）、PaddleFL（百度） | SecretFlow（蚂蚁隐语）、MP-SPDZ |
| 合规价值 | 满足「数据不出域、价值可流动」的监管期望 | 同左；另可做隐私求交/联合风控 |

**FATE**（github.com/FederatedAI/FATE，微众银行开源）：
- 国内首个工业级联邦学习开源框架；支持横向/纵向联邦、逻辑回归、SecureBoost（联邦 XGBoost）、深度学习等算法。
- 底层用 MPC 与同态加密构建安全计算协议；FATE-Flow 负责联邦作业调度，FATE-Board 可视化。
- 适用：金融/政务等强监管行业跨机构建模。

**SecretFlow**（github.com/secretflow/secretflow，蚂蚁「隐语」）：
- 统一隐私计算框架，把 **MPC / 联邦学习 / TEE / 同态加密 / 差分隐私**多技术路线抽象为「密文设备 + 明文设备」的计算图。
- 内置 SPU（MPC 虚拟机）、HEU（同态加密）、SecretPad（零代码建模平台）、Kuscia（跨域调度）。
- 相对 FATE 的差异：**技术路线覆盖面更广（不止 FL）**、MPC 协议栈更完整（SPU 可编译任意 Python 计算图到 MPC）、生态更活跃；FATE 在纵向联邦/金融场景积累更深。
- 适用：互联网/零售等需要更灵活技术栈的场景。

**给数仓团队的判断**（务实口径）：

- 隐私计算**不是**实时数仓团队的日常工具——它是跨机构数据合作的专项能力。
- 团队的**相关性**在于：隐私计算前的 **PSI（隐私求交）结果往往要落到数仓**做特征加工；隐私计算平台输出的模型/标签需要入仓；此时入仓数据的**级别标记与脱敏规则**依然适用（隐私计算输出的标签/分数也可能是敏感数据）。
- 若业务需要跨主体数据合作（如与外部机构联合建模），优先评估 **SecretFlow**（技术面广、文档完善）或 **FATE**（金融场景成熟度）；团队侧投入点是**打通隐私计算平台输出与 Paimon 入仓管道**的 classification 与脱敏 SOP，而非自建隐私计算平台。

### 5.6 审计与 DLP

**审计（Audit）**：

- **数据库审计**：MySQL audit plugin、Paimon catalog 操作日志（Flink SQL Gateway 日志、Dinky 操作日志）、Redis SLOWLOG+命令审计。落点：所有 DDL/DML/敏感字段访问记录**集中采集到日志系统**（如 ELK/Loki），按用户/时间/操作类型可检索。
- **权限变更审计**：Ranger policy 变更、Paimon GRANT/REVOKE、MySQL GRANT/REVOKE 记录与审批工单关联。
- **数据导出审计**：BI 导出、`SELECT INTO OUTFILE`、数据下载接口调用记录；大流量导出告警。
- **PIPL 第 54 条合规审计**：定期（建议年度）对个人信息处理活动做合规审计并留存记录；SOC 2 Type II 审计员抽查也依赖这些日志。

**DLP（数据泄漏防护）**：

- **终端 DLP**：办公电脑外发文件、USB 拷贝、截图识别——由安全团队负责，数仓团队配合定义「敏感数据」特征库。
- **网络 DLP**：出站流量敏感内容检测（邮件/IM/网盘）；对数据团队的实际约束是**禁止用个人网盘/IM 传输生产数据**。
- **存储 DLP**：对象存储/HDFS 敏感数据扫描与告警；对数仓团队的落点是**定期扫描 Paimon/MySQL 中的敏感字段是否按策略加密/脱敏**（可结合 §5.1 的 classification 标签做合规扫描脚本）。
- **API 层 DLP**：数据服务接口的返回字段脱敏校验、调用方权限校验、异常调用模式告警。

## 6. 实时数仓团队的具体能力落点（可固化 SOP 与检查清单）

这是给 data 团队最直接的行动清单。按「管道环节 × 检查点」组织，每一条都是可以写进团队 wiki / CI 模板的具体动作。

### 6.1 CDC 同步管道的分类分级检查点（Flink CDC → Paimon/MySQL/Redis）

**核心原则**：源表级别 + 字段级别标记必须**随 CDC 同步链路传播**，不允许「同步过去就丢失敏感度」。

| # | 检查点 | 触发时机 | 检查动作 | 未通过处置 |
|---|---|---|---|---|
| C1 | **源表定级确认** | 新表接入 CDC 前 | 源 DBA/业务方确认该表最高敏感字段级别（对齐 JR/T 0197 五级或 GB/T 43697 三级） | 阻断接入，先定级 |
| C2 | **敏感字段识别** | 新表接入 CDC 前 | 列名/样本值扫描（身份证、手机号、银行卡、地址、定位、生物特征、健康、14 岁以下标识） | 标记为敏感字段，进入字段级分类清单 |
| C3 | **目的表 classification 标签** | 目标 Paimon 表建表时 | `ALTER TABLE ... SET TBLPROPERTIES ('data.classification'='L3/C2')`（示例） | 未打标禁止写入生产 catalog |
| C4 | **敏感字段加密或脱敏策略选择** | ODS→DWD 加工作业开发时 | 对敏感字段显式声明加密（KMS 字段加密）或脱敏（哈希/遮盖/泛化）策略 | 未声明视为违规，CI 拒绝合并 |
| C5 | **汇聚融合重评** | 涉及多表 JOIN 的新作业上线 | 评估 JOIN 结果是否提升了敏感度（可识别性），必要时上调目的表级别 | 级别变更走审批 |
| C6 | **跨级别写入检查** | 目的表写入前 | 目的表级别 ≥ 源表级别（数据不能流向更低保护级别的表） | 阻断并告警 |
| C7 | **Redis 缓存敏感性检查** | 新增缓存 key 前 | 禁止缓存 L3/C2 及以上字段原值；必须缓存时应用侧脱敏/加密后写入 | 阻断 |
| C8 | **跨地域/出境同步检查** | 新增异地/境外同步链路 | 判定是否触发《促进和规范数据跨境流动规定》豁免/安全评估/SCC/认证；重要数据只走安全评估 | 合规团队审批 |
| C9 | **binlog 与 CDC 位点中的敏感信息** | CDC 作业配置 | 确认 binlog/Kafka topic 的访问权限与加密策略（不能因位点是「中间数据」就裸奔） | 权限收敛 |
| C10 | **删除权/更正权传播** | 收到个人信息删除/更正请求 | 源库删除/更正事件**沿 CDC 链路传播到 Paimon/Redis**（Paimon 需处理 snapshot 中的历史版本——用 `snapshot.num-retained.min` 策略配合定期 expire） | 建立删除传播 SOP 与时效承诺 |

### 6.2 脱敏规则固化清单

| # | 规则 | 适用范围 | 落点 |
|---|---|---|---|
| M1 | **手机号**：`138****5678` 遮盖，或 SM4 加密存储+查询时解密展示 | 所有 ODS 明细层；BI 查询 | Flink UDF（如 `mask_phone`）+ 数据服务层脱敏视图 |
| M2 | **身份证号**：保留前 6 后 4，中间遮盖；或整字段加密 | 所有 ODS/DWD | 同上 + KMS 字段加密 |
| M3 | **银行卡号**：保留前 6 后 4（Luhn 校验保留段），禁止全卡号展示 | 支付/交易域 | 同上 |
| M4 | **地址**：泛化到区/县级别；详细门牌仅特定角色可见 | 用户域 | 视图层或 ABAC 策略 |
| M5 | **定位/GPS**：精度降级（保留 2 位小数 ≈1km），或仅保留城市 | 埋点/日志域 | Flink 算子内处理 |
| M6 | **生物特征**（人脸/指纹/声纹）：**禁止进入数仓明细层**，只存特征向量哈希 | 全域 | 架构性禁入 |
| M7 | **14 岁以下未成年人信息**：单独同意标记 + 默认脱敏 + 保留期限上限 | 用户域 | 字段级标签 + 自动化保留策略 |
| M8 | **生产 → 测试环境**：必须走静态脱敏管道（全量字段脱敏或合成数据），禁止直接 dump | 跨环境 | 独立脱敏作业 + 数据导出审批 |
| M9 | **BI 展示**：默认脱敏视图；原值查看需审批并留痕 | 报表/看板 | 数据服务网关 + 审计日志 |
| M10 | **对外提供**（API/文件下发）：按接收方权限与合同范围裁剪字段；重要数据出境走安全评估 | 数据服务 | 出口网关策略 + 合规审批流 |

### 6.3 权限与加密固化清单

| # | 规则 | 落点 |
|---|---|---|
| P1 | **最小权限**：每个 Flink 作业用独立 catalog 用户（不用 root），只授权其读写的库表 | Paimon file-based privilege + Dinky 用户配置 |
| P2 | **角色分层**：数据工程师（读写 ODS/DWD）、分析师（只读 DWS/ADS）、运维（DDL only）三角色起步 | Ranger/Gravitino 或 Paimon GRANT |
| P3 | **特权访问管控**：DBA/admin 账号使用需审批，多因素认证，操作全量审计 | MySQL 权限 + 审计插件 |
| P4 | **传输加密**：Flink↔Kafka SASL_SSL、Flink↔Paimon（S3/HDFS 加密通道）、MySQL 主从 SSL、Redis TLS、Dinky Web HTTPS | 各组件配置 |
| P5 | **存储加密**：Paimon 底层 S3 SSE-KMS / HDFS encryption zone；MySQL InnoDB 表空间加密；重要/核心数据应用侧字段加密 | 存储层 + KMS |
| P6 | **国密适配**：KMS 支持 SM2/SM3/SM4；字段加密优先 SM4-GCM；TLS 支持 TLCP 以备密评 | KMS 选型 + 加密库选型 |
| P7 | **密钥轮换**：主密钥年度轮换，数据密钥季度轮换，轮换有审计 | KMS 策略 |

## Findings：主要矛盾与次要问题

**主要矛盾**：团队当前技术栈（Flink/Paimon/Fluss）**原生权限与加密能力不足以承载三法+国标映射出的义务**——Paimon 的 file-based IBAC 权限 + 无 Ranger 官方 plugin + 行列级控制依赖外部（引擎/REST Catalog），与「分类分级 → 分级防护」的法定要求之间存在能力鸿沟。这不是「再补一个工具」能解决的，需要**架构性选型**（存储层 ACL 兜底 + 引擎层 plugin + 元数据层统一策略，三条线并行）。

**次要问题**（可按 §6 清单逐步消化）：CDC 链路缺分类分级检查点、脱敏规则未标准化、删除权传播机制缺失、密评/国密适配未提上日程、出境路径判定未流程化。

---

## Recommendations（优先级按 impact × effort 排序）

1. **P0（高影响低投入）**：启用 Paimon 内置权限 + 传输加密补齐 + CI 打标门禁。1–2 周。
2. **P1（高影响中投入）**：敏感字段 UDF 脱敏库 + 审计日志集中化 + 四份 SOP 发布。3–6 周。
3. **P2（高影响高投入）**：权限架构选型（Gravitino+Ranger vs 引擎层 plugin vs REST Catalog 行列级），需 PoC。1–2 月。
4. **P3（中影响中投入）**：国密/密评适配、隐私计算入仓管道、重要数据目录备案流程。按合规团队节奏。
