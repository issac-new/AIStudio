### 1.2 ⚠️ QCUP 053-2012 存在性存疑（勘误 v1.0）

- v1.0 与 STANDARDS-COVERAGE 曾称"QCUP 053-2012 已全文入库"——**不实**。机械核查（2026-09-06）: `standards/unionpay/` 147 份文件**无任何**二维码应用规范全文；`unionpay_inventory.json` 仅有 PDF 清单条目 `"中国银联电子支付二维码应用规范(QCUP 053—2012).pdf" (14页, 0.5MB)`，**PDF 原件在库内不存在**，无法提取
- v1.0 中的"A/B/C 类二维码""码值结构=AID+类型+商户号+终端号+金额+CRC16/SM3"等内容**无法从库内任何原文验证**，按诚实性原则不再作为"已入库规范核心内容"呈现
- 裁决: 银联二维码**现行有效体系以 2016-12 版应用规范+安全规范为准**（known-conflicts KC-004 已裁定 2016 版为现行）；053-2012 仅存历史条目名，内容以本文档公开来源整理版为准
- 已登记 known-conflicts KC-014（QCUP 053-2012 入库状态虚标）

### 1.3 银联 2016 版标准核心（多源交叉核验）

**四方模式**（人民网/平安银行/新浪财经一致表述）:
- 二维码支付沿用"持卡人-发卡行-收单行-银联"四方模式，后台账户仍基于**实体银行卡账户**
- 与互联网巨头"账户+钱包"闭环模式（支付宝/微信支付账户体系）形成路线差异
- 发布定位（人民网原文表述）: 应用规范"侧重于二维码支付的具体场景，定义了二维码支付的应用场景和基于**数字签名的安全机制**"

**关键机制**:
- 交易链路: 用户出示付款码（动态刷新）→ 商户/收单机构扫码 → 银联二维码前置/转接系统 → CUPS 路由 → 发卡行授权 → 应答回传
- 安全: 绑卡 Token 化（配合《中国银联支付标记化技术指引》，见 `TOKENISATION-CN-FRAMEWORK.md`）+ 交易级动态验证 + 数字签名机制
- 清算: 与实体银行卡交易一致（CUPS 清分，T+1）
- 条码互通: 银联二维码网络后续与微信/支付宝/各钱包按监管要求实现"条码互认互扫"（2019+ 商务部/央行推进，属业务层动态，以最新公告为准）

## 二、央行 296 号文合规框架（2018-04-01 实施）

### 2.1 风险防范能力分级与限额（多源交叉核对）

| 风险防范能力 | 交易验证要素组合 | 限额（同一客户单个银行/支付机构） | 典型场景 |
|------------|----------------|--------------------------------|---------|
| **A 级** | 2 种以上有效要素 + 数字证书/电子签名 | 不限额（机构自主风控） | 高安全等级受理终端+证书 |
| **B 级** | 2 种以上有效要素 + 不少于 2 要素的安全防护 | **5000 元/日** 累计 | 动态条码+双要素 |
| **C 级** | 2 种以上有效要素 + 不少于 1 要素的安全防护 | **1000 元/日** 累计 | 动态条码+单要素 |
| **D 级** | 单一要素 | **500 元/日** 累计 | **静态条码**（无论何种验证方式） |

> ⚠️ **勘误 v1.0**: 旧文档"静态码 500 元/笔、付款码 1000 元/笔"表述不准确——296 号文口径是**按风险防范能力 A/B/C/D 分级、以"同一客户单个银行或支付机构单日累计"计**；静态条码固定为 D 级（500 元/日）。现行有效，但引用时标注"截至 2018-04 施行口径，后续监管调整以最新公告为准"（known-conflicts KC-001 裁决一致）

### 2.2 合规要求要点（296 号文，多源交叉）

1. **清算路径**: 跨行交易必须经人民银行跨行清算系统或合法清算机构（银联/网联）转接——断直连合规底线
2. **商户实名与外包红线**: 特约商户资质审核、受理协议签订、资金结算、交易处理、风险监测、**受理终端主密钥生成与管理、网络支付接口管理、差错争议处理**——不得外包
3. **静态条码约束**: 静态条码 D 级 500 元/日；鼓励"一户一码"动态化改造
4. **风险监测**: 建立交易风险监测系统，大额/可疑交易报告

## 三、EMVCo QR Code 对标（官方页面级核验）

### 3.1 双模式

| 模式 | 缩写 | 交互方向 | 中国对应 |
|------|------|---------|---------|
| Consumer-Presented Mode | CPM | 用户出示码，商户扫 | 付款码（主扫方向相反，见下注） |
| Merchant-Presented Mode | MPM | 商户出示码，用户扫 | 收款码/订单码 |

> 术语注: 中国"主扫"=用户扫商户码=EMV MPM；中国"被扫"=商户扫用户码=EMV CPM

### 3.2 版本现状

- **现行公开版 v1.1**（2020-11-27，CPM/MPM 两册独立发布，官网下载页核验）
- v1.0 → v1.1 合并 Bulletin: SB-206（规范澄清）、SB-236（CPM 多应用模板 POI 处理）；v1.1 后增量 Bulletin（SB-254 商户渠道数据对象 2021-06、SB-270 商户原产国 2022-05）
- 数据编码 QR 基于 ISO/IEC 18004；支持卡基与账户基（含 URL 型码）支付

### 3.3 银联码 vs EMVCo 码对比

| 维度 | 银联二维码（2016 版体系） | EMVCo QRCPS v1.1 |
|------|------------------------|------------------|
| 模式 | 付款码（被扫）/ 收款码（主扫） | CPM / MPM |
| 数据模型 | 银联自有码值 + 数字签名机制 | TLV 数据对象模板（ID-长度-值，CRC/数字签名可选） |
| Token | 银联标记化（Q/CUP 指引体系） | Token/PAN 均可承载 |
| 清算路径 | CUPS（四方模式，实体卡账户） | 组织无关（规范不定义清算） |
| 互操作 | 与 EMVCo 标准兼容互通（银联官网: "支持 EMVCo 制定的二维码技术标准，一次接入境内境外统一使用"） | 全球受理基座 |

## 四、交易流程与工程要点

### 4.1 被扫（用户出示付款码，≈EMV CPM）

```
用户 App 展示动态付款码（限时刷新）
→ 商户扫码枪/收银机采集
→ 收单机构 → 银联二维码转接/前置
→ CUPS 按卡 BIN 路由发卡行（或钱包账户侧平台，互认场景）
→ 发卡行验证（Token/要素+风控）→ 授权应答
→ 同步返回收银台 → T+1 清算
```

工程要点: 付款码时效与刷新策略、防重放（一次性消费）、弱网下的收银台超时与冲正（域 90 原交易数据，见 `ISO8583-DETAIL.md`）。

### 4.2 主扫（用户扫商户码，≈EMV MPM）

```
用户 App 扫商户静态码/订单码 → 金额确认（静态码需手输金额）
→ 用户 App → 用户侧收单/钱包平台 → 转接（银联/网联）
→ 商户侧收单机构 → 商户确认
→ 异步通知+二维码小票 → T+1 清算
```

工程要点: 静态码 D 级限额拦截前置到收银台；订单码有效期与幂等；退款走原路。
