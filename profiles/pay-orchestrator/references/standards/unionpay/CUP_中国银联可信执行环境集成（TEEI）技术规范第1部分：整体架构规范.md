Q/CUP 069—2015 
V 
引  言 
随着移动网络和智能终端的高速发展以及消费电子产品越来越智能化，移动应用的种类和数量越来
越多。当前的移动应用已经不再仅限于对智能终端的基本功能、娱乐功能方面的扩展，它所涉及的领域
逐渐扩大到各行各业中，如移动支付相关的金融应用、内容版权保护应用以及云计算下瘦终端的安全应
用等，这些行业应用都需要更高安全级别的终端运行环境。 
然而，由于智能终端多媒体操作系统是以功能性为设计出发点，而非从安全性角度出发，再加上整
个系统的开放性、庞大性、复杂性而导致的系统漏洞，导致木马、病毒等恶意代码不断出现，危害应用
程序，进而威胁用户个人私密信息。虽然可以利用一些软件防护手段，如防火墙、杀毒软件等进行相应
的保护，但由于经常性的系统更新升级以及新型恶意程序的层出不穷，无法做到软件上的完全保护。 
针对上述问题，业界进行了深入的研究工作，提出了一种新型的安全解决思路：把同一终端划为在
硬件层面上相互隔离的两种模式：普通模式和可信模式。终端的硬件资源（如各种外设等）可以分别标
识为两种模式之一，标识为可信模式的硬件资源只能由可信模式下的软件所访问，而标识为普通模式的
硬件资源则可以为两种模式下的软件共同访问。如此，运行在普通模式下的软件将无法直接访问可信模
式下的任何软硬件资源，可信模式下的软件可完全抵御从普通模式下所发起的任何软件恶意攻击。基于
此，可选择在普通模式下运行目前常用的移动操作系统如Android等，在可信模式下则运行一个功能简
单、代码量小、封闭且可人为审核控制的可信操作系统。因而，在这种解决方案下，同一终端可为应用
提供两个独立的操作系统。对于注重安全的安全类应用可选择部署在可信操作系统上；对于注重功能的
功能类应用则可选择部署在移动操作系统上，其中安全类应用可为功能类应用提供安全服务。 
按以上思路，业界对可信模式下的软件系统提出了具体的安全需求说明，并把满足该安全需求的运
行于可信模式下的软件系统称为TEE（Trusted Execution Environment，可信执行环境），至于其具体
的系统架构、管理方式等可以根据具体实现方式的不同而不同。 
随着半导体技术的发展，终端芯片架构不断得到优化，相应的终端主流芯片产品已满足了上述解决
思路所提出的双模式需求，如ARM的TrustZone架构和Intel双平台架构等，为TEE的实现和推广创造了条
件。基于此，当前产业界各大公司和组织相继提出了各自的TEE实现，如GlobalPlatform组织的GP TEE
和Linaro公司的Open TEE分别是各自基于ARM的TrustZone架构上提出的TEE实现。 
中国银联由于所处行业的特性，一直关注着智能终端安全解决方案的前沿技术进展，于几年前就已
开始了TEE相关技术的研究工作，并通过与产业链各方的深入接触与市场反映来看，对TEE存在以下两个
方面的需求：（1）安全应用的统一部署：TEE应支持类Java语言的应用开发方式，实现TEE应用的跨平
台统一部署，降低TEE应用运营方的应用管理难度；（2）TEE控制权：现有的TEE实现大都是采用类操作
系统的设计方式，在同一个终端上只能选择部署一个TEE，即同一个终端上只能有一个TEE控制方。而随
着TEE在智能终端上的作用加强，产业链各方将对在同一个终端上拥有各自所属TEE并控制与运营的强烈
需求，从而实现各自在终端产业链上的产业布局及其商业模式。因而，如何满足产业链对与上述的两个
需求，在一个终端上提供部署多个多种TEE且应用统一部署的能力，将是今后市场所迫切需求的，也是
今后终端产业安全解决方案的主流趋势。

Q/CUP 069—2015 
VI 
TEEI（Trusted Execution Environment Integration，可信执行环境集成）正是银联在深入分析
上述需求和现有技术方案的基础上所提出来的一种创新性的终端整体解决方案，满足当前及其今后市场
对于TEE在运营、产业合作、商业模式构建等方面的需求。TEEI遵循TEE的安全需求，要求智能终端具备
相互隔离的两种模式：普通模式和可信模式，TEEI运行在可信模式下，因而TEEI可完全防御普通模式下
移动操作系统所发起的任意恶意软件攻击。同时，TEEI通过可信虚拟化技术对终端的可信模式及其安全
软硬件资源进行虚拟化，可在一个终端上同时提供多个可信虚拟机，每个可信虚拟机具备与终端可信模
式同等的安全等级及各自的可信外设。产业链各方可在终端生产前与终端厂商进行可信虚拟机申请，之
后由终端厂商在生产构建TEEI时，为各方产生各自的可信虚拟机。在终端生产后，各方即可各自拥有在
终端上的可信虚拟机，并可完全自主的在各自的可信虚拟机上进行各自软件的部署，如简单的单应用软
件或者类操作系统的TEE软件，并予以独自的运营，解决各方对于TEE控制权冲突的问题。此外，TEEI
还提供可信网络，将各方的可信虚拟机以网络形式进行连接，使不同可信虚拟机上的软件之间可互相访
问，并把各方所会用到的各个共通服务以单独可信虚拟机方式部署，形成各种内置可信服务连接在可信
网络上为各可信虚拟机软件提供服务。同时，可信网络也可支持SE类的计算设备（如eSE、SIM卡、智能
SD等）连入可信网络以使用各种内置服务。针对TEE应用的部署问题，TEEI提供了一种标准的可信操作
系统实现N3TEE，是基于N3虚拟机的字节码解释机制，可支持Java语言编写的多应用管理机制，解决TEE
应用的跨平台部署问题。因而，TEEI是一种通过可信虚拟化技术，基于终端的可信硬件环境产生多个可
信虚拟机，在这些可信虚拟机之上运行不同的软件，如N3TEE操作系统、本地单应用、内置可信服务等，
并通过可信网络将终端上所有与安全相关的计算平台、外设、服务集成起来，形成一个可信化的系统集
成平台。

第1 部分：整体架构规范 
1 范围 
本规范主要描述了在终端设备上的TEEI系统的整体概念、各个子功能等相关内容，明确如何在支持
安全硬件的终端设备上部署与开发TEEI系统。 
本规范适用于参与银联的可信平台业务的金融机构所发行的POS机、手机厂商发行的智能手机和其
他智能终端，适用对象包括与POS机、智能手机和其他智能终端的设计、生产、发行、运营以及应用系
统的研制、开发、集成和维护等相关部门。 
2 术语与定义 
2.1 普通模式 
业界对于终端所定义的需要具备的两种模式的其中一种，处于该模式下时，终端上的软件及其硬件
不处于终端的硬件保护下。 
2.2 可信模式 
终端上与普通模式相互隔离的另一种终端模式，处于该状态下时，终端上的软件及其硬件处于终端
的硬件保护下。 
2.3 普通硬件环境 
终端普通模式下的各种硬件资源，包括CPU、内存、I\O、外设等。 
2.4 可信硬件环境 
终端可信模式下的各种硬件资源，包括CPU、内存、I\O、外设等。 
2.5 多媒体执行环境 
    运行在终端普通硬件硬件下的注重功能和开放的软件系统，如Android、iOS等移动操作系统。 
2.6 可信执行环境 
运行在终端可信硬件环境下的注重安全和控制的软件系统，如N3TEE等。 
2.7 虚拟化 Virtualization 
在一个硬件上抽象出多个虚拟硬件的方式，由全虚拟化方式、硬件协助虚拟化方式、半虚拟化方式
等，本规范中所描述的虚拟化主要是基于半虚拟化方式。 
2.8 超调用 
可信虚拟机提供的对于敏感指令和特权指令的调用方法。

2.9 保护域 
基于硬件的一个独立空间，包括专属内存、设备等资源，具备独立的地址空间，与硬件上的其他保
护域之间是相互隔离的。 
2.10 可信虚拟机 
基于终端可信硬件环境所虚拟出的虚拟可信硬件环境，为终端在生产时产生，并预先分配给产业链
各方，各方可在终端生产时或者生产后对各自拥有的可信虚拟机进行软件部署及其之后的运营。 
2.11 可信网络 
一种处于TEEI下的网络通信机制，可对TEEI下的各个可信虚拟机进行互联互通，也可接受TEEI智能
终端上其他计算设备的联网请求，如各个SE设备等，从而达到各个可信虚拟机、SE等安全计算设备上的
软件之间互相通信的要求。 
2.12 内置可信服务 
作为运行在TEEI提供的可信虚拟机之上的一个软件系统，可为TEEI系统内的计算设备提供共通的软
件服务，如可信用户界面服务、身份识别服务等。 
2.13 TEEI 通信代理 
运行在TEEI内，负责与多媒体执行环境通信的接口模块。 
2.14 REE 通信代理 
与上述TEEI通信代理对应，运行在多媒体执行环境内，负责与TEEI通信的接口模块。 
2.15 NFC 通信代理 
运行在TEEI内，通过NFC芯片负责与外部NFC设备通信的接口模块。 
2.16 TEEI 底层 
支撑可信虚拟机、可信网络、TEEI通信代理、NFC代理等功能模块实现的一层可信软件。 
2.17 N3TEE 虚拟机 
一种支持基于字节码解析的解释性虚拟机。 
2.18 N3TEE 
一种运行在可信虚拟机上的可信操作系统，支持使用Java语言开发和运行的多应用框架。 
2.19 客户应用（Client Application） 
一种运行在多媒体操作系统（如Android）上的应用，需要访问TEEI内的安全服务。 
2.20 可信应用（Trusted Application） 
一种运行在TEEI内的应用，为客户应用提供安全服务。 
2.21 本地可信应用（Native Trusted Application）

6 可信虚拟机 
6.1 基本描述 
可信虚拟机是TEEI将可信硬件环境进行可信虚拟化后的虚拟可信硬件环境，可在一个终端可信硬件
环境上虚拟出多个可信虚拟机，每个可信虚拟机可各自部署和运行各种类型的软件，如单应用软件或者
可信操作系统软件。出于性能以及目前平台的虚拟化支持度的考虑，TEEI采用的可信虚拟机是基于微内
核的半虚拟化技术，其虚拟硬件环境与真正实际底层硬件环境存在差别，是经过一定抽象化的硬件环境。 
6.2 硬件接口 
TEEI虚拟出的一套硬件平台，出于性能考虑，是一种抽象化的虚拟机器，对于非敏感性指令采用智
能终端所基于的硬件芯片指令集，而对于敏感和特权指令则以如下抽象接口方式提供给可信虚拟机用户
使用。 
6.2.1 VCPU 
虚拟处理器，可信虚拟机所看到的CPU，是对实际物理CPU的一种虚拟。由于本规范采用的半虚拟化
技术，因而这些VCPU与实际物理CPU是同构的，VCPU指令集为实际CPU指令集的子集，不包括敏感指令和
特权指令，对于这两种指令，需要TEEI底层提供的超调用进行模拟。VCPU主要包含部分： 
——入口地址：VCPU 的PC 指针，可信虚拟机启动时，就从PC 指针指向的代码开始执行； 
——栈：VCPU 的SP 指针，作为可信虚拟机运行时所用的栈； 
——中断处理入口：VCPU 的中断入口表地址，每当可信虚拟机对应的中断产生时，将会调用该中
断入口表地址的代码执行，具体判断产生的中断类型，并调用相对应的中断处理函数进行处理。 
由于VCPU的实现方式，实际物理CPU和VCPU并不是一对一关系，需要实现一对多关系，即在只有一
个物理CPU的硬件设备上通过虚拟实现出多个VCPU，可信虚拟机根据需要占有一个或者多个VCPU，对于
占有多个VCPU的可信虚拟机来说，其上运行的虚拟机操作系统将认为是运行在一个多核机器上。本规范
不作具体的VCPU个数进行限定，其个数由具体实现所限。主要包括功能： 
——创建VCPU； 
——删除VCPU； 
——调度VCPU。 
6.2.2 VMMU 
虚拟内存管理单元，是对实际平台的MMU的一种虚拟，让可信虚拟机认为独自占有设备的内存空间，
从可信虚拟机内部来看，整个内存空间是线性的。为安全性、简单性和实用性，本阶段规范所定义的VMMU
暂不支持实际MMU所提供的页表接口操作，可信虚拟机内的各个应用以及虚拟机操作系统之间的保护隔
离机制都统一由TEEI提供，主要包括功能： 
——创建一个保护域； 
——删除一个保护域； 
——查找一个保护域。

——创建Portal； 
——设置Portal； 
——得到Portal。 
当一个可信虚拟机需要与另一个可信虚拟机时，主要步骤： 
（1）得到对方可信虚拟机的Portal； 
（2）创建线程，绑定到该Portal上； 
（3）调用线程的发送和接收函数就可以通过Portal发送数据到对应可信虚拟机。

现有系统整体架构的情况下，在平台部署运行后做一些改变来满足各个组件之间交互的需要。 
ITS是一系列功能相关的机能集合，服务封装使得系统功能的组织和管理更加灵活和便利，并且由
于对外提供统一的接口，使得TEEI系统的结构更加富有条理性。本规范描述TEEI所必须要支持的几个内
置可信服务。 
8.2 内置可信服务 
8.2.1 可信用户界面服务 
可信用户界面服务（Trusted User Interface， TUI）是在TEEI系统可信执行环境下提供用户界面
展示及相关输入输出信息处理的服务。 
可信用户界面服务的基本功能包括： 
——安全显示：提供TEEI 系统可信应用界面显示接口，显示给用户的信息不能够被任何REE 内的
软件或TEEI 中未经授权的应用所访问、修改或遮蔽； 
——安全输入：提供TEEI 系统可信应用界面输入接口，用户输入的信息不能够被任何REE 内的软
件或TEEI 中未经授权的应用窃取或修改； 
——安全指示：提供TEEI 系统可信应用界面安全指示接口，用户能够确定画面实际上是由TA 显示
的。 
8.2.2 HCE 服务 
HCE服务是TEEI系统提供的一种可模拟非接卡片通信能力的软件服务，以软件的形式实现相应的SE
功能，主要功能包括： 
——卡应用注册； 
——卡应用APDU 处理； 
——卡应用销毁。 
8.2.3 可信存储服务 
可信存储报务是TEEI系统为其上的可信虚拟机软件提供一种通用的数据存储服务，基本功能包括： 
——存储对象创建； 
——存储对象查找； 
——存储数据读写； 
——存储数据销毁。 
8.2.4 生物识别服务 
生物是被服务是TEEI系统提供的一种能安全可信地对用户身份进行认证的软件服务，主要功能包
括： 
——身份采集； 
——身份识别； 
——身份认证。

2) N3TEE 运行时环境：可以看作是N3TEE 的操作系统内核，用来协调和管理N3TEE 中各个模块的
工作。N3TEE 运行时环境包括一个N3TEE 虚拟机实现和一些N3TEE API 类。一方面N3TEE 虚拟机有确保
Java 语言级安全的职责，另一方面N3TEE 运行时环境给实现了N3TEE 运行时环境的终端增加了运行时
的安全需求，导致N3TEE 虚拟机需要一些额外的安全特征。在本规范中，这些额外的特征被指定为N3TEE 
运行时环境特有的。N3TEE 运行时环境所利用的基本运行时安全特征是通过一种称为应用防火墙的机
制，用来加强N3TEE 应用之间的隔离。应用防火墙能够阻止一个N3TEE 应用创建的对象被另一个N3TEE
应用访问，包括阻止非授权访问类实例的域和方法，以及数组的长度和内容。 
3) 
N3TEE Java API：N3TEE 提供的Java API 包括算术运算API、密码运算API、套接字API、时
间API、可信存储API、SE 访问API，TUI API 和Debug API，特别地，N3TEE API 还提供了NFC 访问API。

图10.1 设备启动过程 
具体流程： 
——终端上电 
给终端加电，终端跳转到设备的ROM中，执行ROM中的Boot代码，Boot从指定的Flash地址出读取
Secure Bootloader代码并成功跳转到Secure Bootloader中。 
——Secure Bootloader 
Secure Bootloader判断当前设备是否支持TEEI系统，若支持TEEI系统，判断该TEEI系统是否已经
激活，若已经激活，则使用设备厂商密钥对指定Flash地址的TEEI系统代码进行验证，若验证失败，则
判断系统启动失败，系统停止；若验证通过，则跳转到TEEI底层执行。 
——TEEI 底层 
主要对TEEI进行必要的初始化工作，完成支撑TEEI中的可信虚拟机、可信网络以及默认的内置可信
服务所必须的初始化与配置工作等。 
——启动可信虚拟机 
完成TEEI的初始化和运行工作后，根据TEEI虚拟机默认开机启动配置表启动相应的TEEI虚拟机，并
对虚拟机进行初始化工作。 
——N3TEE 
完成可信虚拟机初始化后，按照可信虚拟机的启动流程，启动其上的软件服务，如N3TEE等，并按
照该软件服务初始化需求完成所需的初始化工作。 
——Normal Bootloader 
在完成可信虚拟机上的软件服务初始化之后，TEEI判断REE下的Normal Bootloader的合法性，并跳
转到Normal Bootloader进行普通运行环境下的必要硬件初始化工作，初始化工作完成，跳转到REE系统
入口处，与当前无TEEI的普通设备的Bootlaoder过程相同。 
——REE 系统启动 
REE执行过程与当前无TEEI系统的普通操作系统如Android操作系统的初始化过程相同。
