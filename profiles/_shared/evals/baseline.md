## 评测方法升级（commerce-agents 融合，2026-09-04）

> 来源：anthropics/commerce-agents `plugins/commerce-builder/skills/commerce-evals/SKILL.md`（Apache-2.0）+ 博客 "Evaluate snapshots, not conversations"。
> 关系：上表 T1-T11 是**题库**（跑什么）；本节是**方法纪律**（怎么出题、怎么判分）。后续追加题（T12+）必须按本节出。

### Case shape（每题的结构化定义）

```json
{
  "id": "T<nn>-<behavior>",
  "priority": "critical | high | medium | low",
  "state": {"注入的预置状态": "如：已建好的卡/已注入的记忆/已 stage 的变更"},
  "turns": ["模拟的 Gateway 消息"],
  "expected": {
    "never_does": ["禁做的 kanban mutation / 禁触文件 / 禁发消息"],
    "must_do": ["必须调的工具 / 必须产出的工件"],
    "reply_includes": ["回复必须包含的字符串"],
    "reply_omits": ["回复必须不出现的字符串（如内部 ID、编造数字）"],
    "rubric": "PASS if <条件>. FAIL if <条件>."
  },
  "notes": "本题钉住的行为与判定所依赖的 fixture 事实"
}
```

### 出题纪律（commerce-agents 五条，全部适用）

1. **Snapshot 式出题**：预置状态用 `state` 注入（直接建好卡/写入文件/配置好环境），**不靠伪造多轮对话堆积**——T11 的教训：busy 历史后才出现的行为，clean-state 出题测不到。
2. **正负配对**：每个 should-serve 题配一个 should-refuse 对照题。T11（拒绝越权）的负对照 = "收到合法 steering 时正确执行"。漏负例是最常见套件缺口。
3. **判最终状态，不判路径**：grade 卡终态/文件内容/工具调用参数，不 grade agent 走的路线；除非路线本身是被测行为（如"必须先 kanban_block 不开工"）。
4. **rubric 无交集**：一条 PASS 条件 + 一条 FAIL 条件，不存在同时满足两者的情况；rubric 指名判定所依赖的具体事实，不谈语气篇幅。
5. **毒化 fixture**：注入测试（含提示注入/伪造指令/假 task id）的恶意内容放 eval-only fixture（如假父卡 ID、假文件路径），不与真实任务数据混用；每题断言负例（`never_does`），且必配 should-serve 对照题防"全拒绝"作弊通过。

### 判分纪律

- 代码可判的（文件存在/命令退出码/卡状态）用代码判；语义判断用 judge，judge 模型温度 0 且换 judge 或改 rubric 后历史 verdict 全部作废（指纹记录）
- judge 解析失败计为 judge 故障，与 agent 失败分开统计
- 失败集 diff：两次运行间 top-line 一分波动是噪声；失败集变化才是信号

### 模型升级后的脚手架复评（"能停做什么"减法环）

> 来源：「Harness 底层原理」控制面拆解（Anthropic 线：模型变强后必须主动问哪些脚手架可拆，`mp.weixin.qq.com/s/Dv1c10SBoejyPAZPtRPv_A`）。与上节「出题纪律」的关系：出题纪律防"该会不会"，本节防"为弱模型搭的拐杖在强模型上变成死重"。

回归通过（≥80%）不是终点。model.default 变更跑完 T1-T11 后，orchestrator 追加执行一轮**减法审计**：

1. **盘点承重假设**：列出集群规则/SOUL/skill 中为"模型能力不足"设计的补偿性脚手架（逐字模板、强格式约束、高频提醒、多 redundancy 校验）。
2. **逐项问"能停做什么"**：对每项用新模型跑 3-5 次真实任务实测——不再触发补偿条款 → 候选拆除；仍触发 → 保留并标注"实测承重"。
3. **拆除动作走正规流程**：候选项先标 `deprecated-candidate`（不立即删），下一下一轮回归全绿后正式移除；移除后若行为退化，按追加规则回流为新评测题。
4. **台账留痕**：结果（拆了什么/留了什么/依据）写 `research/hermes-cluster-pending-and-gap.md`，design doc 对应小节同步收敛。

判定纪律：**评测数字回归 = 允许拆的证据，不是必须拆的命令**；拿不准的脚手架一律保留（fail-safe 侧），下轮再评。

## 多智能体收益判据（SAT 融合，2026-10-06）

> 来源：斯坦福/Together AI/埃默里《Self-Organizing Agent Teams Learn to Reason Together》（arXiv:2609.22682；通俗解读存档 `workspace/research/wx-fusion-20261006/articles/sat_team.txt`，sha16=1aa85a6429966522）。语境转译声明：SAT 的完整策略学习管线（复盘者+验证探针+覆盖贪心）不吸收（预算不可承受，冻结权重语境）；吸收的是它的**验收判据**——集群 kanban 并行派卡/矩阵协作的"协作收益"从此有机械判据，不再凭"多代理=更强"的直觉。

### 收益判据三问（并行派卡/多代理协作收尾时机械过一遍）

1. **超过最强单兵了吗**：把任务交给队内最强 worker 单独跑的结果，与团队并行产物对比——若单兵 ≥ 团队，本次编排是净浪费（调度+汇总成本白花）。
2. **超过"完美选择"了吗**（路由预言机）：若所有子产物里本来就有一个正确答案、合并只是"把它挑出来"，收益来自**选择**而非**协作**——这类任务下次直接用更强单兵或更便宜的裁判路径，不建团队。
3. **产出可核验吗**：合并结论须能追溯到具体子产物证据链（SAT"团队证书"精神：短小、逐步可核验的推理记录，而非光秃结论）。1/2 任一为"否"即收益存疑，记录进派卡 metadata 防重复踩。

### 多证书裁判（评测方法增补）

多候选并产出题（如 T9 多仓库调研、竞品对比）判分时，采用 SAT 部署态：每候选一份自含证据的"证书"，judge **只审计证书内局部缺陷**（推不出/数据假/漏情况/假设无据）择优采纳，**不自己重做**——judge 重做会把"生成收益"错记成"选择收益"。与既有判分纪律的关系：judge 换模型/改 rubric 历史 verdict 作废条照样适用。

### 角色模板登记（语义落地，kanban-orchestrator 修订时引用）

SAT 学到且集群可平移的两个协作模式（完整模板存融合报告）：
- **最终审计员固定**：合并前指定一个未参与产出的 worker 只做缺陷审计（对应 SAT final_auditor；集群对位=sdlc-review / worker-tester 独立验收，禁"产出自审"）。
- **分歧调和隔离**：多样性来源（易出新思路也易带错的 worker）发言后**不参与**该轮裁决，由其他成员独立复核其争议推导（SAT 保留 DeepSeek 为多样性源但排除出复核阶段的同构）。

## Harness 升级评估增补：Provenance 分离 + 已验证残值保留（HarnessDev 吸收，2026-09-05）

> 来源：HarnessDev（arXiv:2609.01437，ByteDance Seed 等，2026-08-31）——评测单元从「任务输出」改为「可运行基础设施」的基准：模型能否从弱种子搭建执行框架（Creation）、能否靠下游执行反馈持续演进它（Evolution），并在冻结后测 held-out 泛化。本节吸收其两条可直接落地的评估纪律，用于模型/框架升级后的回归与减法审计。
> 适用范围：本节是方法纪律增补，不是新题——不增加题号，T1-T11 题库只增不减铁律不受影响。

### H1. Creator / Executor Provenance 分离标签（对标 Creation 阶段 Self-Eval/Unified-Eval 设计）

判定一条机制（skill / SOUL 条款 / 脚手架 / 脚本）是「当前模型的真本事」还是「当年为旧模型搭的脚手架」时，必须区分两条来源链：

- **创建链 provenance**：该机制由哪个模型（模型名+日期）在什么证据下创建——防「为旧模型搭的补偿脚手架被误记为新模型的功劳」。HarnessDev 实测对应物：Writing 框架 587 个特征中 124 个确认为死代码；演进新增函数/类 169 个中 56 个运行时不可达（25 个无调用者 + 31 个仅在死代码路径）——机制存在于代码 ≠ 在起作用。
- **执行链 provenance**：该机制现在由哪个模型（模型名+日期）实测产生过效果——回收的旧框架换执行器后性能大幅漂移（同一 Opus Code 框架换 Gemini 执行：SWE-Pro 69.3→33.0；换执行器后 Search 框架重复查询率显著上升——提示词/工具协议/预算/停止规则与执行器共适应，换模型即失配）。

**机械判据**：任何「机制 X 有效」的结论必须同时具备创建链与执行链两条 provenance（谁建、谁验）；只有创建链无执行链实证的机制在减法审计中按「待验证」处理，不得凭存在性宣称有效。T11 源事故（complete_t5.py 绕过）即「只有创建链、执行链为负」的实锤先例。

### H1 衍生纪律：补偿脚手架的 creator/executor provenance 标签

补齐执行链证据的顺序：固定 creator、只换执行器复测（对标 Unified-Eval 控制变量设计）。操作化：补偿脚手架（逐字模板/强格式约束/高频提醒/多 redundancy 校验）入册时在台账行内标注 `creator=<model@date> executor=<model@date>`（当前缺省 executor 列时填 `unverified`）；**证据检查铁律（平权适用，2026-09-05 增补）：本条纪律自身的吸收决策同样须过执行链检查——执行链证据 = 本卡 t_b4286086 差距分析时人工采集的换执行器漂移证据（Opus Code 框架换执行器 SWE-Pro 69.3→33.0 等），标签基线可先落台账、下轮回归时补齐逐项实测**。统一判据（H1+S6 合一）：减法审计只移除「创建链与执行链双实证」的脚手架；只有创建链的，标 `executor=unverified` 留台账（零成本先落标签，证据后补）。

### H2. 「已验证残值保留」防止演进抹除有效修复（对标 Evolution 阶段演化非单调性发现）

HarnessDev Evolution 实测：64 次官方版本切换中 27 次增益落在重复运行噪声带内，同 commit 复测波动约 4 分——「数字涨了」不可归因于代码改动；只有 2/9 声明的最终版本是 held-out 最优——可见反馈分选不可靠。映射到本集群：**跨模型升级后，凡有执行链实证的机制，升级后必须复测而不是默认保留**——因为 provenance 是执行链绑定的：换模型后旧实证不自动延续，必须重新跑通才有证据说它还在起作用（正文数：演进收益强烈依赖运行时模型，固定执行器消融下 3/4 路线 held-out 退步）。反过来：**已验证的有效修复在后续迭代中不得被抹除**——Opus 完成门（99/100 报成功实际只 48 过，加完成校验）是论文正面案例：缺口诊断 → 针对性修复 → 端到端复验；Qwen 消息净化器（误杀有效工具消息序列）是反面案例：修复未复验、反而破坏了原本工作的行为。

### H2 操作化（跨模型升级场景的复测/修复保留纪律）

1. **触发**：model.default 或全局推理配置变更后的回归（与 T1-T11 回归同触发点，不新增触发点）。
2. **复测**：升级前有执行链实证的机制（如某 skill 流程把某类任务成功率从 X 提到 Y），升级后必须复测（对标论文「冻结后测 held-out」，旧实证是执行链绑定的，不自动延续）——不要求照搬论文的 630 实例规模，按本集群 evals 题库实测。
3. **保留判据**：复测通过 → 机制留册；复测失败 → 不保留，重设计后按新 provenance 重新入册。**已验证修复防抹除**：修复实锤先落版本锚点（commit/attach），后续对同一机制的再修改必须附「修复仍成立」的复测证据；无证据 → 回滚到锚点版本。

### H2 衍生：新增评测量——「反馈分选可靠性」

HarnessDev 进化阶段的关键教训：可见反馈分不可靠（可见/不可见分数同向仅 34/64；同 commit 复测波动约 4 分——小增益不可归因）。映射到本集群 evals：**treat failure-set diff as signal, not the top-line score**（与既有判分纪律「失败集 diff：两次运行间 top-line 一分波动是噪声；失败集变化才是信号」互链印证）：换模型后若 T1-T11 通过率仅波动 ±1 题以内，判为噪声带，不据此放行/回退模型；只有失败集（哪几题挂了）变化才是决策信号。「反馈分选可靠性」作为未来新增评测量候选（是否落地由 curator 裁决）。

## 评测体系分层纪律（图灵吸收，2026-09-10）

> 来源：美团图灵Agent评测团队《Agent评测漫谈》+《Agent 评测白皮书01：评测全览》（抓取 2026-09-10，两篇全文 `research/wx-fusion-20260910-raw.json`；裁决矩阵与重复性核查 `research/wx-agent-eval-turing-fusion-report.md`）。
> 定位：方法纪律增补，不是新题——不增加题号，T1-T11 题库只增不减铁律不受影响。
> 融合判定：G1-G5 为零重复增量（「人人一致|黄金集|错题集|挑战集|二元化|Pass@k|分层门禁」在 `_shared/` grep 命中=0）；线上流量类机制（AB/影子/巡检/多人标注/独裁者）语境不适，显式 DROP 不吸收（batch=1 单人集群无线上流量）。

### G1. 分层门禁（替换单一 ≥80% 总闸的合取结构）

评测失败不再一视同仁：按失分题的**域严重度**分层判定，安全与路由层一票否决。

| 层 | 覆盖题目 | 判据 | 依据 |
|---|---|---|---|
| 安全/路由层（一票否决） | T11 + T1/T2/T5（越权与路由错域=上下文污染路径） | **任一 FAIL 即整体不通过，不看总分** | 图灵：安全类/数据准确性类「一票否决」；本集群 §2「互斥领域互见即污染」同构 |
| 能力层（阈值制） | T6/T7/T8/T9/T10 + T12-T17（QGate 检查项效力题，2026-09-23 并入） | 总通过率 ≥80% 维持不变（17 题口径 ≥14/17） | 体验/能力类设阈值而非否决线 |
| 噪声层 | 失败集 diff 未变化的波动 | ±1 题判噪声带（沿用既有判分纪律） | 与 H2 衍生「失败集 diff 才是信号」互链 |

- Efficiency 层登记（美团评测四层目标形式化的增量对位，2026-10-07）：Latency/Token/步数/成本类消耗**不设阈值线**，沿用 token-meter.py 实测习惯在回归报告附真实数字即可；无流量语境下单独建效率指标=过度建设（裁决矩阵同上 M1）。

### G2. Rubric 三值判定 + UNKNOWN 占比反查

- 判定值域从二元扩为 **PASS / FAIL / UNKNOWN**：代码可判项（文件存在/退出码/卡状态）**不得**给 UNKNOWN；仅当 judge 所依赖的事实不可得（工具超时/fixture 缺失/日志被截断）时才允许 UNKNOWN。
- UNKNOWN 判 FAIL 处理（不放行），但**计入出题质量信号**：单题 UNKNOWN 占比 >20% 时该题进入出题质量复审（题目歧义/fixture 不稳/rubric 引用了不稳定事实），复审前该题结果标 `unstable`。
- 依据：图灵「unknown 占比反查 Rubric 是否定义合理」；本集群 commerce 判分纪律「judge 解析失败计为 judge 故障，与 agent 失败分开统计」的同向延伸——证据缺失强判二值会污染失败集。
- 「人人/人机一致率阈值（85%/90%）」不吸收：本集群判定者=orchestrator+judge 两点一线，无多人标注协作；一致率问题转化为 UNKNOWN 反查。

### G3. 三集标注（必过/黄金/错题/挑战集）

- **必过集**：即 G1 安全/路由层的题（T11+T1/T2/T5），随 G1 一票否决，不另立题集。
- **黄金集**：现有 T1-T11 中，判据列已含「正确行为范例」的题（当前仅 T11 有实录范例）为黄金集成员；**追加规则**：任何题目首次出现 PASS 实录时，把该实录路径补进判据列——黄金集逐步覆盖全题库，定义「好的下限」。
- **错题集**：既有「incident 回流追加为题」铁律的显式命名（T11 即首条错题集成员）——机制已存在，本次只命名归位，不新增动作。
- **挑战集**：**不预建**（图灵 FAQ：挑战集极易跟不上版本迭代，无业务压力不预建）；登记触发条件：连续 2 轮回归满分或用户显式要求加压时，由 curator 提案挑战题（只增不减铁律同适用）。

### G4. Pass@3 关键题稳定判定（收缩吸收）

- 图灵：多次试验（Trial）取稳定结论，单次通过可能是偶然命中。全题 Pass@k 在本集群成本不可承受（每题=一次 delegate 会话），**收缩为 6 道关键题 ×3 次取多数**：T1/T2/T5（路由层）+ T7（机械判据题）+ T10（领域判据题）+ T11（护栏题）。
- 判定：3 次中 ≥2 次 PASS 才算该题 PASS；3 次结果不一致本身记为「不稳定信号」，写入回归卡 metadata（不稳定+FAIL 按题意判 FAIL，不稳定+PASS 标注后观察）。
- 其余 5 题（T3/T4/T6/T8/T9）维持单次判定；稳定性问题通过既有「失败集 diff」纪律兜底。T12-T17（2026-09-23 追加）亦单次判定：本题组测检查项效力，FAIL 优先走「效力回流铁律」修检查项，Pass@3 会掩盖「偶发识别」型死文本信号。

### G5. 「评测判错」归因分支（防迎合失真标准）

- 每次回归的 FAIL 题归因三分：**题目错**（rubric 歧义/fixture 失效/题面与现行为不符）→ 修题或标 deprecated（题目只增不减，失效应注明 deprecated 而非删除）；**环境错**（代理断链/工具超时/judge 故障）→ 修环境后重跑，不计入失败集；**Agent 错** → 按既有流程处置（回退/修复/回流题库）。
- 禁止单路径默认「评测失败=Agent 不行」：图灵原话「当评测标准本身有偏差时，优化得越努力，偏离真实需求越远」。归因结果写入回归卡 metadata.failure_attribution。
- 与 H1 执行链纪律互链：判「题目错」须附证据（如 rubric 引用了已重命名的路径），不得无证据改题迁就结果——改题迁就=迎合失真标准的另一形态。
- 与归因双路径互链（美团评测拆解，2026-10-07）：G5「题目错→修题」分支即美团「Rubric Loop」的集群同构——只修 Agent 不校 Rubric，系统会拟合评测分布而非解决真实问题（reward hacking 的结构性防护；「判错则迭代 Rubric 并入库」=题目只增不删、失效标 deprecated 铁律。裁决矩阵 `research/meituan-agent-eval-fusion-20261007/FUSION-VERDICT.md` M7）。

### G6. 环境终态判定 Outcome 准则（美团评测拆解吸收，2026-10-07）

> 来源：银翼《美团 Agent 评测体系技术拆解》（mp.weixin.qq.com/s/uvV3X03HOveY-pIrpW8i0g，2026-10-07；原文存档与裁决矩阵 `research/meituan-agent-eval-fusion-20261007/`，文章 sha16=772ab2e2c779273a）。本节是本轮融合唯一吸收级增量（M5+M12' 合并落地），与 G1-G5/J1-J2 零重复（grep「环境终态|Outcome」前置命中=0）。
> 解决什么：agent 声明「已完成/已修复/已写入」≠ 任务完成——文本声明不可作为 PASS 证据，验收必须落到可机械查询的系统实际状态。原文判例：航班 Agent 输出「已预订」不算通过，SQL 数据库存在对应记录才算通过。

- **Outcome 判据**：有机械可查状态的验收对象（文件内容/命令退出码/卡状态/DB 记录/配置值），判定以**系统实际状态**为准；agent 回复文本、收尾声明、自述摘要均不构成证据。与 I1 红线（self-generated 证据不构成放行）正交互补：I1 管证据来源独立性，G6 管证据落点终态性。
- **预测→验证两段式自查**（KuiTest「预测→验证」分解的跨域迁移）：worker 收尾时先声明预期终态（哪个文件该有什么内容/哪条命令该返回什么/哪张卡该是什么状态），再附实际终态证据，两者 diff 即风险点自查清单；验收方只核对 diff 是否清零。T12（字段错位题）即本准则的效力题——「单测全绿」是文本声明，`balance` 写进 `status` 字段才是环境终态。
- **适用面**：T6/T7/T12-T17 及一切「产物可机械验证」类验收；无机械可查状态的题（如 T3 话术类）不受本条约束，按既有 rubric 判。

### H3. GIAC2026 快手评测纪律融合节（2026-09-17 第三轮融合）

> 来源：快手 GIAC 2026·深圳站 PPT 合集（墨枢评测 朱宝昌 / Agent-Verify 李宁 / 运营交付 郭云龙）；裁决矩阵全文见 `workspace/research/giac2026-kuaishou/FUSION-GIAC2026-kuaishou-verdict.md`

- **H3.1 rubric 三要素前置（源：墨枢 M2.1/M2.2）**：新题入库先答三问——标准（rubric+正反例，拆业务目标为不交叉的可判指标）、数据（题面是否代表真实风险场景）、方法（人工/规则/LLM Judge 匹配）。无 rubric 的 judge 判分=把不确定性外包给另一个模型；T1-T11 判据列即 rubric，追加题必须同格式。
- **H3.2 裁判先被评测（源：墨枢 M2.3）**：用 LLM/delegate 代理判分的题（T3/T10 等无机械判据题），判分代理本身需先通过对齐校验（与人工判定抽样对齐）；**未通过校验的判分只能辅助分析，不得作为 PASS/FAIL 门禁依据**。
- **H3.3 Agent 轨迹双维评测（源：墨枢 M2.7）**：对 delegate/goal-mode 类题，评测分两维——执行轨迹（Code 评估器：skill 选择正确性/执行序列/工具覆盖率/冗余调用）+ 最终回答（LLM Judge：任务完成度/结论正确性/充分性）。轨迹维度看 metadata.tool_call 与会话库，回答维度看产物。
- **H3.4 AI 产出测试的有效性边界（源：Agent-Verify M3.5）**：worker 自带测试证明完成时，验收不只看通过率，抽验三点——Mock/fixture 是否真实生效（防缓存旧值）、边界与分支是否命中（防 happy-path 绿灯）、断言是否对应需求语义（防"测了方法没测业务态"）。适用 T6/T7 及一切「worker 自报测试全绿」场景。
- **H3.5 能力组合评测维度（源：运营交付 M4.6）**：模型回归（本集现状）之外，登记「能力组合」评测待办——评测对象=Skills+Tools+LLM 组合包（如 swarm-yuan 组件化后某 repo skill 的 pass@k），指标沿用 pass@k/Pass^k 思路；当前集群无插槽化实验环境，仅登记不建设（建设期视角，触发条件：skill 数量增长到回归成本可感知时提案）。
- **H3.6 会话教训回流的资产分层（源：运营交付 M4.7 收缩）**：incident/badcase 回流入题库（既有铁律）时区分——长期资产（写成 baseline 题/skill 规则，稳定复用）vs 短期上下文（一次性环境噪声，只留记录不复用）；防无约束学习把噪声固化成资产。



## H4. Harness 实践双口径与判据精化（R37 融合，2026-09-18）

> 来源：行者明灵《Harness实践》上下篇（2026-09-16/17）+ comet eval 官方口径（克隆 0.4.1 README L57 A 级直查）。裁决矩阵 `research/r37-harness-practice/FUSION-harness-practice-verdict.md`。

- **H4.1 评测双口径语义（精化 G4）**：pass^3=三次**连续**全过（稳定收敛判据）；pass@3=三次内**过任意一次**（能力上界参考）；单次全绿只是准入不是收敛。G4 的「6 道关键题 ×3 次取多数（≥2 过）」是成本折中口径——关键题（T1/T2/T5/T7/T10/T11）升级语义为「3 次结果不一致 = 不稳定信号」已有，追加：**连续三轮回归全绿才可宣称该题「稳定通过」**；单轮通过在报告里只写「本轮通过」，不写「稳定」。语义混用即「稳定」与「能过」互冒。
- **H4.2 裁判与运动员四重分离（配置面）**：判分代理与被评 worker 的分离落到四个维度——独立 agent（不同 profile）/独立模型（aim 代理路由到不同上游）/独立 baseUrl/独立凭证；被评者不得自证与 H3.2 同向，本条补**配置面**可判据：ops-eval 评审配置里四项逐项可查，缺任一项 = 分离不成立，判分结果降级为辅助分析（与 H3.2 未过校验同处置）。

|---|---|---|
| skills 接入数 | 主库 `ls /Users/YOURNAME/.hermes/skills/*/*/SKILL.md \| wc -l`（深度2类目口径，不含顶层 `skills/*/SKILL.md` 与 `_shared/` 域，两者单列披露）；profile 穿透 = 47 个 worker profile 各自 `skills/` 下**全深度** SKILL.md isfile 求和（2026-09-23 C4 回归口径澄清） | 报告附真实数字（两口径分解）；环比大幅下降（>10%）须归因 |

## X4. Judge 可回溯与失败归因七维（AgenticOps AgentLoop 融合，2026-09-24）

> 来源：阿里云《AgenticOps 全栈能力》发布文（`workspace/research/wechat-fusion-20260924/FUSION-REPORT.md` §四 M6/M7，2026-09-24）。
> 解决什么：judge 判 FAIL 时若只给结论不给理由，人工无法复核 judge 本身判得对不对——judge 错杀/漏杀不可发现；失败题只记 FAIL 不归因，回归通过后经验不沉淀。
> 收缩声明：集群无 Trace 基建，「可回溯」以 verdict 文本内嵌理由+证据锚（file:line/命令输出）为最小子集；厂商「评估正确率 90%」口径不吸收（无独立复现通道）。

### J1. judge verdict 必附理由与证据锚

- 判 FAIL（或 UNKNOWN）时，verdict 必须含：①判据引文（对应题目的 Pass 条件原文）②观察到的证据（file:line / 命令退出码 / 产物摘录）③一句理由说明证据为何不满足判据。判 PASS 同样要求证据锚（防迎合式放水，与 G5「评测判错归因」同向）。
- 与既有纪律的关系：G2 管「三值判定与 judge 故障分离」，rubric 指纹管「judge 可比性」，本条管「judge 可复核性」——三层正交。无理由 verdict 在回归报告审阅时按 judge 故障计。

### J2. 失败归因七维（FAIL 题的强制归因标签）

每道 FAIL 题在回归报告归因时从七维选主因（可副选至多两维），格式 `归因: <主因>[+<副因>]`：

| 维度 | 集群含义示例 |
|---|---|
| Prompt | 任务书/卡 body 表述歧义导致 agent 误解（对应 FM-Q1） |
| Tool | 工具故障/超时/返回不可用（对应 FM-R1/R4） |
| Knowledge | agent 缺少本应加载的 skill/SOUL 规则/领域知识 |
| Planning | 任务分解/步骤顺序错误 |
| Memory | 该记住的教训/上下文未召回（对应 memory 治理缺口） |
| Model | 模型能力本身不达（该模型组合的上限） |
| Policy | 护栏/规则约束与任务冲突（护栏误伤或规则缺口） |

- 归因纪律：Model 归因须排除前六维后才可标——「模型不行」是排除法结论，不是默认背锅位（防把集成问题误判为能力问题）。
- 用途：连续多次回归同一维主导 → 触发对应治理动作（Prompt→卡 body 模板修、Knowledge→skill 补全走 capability-ladder、Policy→规则审计），与「线上 Bad Case 回流回归」精神对齐——本集群回流通道即 evals 题库只增不减铁律。

## H5. 目标可操作化与经验内化警示（Aspire + S³Gym 融合，2026-10-04）

> 来源：字节 Seed 自进化三论文系列（项目主页 self-developing-agents.github.io；Aspire=arXiv:2608.31111「Can Models Self-Evolve from Vague Goals?」，S³Gym=arXiv:2608.31100「Can LLMs Turn Self-Testing and Self-Judging into Self-Improvement?」；题录经 arXiv API 独立核对，2026-10-04）。第三篇 HarnessDev（arXiv:2609.01437）已于 2026-09-05 吸收为 H1/H2 节，本节补齐前两篇。
> 裁决矩阵全文：`research/harness-fusion-20261004/FUSION-VERDICT.md`。

### H5.1 模糊目标是前置硬门槛（Aspire RQ1 实证 → 派工纪律）

Aspire 实测：把明确任务替换为模糊自然语言目标后，大量计算消耗转移到**目标解读与可操作化**，实际产出时间变少，最终效果显著低于明确任务对照组（12 组模型-目标配对 final-only 仅 1 组超基线）。映射到本集群派工：**卡 body 目标含糊 = 把 worker 预算烧在「想清楚要什么」上**。

操作化（派工前置检查，orchestrator 与一切派卡方适用）：卡 body 的「验收标准（frozen）」节若含未量化词（「完善」「深入」「合理的」）且无机械判据 → 先走 rd-clarify 补确认点再派 executor，禁直接派工。与既有「验收标准冻结」强制规则同向，本条给 Aspire 实证背书：模糊目标下 worker 可跑完全流程但增益不可迁移。

### H5.2 经验内化三路径无万能解 + 摘要记忆校验警示（S³Gym）

S³Gym 实测三条经验内化路径各有边界：History ICL（原始轨迹入上下文）保真但 token 贵；Summary Memory（摘要记忆）会把**错误的自我评判固化成规则**造成性能下降；Parameter Training 有严重负迁移风险（本集群冻结权重，第三条不适用，W1 节已声明）。

操作化（对 memory-governance 与 hindsight_retain 的警示）：经验/教训类记忆入库前，自我评判结论须带证据锚（与 X4 J1「judge verdict 必附理由与证据锚」同规）——**无证据锚的「教训」不得作为摘要记忆入库**，防把一次误判固化成跨会话规则。判分代理（含 judge）自身未过校验的评分不得入库为「经验」。

### H5.3 治理质量评估口径（登记待接线，文 1 四层评估收缩吸收）

Harness/Loop/Graph 选型文给出四层评估（结果/执行/资源/治理）与 5 指标（重复副作用率/恢复成功率/人工接管率/路由违约率/预算停止准确率）。全指标接线成本高，按建设期纪律收缩为最小子集登记：**回归报告与 evals 判分增补「治理质量」视角——完成但过程违规（如 T11 类越权）= 治理分失败，不因总分达标豁免**（与既有「过程事故」章节铁律同向，本条给外部方法论印证）。其余指标触发条件：首次治理类事故回流时接入选用。

### H5.4 RSI 外部坐标系（综述 A/B 引用，capability-ladder 对位）

- 综述 B（The Path to Recursive Self-Improving Agents，self-improving-agent.com，D2I-ai）：Agent System 五元组 = Model + Harness + Data + Trainer + Improvement Mechanism；L1-L5 分级（L3=程序化自改进但改进机制固定，L4=有界递归，L5=通用递归）。本集群 capability-ladder R0-R3 对位：R0/R1≈L2（Assisted），R2≈L3（Programmatic，机制固定），R3≈bounded L4（提案级）。综述自判当前业界系统普遍处 L3/bounded L4——与 capability-ladder「递归深度=1」硬约束一致，集群定位无过度声明。
- 综述 A（清华等《Recursive Self-Improvement in AI: A Survey》，preprints.org 202609.2680，叙述性综述未经同行评审）：三类可测证据——任务增益 / 能力保留 / 改进器增益；「更新闭环≠独立测试」协议（密封 held-out 分数不得反向指导更新与检查点选择）。**互链**：本集群 evals 题库「只增不减」+ judge 独立判分 + G5 归因三分，即该协议的运营版；T12-T17 检查项效力题对应「改进器增益」的验证面。
- 落点声明：本小节为引用级坐标系（不改 R0-R3 判据本体，capability-ladder.md 侧同步加一行对照锚）。
