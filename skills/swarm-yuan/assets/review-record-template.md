# 审查记录 YYYY-MM-DD

> 审查是逻辑错误的兜底机制之一（与测试并列）。本文件是证据载体——"看过了"没有记录等于没看。
> 审查口径见 `references/independent-review-protocol.md`：独立性由冷读上下文产生，不由"请严格审查"产生。
> 合规门禁 check_review_record（REVIEW_RECORD_REQUIRED=1 时启用）要求三要素：评审人/日期/结论；本模板新增字段用于独立审查机检。

| 字段 | 值 |
|------|-----|
| 评审人 | <子代理标识 或 人工姓名> |
| reviewer_context | <fresh / degraded / unavailable>（只有 fresh 构成有效独立审查；机器按此键解析） |
| 日期 | YYYY-MM-DD |
| 范围 | <本次审查的文件/commit 范围> |
| 结论 | 通过 / 通过（带 N 项建议） / 不通过（须修复 M 项） |

## 五维审查要点（S3 内容检查表）

- **正确性**：业务规则/边界条件/异常路径是否符合 spec §1 意图？
- **安全**：注入/权限/敏感信息是否覆盖 OWASP Top 10 面？
- **性能**：有无明显 N+1 查询/大对象拷贝/热路径阻塞？
- **可维护**：函数长度/命名/抽象层次是否符合分层约定？
- **测试覆盖**：spec §11 声明的用例是否都有对应测试？接口端点是否有正常 + 失败路径？断言是否能捕获错误值？
