# 原则卡模板（principles/p-&lt;名&gt;.md）

> **用途**：把团队的核心判断从"墙纸"变成可引用、可审计的短卡。**引用必须绑定决定**——交付物里写「原则引用：<卡名> → 改变了 <具体决定>」，只写卡名不写改变了什么，视为没应用。
> **来源**：pstack 24 张 principle 卡 + 引用契约（见 references/pstack-methodology.md §五）。
> **形态**：每张 ≤25 行，固定四段；只许引用本轮真读过的卡。

---

```markdown
# {原则名}

**适用时机**：{一句话，可判定——"当 X 出现时"而不是"始终秉持"}

**理由**：{为什么这条成立；说清代价——不遵守会付出什么}

**模式**：
- {可直接照做的动作 1}
- {可直接照做的动作 2}

**自检问句**：{能被回答"是/否"的问句；答"否"就是没做到}
```

---

## 建议的最小集合（4-6 张，按项目形态取舍）

| 卡 | 主张 | 自检问句 |
|---|---|---|
| `p-root-cause` | 修系统第一次做错的地方，不修症状 | 触发症状的那个状态本身合法吗？（合法→出错代码是根因；不合法→加 guard 只是藏 bug） |
| `p-premise` | 两个共享同一前提的修法都失败时，怀疑前提 | 这几次失败的修法共同假设的那句话，写下来了吗？测过吗？ |
| `p-reattach` | 先删死代码与冗余校验，再在更简单的基础上建 | 这行代码删掉会怎样？答不上来就先查清 |
| `p-verify` | 对真实产物取证，不用代理指标 | 这条结论的证据在第几级？（你说的话 < file:line < 走一遍 < 跑脚本 < 运行中复现） |
| `p-number` | 报数字前先说清什么限制了它 | 这个数字可能测的其实是什么？ |
| `p-guardrail` | 校验只在系统边界，内部信任类型 | 这份数据正在跨系统边界吗？不是则校验是冗余的 |

## 结构校验（防残片）

pstack 自身有 4 张卡在发布流程中被截断成残片（正文只剩一句或半条 bullet），仓库没有任何校验能发现。本仓的 `check_skill_docs` 对 `principles/*.md` 断言：**每张卡 ≥12 行且四段齐全**（适用时机 / 理由 / 模式 / 自检问句），缺一段即 fail。

## 交付契约

- 交付模板（review-record / 合入说明）增强制字段：`原则引用：<卡名> → 改变了 <具体决定>`。
- 一轮内引用未读过的卡，视为造假。
- 引用条数不是指标——0 条也可以交付；写了卡名却指不出改变了什么，比不写更差。
