## 文档边界与读法

本文是 swarm-yuan 的唯一规范设计文档，回答四个问题：系统是什么、为什么这样设计、怎么落地、凭什么有效。操作命令查 `docs/usage-manual.md`。演化过程与决策史查 `docs/design-evolution.md`。上游运行时基线查 `docs/upstream-baseline.md`。全部数字的真值在 `swarm-yuan/assets/facts.conf`，self-check 做机器对账。

文档角色：本文为规范源；终态设计摘要已于 2026-10-26 合并进本文并归档到 `docs/reviews/design-terminal-2026-10-26-archived.md`；带日期的设计文档是历史记录，不作为规范源。证据分级 M0–M4 的定义在 `assets/registry/README.md`，验收指标见附录 D。

读法：第一、二章给判断依据（要不要用、为什么需要）。第三章是主体，讲每层机制与检查。第四章把机制映射到文件。第五章给适用边界。第六章收口。数字、来源、验收明细收在附录，正文不罗列。

术语先消歧三条，其余见使用手册术语词典：

- 同一实体有两个名字：生成物（生成时）、目标技能（交付使用后）。
- 门禁是词法与结构层面的模式检查。验证是测试与审查的语义核验。两者不是一回事，分工见 3.4/3.5。
- **组件库清单**是全文唯一称谓（"地图""零件目录"是已废弃旧称，指同一物）。

# 一、What：它是什么

**swarm-yuan 是一个生成器：对任意代码仓库跑一次，产出一个项目专属的研发能力技能（目标技能）。** 此后该项目的一切 AI 编码都受这个技能约束。

系统的全部内容是一条链：

```
①认知项目的结构与关系 → ②整理工程规范
→ ③结合框架最佳实践与既有业务实现 → ④形成组件库与拼装式开发模式
→ ⑤吸收开发者的实际研发习惯 → ⑥装配成目标技能
→ ⑦用目标技能完成日常研发、测试、验证、交付（结合既有测试案例与工具）
→ ⑧使用中按具体问题迭代成长 →（项目演进，回到①重新同步）
```

每一环对应一份实物：

- 认知产出组件库清单（组件/接口/数据三类）、关系边集、配方（业务功能清单 + 任务拼装序列）。
- 规范产出铁律、三值规则与门禁配置。
- 习惯产出开发偏好。
- 装配产出目标技能六段目录。
- 日常开发靠门禁与验证。
- 成长走两条更新通道。

第二章论证这条链为什么必须存在。第三章讲它怎么做出来并保证可信。第四章说它落在哪些文件上。

系统分两部分，体积约束相反：**生成器厚、目标技能薄**。探查知识只在生成时读一次，允许厚。目标技能在每次开发会话里重复加载，必须薄。重复加载的内容有字节预算，超上限 CI 即失败（口径见附录 A）。

# 二、Why：为什么需要它

**AI 写代码的瓶颈不在会不会写，在懂不懂项目。** 不认识项目就动手：改了不该改的文件，升级了不该升级的依赖，重复造已有组件的轮子。检查靠人逐行 review。缺陷不在生成，在认知。

这些失败分成两类，两类要用完全不同的工具：

- **不懂规矩**：不知道只读区不能改、稳定组件不能动、提交要带测试。这类失败有词法和结构特征，机器能识别。
- **想错逻辑**：规矩全守了，但算法写错、边界漏了、契约悄悄破坏。这类失败没有固定模式可匹配，只能靠真跑测试和独立审查发现。

因此系统有两件核心工具：

- **门禁**管第一类：模式匹配，写前、写时拦截。
- **验证**管第二类：语义核验，交付前证明。

另设独立验证器（3.5），证明门禁本身没有形同虚设。指望门禁抓逻辑错误，是这类系统最常见的自欺。

为什么不直接用现成方案？lint 规则包只覆盖第一类失败的一小部分，且不含项目认知。人工写项目文档没有机器检查，写完就开始过时。让 AI 裸写等于放弃拦截。三者分别缺了链条上的认知、检查、约束环节。

反证：链条缺一环会怎样——

- 缺认知：不探查直接生成规则，门禁照抄通用模板，与项目无关，AI 第一件事就是绕过它。
- 缺清单核验：清单靠编凑数，照着拼装必然出错（机制见 3.1）。
- 缺约束：认知停在文档里，AI 读完照犯，提示词约束不了行为（3.4 展开）。
- 缺验证：门禁全绿不代表逻辑正确，带着缺陷交付。
- 缺成长：项目演进三个月后技能过时，系统退化成一次性脚手架。

由此确定四条设计原则。每条都对应一个可验证的兑现机制，兑现点在第三章逐一指认：

1. **拼装式开发**：新功能 = 既有稳定单元拼装 + 最小新增胶水。组件库清单来自探查。写新代码前按七层下探找零件，任一层命中即停。顺序：代码库已有 → 标准库 → 平台原生 → 已装依赖 → 一行调用 → 最小实现。拆分错误由检查链拦截（3.5）。
2. **特征卡立法、门禁执法、验证器司法**：特征卡定义项目应该是什么样。门禁检查代码实际是什么样。独立验证器证明检查本身有效。三者互不越界。（三权分立是叙事说法，实物对应见第四章。）
3. **诚实降级**：运行时没装就显式披露，不假装全深度整合。权限边界一律 fail-closed，失败时拒绝、不放过。
4. **AI 全自动、零手动配置**：生成由 AI 一键完成。使用时研发人员对 AI 说话。bash 命令只是排查与 CI 的备份通道。

# 三、How：怎么做到

> 本章按链条顺序分六层，每层开头交代与上一层的衔接。读完应能回答：每一环由什么机制兑现，机制由什么检查兜底，检查的证据落在哪。

## 3.1 认知层：先认识，再行动

第二章确立了认知先行。本层回答：认知怎么做，产出的组件库清单凭什么可信。

**认知的产物是三份清单，不是一份读后感。** 探查先做项目形态判定，再按判定出的维度全量穷举，产出三样东西：

1. **组件库清单**：组件、接口、数据三类内容，统一两列表（路径 + 说明与约束）。路径供脚本检查。说明列写 AI 读代码后的理解与稳定性标注。
2. **关系边集**：谁依赖谁的机器可读记录。脚本先提取 import 边与声明式映射边，AI 再补调用、路由、消息、批处理装配等语义边。声明式映射边（MyBatis 举例）：
   - namespace→Mapper 接口
   - resultMap→实体
   - resultMap 内 column→property 字段明细

   这类字符串耦合编译器不检查，改了字段漏改 XML 是静默缺陷。
3. **配方**：业务功能清单 + 高频任务的拼装序列。每个配方五要素：触发场景、前置查询、复用件、胶水、门禁与验证。

三者分工：清单回答有什么零件，边集回答谁依赖谁，配方回答怎么拼。

**文档证据分级：设计文档、需求文档入探查，以代码为准。** 仓库里的设计文档（docs/、ADR）与需求文档（PRD/需求规格）是架构决策与外部交互设计的证据源。应用内信息以代码为主，设计文档为辅（提取意图与背景），需求文档仅在需求分析时参考。PDF/Word 文档先转 Markdown（图片转 mermaid/OCR）再提取。转换产物入 docs/converted/ 可追溯。文档与代码不一致时，必须在 spec 里显式声明冲突，不留隐瞒项。

**字符串耦合单独设防线。** 有一类依赖只活在字符串里，编译器不检查：

- mapper XML 的列名
- 批处理 SQL
- 消息端点名
- JPQL 实体名
- bean 装配类名

改了 Java 侧不改字符串侧，编译照绿，执行时静默出错。对这类耦合统一两手。能提取的进关系边集（mapper 的 namespace/resultMap/字段明细、JPQL 引用、bean 装配），机器可查"改这个字段还牵动哪些文件"。不能提取的（批处理 SQL 列名、消息端点双边）建链路清单与配对表，改数据模型前必查。数据模型、mapper XML、批处理任务、ORM 迁移资产四个维度各有计数核验。模型与迁移的漂移由专门门禁拦截。

**组件库清单过三道检查才可交付。** 清单一旦失真，拼装式开发整体失效：

1. **防漏：计数核验。** 清单条目数不得少于自动化枚举数的 95%，每个维度独立核验。
2. **防伪：路径核验。** 清单和配方里登记的每个路径逐个验证存在。查出幻觉路径即阻断激活，技能停在 draft 态，全量门禁不解锁。
3. **防过时：稳定性审计。** 标注"稳定/禁止改"的单元用三个自动化信号复核：近期变更次数、引用次数、有无同名测试。标注与事实冲突就提示复核。这一级只提示不阻断，因为信号是启发式，判断留给人。

框架与技术栈的最佳实践不进组件库清单，以**框架规则集**的形式按探查结果激活。探到哪个框架，才注入哪个框架的约束与门禁片段。每条规律必须在项目代码里找到证据才实例化，找不到就剔除并记录反例。既有业务功能实现编目进配方的功能清单。每个功能注明四件事：由哪些组件拼成、走哪个接口、落哪些数据、有没有测试。这些功能是后续同类任务的先例。

## 3.2 规范层：规矩从哪来

认知层产出了项目是什么样。本层回答：项目的规矩从哪来，以什么形式进入技能。

规范有三个来源，按可信度排序：

- **已写下的**：AGENTS.md、CLAUDE.md、记忆中的规则与偏好，直接提取。
- **实际做的**：git 历史的行为统计（提交前缀、分支命名、共变文件、热点文件、测试提交占比）。脚本自动化出初稿，AI 审读后才采纳。统计事实不等于规范，书面规则优先。
- **推导出的**：探查期从编排约束与只读判定推导的项目特有规则初稿，例如生成代码目录禁手改。

三源汇合后按形式分工。规矩的表述进技能铁律段，引用来源而不写死值。规矩的执行进三值规则与门禁：一条规则的 allow/prompt/forbid 是机器可读的数据，不是散文。规矩的参数进 conf 文件，机器出初稿、AI 补语义项，每个值带来源注释。表述与执行分开是刻意的：组件库清单与铁律管"是什么"，规则与门禁管"应当怎样"，两区不混写。

## 3.3 装配层：生成与激活

前两层的产物要装配成目标技能。本层回答：装配怎么分工，技能在什么状态下可用。

生成的分工红线：**自动化出初稿，AI 判断质量。** 脚本只做信号可信的事：枚举、拷贝骨架、渲染配置初稿、核验计数。判断性环节必须 AI 做：特征卡填值、规律实例化、习惯采纳。反向分工都是事故源：脚本假装能判断质量，或 AI 重复跑自动化流程。

激活有一道状态门，把前面的检查变成硬门槛。骨架生成后是 draft 态，全量门禁禁用。三关全过才激活解锁：占位符清零、清单路径零幻觉、计数核验达标。draft 可断点续传，active 必须全绿。两种状态区分"还在填"和"已可用"。

升级前核验项目状态机，任务停在中间阶段即拒绝并点名解除路径（仅注册与已归档放行，环境变量可显式豁免）。通过后在同一文件系统的临时副本完成模板更新、配置补缺与框架注入，再发布整个目录；失败保留原技能，成功归档完整原件。未指定档位时继承原档，显式升档复用创建流程补缺，保留已填正文和配置，回到 draft 等待新增内容完善。恢复副本与原技能都不重新安装项目 Git hooks。

升级支持预演（`--upgrade --dry-run`）：走完整流程但不写入任何文件，输出将 add/change/delete 的文件三态清单，暂存副本放系统临时目录且不落 trace。预演与在途门互补——门管“现在能不能升”，预演管“升了会动什么”；在途态对预演放行，真升级仍拦截。

项目整体迁移或克隆后，升级会把 AUTO:detected 的项目根（`PROJECT_DIR`、SKILL.md 项目根、操作档中的旧根路径）刷新到新位置；历史 spec/review 保留原路径作为证据；技能目录不在新项目根内时只告警，避免误改外部技能。

装配守厚薄分界。进目标技能的每份文件都按"每次会话重复加载"计价。上下文预算、入口文件、概念数量各有预算上限，CI 机器断言。预算是恒等式——新内容进技能，必须给既有段落瘦身腾位。只增不减就是膨胀。

## 3.4 使用层（上）：门禁管"不懂规矩"

技能激活后进入使用期。第一道防线是门禁：词法与结构层面的模式匹配，写前、写时拦截。

门禁在三个位置拦截：

- **写之前**：hooks 拦"无 spec 写源码"，拦命中 forbid 规则的命令。拒绝消息必带替代方案——拒绝即指路，AI 能自动改道。
- **改之时**：每次编辑过范围与敏感度检查。
- **收尾时**：按任务类型选门禁序列执行。

多门禁同跑有执行纪律：按"构建、测试、接口、契约、复用、一致性、分层、文档、安全、依赖"的顺序串行。任一步失败即停，不用后面的绿掩盖前面的红。每步留痕到执行账本，审查时据此确认序列真跑过，而不是声称跑过。

"无 spec 写源码"这条流程约束按四层拦截落地，判据出自同一个库（spec-first-lib.sh）：

- 写时：宿主 hooks 经 spec-first-bridge 统一判据后以 exit 2 阻断。已实测：Claude Code、Codex、ZCode 三家。已生成配置、尚未实测：Cursor、Gemini、OpenCode、Kimi-Code、Windsurf（Devin CLI）五家。
- 提交时：git pre-commit，宿主无关。候选 spec 与批准正文都来自实际提交的暂存区；未暂存批准不能放行，暂存撤回也不能被历史正文掩盖。
- 门禁时：check_spec_first，入核心序列。
- 流程准入：状态机 build 阶段。

能力状态在规则文件里分三态明示，实测与仅生成配置明确区分。强制面一律以提交与门禁为准，不假装写时拦得住。宿主输入保留命令换行与转义字符；包装命令归一后继续分段，每段单独裁决，未知段保留 prompt，最终取最严结果。该词法检查不承担完整 Shell 解释器或沙箱职责。

门禁分 strict、warn、advisory 三级，分级依据是检查信号的可靠性。能给出稳定失败信号的才阻断交付。信号有噪声的降为提示，由 AI 判断采纳。判断不了的（例如"这次复用是否贴合场景"）不假装能判。门禁输出三个问题，引导 AI 自查并留痕供审查回放。自动化只管信号可信处，判断留给 AI 并留痕。这条边界防止系统对自己的能力说谎。

门禁自身的复杂度同样受预算管住。门禁总数冻结在上限内。新增须等额删除。例外上调须逐例登记留痕（登记处：facts.conf 键注记与 CHANGELOG）。配置变量与上下文预算同理。帮项目降复杂度的工具，自己不能失控。失败方向另有一条原则：权限边界 fail-closed。fail-open 只允许发生在还有下层兜底的地方，例如 hooks 失败不阻断，因为命令还要过门禁。

## 3.5 使用层（下）：验证管"想错逻辑"

门禁管不住逻辑错误。第二道防线是验证：语义层面的真跑与独立审查，外加对检查者自身的检查。

验证有三件：

- **测试真跑且有效**：执行项目测试命令看退出码，检出"零用例空跑通过"的假阳性通过（`TEST_QUALITY_STRICT=1` 时直接失败）；配了覆盖率阈值后解析 lcov/cobertura/jacoco/clover/coverage-summary/coverage.out，低于阈值即失败；再扫测试源核验零断言、断言密度、负向/边界用例占比与聚焦测试（`.only`/`fdescribe`/`fit`）。可选配置变异命令，低于 mutation score 阈值即失败。接口测试按 HTTP 方法 × 路径模板枚举端点（OpenAPI YAML/JSON、proto 与常见路由声明均可枚举），要求测试调用中的方法与路径匹配；路径参数按真实值匹配，不能用集合路径代答；启用状态码要求后，每个已覆盖端点的请求附近都须有自己的状态码/错误路径断言。阈值未配置时明示"未启用"，不假装已覆盖。测试文件本身进清单维度做计数核验。测试体系存在而没配执行命令会显式提示。
- **独立审查**：以第三方视角重看产物。审查记录落盘才算数，口头"已审查"不算。
- **独立验证器**：直接运行与验证器共用一个框架夹具执行器，违规侧必须检出指定问题，合规侧检查禁止出现的告警 ID；advisory 门禁不以非零退出码作为唯一判据。ShellCheck 错误、工具故障、夹具准备或清理失败都使整体失败，日志按运行隔离。同时锁定命令行行为逐字节等价。样例全绿证明不了真实项目全覆盖；真实项目回归矩阵与连续运行稳定性要求见附录 D。本轮构造夹具验证不能替代该矩阵。

验证依赖留痕。调用、决策、门禁执行、拦截分别记账。决策写入互斥保护序号与前驱，文本按 JSON 转义；`trace-log.sh --verify-chain` 核验决策账本内部顺序与校验码，旧格式只允许位于链首之前。现用 `cksum` 是一致性校验，不是密码学防篡改证明；缺少外部可信锚时无法发现整链重写或末尾截断。`ref_trace_hash` 只记录调用末行引用，目前没有跨账本自动核验，不能宣称全链防篡改。审计按"一个用户目标 + 一个验收边界"逐项对账。

回归自身走统一测试入口：一条命令按层选择测试集（静态语法、门禁正反例夹具、框架正反例夹具、生成链路、独立验证器），每条测试带层级与并行安全元数据；并行执行时共享状态的测试逐个独占、互不干扰的测试按并发度分批，本地全量回归与 CI 跑同一入口同一参数。并行只加速执行，不降低验证强度——各并行单元的结果仍按原判定收敛，提速不改变任何一条测试的通过与失败含义。

**门禁与验证怎么接力，看拼装检查链这一个实例。** 拼装式开发的核心风险是拆错。一类是把本该复用的当成新写（重复造轮子）。一类是把该保护的改了（偷改稳定单元）。检查链按时间接力。spec 阶段先声明切分方案：复用哪些既有单元、新增哪些胶水、为何不能复用。切分本身先过七层下探，落到"最小新增"须给理由。编码时门禁查三件事：

- 新增胶水与稳定单元重名（重名即失败，应直接复用）
- 改稳定单元而未声明（失败）
- 稳定单元的下游受波及（提示声明）

配方引用的复用件路径验真，入口拦下幻觉零件。测试兜底逻辑正确性。任务再小，验证、错误处理、安全检查、无障碍四类不裁剪。自动化能判的全部判，判不了的降为 AI 自查留痕。这条链就是第二章"两类失败、两种工具"的完整展开。

fix 任务在验证层还有一条研发环境取证支线（存量项目排障底座）：日志定位 → 只读查库 → 远程断点复现 → 根因定论 → 修复 → 回归，六步流水线落在目标技能 references/bugfix-runbook.md，每步证据进账本。外部资源访问的三个脚本随技能分发：`tunnel.sh` 经堡垒机（ProxyJump 标准协议，Xshell 图形客户端建的同构隧道也能被 doctor 体检）编排数据库与 JDWP 端口转发；`ops-readonly-guard.sh` 对 AI 发出的每条 SQL/命令做 fail-closed 只读判定（只读放行、写拒绝、未识别默认拒绝），判定落 `.swarm-yuan/ops.jsonl` 账本供回归时对账；远程调试纪律与降级路径见 references/remote-debug-jvm.md（JDWP 无认证无加密，只活在回环绑定 + 隧道里）。设计理由：只读的第一道防线必须在凭证层（数据库只读账号、SSH 受限用户）——静态判定拦不住凭证本身的权限；守卫是第二道防线，账本是第三道。守卫不新增门禁（门禁预算 56 冻结），它在执行时点拦截，比验证时点的门禁更早一步。

强监管项目在合规层还有一条迎检支线（compliance 档随技能分发）：监管执法检查的技术检查点以条目级底稿形态进入目标技能——references/regulatory-checkpoint-table.md 承载 173 条检查点（优先级/控制点/检查点/判断阈值/证据类型/义务条款/处罚编号），references/compliance-checkpoints.md 承载五步判断法（找义务→找系统→找证据→找缺陷→找后果）、成熟度分级 V0～V5、处罚条款库 21 条、法规现行版本基线、智能体安全 6 域 20 项与采购 AI 40 项检查点，以及门禁与检查点的机检映射表。`scripts/inspection-ledger.sh` 把这套知识变成可执行的证据面：`checklist` 按技术域渲染人工核查清单；`ledger` 运行合规门禁套件并把每个门禁结果映射到检查点，输出统一台账（域/编号/检查项/依据/证据/结论）；`agent-audit` 对目标技能自身配置出智能体安全证据（硬编码凭证、沙箱目录、审批门禁、留痕面）。设计理由：机检映射不是判定——门禁通过只代表机检面未见异常，检查点的完整结论仍要按证据类型补齐人工证据，门禁未配置在台账里如实记为未配置；判定只认证据，口头说明不作依据。迎检能力不新增门禁（门禁预算 56 冻结）：机检面复用既有合规门禁，新增的是知识层与台账层。

## 3.6 成长层：项目变了，技能跟着变

前五层把技能立起来。本层回答：它凭什么不过时。

成长有两条通道：

- **结构通道**：项目指纹（文件数、扩展名分布、目录哈希）在会话开始时自动比对。变了就给出变化范围，只对该范围局部重探查，单条更新清单，落新基线。更新有保险线：条目骤降过半视为探查失败，保留旧清单。受影响条目按三态处置：仍成立则更新。证据源已变但新证据不足，降级标注待核。证据源已消失，归档保留可追溯（见 references/knowledge-lifecycle-methodology.md §五）。
- **问题通道**：使用中解决的新问题按三选一归位（进清单、进配方、进规则），每次留决策记录。新问题包括新的复用解法、新发现的约束、踩过的坑。前者防"项目变了技能没变"，后者兑现"按具体问题迭代成长"。

会话续传只读取最后完整的 journal 快照。阶段恢复先校验阶段、行数和快照前决策校验码，再把恢复前状态与完整决策账本存入 `restore-backups/`，最后替换状态文件与决策前缀；它不恢复源码。恢复与决策写入共用互斥锁，残留锁必须先确认没有活跃写入进程再清理。

生成器自身吸收外部方法论走同一条纪律：调研、评审、落地为条件或引导，全程留痕。外部信息按证据分级采信（A=本机实测、B=官方一手直查、C=二手转述，转述未经核验不进基线）。上游的安装器与装配行为不进载体，只吸收机制。

成长的预算约束与装配同一条：**成长 = 预算内替换。** 新知识进来，必须有旧知识出去，或总量不增。否则不是成长，是膨胀。

## 3.8 完备性：凭什么就是这些机制

最后一个问题：机制清单凭什么完备且不冗余。答案是一个封闭的类型空间。全部机制所操作的实体、关系、动作登记在三份类型目录里（`assets/ontology/`，计数见附录 A）。每条关系都有机器锚，关系的实例可验证存在。每个机制必须能回答"我实现哪条关系"。答不出就是无消费方的机制，删除或先补定义。

新机制入场走四问：引入什么实体，产生什么关系，关系的机器锚是什么，锚失效怎么检测。走完四问，实现通常收敛为一个字段加两处对账点。此前"文档声称与实现漂移"的缺陷，根因都是关系没有机器锚。因此先登记锚，再写实现。

# 四、实现：机制落在哪些实物上

本章把机制映射到文件，一页说完。

**生成器侧**（本仓库 `swarm-yuan/`）：探查方法论与填充规范在 `references/`。门禁实现与规则数据在 `assets/`。生成与核验脚本在 `scripts/`。独立验证器在 `verifier/`。生成流程的逐步行事与自动化/AI 分工详见 `references/generation-flow.md`。

**目标技能侧**（生成产物，六个目录）：SKILL.md 是每次会话的入口（体积封顶）。references/ 装组件库清单、配方、工作流与项目文档（含开发偏好）。assets/ 装 spec 等模板。scripts/ 装门禁与工具。rules.d/ 装三值规则。hooks/ 与 settings 把技能挂进宿主。逐文件规格与命令清单见使用手册，不在此罗列。

三权分立的实物对应：立法 = 特征卡与清单（内容），执法 = precheck 门禁 + hooks（条件），司法 = verifier 目录（独立验证）。与宿主的分工固定：宿主管 agent 循环与沙箱。技能只管项目上下文、业务规则、操作边界，不碰宿主内部。

读者双轨：SKILL.md 写给 AI（零手动配置铁律），使用手册写给人（命令与排查）。

# 五、When：何时用、何时不用

| 适用 | 不适用 | 替代 |
|------|--------|------|
| 团队协作（≥2 人） | 个人脚本、一次性原型 | AI 裸写 |
| 中大型项目（≥80 文件） | 极小改动（typo 级） | 直接改 |
| 强监管、合规交付 | 无 AI 辅助的纯人工开发 | 传统 lint/test |
| 长期维护（技能须跟项目演进） | 只要门禁不要认知设施 | 单文件门禁脚本 |
| 小项目要基础门禁（lite 档） | | |

不建技能的轻量替代三选一：把单文件门禁脚本拷进项目配 conf 直接跑。传统 lint 加 Git hooks。一次性任务直接对 AI 说需求。

对外表述守三条纪律：

- 不说"100% 可靠"，说"已验证组件 + 受约束生成 + 独立校验"。
- 引用数字标口径与归属：清单计数是某个项目的探查产物，不是技能自带指标。
- "三权分立"对外用时标注是叙事说法。

本质一句话：bash 脚本加 Markdown 挂在 AI 编码助手的 hooks 上，写代码前拦截，交差时独立验证，外加本地观测。

# 六、核心总结

回到那条链，全文主张收成三句话。

**必要性**：链条缺一环，失败模式已在第二章逐环点名。缺认知则规则无根，缺检查则清单失真，缺约束则认知白做。缺验证则带着缺陷交付，缺成长则三个月过时。

**充分性**：链条每一环有机制（第三章）。每个机制有检查（3.7 衔接总表）。每个检查有实物与证据（第四章与附录 D）。充分性不靠形容词，靠逐格可点。

**可复核**：系统声称"降复杂度的工具自己不能失控"，于是自身受同一套约束。数字统一由 facts.conf 对账，正文不手抄口径。声称的机制全部过 CI。每个设计取舍都能在决策史里查到全文。

## 附录 D：验收与复审

设计要能验收，否则是空谈。全部声称收敛为下表的可机器复核指标（测试资产清单与 CI 矩阵见使用手册）：

|---|------|------|----------|

诚实边界（对外宣称的政策约束）：fixture 是构造样例。它证明门禁能按设计动作，证明不了真实项目全覆盖。真实缺陷由真实项目回归补位。回归是固定矩阵：

- JS 全栈样例（Vue3 + Express + SQLite）与 Java 企业栈样例（Spring Boot + MyBatis XML + Spring Batch + Vue/Element）各一套，可编译、带真实测试套件。
- 每轮走完整"生成流程 + 典型研发工作（feature/fix/refactor）"。要求真实工具链（mvn / npm）全绿。
- 后续轮次按矩阵扩族（React、Django、Go 等）。

外部效度未达 `verifier/v2/external-validity.md` 阈值前，任何"守护代码合规"类宣称必须带品类限定。

机制扩容有节奏约束：两批之间至少间隔一个真实使用周期。先用当前形态生成真实目标技能验证，再进下一批，防止预算再度膨胀。

## 附录 F：治理不变量

合并自终态设计摘要。五条治理原则：

| 原则 | 含义 | 机器锚 |
|---|---|---|
| 事实单源 | 有两处以上引用的事实只保留一个权威源，其余由脚本生成 | 注册表三向对账，纳入自检与 CI |
| 清单即数据 | 分发、装载、安装与宿主范围由表驱动，代码中不出现第二份清单 | 分发表与宿主表，代码只读表 |
| 历史与状态分离 | 注册表只存当前值与最近一次修改，过程史进入修改记录 | 表行不携带版本史，记录追加 |
| 宣称与证据绑定 | 对外的支持、整合与实证表述须对应五级记分与证据指针 | 表内等级列与术语校验 |
| 能力有生命周期 | 分为进入、激活、验证、观察、退役五态，无退役条件不得新增 | 框架表与运行时表有 `status` 列；`registry-render.sh --lifecycle` 输出候选 |

| 配置变量预算 200 | 自检同上 | 强制 |

| 入口文件 20000 字符硬顶 | 生成链路断言 | 强制 |

## 离线分发设计（2026-10-22 终口径）

目标环境画像：GitHub 不可达，npm/pip 源（内部镜像）可用，Windows / macOS / Linux 三平台。

- **分层原则**：可经 npm/pip 源安装的运行时**不随包**（安装命令走源，逐条披露结果）；源装不了的才随包——vendor-knowledge 知识资产、仓库 docs/ 档案、gstack/superpowers/ECC 源码包（MIT，`scripts/src-pins.conf` 钉定基线 SHA）。
- **三件产物**：`-novendor`（5M，纯走源）/ 全量（~52M，附带 npm/pip 顶层包，依赖树仍由源解析）/ `-everything`（~71M，零降级件：knowledge+docs+github 源码全随包；含版权书籍全文故**仅本地/内部分发，不上公开 release**）。
- **一键安装（三平台同构）**：Windows 双击 `install-offline.bat` ≡ macOS/Linux `bash install-offline.sh`——无参数=全宿主自动检测（11 宿主含 hermes/dsh/cc-switch）+ 走源运行时 + github 源码 + 知识入驻；`--minimal` 关默认；`--with-knowledge` 知识进已装技能目录（支付 profile 离线生成可用）。
- **可审计性**：包内 `.bundle-version`（version/source_commit/built_at）——无 git 环境版本溯源不落 unknown；`vendor-status.tsv` 逐条对账（ok/skipped/failed/excluded）；SHA256SUMS 全文件校验、含空格文件名保真、被改文件拒装。
- **已知边界（如实）**：Chromium 离线不可引导（gstack 以 `--no-browser` 装，环境限制非缺件）；conf 命令值 eval 为「受信本产」设计前提（目录名注入已封堵）。
