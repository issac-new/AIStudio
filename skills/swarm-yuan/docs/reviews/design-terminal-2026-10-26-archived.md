# swarm-yuan 终态设计说明

## 摘要

系统对代码仓库执行一次结构化探查，生成该仓库专属的研发技能。此后该仓库的 AI 编码在技能约束下进行。系统由生成器、目标技能与治理体系构成。生成器负责识别项目结构与规则。目标技能负责在日常编码中执行约束。治理体系负责证明约束确实生效。

数字以 `swarm-yuan/assets/facts.conf` 为唯一来源。本文所列计数与该文件对账。

## 一、定位与范围

### 1.1 系统定位

系统分为生成器与目标技能两部分，两者的体积约束相反。生成器在生成阶段读取一次，允许承载较多知识，此类内容置于 `references/`。目标技能在每次会话中重复加载，须保持精简。入口文件上限 11KB，组件库清单上限 32KB，上下文总体积上限 600KB，超出即判定失败。入口文件另设 20000 字符硬顶：宿主压缩后重挂载技能在 20000 字符处截断，超线内容整会话丢失。预算可登记调整，硬顶锚定宿主行为，不可越。

生成流程共十三步，产物为目标技能的六段目录。六段分别为入口、方法论、模板、脚本、规则与宿主挂载。生成档位四档。lite 面向小项目与基础校验。standard 为默认档。compliance 面向强监管交付，auto 依据合规信号与仓库规模选择。

### 1.2 非目标

以下四项不属于系统职责，列明以避免误用。

第一，系统不提供通用 lint 与测试框架。系统产出项目专属约束，不替代项目自身的工具链。

第二，系统不管理宿主的 agent 循环、沙箱与模型调用。上述能力属于宿主职责。

第三，系统不支持纯人工开发流程。其设计前提为 AI 驱动研发。

第四，系统不以构造样例的通过率替代真实项目覆盖。外部效度未达阈值前，对外宣称须限定适用范围。

### 1.3 现有优势

系统当前具备三项优势，后续设计须予以保持。

证据纪律：来源按三级采信，能力按五级记分，注册表与代码、样例执行三向对账。

负向预算：门禁总数固定为 56，配置变量上限 200，另设四项体积上限与例外登记；入口文件另受 20000 字符硬顶，不随预算登记上调。

真实项目回归：Java 企业栈与 JS 全栈各一套，使用真实工具链执行。

## 二、架构

### 2.1 总体结构

系统包含一个生命周期内核与三个分层平面。

生命周期内核为：生成、使用、成长、吸收。

三个平面分别管理一类事实。知识平面管理方法与项目认知，包含方法论（篇数以 `FACT_REFERENCES` 为准）、框架规则集 81 套与物化运行时两套。执行平面管理生成、门禁与验证，包含生成流程、门禁引擎与独立验证器。治理平面管理事实、预算与证据，包含六张注册表、数字单源、例外登记与决策记录。

### 2.2 注册表平面

六张注册表为事实的唯一来源；各表行数以表文件为准，由 `registry-render.sh --check` 机械核对，本文不手抄。

| 注册表 | 记录内容 |
|---|---|
| 门禁表 `gates.tsv` | 每个门禁的域、执行档、强度、配置变量、样例与证据等级 |
| 框架表 `frameworks.tsv` | 每套框架规则的信号、门禁片段、样例与探测命令 |
| 文档表 `references.tsv` | 每篇方法论的来源、证据、消费节点、分发范围与触发条件 |
| 运行时表 `runtimes.tsv` | 每个上游组件的许可证、通道、包名、基线、整合方式与等级 |
| 宿主表 `hosts.tsv` | 每个宿主的检测方式、安装路径、钩子形态、适配器与证据 |
| 分发表 `dist.tsv` | 每个分发文件的档位、模式、离线与源码包要求、上下文体积 |

脚本由注册表生成计数与汇总视图；能力清单（`capability-map.md`）当前由人工策展，由 G25 做双向对账。自检执行反向校验：注册表与代码、注册表与样例是否一致。任一侧出现多余条目即判定失败。文档中的数字不作手工抄录，由 `tests/test-doc-numbers.sh` 的数字断言逐条校验（断言数以运行输出为准）。

### 2.3 证据分级

能力按五级证据记分。注册表中标注的等级即对外宣称的上限，不得高报。

| 等级 | 含义 | 准入要求 |
|---|---|---|
| M0 | 已登记 | 注册表存在对应行，且有负责人 |
| M1 | 已接入 | 存在真实消费点，不限于文档描述 |
| M2 | 双态验证 | 违规与合规样例均通过，违规侧必须检出 |
| M3 | 环境实证 | 在真实宿主或真实仓库执行通过，附证据指针 |
| M4 | 持续回归 | 纳入每轮全量回归，失败即判定红 |

当前记分如下。56 个门禁中，53 个达到 M2，3 个为 M1。81 套框架规则全部达到 M2。方法论为 M1（篇数以 `FACT_REFERENCES` 为准），其用途为引用，不设双态样例。22 个上游组件中，2 个达到 M3，15 个为 M1，5 个为 M0。11 个宿主中，3 个达到 M3，3 个为纯目录目标，5 个已生成配置但未实测。逐项候选由 `registry-render.sh --lifecycle` 输出。

证据缺口不作隐藏，登记于三份例外表。分别记录没有真实消费点的事实、缺少样例的门禁，以及含义不一致的强度分层。

## 三、失效模型与职责划分

### 3.1 两类失效

AI 在陌生仓库编码，失效集中于两类。

第一类为规则违反。包括修改只读配置、升级锁定依赖、重写标注为稳定的组件、提交不带测试、命令使用禁止形式。此类失效具有词法与结构特征，可由机器识别。

第二类为逻辑错误。规则全部遵守，但算法错误、边界遗漏、或破坏接口契约。此类失效没有固定模式，须通过真实测试与独立审查发现。

两类失效的共同成因是项目认知缺失，与技术能力无关。

### 3.2 三类职责

系统设三类职责，互不替代。

门禁负责拦截第一类失效，在编码前、改动时与收尾三个时点执行。验证负责核验第二类失效，在交付前执行测试、接口校验与独立审查。独立验证器负责复核门禁，以违规与合规两组样例检验门禁的检出能力。

三类职责不得互相代签。门禁全部通过，不能证明功能正确。测试通过，不能证明门禁没有遗漏。

## 四、认知层

生成技能前，系统先判定项目形态。判定项包括单模块或多模块、是否包含前端、是否为微服务、是否存在数据管道。形态决定探查维度。

随后产出三份材料。

**组件库清单**分为组件、接口、数据三类，每行两列。第一列记录路径，供脚本校验。第二列记录用途、稳定性与使用约束。

**依赖关系表**记录依赖方向。脚本提取可机械识别的部分，例如 import 关系、MyBatis 命名空间与 Mapper 接口的对应关系。AI 补充需要语义理解的部分，例如控制器调用的服务、消费者订阅的主题。

**任务配方**记录业务功能与常见任务的组织方式。每项记录四项内容：组成单元、经过的接口、写入的数据表、对应的测试。遇到同类需求时，按既有配方组织实现。

清单存在三类常见缺陷，各配一项校验。

遗漏：脚本枚举出 400 个类，清单仅记录 200 条，后续复用必然缺件。校验方式为按维度自动计数，清单条目不得少于枚举数量的 95%。

虚构：清单记录 `src/service/OrderExportService.java`，实际不存在该文件。校验方式为逐条验证路径存在。发现虚构路径即阻断激活，技能停留在草稿状态。

过期：清单将某文件标注为稳定且禁止修改，实际该文件每周发生修改。校验方式为观察三个信号：近期修改次数、其他文件的引用次数、是否存在同名测试。信号与标注冲突时提示复核。此项仅提示不阻断，因为信号属于启发式判断，结论由人确定。

另有一类缺陷不体现在编译期。Java 字段名为 `orderStatus`，XML 中写为 `order_status`，两者依靠约定对应。仅修改 Java 而不修改 XML 时，编译可以通过，运行时查不到列。此类字符串耦合有五处：mapper 列名、批处理 SQL、消息主题名、JPQL 实体名、bean 装配类名。可提取的部分进入依赖表，修改字段前反查。无法提取的部分建立对照表，修改数据模型前人工校验。

框架规则不进入组件库清单。探查确认项目使用某框架后，才注入该框架的规则。当前有 81 套，覆盖 Spring 系列、MyBatis、分库分表、Dubbo、消息队列、Vue、Element Plus、React 与常见中间件。每条规则须在项目代码中找到实例才生效。找不到实例的规则删除，并记录未采用原因。通用教材条目不得作为项目事实。

## 五、规范层

项目规则有三个来源，可信度依次降低。

**书面规则**最可信。AGENTS.md、CLAUDE.md 与团队记忆中已写明的规则，直接提取。

**行为统计**次之。读取 git 历史，统计提交信息风格、分支命名方式与文件共现关系。同时统计修改频率与带测试提交占比。脚本生成初稿，AI 审阅后采纳。统计数据是事实，不构成规则，因此书面规则优先。

**推导规则**再次。探查发现某目录只读、某类文件由工具生成时，据此推导禁止手工修改一类的规则。

三个来源汇合后分两处存放。规则表述进入铁律段，写明规则与出处，不写死具体值。规则执行进入规则表，每条规则分允许、提示、禁止三档，多条命中取最严档。禁止档须同时提供替代做法，使 AI 遇到拦截时能够处理。参数进入配置文件，每个值附一行来源注释。

表述与执行分离是设计选择。组件库清单与铁律回答系统是什么。规则表与门禁回答系统应当如何执行。

## 六、装配层

装配分工固定：脚本承担机械工作，AI 承担判断工作。

脚本负责枚举文件、复制骨架、生成配置、校验数量。上述工作信号明确，机器执行不会出错。判断类工作由 AI 完成，包括特征卡取值、框架规则适用性判断、开发习惯采纳。反向分工导致两类问题：脚本对质量作出判断，或 AI 重复执行机械工作。

新生成的技能处于草稿状态。草稿状态下全量校验禁用，支持断点续传。三项条件全部满足后转为可用状态：占位符清零、清单路径无虚构、数量校验达标。转为可用状态后方可投入日常使用。该状态区分使使用者能够判断产物是否可用。

升级前核验项目状态机：任务停在中间阶段即拒绝升级并点名解除路径，仅注册与已归档状态放行，显式环境变量可豁免；升级可先预演（--dry-run 报告将新增、变更、删除的文件三态清单，零写入，预演不受在途门拦截）。升级分两步执行。先在临时目录完成全部改动，再整体替换。失败时保留原技能，成功时归档旧版本。框架规则注入时记录一段校验值。发现手工修改区块，即中止注入并提交裁决。注入前自动保存快照，支持整体回滚。

预算为硬约束。新内容进入技能前，须为旧内容腾出空间。只增不减视为膨胀。门禁总数固定为 56，配置变量上限 200，当前为 197。新增须等额删除，或逐条登记例外。

## 七、门禁

门禁在三个时点执行。

**编码前**拦截两类行为。第一，未提交方案即修改源码。第二，命令命中禁止清单，例如 `rm -rf` 的各种拼写变体。拦截时提供替代命令，不只给出否定结论。

**改动时**校验范围。校验本次改动涉及的文件是否位于允许修改的目录，是否触及敏感配置。

**收尾时**按固定顺序执行整套校验：构建、测试、接口、契约、复用、一致性、分层、文档、安全、依赖。任一步失败即停止，后续步骤不再执行，避免后续通过掩盖前述失败。每步写入执行记录，审查时依据记录确认校验确实执行。

56 个门禁有两种分类方式，可互相校验。按严格程度分为：核心 11、架构 18、合规 19、仅提示 6、治理尾项 2。按覆盖对象分为：安全 10、架构 18、流程 11、质量 6、合规 11。两种分类合计均为 56。

严格程度依据信号可靠性确定，不依据重要性确定。信号稳定的门禁才阻断交付。信号有噪声的降为提示。无法判断的不作判断，仅输出问题清单供 AI 自查并留痕。例如「本次复用是否贴合场景」一项，机器无法判断，即不输出结论。

权限边界一律从严，宁可拒绝，不可放过。只有在下一层仍有兜底时，才允许某一层放宽。例如钩子执行失败不阻断，因为命令随后仍须通过门禁。

「未提交方案不得修改源码」由四层执行，四处使用同一套判定函数，结论一致。编码时由宿主钩子以退出码 2 阻断。Claude Code、Codex、ZCode 三家已实测。其余五家已生成配置但未实测，规则文件中如实标注。提交时由 git 钩子拦截，与宿主无关，依据暂存区中是否存在已批准方案。执行门禁时由核心序列中的对应步骤拦截。切换阶段时由状态机拦截。

外部资源访问另设执行时点守卫，不属于门禁，不占用门禁预算。修复任务连接研发环境取证时，AI 发出的每条 SQL 与远端命令先经只读守卫判定。只读放行，写操作拒绝，未识别默认拒绝。判定结果写入操作账本，回归时对账。拦截发生在执行时点，早于门禁的收尾校验。只读的第一道防线在凭证层，数据库账号只授查询权限，SSH 使用受限账号。守卫是第二道防线，账本是第三道。远程调试协议 JDWP 无认证，调试端口仅经堡垒机隧道转发并绑定本机回环地址。

## 八、验证

门禁无法发现逻辑错误，验证补充这一部分。验证包含四项内容。

**测试须真实执行并具备有效性。** 首先校验测试命令的退出码，随后排除三类失真。第一，无任何用例执行却判定通过，直接判负。第二，配置覆盖率阈值时解析报告，低于阈值判负。第三，扫描测试源码，校验四项内容。是否存在零断言用例。断言密度是否足够。负向与边界用例占比。是否存在 `.only` 等聚焦测试。可另行配置变异测试，分数不足判负。

有一类情况须单独说明。覆盖率阈值写入配置，不等于实际执行。测试命令未携带覆盖率开关，或报告插件未安装，阈值即不生效。此类校验还须确认执行条件：插件是否安装、命令是否携带开关。缺少任一项即判负，不得判为通过。

**接口须逐端点校验。** 从 OpenAPI、proto 或路由声明中枚举端点。Spring 中未写明路径的映射，以及类级公共前缀，均计入完整端点。测试调用的方法与路径须对应。路径参数使用真实值，不得以集合路径代替。每个端点附近须有自身的状态码断言或错误分支断言。未配置时明确说明未启用。

**审查须由他人执行。** 未参与编码的人员完整审阅，审查记录落盘方为有效。口头确认不计入。

**验证器须检验门禁。** 使用故意违规的样例检验门禁，未能检出即视为失效。工具报错、样例准备失败，均计为整体失败，不计为通过。

全部过程留痕。调用、决策、门禁执行与拦截分别记录。决策记录包含序号、前驱与校验码。此处须说明口径：当前使用校验和，可以发现记录内容发生变化，但不属于密码学级别的防篡改。缺少外部可信锚时，整本重写或末尾截断无法发现。因此系统不宣称具备防篡改能力。

回归只有一个入口。一条命令按层执行：语法校验、门禁正反例、框架正反例、生成链路、独立验证器、真实项目。每条测试标注层级与并行安全性。共享状态的测试依次独占执行，互不影响的测试并行执行。本地与 CI 使用同一入口、同一参数。锁定测试清单以 `tests/index.tsv` 为准；未登记测试由 runner 契约测试拦截。

## 九、成长机制

技能是生成时刻的快照，项目在此后继续演进。系统设两条通道应对。

**结构通道。** 每次会话开始时比对三项：文件数、扩展名分布、目录结构。三项合成为一个值。值发生变化即给出范围，仅重查该范围，逐条更新清单，然后写入新基线。另设保险线：清单条目减少超过一半，视为探查失败，保留旧清单。受影响条目分三种处理。仍然成立的更新。证据来源变化但新证据不足的标注为待核。证据来源消失的归档保留，以便追溯。

**问题通道。** 新解法、新约束与已发生的问题，三选一归位：进入组件库清单、进入任务配方、进入规则表。每次留存一条决策记录。

会话中断后续传，只读取最后一份完整快照。恢复分三步执行。校验阶段、行数与校验码。将当前状态与完整决策记录备份。替换状态文件与决策前缀。源码不恢复。恢复与决策写入共用一把锁。残留锁须先确认无活跃写入进程，再行清理。

成长与装配共用同一条预算：新知识进入，旧知识退出，或总量不增加。

## 十、治理原则与不变量

五条治理原则各有机器执法点。

| 原则 | 含义 | 执法 |
|---|---|---|
| 事实单源 | 有两处以上引用的事实只保留一个权威源，其余由脚本生成 | 注册表三向对账，纳入自检与 CI |
| 清单即数据 | 分发、装载、安装与宿主范围由表驱动，代码中不出现第二份清单 | 分发表与宿主表，代码只读表 |
| 历史与状态分离 | 注册表只存当前值与最近一次修改，过程史进入修改记录 | 表行不携带版本史，记录追加 |
| 宣称与证据绑定 | 对外的支持、整合与实证表述须对应五级记分与证据指针 | 表内等级列与术语校验 |
| 能力有生命周期 | 分为进入、激活、验证、观察、退役五态，无退役条件不得新增 | 框架表与运行时表有 `status` 列；门禁与文档以 `claim` + 豁免表 + `registry-render.sh --lifecycle` 候选清单进入季度评审。自动退役拦截尚未建立，列为未决 |

不变量与执法强度如下。

| 不变量 | 执法方式 | 强度 |
|---|---|---|
| 门禁预算 56 | 自检复杂度预算断言 | 强制 |
| 配置变量预算 200 | 自检同上 | 强制 |
| 四项体积上限 | 自检断言与生成链路断言 | 强制 |
| 入口文件 20000 字符硬顶 | 生成链路断言 | 强制 |
| 注册表与代码、样例三向一致 | 注册表对账 | 强制 |
| 零消费事实键须登记例外 | 对账与例外表 | 强制 |
| 每项能力具备证据等级 | 记分表与宣称矩阵 | 强制 |
| 激活三项条件 | 激活命令 | 强制 |
| 行为保持式拆分 | 基线产物逐字节比对 | 强制 |

### 风险与未决事项

预算约束门禁数量；2026-10-24 起，引擎域源代码与框架注入代码的行数也有冻结上限（`FACT_ENGINE_CODE_LOC_MAX` / `FACT_FRAMEWORK_GATE_LOC_MAX`，由 self-check 强制）。分发体积只计量文档字节数；脚本执行时间仍无独立上限，列为未决。

能力退役目前只有候选清单与季度评审，没有自动拦截；`registry-render.sh --lifecycle` 输出 claim 不足、无夹具、未整合与未实证的候选，处置仍由人裁决。

## 十一、验收指标

抽象表述无法验收。以下指标均可通过命令复核。

| 指标 | 标准 |
|---|---|
| 门禁可达率，即默认执行时是否实际执行 | 100% |
| 核心概念数量 | 不超过 5 个 |
| 新会话至首次读代码的动作数 | 不超过 3 步 |
| 入口文件与组件库清单体积 | 11KB 与 32KB，入口另受 20000 字符硬顶 |
| 单次会话读入模型的内容总量 | 600KB，超出逐条登记 |
| 文档矛盾处与无消费点文件 | 均为 0 |
| 三档差异 | lite 不安装钩子，compliance 含行业注入 |
| 已吸收方法的实际采用比例 | 100%，抽样审计 |

构造样例只能证明门禁按设计执行，不能证明真实项目不失败。真实缺陷依靠真实项目回归发现，矩阵固定。一套 JS 全栈，技术栈为 Vue3、Express、SQLite。一套 Java 企业栈，技术栈为 Spring Boot、MyBatis XML、Spring Batch、Vue 与 Element。每轮执行完整生成流程与典型研发工作，功能、修复、重构各一次，要求真实工具链全部通过。

较重的一份样例另覆盖分库分表、连接池、Dubbo 契约与消息队列。当前后端 30 个用例、前端 19 个用例全部通过。四项行覆盖率分别为 79.18%、91.66%、78.12%、79.18%。

新增能力有节奏约束。两批之间至少间隔一个真实使用周期。先用当前版本生成真实技能并投入使用，再进入下一批。

## 十二、分发与安装

三个平台的安装入口一致。Windows 双击批处理文件，macOS 与 Linux 执行同目录脚本。

不带参数即执行完整安装。检测本机已安装的 AI 工具并逐个安装技能。运行时从包源安装。源码包安装到对应位置。知识资产复制到已安装技能的目录。需要控制范围时，使用单宿主参数，或使用最小化参数仅安装本体。

离线包的分层原则如下。可从 npm 或 pip 源安装的，包内不附安装包，只附版本号与安装命令。安装时逐条从源获取并报告结果。无法从源安装的才放入包内，包括知识资产、仓库档案与三个只能从代码托管获取的源码包。三个源码包均为 MIT 许可，按基线提交固定。可用环境变量替换。

包内提供四项自查材料。版本文件记录版本、源码提交与构建时间，无 git 环境时不会显示未知。对账表逐条记录每个运行时的通道、获取到的文件与状态。校验和覆盖全部文件并逐条比对。文件一旦修改即拒绝安装。文件名含空格时也能正确解析。安装中断时清理暂存目录。

三项边界须明确说明。浏览器组件需要在线引导，离线环境跳过，属于环境限制，不是包缺件。包的依赖树由目标机源解析，完全断网环境须先将依赖同步至镜像。配置中的命令按原样执行，前提是配置文件可信。目录名注入已经封堵。命令内容本身不作过滤，过滤将破坏功能语义。

## 十三、适用边界与对外表述

适用五类场景。第一，两人以上协作。第二，中大型仓库，80 个文件以上。第三，强监管交付。第四，需要长期演进的仓库。第五，需要基础校验的小项目。

不适用四类场景。第一，个人脚本与一次性原型。第二，错别字级改动。第三，纯人工开发。第四，只需要门禁而不需要认知设施。后三类的轻量替代方案有两个。将单文件门禁脚本复制到项目并配置。或使用传统 lint 加 Git 钩子。

对外表述守三条。不使用「百分之百可靠」一类表述，改用「已验证组件、受约束生成、独立校验」。引用数字须标明口径与归属。组件库清单的计数来自某个项目的探查结果，不是技能自带的指标。三权分立一类说法对外须标注为叙事表达，实物对应为特征卡与清单、门禁与钩子、独立验证器。

## 结语

系统的全部内容可以归纳为一句话。脚本与文档接入 AI 编码助手的钩子。编码前拦截。交付前验证。过程留存于本地记录。

可信度不依赖声明，而依赖三份可当场查阅的材料。六张注册表与五档记分。数字断言的通过记录。真实项目回归的用例数。
