——N3TEE 虚拟机（N3TEE VM） 
N3TEE 虚拟机，指的是N3TEE 上可信应用的专用虚拟机，主要用于让使用高级程序语言所编写的
N3TEE 可信应用在N3TEE 上能够正常运行。具有以下特性：  
 虚拟机可解释执行Java 语言所编写的为Rich OS 中CA 提供安全服务的可信应用； 
 虚拟机是CA 请求应用的可信服务时，为执行应用而加载到RAM 中运行，应用执行完成后虚拟
机可从RAM 卸载； 
 虚拟机系统对垃圾回收机制的支持是可选的，建议应用在安装时分配好需要的存储。 
 
    需要说明的是，N3TEE 虚拟机可支持以下三种形式的虚拟机实现： 
 支持NEF 可执行文件格式的虚拟机； 
 支持DEX 可执行文件格式的虚拟机； 
 支持JEFF 可执行文件格式的虚拟机； 
关于各种虚拟机指令集与可执行格式等具体实现要求请参见附录C 相关内容。

应用框架位于应用层和基础功能层之间，是底层功能在经虚拟机虚拟化过后的运行时主要表现形
式。应用框架可依托于底层基础功能实现为上层应用提供应用间通信和生命周期管理、安全与访问控制
等相关功能，并通过应用编程接口形式提供给上层应用使用。 
 
——可信应用编程接口 
N3TEE 应用编程接口具有以下特性： 
 
API 主要基于《N3TEE 应用编程接口指南》实现，主要包括可信存储、密码计算以及TUI
等； 
 
API 不支持智能卡采用的APDU 的通信协议，采用《N3TEE 应用编程接口指南》定义的通信
协议； 
 
API 不支持Transient 对象的创建，因为所有Java 对象都在RAM 中分配； 
 
由于《N3TEE 应用编程接口指南》中的定义API 不支持事务机制，因此 API 也不提供事务
相关的类，但虚拟机实现要考虑虚拟机、应用的代码、数据的一致性、完整性保证。 
具体请参见《N3TEE 应用编程接口指南》。 
 
——可信应用 
N3TEE 可信应用具有以下特性： 
 
N3TEE 上的可信应用是采用Java 语言编写的应用，为CA 提供安全相关的服务，可信应用
通过调用 API 访问子系统提供的系统服务。 
 
TA 通过内部可信API 可以请求应用的服务，应用也可通过 API 请求TA 或其他应用的服务。 
 
虚拟机在易失性存储（RAM）中创建类实例，因此应用不能依赖类实例实现持久化，应通
过可信存储API 实现持久化； 
 
虚拟机系统应支持一个或多个称为安全域的特权应用，完成应用的下载、安装、删除等管
理功能。 
 
5 
N3TEE 应用编程模型 
5.1 持久化 
持久化是指把内存中的数据保存到可永久保存的存储设备中。 
——N3TEE 不支持对象的持久化，客户应用和可信应用建立会话、可信应用执行客户命令时，运
行应用的各入口点方法时创建的所有Java 对象，当会话关闭时被销毁； 
——可信应用应通过可信存储API 实现应用信息的持久化； 
——N3TEE 虚拟机支持可信存储的持久化，且持久化可信存储修改操作具有原子性； 
——不同可信应用间的存储进行隔离。每个可信应用能够访问自己的存储空间，该存储空间被可信
应用所有的实例所共享但是与其它可信应用相隔离。 
5.2 多线程 
N3TEE 当前版本不支持多线程。

N3TEE 应用环境 
6.1 应用标识 
可信应用采用UUID（通用唯一识别码，Universally Unique Identifier）进行标识。 
UUID 结构定义如下： 
typedefstruct 
{ 
uint32_t  timeLow;  
uint16_t  timeMid;  
uint16_t  timeHiAndVersion;  
uint8_t   clockSeqAndNode[8]; 
} TEEC_UUID; 
各个字段的说明如下： 
——timeLow： 时间戳的低字段。 
——timeMid： 时间戳的中间字段。 
——timeHiAndVersion：时间戳的高字段，复合版本号。 
——clockSeqAndNode：时钟序列以及唯一节点标识符。 
UUID 各字段定义可参照规范RFC4122《A Universally Unique IDentifier (UUID) URN Namespace》。

6.3 N3TEE 应用的生命周期 
图3 中描述了N3TEE 可信应用的生命周期状态，并列出了触发从一个状态迁移到另一个状态的管
理操作。可信应用的生命周期状态是持久状态，它们不会受到终端断电的影响。从一个状态到另一个状
态的迁移是原子的，由远程服务器发出的管理操作触发，直接在可信应用上执行或在其父安全域内进行。 
可执行生命周期状态表示可信应用完全运行，并能够处理REE 端普通应用以及其他TEE 可信应用
打开的会话。在这种状态下，控制可信应用并具有请求的特权的授权安全域可执行的管理操作包括存储
数据、卸载和锁定可信应用。 
锁定（Lock）生命周期状态用来防止REE 普通应用和其他TEE 可信应用使用此可信应用。用于执
行更新个性化数据或代码等维护操作时，确保可信应用没有被使用。与处于锁定状态的可信应用打开会
话的任何尝试都将被拒绝。在此状态下，控制可信应用并具有请求的特权的授权安全域可执行的管理操
作包括存储数据、更新、卸载和解锁可信应用。 
当可信应用的父安全域被锁定时可信应用自动切换到不活动状态，切换到这种状态会立即自动关闭
与这个可信应用实例打开的所有会话。如果父安全域被解锁，可信应用切换回不活动状态前的原状态。
此状态下，控制可信应用并具有请求的特权的授权安全域可执行的管理操作包括卸载可信应用。 
N3TEE 应用的安装、更新、锁定、解锁以及卸载等操作参见《N3TEE 应用管理指南》中可信应用
特权操作相关章节。 
N3TEE 的特定实现可以具有简化的生命周期管理。比如，如果该TEE 系统内只有一个安全域，那
么该安全域下的所有可信应用始终处于活动状态。

6.4 N3TEE 应用的入口点方法调用 
6.4.1 
概述 
每个N3TEE 应用文件包括一个或多个类，并且包含且仅包含一个N3TEE 入口点应用类。 
6.4.2 
N3TEE应用类 
N3TEE 应用类必须继承TEE 中的可信应用基类，该基类必须包含三类入口点方法，即CA 与该TA
建立会话时回调的打开会话方法（如OpenSession）、CA 发送命令时回调的命令处理方法（如Invoke 
Command）以及CA 关闭会话时回调的关闭会话方法（如Close Session）。 
说明：N3TEE 应用API 的使用参见《N3TEE 应用编程接口指南》。 
6.4.3 
应用的属性 
N3TEE 应用通过 API 可访问应用自定义的属性，N3TEE 应用自定义的属性在安装时指定。 
6.5 N3TEE 应用的部署方式 
如图4 所示，N3TEE 应用采用可信服务管理进行部署，主要由管理层、安全层和协议层三个层次
组成。 
1) 
管理层 
——定义了用于管理N3TEE 应用的操作以及使用条件和每个操作的详细行为。 
2) 
安全层 
——定义了参与者，以及如何将不同的业务关系和责任能够映射到具有特权和关联的安全域； 
——定义了安全机制用于认证建立安全通道的实体，保护通信内容，授权由安全域进行的管理操作； 
——定义了密钥和数据的配置方案，和相应的密钥管理。 
3) 
协议层 
——定义命令集（通过TSM 服务接口）用于执行管理操作； 
——定义的命令集，用于和安全域之间建立安全通道。 
N3TEE 应用采用可信服务管理进行部署，能够确保N3TEE 应用的安全性和完整性，保证数据的保

安全与访问控制机制 
7.1 安全隔离 
7.1.1 REE与N3TEE的隔离 
由于在安全自举过程，N3TEE需配置SoC，使得REE端执行的软件无法访问专用于TEE的外设以及数据。
例如，在ARM平台下，可在将控制移交给对于N3TEE而言不可信的软件前，配置SoC上TrustZone保护控制
器TZPC的实现。 
7.1.2 
应用隔离 
N3TEE 的实现应对任意两个可信应用之间提供数据隔离，即不同可信应用之间不能访问对方的私
有数据。私有数据包括运行时存在于内存中的数据，也包括存在于永久性存储设备上的数据。为实现可
信应用之间的这种隔离，N3TEE 必须在应用之间实现防火墙机制。具体实现方式可参照附录。 
7.1.3 
代码隔离 
N3TEE 应用框架的实现保证一个N3TEE 应用（包括安全域）不能以任何方式访问其他N3TEE 应
用以及N3TEE 系统组件的代码以及元数据，确保N3TEE 及其应用的不可访问性；进而，也保证了每
个N3TEE 应用以及N3TEE 系统组件代码和数据的完整性和一致性。 
7.2 访问控制 
7.2.1 客户应用到可信应用的访问控制

A.2 基于应用防火墙的应用隔离 
N3TEE 可以借助应用防火墙来隔离不同的TA 实例。应用防火墙存在于任意一个TA 实例和其他实
例之间。 
TA 之间不共享任何数据，包括对象和类的静态域。比如，TA1 创建的对象只有自己可见，由于应
用防火墙的隔离，任何其他TA 都无法看见该对象，进而也无法访问该对象，这是由虚拟机本身的安全
机制保证的。类似的，不同TA 之间也看不到对方的同一Java 类的静态域。 
每个TA 都有自己独立的永久存储，永久存储之间的隔离机制也是由防火墙提供的。 
TA 之间仅共享代码，比如所有TA 实例共享类库代码，同一TA 包生成的TA 实例共享同一份TA
代码。由于虚拟机本身的安全性和防火墙的存在，TA 实例没有任何手段去访问另一实例的数据。
