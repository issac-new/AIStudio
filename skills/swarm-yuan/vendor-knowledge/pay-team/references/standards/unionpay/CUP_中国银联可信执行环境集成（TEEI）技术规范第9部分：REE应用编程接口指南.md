5. 基于ARM 可信硬件进行实现 
5.1. 综述 
N3 TEE 是一个可移植、开放的可信执行环境，可在设备上执行可信的应用，N3 TEE 使
用ARM TrustZone 技术将平台分隔为两个区域，其中一个区域运行传统的多媒体操作系统
（Android），可执行多媒体应用，另一个区域运行N3 TEE 可执行环境。 
N3 TEE 包括一个Java 运行环境以及使用Java 编写的可信应用。可信应用以设备上的
客户-服务器架构向Android 应用提供安全功能。Android 应用通过通信机制以及N3 TEE 提
供的API 函数请求N3 TEE 的安全功能，Android 的调用者通常是一个应用，称为客户端应
用，这些API 称为客户端API。 
    N3 TEE 提供内部API 用于可信应用的开发，这些API 称为可信应用API，可信应用通过
调用这些API 实现安全功能。 
5.2. 客户端应用应用编程接口 
5.2.1. 接口概述 
1.1.1.1. 客户端API 概述 
客户端API 是运行在REE 中的客户端应用访问N3 TEE 中的可信应用提供的服务和数据
的底层通信接口，为了更好地满足用户客户端应用开发的便捷性要求，本文档将在兼容业界
TEE 技术CA 基于C 语言开发的前提下还进一步提供了基于JAVA 语言的CA 应用开发接口，
故以下本文档内容将包括C 语言以及Java 语言两个版本。

1.1.1.3. 设计原则 
1.1.1.3.1. TEE 客户端C API 的设计原则 
——原则1：使用C 语言  
C 语言是几乎所有的驻留客户端应用的应用框架和操作系统的基本实现手段。 
——原则2：阻塞式函数调用 
大部分客户端应用开发者都习惯于返回调用代码前，调用方被阻断等待底层任务完成的
同步式函数。异步接口难于设计，也难于移植到多媒体执行环境中，尤其是对于熟悉同步
API 的开发者来说使用困难。 
此外，支持阻塞API 的取消功能的实现需要所有目标平台支持多线程机制。 
——原则3：源代码级可移植性 
为了启用编译时以及设计时的优化，本指南没有对二进制代码兼容性提出要求。为保证
在某个实现上功能正确，客户端应用开发者需要与该实现定义的TEE 客户端API 的头文件版
本一起重新编译其代码。

——原则4：客户内存分配 
在可能的情况下， TEE 客户端API 将内存分配的责任交给了调用方的客户端应用的代
码。这种方式将内存分配位置的选择权交给了客户开发者，可以使用，例如基于栈内存分配
的简单的优化方式、或静态全局内存、或本地线程存储等加强灵活性。 
这种设计选择在API 中使用指向结构体的指针而不是不透明的句柄来表示任何操作对
象是明显的。 
——原则5：零拷贝数据传递的目标 
在宿主操作系统和硬件实现支持零数据拷贝机制的情况下，TEE 客户端API 的功能选择
应尽可能实现客户端应用和可信应用之间的零拷贝数据传递。这种机制可最小化通信的开
销，更好地提高软件的效率，尤其是对使用缓存的处理器而言，因其数据拷贝方式往往都会
造成缓存污染，故而数据拷贝对其就是一种代价高的操作。 
然而短消息可通过拷贝的方式传递，避免共享内存的开销。 
——原则6：利用指针实现内存共享:   
TEE 客户端API 会用来实现例如加密或者安全存储等更高级的API。在这些场合，调用
者经常会通过简单的C 语言指针来提供内存缓冲区进行数据的输入或输出。TEE 客户端API
必须允许对这种类型内存高效共享，而且这种机制并不依赖于能够使用客户端API 分配内存
块缓冲区的客户端应用。 
——原则7：只指定通信机制:   
本指南所定义的API 着重于定义底层通信通道。但不定义通道所传递的消息格式，也不
定义指定可信应用所使用的协议，这些内容需要在N3TEE 其他指南中定义。 
1.1.1.3.2. TEE 客户端Java API 的设计原则 
Java 具有简单、面向对象、跨平台性、安全性以及自动垃圾回收等优点。 
由于Android 应用开发主要采用Java，提供Java 客户端API 更易于用户开发基于TEE
技术增强安全的客户端应用。 
Java API 实现需要基于C API 的实现，换句话说是C API 的Java 封装形式，因此C API
中的一些基本概念如会话、命令以及共享内存的概念也适用Java API，但C 语言特有的一
些概念或术语，如内存引用等不适用Java。 
1.1.1.4. 基本概念 
1.1.1.4.1. 上下文 
TEE 上下文是客户端应用和TEE 之间存在的一个抽象逻辑连接。TEE 上下文必须在会话
创建之前初始化，一个客户端应用可以同时初始化多个TEE 上下文。当不在与TEE 连接时，
应当结束TEE 上下文，允许资源被释放。 
客户端应用可以针对同一个TEE 或多个可用的TEE，同时初始化多个上下文。某一时刻
存在的上下文的数量是基于实现定义的，可以根据运行时资源限制进行调整。

会话是存在于客户端应用和指定的可信应用之间的逻辑连接的一种抽象，在一个特定
TEE 上下文范围内客户端应用可以打开一个会话。并发的会话数量是由实现定义的，并依赖

当创建一个新的会话时，客户端应用必须指定其希望连接的可信应用的UUID。如果客

应用进行初始的数据交换。

1.1.1.4.3. 命令 
命令是在会话内客户端应用和可信应用间的一个通信单位。当开始一个新的命令时，客
户端应用通过传递一个数字标识符来确定它想执行的、在可信应用中定义的功能，依据可信
应用为该功能所公开的协议也可提供相应的操作负载。命令的调用会阻塞客户端应用的线
程，等待可信应用的回答。一个客户端应用可以使用多个线程对应并发的多个命令。并发命
令的数量可以由实现来定义，这依赖于TEE 和使用的可信应用的设计，也依赖运行时资源的
限制。 
——操作负载  
一个开启会话或者调用通用命令的操作可以携带一个可选的有效负载，传入一组保存在
操作结构体中的操作参数的定义。在本指南中，每个操作最多可指定4 个参数。 
每个参数都可以是一个内存引用或者是一个值参数，并且拥有一个对应的方向：它可以
是输入、输出或者两者都是。对于内存引用的参数，数据流的指定方向决定了底层内存缓冲
区何时需要与可信应用同步。 
内存引用参数用于通过共享内存缓冲区的方式交换数据。值参数携带两个32 位整数的
小数量的数据，没有共享或者同步内存的负担。 
内存引用或者值参数内持有的数据结构格式，由使用可信应用函数的协议定义，相关内
容不在本指南中阐述。 
——临时共享内存注册 
内存引用可以是一个已注册的内存引用或者是一个临时的内存引用。 
——已注册的内存引用是在操作前已创建的共享内存块中的一个区域。 
——临时内存引用直接指定一个属于客户端应用的内存缓冲区，在操作执行阶段由TEE
客户端API 临时注册。 
临时内存引用可以为空，用来表示参数的特殊用例。为空的输出内存引用通常用于请求
所需的输出大小。

1.1.1.6.1. TEE 以及可信应用的安全 
TEE 和任何可信应用的实现都必须认为来自多媒体执行环境的输入数据都可能是恶意

如下内容需要TEE 或者可信应用开发者关注： 
共享内存由多媒体执行环境所持有，并映射到TEE 内存空间中。TEE 和可信应用中的代
码必须假定共享内存的内容是不可信且随时可能变化；存储在共享内存中的数据可能会在可
信应用代码执行的任何时候被恶意更改。注意，为保证行为按照定义运行，为了规范客户端
应用，必须遵从共享内存的约束。 
——登录连接方法 
本指南定义了很多连接方法，这些方法允许实现为客户端应用生成一个身份令牌并提交
给可信应用。此身份令牌中的信息基于多媒体执行环境中某些可信实体控制的参数生成，诸
如操作系统内核等。这些登录令牌由多媒体执行环境中的可信进程来生成的，而不是由TEE
自身产生的。因此，可信应用开发者必须了解，登录令牌的合法性受多媒体执行环境的安全
性约束，而不受TEE 的安全性约束 
1.1.1.6.2. 多媒体操作环境的安全 
在大多数实现中，TEE 是一个独立的操作系统，与运行客户端应用的多媒体执行环境
并行存在。与多媒体执行环境集成的TEE 不能削弱多媒体执行环境自身的安全性，这点是
非常重要的。TEE 客户端API、 TEE 和可信应用的实现必须确保客户端应用不会使用它们
暴露的特性绕开多媒体执行环境的用于隔离进程的安全沙箱。 
1.1.1.7. 实现定义的行为以及程序员错误 
本部分所提到的很多功能被描述为实现定义的或者程序员错误。 
——实现定义的行为 
当功能行为被描述为实现定义时，意味着一个特定实现的TEE 客户端API 必须同指南定
义的行为一致，并且必须文档化。然而，实际行为并未被指定为本指南的一部分。客户端应
用开发者可能会选择依赖这个实现定义的行为，但必须清楚的是它们的代码不能被移植到另
一个实现上。 
——实现定义的字段 
允许实现扩展一些定义在本指南中的数据结构，并将扩展的定义设定在实现定义类型的
字段imp 中。实现不可以添加imp 以外的新字段。实现可以使用imp 字段存放任何私有的、
想附加到结构体所代表的上下文中的数据，但是客户端应用代码不能直接访问imp 字段的内

步骤3：标记为输入的所有值参数字段是由实现来读取。适用于TEEC_VALUE_INPUT  或
者TEEC_VALUE_INOUT  类型的参数。 
步骤4：向可信应用发起操作。在命令执行期间，可信应用可以从输入内存引用所指向
的内存中读取数据。也可以将数据写入输出内存引用所指向的内存中。但在命令完成之前，
不能保证这些修改都能被客户端应用查看到。 
步骤5：命令完成之后，实现必须更新标志为输出内存引用结构体中的size 字段。 
对于非空的且标记为输出内存引用，更新的size字段可以小于或等于原来的size字段。
这种情况表明，字节数实际由可信应用写入，且实现必须使此区域与客户端应用内存空间保
持同步。 
对于所有标记为输出的内存引用，更新的size 字段可以大于原来的size 字段。对于空
的内存引用，所需的缓冲区大小可以由可信应用指定。在这些情况下，已传送的输出缓冲区
过小或者不存在，且返回的大小为输出缓冲区大小，该缓冲区是操作成功所必需的。此种情
况下，实现不应该将任何共享数据与该客户端应用同步。 
该行为的详细描述请参见2.3.5 章节中的“可变长度返回缓冲区”部分。 
步骤6：当命令完成时，实现必须更新所有标记为输出的值参数字段，即
TEEC_VALUE_OUTPU 或者TEEC_VALUE_INOUT 类型的参数字段。
