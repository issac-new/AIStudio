> 分工互指：工程标准（GB/T 25000 系列）与门禁的映射见 `standards-compliance.md`；金融行业立法清单由生成器侧 industry profile（`--industry finance`）加载；本文覆盖**监管执法检查域**——回答每个检查点的「依据是什么、查什么、看什么证据、不合格怎么改」。计数口径权威源：`../assets/facts.conf`（FACT_INSPECTION_CHECKPOINTS=173、FACT_PENALTY_CLAUSES=21）。引用纪律：全部法规引用落到条文号或标准号，以检查基准日现行有效官方文本为准。

## 0. 方法论：五步判断法与证据链

**五步判断法**（每个检查项通用）：

1. 找义务——是否存在法定义务、政策要求或许可条件；
2. 找系统——义务由哪个系统、流程、岗位承载；
3. 找证据——制度、配置、日志、台账、报告是否完整；
4. 找缺陷——缺失、过期、无效、迟报、虚假、不可追溯，六类对号入座；
5. 找后果——匹配处罚条款（§2）或内部问责条款，区分机构责任与个人责任。

**证据链要求**：判定只认证据，口头说明不作依据。配置项、代码扫描输出、日志记录、台账文书四类才作数。

**成熟度分级**（V0～V5，判定现状用）：

| 等级 | 特征 | 风险定性 |
|---|---|---|
| V0 | 无制度、无系统、无记录 | 高风险，可能直接处罚 |
| V1 | 有制度无执行 | 中高，认定未有效履行义务 |
| V2 | 有系统无控制（权限大、无审计） | 高，证据易固定 |
| V3 | 有控制无证据（口头有、导不出） | 中，易被质疑 |
| V4 | 有证据可追溯（能抽样还原一笔交易、一次变更、一次告警处置） | 低 |
| V5 | 持续优化（有审计、复盘、迭代） | 最低 |

**通用判断十维度**：制度是否存在、是否执行、是否有效、是否及时、是否完整、是否真实、是否授权、是否闭环处理、是否可审计、是否跨境合规。

**统一台账字段**（`inspection-ledger.sh` 输出即按此对齐）：

| 域 | 编号 | 检查项 | 依据（法条/规则/场景） | 证据（文件、配置、日志） | 结论（符合/不符合/部分/不适用） | 问题事实 | 整改措施 | 责任人 | 期限 | 复核结果 |
|---|---|---|---|---|---|---|---|---|---|---|

填写纪律：结论四选一并挂证据编号；不符合与部分符合项必须填整改措施、责任人、期限三格；复核结果由责任人以外的人填写。登记链路：系统控制点 → 检查证据 → 违法或违规事实 → 处罚或问责条款 → 整改 → 复核销号。

**处罚程度分层**（台账定级规则）：轻微（首查即改，责令改正/警告）→ 一般（法定区间罚款）→ 严重（拒不改正、造成泄露/中断，较高罚款加暂停业务）→ 特别严重（重大金融风险、大规模泄露，顶格罚款加吊销许可加禁业加移送刑事）。

**迎检 SOP 精要**：

- 检查前八件事：核验通知书与执法证；成立迎检领导小组；设唯一对外资料接口人；建资料提交台账与三级复核（业务、合规、法务）；自查自纠并固化证据（禁止临时补造）；统一访谈口径；人员培训（禁止毁损证据、不随意作答）；备专用查询终端（录屏审计、权限最小化）。
- 检查中三条：资料提交逐项审批（防超范围、防版本错）；关键岗位访谈由合规人员陪同并记录；每日复盘统一次日口径。拟认定重大违规、数据泄露、系统中断三类事项立即升高管层。
- 事实确认期：逐字核对《事实认定书》，区分事实与定性；法定异议期内（以通知书载明的程序规定为准，通常 5 个工作日）提交书面异议加佐证；必要时申请听证、延期、保密处理。
- 检查后七步：问题分级（重大、严重、一般、提示）→ 根因分析 → 整改方案（系统改造加制度修订加人员问责）→ 按时提交整改报告 → 内部问责复盘 → 制度修订与复查回头看 → 全部材料归档。

## 1. 执法检查域总览

### 1.1 检查基线与定制

主表 TECH-001～173 以「非关基 + 等保第三级 + 业务连续性第 4 级 + 银行卡清算审慎经营」为事实基线编制。用于其他项目时先替换三件事：① 监管身份（是否关键信息基础设施运营者、持牌机构类型）；② 等保级别与连续性级别；③ 行业专属义务（反洗钱/反诈/清算/支付/数据出境）。身份变化时罚则挂接随之变化——例如密码类检查点，非关基运营者适用《商用密码管理条例》第 62 条（1 万～10 万），关基运营者才适用《密码法》第 37 条（10 万～100 万）。

### 1.2 五条主线

| 主线 | 核心问题 | 核心证据 | 核心罚则 |
|---|---|---|---|
| 等保 3 级 | 控制点是否真落实 | 备案、年度测评、日志、三员分立、漏洞整改 | 网安法 61/62 条 |
| 连续性 4 级 | 恢复能力是否真实可验证 | BIA、RTO/RPO、备份、真实切换演练 | 人行法 46 条、行业监管办法 |

| 反洗钱/反诈 | 能否有效识别、报告、处置 | 监测规则、报送回执、协查记录 | 反洗钱法、反电诈法 |

### 1.5 红线（外资控股/跨境背景机构的最高优先级项）

以下四条按严重程度排序，前缀为触发情形——不满足触发情形的项目按普通高风险项处理：

1. 【合作发卡且同品牌境外机构已存在外币清算】**核心业务迁移期**：行业监管办法要求原则上自开业之日起 3 年内将涉及境内成员机构的核心业务迁移至境内处理并定期报告。迁移路线图、割接记录与定期报告是检查重点，逾期未迁移可认定情节严重（TECH-171）。
2. 【境内清算业务】**名为境内清算、实为境外透传**：境内交易授权报文绕道境外网络处理，或核心路由表由境外下发，违反「境内业务基础设施必须在境内」底线，可至吊销许可证。应对：境内网络拓扑图、数据流图，证明境内交易在境内机房闭环（TECH-001/002）。
3. 【调用境外风控/评分模型】**全球模型调用导致数据非法出境**：将境内持卡人明文卡号、身份证号、精准位置、设备指纹传至境外评分且未通过数据出境安全评估或标准合同备案，可触发个保法第 66 条营业额百分比顶格罚款。应对：境内外风控边界界定、脱敏/匿名化方案、API 字段审查记录、出境评估申报或备案回执（TECH-014/015）。
4. 【境外母公司/外包技术支持】**境外技术团队隐形运维**：境外技术人员未经堡垒机直接操作境内生产库，或境内员工将生产数据导出发给境外。应对：跨境远程运维审批制度，全部境外支持走境内堡垒机、临时脱敏账号、全程录屏、保留审批工单（TECH-016/035/089/155）。

## 4. 智能体安全（A1～F3，6 域 20 项）

主要风险：智能体赋权过高——开发时未遵循最小权限原则、权限分配未按任务场景动态调整、与系统/API 集成时权限传递和边界控制不严。带 ★ 的项有 `inspection-ledger.sh agent-audit` 机检子集（证据面见表注），其余为人工核查项。

### A 赋权与权限治理（3 项）

| 编号 | 检查项 |
|---|---|
| A1 | 智能体赋权遵循最小权限原则，不存在超出任务所需的过高权限 |
| A2 | 权限分配根据任务场景动态调整 |
| A3 | 智能体与系统、API 集成时，权限传递和边界控制严格 |

### B 身份与凭证管理（4 项）

| 编号 | 检查项 |
|---|---|
| B1 ★ | 禁止硬编码凭证：代码、配置文件、镜像中无任何明文密码 |
| B2 | 凭证具备时效性：所有 API Key、服务账号均设有效期（建议不超过 90 天），不存在永久长期凭证 |
| B3 | 人机权限分离：智能体独立使用专用服务账号，不复用开发人员个人高权限账号 |
| B4 | 最小化网络暴露：数据库、服务开启 IP 白名单或应用层认证，拒绝无来源限制的公开访问 |

### C 工具与数据权限粒度（4 项）

| 编号 | 检查项 |
|---|---|
| C1 | 读写分离与操作分级：只读类直接放行；写入类单独审批或强制限流；高危类（Shell 执行、物理删除）默认禁用，启用须经安全审批 |
| C2 | 数据行级权限隔离：查询强制携带租户或用户标识，不存在无条件查全量的工具接口 |
| C3 | 禁止直接暴露底层指令：不向模型暴露 exec、os.system 等原生调用，工具调用均为白名单 |
| C4 ★ | 文件系统沙箱限制：仅能访问指定工作目录，无法读取系统目录或用户私有目录 |

### D 系统指令与操作控制（3 项）

| 编号 | 检查项 |
|---|---|
| D1 | 系统指令强制锁定：System Prompt 顶层固化不可逾越的安全红线，对用户不可见、不可覆盖 |
| D2 ★ | 高危操作人工审批门禁：写入类、高危类工具调用须真实用户确认后方可执行 |
| D3 | 多跳权限衰减：子智能体权限只减不增，严禁反向继承或扩大 |

### E 审计能力（3 项）

| 编号 | 检查项 |
|---|---|
| E1 ★ | 全链路操作日志：每次工具调用记录用户身份或会话 ID、工具名、脱敏参数、执行结果状态、时间戳五必填字段 |
| E2 | 越权与异常告警：单次会话工具调用超 100 次/分钟、非工作时间（0 至 6 时）高危操作、调用黑名单工具三类情形触发实时告警 |
| E3 ★ | 日志覆盖范围完整，留存时长满足要求 |

### F 异常控制能力（3 项）

| 编号 | 检查项 |
|---|---|
| F1 | 具备异常调用监控能力 |
| F2 | 告警配置规则齐全 |
| F3 | 告警有效 |

三类典型缺陷（实查高频结论，自查时优先对照）：① 权限与岗位不挂钩——全部智能体挂全量工具集，岗位间配置差异只有名称；② 文件系统无边界——shell 与文件工具以当前用户身份在宿主运行，可读系统目录与其他用户目录，沙箱目录为空；③ 审计残缺加告警缺失——跟踪文件零条工具调用记录、会话库缺用户身份、参数不脱敏、三类告警一条都没有。

整改排期范式（按暴露面定级）：P0 一周内——审批档位显式化、按岗裁剪工具集、打开执法总闸；P1 两周内——修审计落盘、文件系统边界二选一（容器后端或目录白名单）、剔除出厂默认口令；P2 排期——落地三条告警、专用服务账号与最小凭证集、红线固化、堵多跳权限扩大、密钥轮换台账。

## 7. 三域衔接与使用指引

同一合规主题在三个域各有落点，查完一个域顺带核对另外两个域，避免同一问题三处各改一半：

| 主题 | 执法检查（TECH） | 智能体安全 | 采购 AI |
|---|---|---|---|
| 数据治理 | ④ 数据分级打标、脱敏、导出审批 | C2 行级隔离、C4 文件边界 | PA-36～38 主数据统一、AI 不直接覆盖主数据 |
| 审计留痕 | ⑥ 日志 6 个月留存、防篡改、三员分立 | E1 五必填字段全链路日志 | PA-06/19 证据包四件套 |
| 异常告警 | 监控告警闭环、重大故障自动上报 | E2/F1-F3 三类告警 | PA-18/31/34 整改超期与预警升级 |
| 权限最小化 | ⑦ 账号生命周期、MFA、特权双人 | A1-A3、D3 最小权限、动态调整、权限衰减 | PA-03 人机职责边界 |
| 高危操作管控 | 堡垒机高危命令拦截、变更分级审批 | C1 高危默认禁用、D2 审批门禁 | 场景三 定标权在人 |
| 版本与变更 | ⑫ 变更分级审批、回退、灰度 | 整改 P2 红线固化 | PA-05 规则版本管理 |

工作流分工：③ spec 阶段识别适用检查点并写入合规矩阵（spec §22）；⑤ 编码阶段遵守判断阈值；⑦ 独立审查阶段运行 `inspection-ledger.sh ledger` 出机检台账、按 `checklist` 补人工证据；迎检窗口启动时按 §0 SOP 执行。编号口径：TECH 主表面向监管执法（义务来自法条与许可条件），PA 面向业务合规（义务来自政策与企业制度），两域重叠时（如金融机构建设采购 AI）合并取证、分别定级。
