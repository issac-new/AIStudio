> **何时读我**：节点⑦独立审查、生成流程 Step 11、spec/plan 评审，或任何"让 AI 审查 AI 产物"的场合。本协议是审查的强制口径；`review-methodology.md` 的五维清单是它的 S3 内容检查表。

# 独立审查协议（Independent Review Protocol）

> 来源：Google `elephant-goldfish-model`（Apache-2.0）的 Goldfish 设计——审阅者被刻意剥夺作者上下文，独立性由信息不对称产生，不由语气指令产生（`skills/egm-review/SKILL.md:21-28`、`agents/*.md`）；本仓同根机制见 `agent-skills-methodology.md` §9 doubt 协议与 `subagent-orchestration.md` 新上下文纪律。
> 适用范围：需要先做设计决策的 spec/plan/架构产物审查。一行配置、报错明确的 bug 修复不适用，走平常流程。

## 一、三个角色

| 角色 | 能看到 | 负责 | 不得 |
|------|--------|------|------|
| 作者 | 需求、历史决策、探查结果、全部会话上下文 | 起草 spec/产物、回应 finding | 用自审代替冷读；向审阅者传自己的结论 |
| 冷读审阅者 | 待审文档路径、被引用源码路径、审查标准 | 找未言明假设、含糊需求、实现风险、经不起追问的结论 | 读会话历史；读作者推理；接受口头补充；参与起草 |
| 裁决人 | 目标与约束 | 拍板取舍、批准或驳回设计 | 被 AI 代替拍板 |

**独立性判据只有一条**：审阅者在开始审查前，没有见过作者的结论和推理。同一上下文里的"请严格审查"不满足这条判据。

## 二、冷读派发：输入白名单与黑名单

派发 prompt 必须携带（白名单）：

- 待审文档的绝对或仓库根相对路径（`TargetFile`）。
- 文档里逐字引用的源码路径，或该引用的最小片段（`file:line`）。
- 本协议路径，以及本阶段用到的标准：五维清单（S3）、理解度判据（S2）、就绪判据（S4）。
- 阶段名、输出文件路径、findings 表格式。
- 一句固定声明：**"你没有此前的会话历史。不要询问作者为什么这样设计，只按文档和源码判断。"**

派发 prompt 禁止携带（黑名单）：

- 会话历史、聊天记录、作者的设计推理。
- 先前轮次的 findings（复审阶段只传上一轮 finding 的处置证据与本轮增量 diff）。
- "作者认为已解决""这里已经讨论过"一类结论。
- 未落盘的 URL、口头承诺、聊天里的临时决定。需要引用时先落盘为文件，再传路径。

## 三、派发阶梯与停机

按可用能力逐级下降，**不得跳级，不得用同上下文自审冒充**：

1. 有命名子代理 → 直接派新上下文子代理。
2. 只有通用子代理 → 派通用子代理，prompt 里先让它读角色定义，再审查。
3. 不能嵌套子代理 → 主会话直接派一个全新子代理（direct dispatch），仍须干净上下文。
4. 完全没有子代理 → **停机**。输出：`review-unavailable: 本环境无子代理，无法执行冷读审查；同上下文自审不构成独立审查。` 记 `not run`，节点⑦不得通过，合入被阻。
   - 用户显式豁免时，落 `decisions.jsonl` 的 UserChallenge 记录（豁免理由、残余风险、批准人），门禁按豁免放行。
5. 审阅者超时、崩溃、读不到角色或标准 → 重试一次；仍失败记 `not run`，**不得记为零发现**。

**分层边界**：探查、互不依赖的多文件实施等非审查类并行，没有子代理时可以内联执行，但必须标 `degraded` 并在交付说明披露。审查类活动不适用降级——这是本协议与"运行时未装不阻塞"原则的唯一分界：审查独立性是质量不变量，不是可选运行时。

## 四、审查阶段

### S1 全局审视（Zoom Out）

- 输入：全文、需求边界。
- 判据：范围是否必要（YAGNI）、能否复用既有单元、是否过早陷入实现细节、是否在解决根问题、文档上下文是否足以支撑决策。
- 失败：上下文不足时**立即停**，列出缺失项要求补；不得靠猜继续。
- 产出：`review-s1-zoomout.md` 或审查记录的 S1 段。

### S2 理解度审查（Comprehension）

- 输入：只有待审文档，**不给项目背景、不给作者解释**。
- 判据：一个刚加入项目的新人能否复述四件事——要做什么、不做什么、边界在哪、怎么验证。
- 方法：先逐节复述，再列"读不懂/缺上下文"的位置。
- 失败：任一核心节无法复述 → Blocker。文风问题不算，缺关键上下文才算。
- 产出：复述标题 + findings（无 finding 也保留复述标题，作为已读证据）。

### S3 设计批判（Critique）

- 输入：文档、被引用源码、五维清单（正确性/安全/性能/可维护/测试覆盖）。
- 判据：未言明假设、含糊需求、实现风险、边界条件、共享状态与隐藏耦合、异常输入下的失效模式。
- 每个方案必须回答：**用户没看到什么？最强反方论据是什么？反方是否成立？**
- 产出：findings 表——严重度（must-fix / should-fix / nice-to-have）、`file:line`、证据、修复建议、不修的后果。无证据行的 finding 降级为附录，不压主报告。

### S4 实现就绪（Readiness）

- 输入：文档、就绪判据、计划改动范围。
- 判据：实现者是否还需要做设计决策；允许改写的文件边界是否明确；回滚与验证是否可执行；是否把取舍留给了实现者。
- 产出：就绪结论 + 写边界清单（本阶段后实现可写的文件集合）。

### 复审（Re-review）

只审本轮增量 diff 与上一轮 finding 的处置证据；已由用户裁决的取舍（settled）不重开。发现"已修复项再现"时重开并标 `churn`。

## 五、反谄媚语言契约（可机检）

- **先讲问题**：findings 在前；优点不设专段。确需肯定时只写事实（"该路径有失败用例覆盖"），不写评价。
- **禁用词**（命中即不合格）：brilliant、great、smart、correct、perfect、excellent、spot-on、seamless、robust、blazingly fast、seamlessly、effortlessly、literally、drastically、obviously；完美、优秀、很棒、非常正确、天衣无缝、无缝、健壮、极快、显然、毫无疑问。
- **禁止复述用户措辞再认可**：可以引用原话核对，不得复述后加"同意"。
- **禁止道歉开场**：I apologize、I am sorry、Forgive me、抱歉。
- **同意须挣得**：只有扛住 S1-S4 才能写"通过"；通过也必须列残余风险。
- **零发现必须写**：`未发现（已检查范围：…；已核对断言：…）`，不得用赞美代替结论。
- **每个方案至少一条最强反方论据**；没有反方论据视为审查未完成。

## 六、收敛语义

- **clean 轮** = 必需阶段全部 completed + 零 must-fix + 零 should-fix（或已明确处置）+ 零 `not run`。
- **`not run` ≠ 零发现**：有 `not run` 的轮次一律不 clean。
- **converged = 连续两轮 clean**；首轮 clean 不算收敛。
- **上限 5 轮**；第 5 轮仍不 clean → 升级用户裁决，不得自行放行。
- **三态**：`settled`（用户已接受的取舍，不重开）、`fixed`（已修复，再现即重开并标 churn）、`churn`（新发现可回退修复环重跑）。

## 七、留痕字段

审查记录（目标技能 `references/review-record.md`，项目 `docs/reviews/YYYY-MM-DD.md`）必须含：

| 字段 | 内容 |
|------|------|
| 评审人 | 子代理标识或人工姓名 |
| 评审上下文 | `fresh` / `degraded` / `unavailable`；只有 `fresh` 构成有效独立审查 |
| 冷读输入 | 文档路径 + 源码路径；声明未传会话历史与作者推理 |
| 阶段完成表 | S1-S4 各自 `completed` / `not run` + 产出文件 |
| 理解度结论 | 可复述 / Blocker + 复述标题 |
| findings 表 | 严重度 / `file:line` / 证据 / 修复 / 不修后果 |
| 收敛声明 | round N、是否 clean、连续 clean 轮数、残余风险 |
| 禁词自检 | 扫描命令与结果 |
| 未运行项 | 显式列出，不折算为零发现 |

机检：`check_review` 在 `REVIEW_RECORD_REQUIRED=1` 时核验上表字段；缺字段 fail；禁词命中 fail；`not run` 却声明 clean fail。默认档只 warn，存量项目不被批量转红。

## 八、最小可行做法

项目小、人手少时不必一次上全四阶段。最小闭环是三件事：

1. 派一个干净上下文的子代理，只给文档与源码。
2. 让它先复述（S2），再挑刺（S3），findings 必须带 `file:line`。
3. 把"评审上下文"和"未运行项"写进审查记录。

这三件事做到，就已经消掉"同上下文自审"和"无人反对即通过"两类假通过。
