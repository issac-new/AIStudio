# 活文档漂移方法论（Living Docs Drift）

> 来源：Google `elephant-goldfish-model` 的 `egm-drift-report` 技能（Apache-2.0）：拿已入库文档与当前源码逐条比对，四类漂移，报告落盘；与其 `egm-bootstrap` 形成"生成文档→漂移监控"闭环（`skills/egm-drift-report/SKILL.md:24-56`、`docs/designs/architecture.md:168-169`）。

## 一、与结构指纹的分工

| | 结构指纹（`project-fingerprint.sh --diff`） | 本文档（漂移报告） |
|---|---|---|
| 回答 | 文件数、扩展名分布、路径集变没变 | 文档里的断言和源码事实还对不对 |
| 盲区 | 同路径文件原地修改完全看不见 | 需要逐条读文档与源码，成本高 |
| 时机 | 每次会话开始，自动 | 反馈回路每轮、发布前、spec 归档时 |

两者不是替代关系：指纹负责"发现该重新看"，漂移负责"重新看时看什么"。**指纹没变，内容也可能已经漂移。**

## 二、四类漂移

1. **缺失功能**：文档说某能力存在，源码里没有对应实现。
2. **模型不全**：文档的实体、字段、状态机少于源码现状。
3. **逻辑捷径**：文档描述的分支、校验、失败路径在源码里被简化或绕过。
4. **架构分歧**：模块边界、依赖方向、调用链与文档描述不一致。

反向也要查：**源码里存在而文档完全没覆盖的逻辑，同样算漂移**。文档不是只对"写过的部分"负责。

## 三、比对程序

1. **提取断言**：逐节读文档，抽出可验证的断言——文件路径、符号名、命令、配置键、行为描述、数字。
2. **定位源码**：先用组件库清单与 relations 边集定位，再用检索阶梯（L1 边集→L2 索引→L3 语义→L4 实现）；找不到即候选漂移，不凭文件名猜。
3. **逐条判定**：一致 / 漂移 / 无法判定。无法判定的标"未覆盖"，不猜、不折算为一致。
4. **写报告**：按 `assets/drift-report-template.md` 落到 `docs/reviews/YYYY-MM-DD-drift-report.md`。同日多轮追加，不覆盖。
5. **修复**：双向二选一——改文档或改代码，并在报告里写理由。**不得只改一边留假一致**；改文档属于决策，落 `decisions.jsonl`。

## 四、报告格式

```markdown
## <文档路径>

- [缺失功能] 文档断言"X 会做 Y" → 源码无对应实现（`path/file:line`）→ 建议：删除该断言或补实现
- [模型不全] 文档字段 A/B → 源码另有 C/D（`path/file:line`）→ 建议：补文档
- [逻辑捷径] 文档描述重试三次 → 源码仅一次（`path/file:line`）→ 建议：改代码或改文档
- [架构分歧] 文档称 A 不依赖 B → 源码存在直接依赖（`path/file:line`）→ 建议：修订边界图
```

无漂移写：`未发现漂移（已核对 N 条断言，覆盖文档 M 份）`。不要只写"看起来一致"。

## 五、触发点

- **反馈回路每轮**：指纹 `--diff` 报出结构变化后，对受影响文档跑一次漂移；结构没变则按周期（建议每月）跑一次内容漂移。
- **发布前**：与主干回归同批，至少覆盖本次变更触及的设计文档与 README。
- **spec 归档时**：`DESIGN_SYNC: touched` 的设计文档，归档前核对声明与实现一致。

## 六、与知识生命周期的关系

`knowledge-lifecycle-methodology.md` §五的三态（仍成立→续期 / 证据不足→degraded / 证据源消失→归档）管**单条知识**的存废；本方法管**整份文档**与源码的一致性。单条知识判"证据源消失"时，漂移报告提供证据；漂移报告的结论又反过来触发单条知识的续期或归档。

## 七、成本控制

- 一次只比一份文档，不并发读全库。
- 先比"文档里点名了路径/符号"的断言，再比纯行为描述；前者命中率高、成本低。
- 报告只写差异，不写"已读但一致"的流水账；覆盖度用一句统计交代。
