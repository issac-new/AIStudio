## 核心命题

FDE 的规模化取决于平台底座。平台只优化一个北极星指标：**TTVV（Time to Validated Value，从发现问题到验证价值的时间）**。检验标准一句话：**随着项目越来越多，解决下一个问题有没有持续变快？**

## 三层边界框架（平台化判断）

| 层级 | 策略 | 内容 |
|---|---|---|
| 应用层 Solution | 多生成 | 界面、提示词、胶水代码、一次性工作流（AI 编程随时重建，平台不控制细节） |
| 能力层 Capability | 多复用 | 技能、工具、领域服务、评测数据集（反复出现+语义稳定才抽象） |
| 治理层 Control | 多沉淀 | 身份、权限、密钥、模型网关、审计、可观测性（即使能快速生成也统一建设） |

## 抽象判断五维公式

**平台化价值 ≈ 重复 × 稳定 × 业务价值 × 重建成本 × 治理需求**
- 只出现一次、需求天天变 → 留在灵活边缘
- 被 N 个项目使用、定义稳定、出错风险高 → 进稳定核心
- 用于融合候选机制打分（1-5 分/维，≥15 进 P1，≥18 进 P0）

## 关键机制

- **Use Case Pull（场景拉动）**：能力不由平台团队预先规划（"100 个通用技能"是反模式），从真实项目长出来：项目逻辑 → 重复模式 → 稳定性验证 → 抽象 → 领域能力 → 下一个项目
- **六层上下文**：数据/语义/知识/运行/用户/任务——RAG、记忆、画像、本体本质都在回答"当前任务如何构建足够准确的业务上下文"
- **渐进式产品化**：探索→原型→验证→产品化→规模化，治理强度随业务确定性增加
- **Field to Product 飞轮**：生产失败→失败样本→评测数据集→修复→回归评测；每个项目结束 Asset Review 三分：客户专属留项目 / 领域可复用进领域层 / 平台通用进平台核心
- **本体 = 业务中间表示（BIR）**，按成熟度渐进：元数据→语义模型→业务对象→领域模型→本体→知识图谱；不要第一天全建
- **稳定核心 + 灵活边缘**：企业定制永不消失，平台缩小每个项目重新解决的问题集合

## 四个误区（文章明示，融合时同样适用）

1. 平台过重（演示要先配十个模块）2. 平台过薄（一年后无法治理）3. 过早抽象 4. 项目越来越多而平台没有越来越强（最危险信号）
