# 设计文档章节接口契约

## 触发条件

当设计文档分为“机制设计 → 实现配置 → 运转与维护”，或读者反馈章节割裂、看不出组织和衔接论证关系时使用。本 skill 补足章节间的工作流，不替代具体领域设计内容。

## Procedure

1. 先读三章的章首、章末、主图和小节标题，列出每章的输入、输出、证据和失败出口；不要直接改某一章的导语。
2. 在中间章开头放跨章接口表，至少覆盖 `§3 → §4`、`§4 → §5`、`§5 → §3`；运行结果会触发实现修复时，再补 `§5 → §4`。每行必须写上游输出、下游消费、具体落点和失败处理。
3. 在运转章开头放回流判定表，至少区分“运行通过”“载体缺陷”“机制缺口”，分别指向继续执行、修复实现、修改设计。
4. 写清证据门：只有现有判据无法覆盖且同类问题复发时才回写机制设计；脚本失败、配置漂移、准入资料缺失只修实现载体并重验原判据。
5. 用一张主图表达设计要求、执行载体、运行证据和回流方向；用表格承载图上无法表达的条件。图、表、正文必须使用同一组术语。
6. 修改图号或跨章结构后，全文扫描图题、图号、章节引用、旧编号和悬空 § 引用；全量检查 Mermaid 源码，不把源码闭合误报成渲染通过。
7. 提交前保存文档快照，运行畸形表格行、围栏闭合、替换字符和 `git diff --check` 检查；提交后用 `git show HEAD:<doc>` 验证关键接口真的进入提交。

## Always-on rules

- 章节的接口是交接物，不是章节编号；“本章承接上一章”不能替代输入/输出/消费/回流。
- 不把所有异常都归因于设计缺陷；先区分机制缺口和载体缺陷，避免设计章膨胀、判定标准失效。
- 图是关系总览，表是判定契约；两者不可互相冒充。
- 交付时分别报告源码验收和渲染验收；未渲染必须明确标为未验证。

## 可复用模板

接口表和回流判定表模板见 `references/chapter-interface-and-feedback-tables.md`。仅在需要落表时读取，避免把模板细节塞进每次操作的主流程。

## 常见陷阱

- 只增加三章导语或各章独立流程图，却没有交接物：视觉完整但论证仍割裂。
- 只改接口表，不写失败处理：异常没有回流目标，维护章仍然是说明文。
- 只验证当前工作区：自动备份或并发 Git 操作可能改变 HEAD；提交后必须读回目标文件。
