# Worker 完成自述的独立核验

> 来源：Field-to-Skill 基线挖掘 t_f4fd26da（2026-08-25），3 判例提炼。
> **不信任 worker 自述，亲验后收。** AGENTS.md「不信任 agent 输出，要亲自查证」的可执行版。

> **哲学依据注脚（2026-09-08 增补）**：「不信自报，只验前提→结论链」的形式化立场出自 Copi《逻辑学导论》（Introduction to Logic）——有效性判定只关心「结论是否可从前提中必然推出」，不关心推理者的心理动机。对应到验收纪律：worker 的自述属于动机性声明，不构成验收证据；唯有可检验的前提（文件/命令/输出）与推理链（验证步骤）才算数。
> 来源: synthesis-fusion-plan.md C2 / philosophy-logic-report.md §2.2 S12（人大社书讯原文直引）

## When to Use

当 orchestrator（或任何验收方）收到 worker 的 `kanban_complete` 自述完成报告，且验收决策依赖于 worker 自己声明的文件变更/测试结果/产物存在性时。

## 1. 触发信号

worker `kanban_complete` 的 summary/metadata 中含以下任一声明：

- 「N 个测试通过 / 全绿 / 回归零新增」→ 必须亲自跑一遍
- 「文件 X 已创建/已修改」→ 必须 `ls`/`grep`/`py_compile` 机械验证
- 「artifact 已产出到路径 P」→ 必须验证 P 存在且非空、格式可读
- 「delegate_task 后台任务 Y 已派发」→ 必须确认 Y 有 kanban 卡或持久句柄，非会话蒸发
- 任务含「根因治理/系统修复/数据管道」类高虚报风险关键词

## 2. 标准步骤

1. **列出 worker 声明清单**：从 summary+metadata 提取所有可证伪声明（文件、测试、产物、外部副作用）
2. **逐项机械验证**（不走 worker 自报通道）：
   - 文件存在：`ls -la <path>` 且 size>0
   - 语法有效：`python -m py_compile` / `yaml.safe_load` / `bash -n`
   - 测试真实通过：`pytest <path>` 亲自跑，对比 worker 声称的 pass/fail 数
   - 产物可读：PDF 用 pymupdf 提取文字数、HTML 用解析器、JSON 用 `json.load`
   - 外部副作用：cron job 用 `cronjob action='list'` 确认、kanban 卡用 `kanban_show` 确认、DB 变更用只读查询确认
   - **CLI 工具脚本类交付**（退出码契约、mock 实测、去重幂等、边界 grep）：按 `references/cli-tool-script-acceptance.md` 配方逐步执行，不复用 worker 的测试脚本
   - **随交付附带的校验产物必须打开亲读**（visual-check JSON、测试报告、lint 输出）——worker 的文字自述可能与自己附上的校验产物直接矛盾（文字写「N/N pass」而产物 `status: fail`），产物是更强的证据源
3. **回归基线对比**（worker 声称「无关改动导致既有失败」时）：
   - 改动前全量测试基线 → 改动后全量测试 → diff 失败集合
   - worker 声明的「无关失败」必须能在基线中复现，否则即 worker 引入
4. **超范围改动检查**：`git diff --stat` 对照任务 body 声明的改动文件清单，发现清单外文件 → 要求 worker revert 或另建任务；清单外脏文件先做**运行时归属判定**再定性——被进程持续追加的运行时数据（影子日志 jsonl/缓存/台账，mtime 落在卡运行窗内、内容为追加式日志行）属正常自写不算越界；mtime 早于卡创建或内容是源码/配置改动才按越界处置
5. **验证结论写 kanban_comment**：每项声明标注 ✅真实 / ⚠️误导 / ❌虚假，含证据命令与输出

## 3. 陷阱

### A. 「worker 说做了」≠「做了」（核心反例）

- t_1007448f 的 RSS 重构是自我声称的虚假完成，delegate_task 句柄随会话结束蒸发，无 kanban 卡无代码
- **t_baa58d68 反向案例**（2026-08-25）：worker 25 分钟内改完 cron/scheduler.py + cron/jobs.py + 新测试，但**没 commit**。run90 90 turns 烧完前已无余力跑测试 + commit + kanban_complete，dispatcher 判 gave_up 后改动仍裸在工作树——再被上游 git pull 一次就丢。**「代码在文件里」不等于「代码已持久化」**：源码改动必须 `git log` 可见 commit 才算落地

### B. 「代码在文件里」≠「代码已持久化」——commit 是源码改动的硬验收项

worker 改源码类任务（含 hermes-agent 主仓、F1/F2/F3/F4 这类）的验收必须多查一项：`git log` 见 commit hash。若无 commit：
- 不能判定 worker 已交付（即便文件 diff 可见）
- 改动暴露在丢失风险下（上游 pull 冲掉 / dispatcher 重派时 worktree 被清）

**核验模板**：
```bash
git log --oneline -5
# 验收卡里标注的「commit 已落」必须能在 git log 里 grep 到 commit message 的卡号
```

### C. 「局部测试过」≠「无回归」

- t_37053748 worker 只隔离跑了自己声称的 hunk，没跑全量基线对比，实际引入 18 个失败
- **全仓跑暴露的旧债错误集要与交付范围切割**：按验收命令跑出的 errors（如 `ModuleNotFoundError: No module named 'anthropic'` 这类可选依赖缺失的 collection error）若全部落在交付未触及的目录，属既有环境态，不阻断验收但要与 worker 声明的 pass 数并列记录，不误判为交付引入。反之若交付范围内有 error，先建改动前基线再定责。
- **验收命令的测试文件范围从 commit 内容反推，不靠猜文件名**：`git show --stat <commit>` 列出新增测试文件再拼命令——凭记忆拼路径会得到 `no tests ran`（空跑不报错、rc=0），易误判为「测试不存在」或「worker 没写测试」。

### D. 「curl HTTP-200」≠「功能验证」

- 对网站首页 200 不是对 RSS feed 解析的验证——验证手段必须匹配声明的功能层级

### E. 「任务 done」≠「工作真实完成且留痕」

- t_46afbcca 工作做完了但没调 complete，状态脱节——审计时需双向核对

### F. 验证本身要留痕

- 把验证命令+输出写进 kanban_comment，否则下次审计还要重做

### G. Orchestrator 接管 commit 合法应急路径（2026-08-25 t_baa58d68 实证）

worker iteration 预算耗尽但代码改动已落盘、未 commit、未交付的处置：
1. 立即 `git diff --stat` 看改动是否完整（grep 实证关键机制块 + `pytest <新测试文件>` 亲自跑）
2. 验证通过 → orchestrator 直接 `git add` + `git commit`，commit message 含卡号（让 git log grep 可追溯）
3. DB 直改：`UPDATE tasks SET status='done', completed_at=<ts>, result='Orchestrator 接管 commit (commit <hash>) — <诚实留痕>' WHERE id='<task_id>'`
4. kanban_comment 留痕说明接管原因，避免 dispatcher 重派重复劳动

**适用边界**：仅当 worker 已无 run 可接管（gave_up / blocked）+ 代码改动可见 + orchestrator 可独立验证。不适用于 worker 还在跑的情况（会撞车）。

### H. 「自述通过」≠「校验产物通过」——自附校验产物优先于文字自述

worker 交付时附带的自检产物（visual-check JSON、测试输出、lint 报告）可能与其
summary 声明直接矛盾。验收时先打开产物比对声明：产物 `status: fail` 而文字称
「全部通过」属误导性声明，按 ❌/⚠️ 标注并要求解释，而不是默认产物是工具误报。

### I. 验收标准里的数字本身可能算错——先数产物再定谁错

交付数字与任务卡验收数字不符时，先机械清点实际产物（如从源 JSON 数节点/行数），
再判定谁错。合理的设计聚合/简化常使卡面数字失真——此时修正判据口径而非强迫产物
凑数；worker 报告照抄了卡面错误数字时，两边都要修正。

### J. 逐节点状态判据必须匹配该节点的产物类型

状态看板的红/黄/绿判据（如「PDF 缺失=红」）只对产出该类产物的节点成立；把它套到
产物类型不同的节点（如以文档标记为交付物的节点）会误报红。评审状态看板时逐节点
核对判据适用性，发现误判要求修正节点状态与判据表，而非只改颜色。

### K. 可视化渲染色的语义叠加陷阱——状态与类别必须分离核验

当节点颜色由「类别 type」决定而状态由独立字段（tag）承载时，视觉上的「红/黄/绿」
可能是类别色而非状态色（如 type=security 渲染红色，但 tag=GREEN 状态正确）。
验收时**数据源 JSON 才是事实**——直接读节点的 tag 字段判定状态；渲染截图的颜色
只用于发现语义叠加问题（状态与类别同色会误导阅读），作为设计缺陷记录返工建议，
不作为验收不通过的理由。

### L. 「无命中」≠「机制正确」——检测/过滤类机制的验收必须有阳性对照

验收会输出「排除/无结果」的机制（freshness 判定、stale 检测、过滤规则）时，干跑的
空结果有两解：机制正确排除了该排除的，或输入根本没走到判定分支。空结果只证明输入
未触发，不证明机制正确。必须构造一个保证命中的阳性对照输入（fixture 注入或临时降
阈值），读到结构化判定字段（如 `stale_evidence: true`）才算验证过。

同理，机制的环境探测函数要用**真实目标路径**单测：探测在合成输入上通过 ≠ 在真实
环境有效——典型反例是用 `.git` 存在性判断 repo 根，而目标路径只是仓库子目录，探测
恒失效但干跑显示「正常无命中」。验收标准里写的「应判 stale/应命中」如果从未真正
触发过，按未实现处理，打回时要求贴出含判定字段的真实输出。

### M. 验证器与生成器分离 + 证据五问（2026-09-17，融合自快手 GIAC2026 运营交付/Agent-Verify）

**核心原则：生成方不得同时是唯一验证方。** Agent 同时产出代码和测试 Case 时，天然倾向验证「干了啥」（行为印证）而非「该干啥」（意图符合）——即「AI 伪验证循环（test oracle）」。落地三条：

1. **验证器独立判定**：验收用的测试/断言由验收方（orchestrator 或未参与生成的 Checker worker）构造或至少复核；worker 自带测试只作参考证据。判定 fail 的验证器必须带 SpecId/锚点，可回溯到原始需求条目。
2. **验证证据五问**（QuickTest 证据公式收缩版，逐问留痕进 kanban_comment）：① 输入可控——前置条件（fixture/mock/环境）真实构造了吗？② 行为触达——真的走到目标代码路径/场景了吗？③ 状态完整——除最终产物外有过程证据（中间输出/日志/trace）吗？④ 时机正确——等待的是明确事件完成还是 sleep 猜测？⑤ 失败可定位——若断言失败，能否唯一定位到需求条目？五问有「否」→ 验证深度降级处理（见 output-contract.md 分层 Verify 声明项）。
3. **「看最后一张截图」=伪验证**：单点终态证据（截图/退出码 0/测试全绿）不能独立支撑「可交付」结论，必须与前置条件、执行路径、过程状态组合成交叉验证。

> 与判例 D（「curl HTTP-200≠功能验证」）同源：验证手段必须匹配声明的功能层级。

### N. 双库陷阱——可登记类交付物（gap_register/台账条目）必须双库 grep 验收

验收含「登记 gap / 台账条目」类交付物时，先想到登记库不止一个（gap_register 有
`~/.hermes/gap_register.yaml` 小库与 life-workbench 大库两个活跃副本，另有类似
registry/ledger 双份情形）——worker 自述「已登记」可能落错库或根本没登记。验收
必须双库 grep 关键词确认条目真实存在，且登记位置与派单指定口径一致；落错库
（条目仍在）记口径备注不算漏登，但要在 kanban_comment 标明后续统一口径。
派单时在 body 明确指定目标库路径与 CLI 命令，从源头消除歧义。

### O. 代回写前产物引用逐一定位——三轮找不到就诚实回退

worker 因环境阻塞（如外置卷权限被吊销）留言「分诊已定案、只差回写」时，orchestrator
代为回写前必须逐条验证其结论引用的落地产物，三步定位法：

1. **前缀 glob**：工作区目录常带 slug 后缀（`<gap-id>-<slug>/`），用 `glob("前缀*")`
   模糊匹配，不拿留言原文路径硬 stat——路径不完整的 ENOENT 是「路径不全」不是
   「文件不存在」。**glob 零命中只证明「该前缀下无匹配」**：手拼搜索根少写任何一级
   目录段都会静默空转、被误读成「产物不存在」——判不存在前先核实搜索根本身（从
   已知存在的祖先目录用 find/mdfind 全域兜底，或先 ls 出真实父目录链再拼 glob）。
   glob 命中目录后抛 IsADirectoryError 恰是存在性铁证，改用目录读法（os.walk 收集
   文件名+抽样读内容）重验，不据此判缺失、不据此回退条目；
2. **git 全历史**：`git log --all --name-only -- "*<文件名>"`——工作树已丢但曾被
   备份/提交过的产物在这里找。**文件名 pathspec 会命中全仓同名文件**（research/*、
   rd/archive/* 等处常有几十个同名文档），历史命中必须对候选 commit 跑
   `git ls-tree -r --name-only <commit>` 取精确路径核对目标前缀——同名异物不算证据；
3. **双根兜底**：正本 workspace 与旧副本树各扫一遍。

三轮全空才判「产物不存在」；找到同名文件还必须做**内容关键词比对**——同名≠同一物
（同名 analysis.md 在仓库历史里有几十个，多为无关文档）。产物验证失败的条目回退
原状态（todo）并在 evidence 留「代回写时引用产物未找到，回退待专项」，不采信不可
验证的完成声明：账面少几条办结可补救，假办结混进台账会永久误导后续专项规划。

worker 自述「分诊已定案、逐条清单已备好」但清单无落盘载体（不在评论、不在文件、
不在 DB）时，其自述分布（如「done N / dropped M / todo K」）不采信入账——逐条
理由没落盘就无法逐条对账。以验收方独立产物亲验得出的分布为准，并在对账 comment
里注明两版分布的差异与缘由，不留无声偏差。

### P. 二手参考输出（MoA 多模型参考等）先过污染检测再采信

多模型参考/二手摘录进入裁决前先做四项污染检测，任一命中即整份弃用：①同一行或同一
结论重复数十遍；②控制字符乱码（BEL 等）刷屏；③引用不存在的标识（卡号/任务号查无
此物）；④时间戳落在未来（晚于当下取证时刻）或叙述性文本混进「工具输出」。被污染
参考的数字一律不并入账本，也不因「多份参考一致」而采信——两份参考可能同源幻觉。
参考与自己新鲜机械取证冲突时，以快照较新且无污染者为准；参考快照早于自己最新取证
时，禁止用旧参考推翻新证据。

### Q. 批处理补跑的进程退出码不作数——以日志步骤矩阵独立终验

补跑/批处理脚本常无 `set -e` 且末行是无条件 `say`/`echo`——进程 rc=0 是结构保证
不是成功证据。终验以日志里的步骤级 rc 矩阵 + 产物清单（存在性/大小/marker 对账）
为准，退出码只当「跑完了」信号。

### R. 自己的收口声明同样要独立复验——「代码里有 complete 调用」≠「complete 已执行」

编排方代收口的收尾动作常包在脚本里：占位 `pass`、异常被吞、提前 return 都会让
kanban_complete 静默未执行，而叙述文字里已经写下「已办结」。两条纪律：
1. `kanban_complete` 返回 ok 只当「调用成功」；卡真正进入终态必须 sqlite 直读
   tasks.status 确认后才对外宣称 done，补的对账评论按 comment id 查回原文确认
   在卡上——「代码里发了评论」不是已留痕的证据；
2. 「不信自报」适用于自己——本轮早前的结论会随会话推移变陈旧，甚至本来就基于
   后来被推翻的前提（如产物存在性误判）。重复任何「done/办结」声明前，一律从
   事实源重新取证（卡态直读、评论查原文、登记册回读），不以「上一轮已说过」为据。

### S. 验收脚本先跑自证再采信——别让自己的口径错误伪造验收结论

「不信自报」也包括不信自己的初版验收脚本：本类脚本的典型错误不是漏验，而是**用错误口径得出一个看起来成立的结论**。三条硬规则：

1. **零命中先验搜索根，再判「缺失/不一致」**：grep/find 零命中有两解——目标真不在，或搜索根本身写错（glob 模式不匹配、路径少一级、列名臆测）。判不存在前先确认搜索根有效（`ls` 出真实父目录再拼路径；SQL 先 `PRAGMA table_info`）——模式不匹配的 glob 返回空列表，会被误读成「该机制零覆盖」，直接影响等效性裁决（把已有机制误判为空白去重复建设）。
2. **字节/字符/行数口径不混用，跨文件比对走共同前缀逐字节**：中文 UTF-8 每字 3 字节，`len(str)` 与 `os.path.getsize` 天然不等；「改动范围是否为纯增量」不能拿两个文件的总长度相减（总长含各自附录/尾部），要比对**到插入点为止的共同前缀**是否逐字节一致——范围口径错会把「零改动」误判成「§1-§7 被改动」，反过来也可能把改动误判为纯追加。
3. **聚合布尔必须显式携带每一子项，失败项不能被吞**：`allok = allok and ok` 收尾只打一行总判时，早前失败会被后续 ✓ 流水淹没；复核汇总至少显式列出 `[PASS, FAIL, ...]` 数组并打印全部 FAIL 标签，让「几项过、几项挂」在输出里可见。且比对类脚本的**区间定义本身要先自证**：打印两侧比对的起止锚点（小节标题/偏移+长度）供肉眼核对，再信比对结论——区间口径写错时，逐字节比对会「精确地」验一个错误的问题，聚合真值照样掩盖它。

**收尾自问**：结论是「ALL PASS」时，问一句「这个 PASS 里每一项都是按正确口径验出来的吗」——聚合结果为真不等于每个子验证有效。

### T. 数据治理类交付的验收三件套——备份差集 + 台账全覆盖 + 内嵌抽读

worker 声称「N 条链接清理/字段归位/零数据删除」类 DB 与结构化数据交付时，validator 退出码 0 与计数对账都不够——**删除是否正当只有对照治理前备份才能判定**。三步：

1. **备份差集**：治理前必须有全量 dump（对象数+链接数）。验收时把备份链接集与现库链接集做差集得到「真实删除清单」，再与 worker 自报计数对账——两个数必须一致；对象总数变化要有解释（如 +2 = 文件入库新对象），「零删除」以差集为证不以自述为证。
2. **台账全覆盖**：真实删除清单中每一条都必须能在治理台账里找到对应处置记录。匹配要按记录的 action 分别适配字段（台账键形常是 consumer/quote/task/path 等多种，单一匹配式会漏报「未覆盖」）。差集中任何一条无台账去向 = 未授权删除，打回。
3. **内嵌抽读**：声称「内嵌保留后删链」的记录，抽样打开消费方对象的属性包，确认内嵌字段（如 evidence_quotes）真实在位且非空——台账写了内嵌 ≠ 字段里真有。

## 4. 核对任务树状态（fan-in 卡的必检项目）

对有父子依赖的任务，先机械读取整棵任务树，再写进度或完成结论：

1. 查询每个子卡、汇总卡和根卡的 `status`、`worker_pid`、`completed_at`；不要用「已产出文件」推断卡已完成。
2. 只有当验收所需子卡全部 `done`、汇总卡已实际运行并完成、根卡进入终态时，才可写「全部完成」；任一卡为 `running`/`todo`/`blocked`，必须明确写「未完成」并列出阻塞卡。
3. `kanban_comment` 只是留痕，不能证明 worker 收尾、汇总卡启动或父卡依赖已释放。
4. 把「已发送给家长/用户」视为外部副作用，必须有发送工具的成功结果、目标标识和消息/附件标识；内部 comment、日志片段或计划不能支撑该声明。缺回执时写「未验证送达」，不可写「已发送」。
5. **主卡完成报告点名的产物在声称路径缺失 → 先查子卡再判失实**：主卡 worker 可能把落地拆进了子卡（其自述按主卡视角写、不列子卡状态），产物随子卡完成才到货——此时报告定性为「委托完成」，验收转入子卡逐项做；子卡全终态前父卡只能出「部分交付」结论。判失实前查整棵任务树（本节 §4 上方的 fan-in 检查）——否则把委托交付误判为虚假完成，或反过来把子卡未到货的空头报告误收。

## 5. 验证（skill 生效的机械检查）

- 抽查 3 张 worker done 卡：每张至少 1 项声明有 orchestrator 独立验证记录（comment 含验证命令原文）
- 对 fan-in 卡抽查整棵任务树：状态结论与 DB 逐项一致
- 虚假/误导声明发现率 >0（若长期为 0，要么 skill 未被执行，要么 worker 质量已质变——需复核确认）
- 验证后发现的失实声明有后续处置（revert / 补充完成 / kanban_block 升级）

## 5. Diamond Checker 卡模式：把独立核验前置成最后一张卡（2026-08-27 实证）

判例 t_c524d54c（phlexing 三面资产盘点）：三张并行子卡（网络面/本地数据/暴露面）全 done 后，`parents=[三张子卡]` 建独立 Checker 卡，assignee 选**未参与任何子产出**的 profile。实际产出证明其价值——**3/3 子报告各被纠出 ≥1 处口径失实**：

- 「19 张证书」实为 19 条 CT 记录 = 12 张唯一证书（同 serial 去重）
- 「基线后新增的 2026-05-15 证书」实为基线 7 月原始证据（crtsh.json）已含该 serial——**「新发现」类声明必须回查基线原始证据文件**，防「其实基线已有」
- 「9 项资产复验」口径实为 8 基线项 + 1 新增项，数字含义不同

Checker 卡四条硬约束（写进 body 才有效）：
1. **机械验证而非通读打分**：抽验断言脚本落盘（本例 checker_verify.py 等 15 断言 + 追加 3 项全 PASS，可复跑）
2. 修正以「Checker 修正 A/B/C」标注在合并报告对应章节，**不改子报告原文**（保留审计轨迹）
3. 缺文件不代写 → `kanban_block(kind="dependency")` 退回对应子任务
4. 合并=幸存内容（去重排序后逐项加总核对），不是子报告拼盘；总表数字必须等于各分表加总

与 §2「orchestrator 事后亲验」的关系：Checker 卡是把本 skill 的核验纪律**委托给第四个 worker 前置执行**，适合三面以上并行产出需要交叉合并的重型任务；orchestrator 仍需对 Checker 产出做轻量抽验（文件存在+断言脚本可复跑），不因有 Checker 而豁免。
