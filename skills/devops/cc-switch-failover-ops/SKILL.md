# cc-switch Failover Ops — Rate-Limit Cascade & Queue Hygiene

Triage provider instability that is NOT a wire_api/404 mismatch: an upstream **account-level rate limit** (HTTP 429) cascading into circuit-breaker trips and failover-queue exhaustion, surfacing as intermittent `503 无可用 Provider` under burst load. Confirmed case: MGLM (BigModel `open.bigmodel.cn/api/anthropic`, app_type=claude), 2026-09-04/05 — 3,134× 503 + 736× 429 in 2 days, zero in the 3 days prior.

> For the codex `wire_api="responses"` → 404 territory, see `cc-switch-provider-troubleshooting` (lives in default profile; this skill complements it).

## The cascade chain

```
Burst traffic (cron fleet / parallel workers converge)
  → upstream account-level rate limit: HTTP 429, BigModel code 1302 「账户已达到速率限制」
  → cc-switch circuit breaker trips (claude config: failure_threshold=20, error_rate=0.9, min_requests=30)
  → failover to next provider in queue (e.g. H6W — itself half-healthy: 500/502s)
  → queue remainder is stale: 403-quota provider never evicted, healthy provider never enqueued
  → all exhausted → cc-switch emits 503 「无可用 Provider」
```

**Key insight**: a 503 whose `error_message` is exactly `无可用 Provider` is **generated by cc-switch itself**, not the upstream. Upstream failures carry `上游错误 (<code>): ...` prefixes. This one string splits the diagnosis in half.

## Diagnostic playbook (all against `~/.cc-switch/cc-switch.db`)

### 1. Error signature distribution (7-day window)

```bash
sqlite3 ~/.cc-switch/cc-switch.db "
SELECT status_code, substr(error_message,1,120) AS err, count(*) AS cnt
FROM proxy_request_logs
WHERE provider_id='<provider_id>'
  AND created_at >= strftime('%s','now') - 7*86400
GROUP BY 1, 2 ORDER BY cnt DESC LIMIT 15;"
```

Read: 503+「无可用 Provider」 = internal exhaustion; 429+code 1302 = BigModel account rate limit; 502 `Connect` = upstream unreachable; 400 codes 1301/1214 = content filter / empty input (ignorable noise).

### 2. Hourly failure timeline (find the burst window)

```bash
sqlite3 ~/.cc-switch/cc-switch.db "
SELECT strftime('%m-%d %H:00', created_at, 'unixepoch', 'localtime') AS hr, count(*) AS c
FROM proxy_request_logs
WHERE provider_id='<provider_id>' AND status_code = 503
  AND created_at >= strftime('%s','now') - 3*86400
GROUP BY strftime('%m-%d %H:00', created_at, 'unixepoch', 'localtime')
ORDER BY min(created_at);"
```

### 3. Per-minute burst rate (confirm the trigger)

```bash
sqlite3 ~/.cc-switch/cc-switch.db "
SELECT strftime('%H:%M', created_at, 'unixepoch', 'localtime') AS minute,
       count(*) AS total,
       sum(CASE WHEN status_code=429 THEN 1 ELSE 0 END) AS s429
FROM proxy_request_logs
WHERE provider_id='<provider_id>'
  AND created_at BETWEEN <ts_start> AND <ts_end>
GROUP BY 1 ORDER BY 1;"
```

Confirmed pattern: 477 → 1,016 → 691 req/min over three minutes; 429s begin immediately after the peak.

### 4. Failover queue state (the weak bench)

```bash
sqlite3 ~/.cc-switch/cc-switch.db "
SELECT p.name, p.in_failover_queue, p.is_current, p.sort_index, ph.is_healthy, ph.consecutive_failures
FROM providers p LEFT JOIN provider_health ph ON p.id=ph.provider_id AND ph.app_type='claude'
WHERE p.app_type='claude' ORDER BY p.sort_index;"
```

### 5. Who served traffic during the incident

```bash
sqlite3 ~/.cc-switch/cc-switch.db "
SELECT p.name, l.status_code, count(*) c
FROM proxy_request_logs l JOIN providers p ON l.provider_id=p.id AND p.app_type='claude'
WHERE l.app_type='claude' AND l.created_at >= <incident_start_ts>
GROUP BY 1, 2 ORDER BY c DESC;"
```

### 6. Latency baseline (is the provider just slow, or failing?)

```bash
# p50 first-token latency via OFFSET trick (sqlite has no percentiles):
sqlite3 ~/.cc-switch/cc-switch.db "
SELECT first_token_ms FROM proxy_request_logs
WHERE provider_id='<id>' AND status_code=200 AND first_token_ms>0
  AND created_at >= strftime('%s','now') - 2*86400
ORDER BY first_token_ms LIMIT 1 OFFSET (
  SELECT count(*)/2 FROM proxy_request_logs
  WHERE provider_id='<id>' AND status_code=200 AND first_token_ms>0
    AND created_at >= strftime('%s','now') - 2*86400);"
```

MGLM baseline: p50 ≈ 3.9s — high but normal for BigModel flash; latency is not the failure mode.

## Circuit breaker reference (proxy_config row per app_type)

Column order: `app_type, proxy_enabled, listen_address, listen_port, enable_logging, enabled, auto_failover_enabled, max_retries, streaming_first_byte_timeout, streaming_idle_timeout, non_streaming_timeout, circuit_failure_threshold, circuit_success_threshold, circuit_timeout_seconds, circuit_error_rate_threshold, circuit_min_requests, ...`

claude row (2026-09): retries=6, thresholds 20 / 2 / 90s, error_rate=0.9, min_requests=30. A high error_rate (0.9) + high min_requests (30) means the breaker is SLOW to trip on pure-rate-limit bursts — many real user requests eat 429s before protection kicks in.

## Fixes & prevention

1. **Quota providers (403) must be manually reset** — cc-switch does NOT auto-evict them from the failover queue, so they burn a retry slot every cascade. Reset weekly or drop from queue.
2. **Depth over breadth**: every provider with a valid key should have `in_failover_queue=1`; verify `sort_index` gives a sane order.
3. **Stagger cron fleets** — the burst trigger was jobs converging on the same minute (23:57–23:59). Offset schedules across a window instead of fixed boundaries.
4. **Tune claude breaker for rate-limit storms**: lowering `circuit_error_rate_threshold` (0.9 → ~0.5) trips earlier and sheds load sooner; raising `circuit_min_requests` avoids tripping on small samples.
5. **Health table can look clean after the fact** (`is_healthy=1, consecutive_failures=0` post-cooldown) — always reconstruct from `proxy_request_logs`, never trust current health state for incident analysis.

## sqlite gotchas hit in practice

- `created_at` is **unix seconds** here (10 digits); some installs use millis. Sanity-check magnitude before datetime math: `datetime(created_at,'unixepoch','localtime')` on a millis value yields NULL/1970s.
- `GROUP BY 1` / `GROUP BY <alias>` on the hour-bucket expression silently returned ONE all-NULL group in one terminal session; repeating the full `strftime(...)` expression inside GROUP BY worked. When a time-bucket GROUP BY returns a single NULL row, rewrite GROUP BY with the explicit expression before doubting the data.
- Filter `GROUP BY ... ORDER BY min(created_at)` to keep chronological bucket order.
