# As-Is 设计文档治理（终态文档 ≠ 档案）

> 来源：2026-08-22 Hermes 终态设计文档两轮用户纠偏实战（33 页档案混合版被否 → 5 页纯终态 → 设计实质回填 31/31）。
> 会话细节见 `references/hermes-design-doc-2026-0822.md`。

## When to Use

- 撰写或重构任何"终态/当前架构"设计文档（系统设计、集群总览、架构决策记录汇总）
- 用户反馈"这是档案不是终态"/"太长混入历史"/"内容都整合进去了没"
- 周期性更新设计文档（重大变更/债务清理/新融合波次之后）

## 两条核心纪律（用户两次纠偏的产物）

### 纪律一：终态文档只写现在时——历史叙事属于档案层

终态文档回答"现在是什么、怎么运行"，不回答"怎么演变来的"。以下内容**禁止**出现在终态文档正文：
- 演化史/时代叙事（"五时代""七波融合"时间线）
- 考古记录、决策台账（78 项决策之类）
- 评审记录、版本修订史（v1.0→v1.1 的 changelog）
- "此前如何、后来如何"的对比叙事

历史材料一律归 `research/` 等档案目录，终态文档头部一行指路即可。
**反例教训**：33 页"终态"文档 2/3 是历史 → 用户："那是档案而不是终态"。压缩到 5-6 页。

### 纪律二：剔除历史时不得误伤设计实质——回填义务

档案里很多设计以历史形式记载，但它们是**现行机制**，必须出现在终态文档。矫枉过正（纯叙事剔除）会把设计实质一起丢掉。
**回填方法**：机械覆盖率核对——从档案（各波方案/规则/评审）提取设计实质关键词清单（30+ 项），逐项 grep 终态文档，缺失即回填。
**实例**：剔除历史时丢了 9 项（[已移除] 领域铁律/分发红线/四类记忆架构/防退化四层防线/技能路由决策记录/平台过滤分级/推理分级/Knowledge PII 通道等），31 项核对全部补齐。

### 纪律三：设计阶段文档只写设计态——运行态议题一律出走

系统还没运转起来时，设计文档只回答「要建成什么、为什么这么建」。以下内容**禁止**进入正文，移台账（如 `research/*-pending-and-gap.md`）：
- 运行态势快照（「当前态势」多维表）
- 演进方向/优先级路线（P0-P2 roadmap）
- 风险与不确定性章节
- 一切「运行/未运行/系统未运转」的状态表述

配套判定纪律——**主要矛盾必须对照系统所处阶段**：给未运行的系统套「治理执行率 0%」当主要矛盾是**假矛盾**；真实主要矛盾是「尚未从设计态进入运行态」（编制存在 ≠ 运行存在），治理问题是它的投影。抓矛盾前先问：「这个系统现在处于什么阶段？第一性问题是内部问题，还是存在方式问题？」

**历史事故与设计分离**：形成系统过程中的运行 bug 叙事（「数月无人发现」「事故驱动」「最痛的教训」类措辞）不进设计文档；保留**结果数字**（备份覆盖盲区 58 vs 312、执行率 0%）作为设计依据——数字是决策的输入，过程叙事归台账。版本历史措辞（「2026-09-02 增补」「归档定稿」「实测」）统一为无时态表述或「数据快照」。

## 终态文档结构模板

```
一 系统定义（一句话 + 核心数字表，全部实机复验）
二 设计哲学（提炼条目，每条一句话，不带证据链叙事）
三 架构（分层：基础设施/身份组织/本体/调度能力/治理/质量验收）
四 运行机制（cron/watchdog/季度/按需 全节奏表，写实际 schedule）
五 债务与观察项（诚实清单：项/状态/下一步，附"已清"脚注）
六 扩展方式（维护契约：新增设计按层追加；档案实质变更须同步；变更后跑审计）
```

## 更新工作流

1. **变更触发**：重大落地/债务清理/新融合波次完成后，更新受影响小节 + 核心数字表
2. **数字一律重测**：引用率/profile 数/cron 数等用机械命令现算（audit 脚本/sqlite/ls），禁止沿用旧值
3. **覆盖率核对**：变更后跑关键词清单 grep（见纪律二），新增设计实质同步进清单
4. **纯度检查**：机械扫描历史词（时代/波次/考古/评审记录/修订史），命中必须是指路行才合法
5. **渲染与分发**：HTML+Chrome headless（--no-pdf-header-footer）+ pymupdf 验收，随后 git commit

## Pitfalls

- **🔴 删除实体编号体系必须全文扫悬空引用（2026-09-02 实锤）**：把决策编号体系（D1-D8）从设计文档 §三 删除后，§4.2 小节标题「（D1 落地）」、团队表「（D1/D2）」、术语表「§3.1 D3」等 **24 处悬空引用**残留在全文各处。修法：删除任何编号/实体体系后 `grep -n 'D[1-8]'`（或对应模式）全文扫一遍，逐处改指新坐标（如 §3.1 S1-S7）或删除。悬空引用比内容缺失更伤可信度——读者顺引用找过去什么都没有。

- **🔴 简洁 ≠ 术语墙 + 电报体（多轮用户纠偏合流）**：终态文档面向**无过程背景的读者**——「简洁」的对面是「黑话密度」和「说明书腔」。纪律：①每个术语首次出现配一句大白话解释（profile=AI 助手、fail-closed=出问题默认拒绝、watchdog=定时巡检脚本、TTVV=任务耗时统计）；每层标题带「干什么」副标题（基础设施层=跑在什么上）。②禁电报体句法——一句到底带多重括号嵌套、箭头串步骤（S1→S8）、代号指代（形态A/B/C/D），一律改写为一步一事的列表、代号换症状直述；每条纪律补一句「为什么」。③机械验收：非表格段 >500 字符必须清零——超长段即读者迷失点。改写铁律：信息零删减，只拆句、拉平括号、补 why；术语本身保留（首现解释即可）。维护契约写作纪律：禁止默认读者有背景。
- **正文/附录分工——领域明细进附录，正文留机制锚点**：岗位级配置数字、领域知识库构成、领域流水线细节不进正文，入附录；正文只留机制层面引用（「明细见附录 B」）。判定线：机制证据（隔离实测/路由机制/名册门禁/多域共用的管道机制）留正文，领域专属明细入附录。
- **docsync 锚点不可移动**：`<!-- gap-closed:<id> -->` 注释是自动回写的幂等键——重组/移动章节时原位保留，挪动会破坏防重与审计对账。
- **开头区按逻辑链排**：头部引用块按「一句话理念→系统是什么→体系位置→文档边界→写给谁看→修改纪律」排序，一条线读完不回跳；不按堆积式声明罗列。
- **「已有数据」声明必须验证动态数据源**：静态文件存在 ≠ 数据存在。cron 执行史可能只有 1 天、kanban 可能根本没有某类事件——写"从已有数据提取 X 指标"前先 sqlite count 实测（本坑来自融合方案蓝军评审：σ band 建立在 1 天样本上）。
- **单点事实源冲突**：给终态文档/规则补内容时，先查该事实是否已在别处定义（卡字段/共享规则），重复定义违反单一事实源——宁可加指针不加复制。
- **版本号堆积**：终态文档不要带 v1.0→v1.1→v1.2 修订史正文；一行"Final + 日期"即可，修订史归 git log。
- **数字口径必须注明**：平均值的分母口径（哪些 profile、简单还是加权）、计数口径（find 的波动范围）写进表格备注，否则评审必抓。

## 跨文档一致性审计（本次实战新增，最高频漏点）

> 同一系统被多份文档描述（终态设计文档 / 统一治理框架 / 一致性报告）时，**数字/实体/层级必须完全自洽**——光"文档内部无悬空"不够，文档之间也会漂移。

### 🔴 双源矛盾必查（例：board 数）
终态设计文档写"7 块看板"，统一治理框架写"27 profile × 9 board"——**后者错**（实机 7 块 board）。修法是**以实机为准、挑错文档改对**，不是两份都改。机械配方见 `references/doc-impl-consistency-audit.md`。

### 审计四线（缺一线即漏）
1. **文档↔实现**：文档声称的路径/脚本/cron/数字逐一 `ls`/`find`/`sqlite`/`python` 复验
2. **文档↔文档**：多份文档对同实体计数/命名必须一致（board 数、profile 数、skill 数、cron 数）
3. **引用↔存在**：文档/SOUL 引用的 `.md` 文件名、profile 名、skill 名必须真实存在（见 `references/doc-impl-consistency-audit.md` 配方 B/C）
4. **目录承诺↔结构**：文档声称的目录树（如 knowledge 五层）必须对齐实际 `find`

### 修复优先级（不可乱序）
先修**真实实现缺口**（缺文件/补丁/接线）→ 再修**文档↔文档矛盾**（单一事实源，以实机为准）→ 最后修**文档↔实现数字漂移**（文档对齐实机；实机有错则先修实机）。任何"修复设计文档"任务，完成判定必含"已跑机械审计且零悬空/零漂移"。
