# 设计文档审查收尾（Design-Doc Closure）

用于多轮设计文档重构后的全章复核、完成判定和安全提交。它补充结构重构技能：前者规定怎么写，本 skill 规定怎样证明已经完成并把正确文件提交出去。

## Always-on rules

- 用户要求“每个章节都检查”时，按全文目录逐节复核；不能用最近修改的小节通过，替代全章验收。
- 算法/机制图先于解释文字；实例图只能放在主算法之后。检查顺序必须同时验证正文顺序、图号顺序和跨章节引用。
- 不把“文件已修改”当作“任务已完成”。完成判定至少需要：结构检查、内容保全、格式扫描、diff 范围核对和提交后复读。
- 工作区可能含其他任务改动；提交时只 `git add <目标文件>`，禁止用全量 `git add .` 把无关文件带入提交。
- 目标文件提交后必须从 `HEAD:<目标文件>` 重新读取并复跑关键探针；提交命令返回 0 只是 Git 接受了对象，不证明内容满足验收标准。

## Procedure

1. **建立验收面**
   - 读取当前文档目录和任务验收标准。
   - 列出每章的结构链：`章节回答什么 → 总图/机制图（若有）→ 分步解释 → 判定与边界`。
   - 标记算法图、实例图、跨章节引用和需保全的关键机制句。

2. **做全章机械扫描**
   - 检查 Mermaid 围栏成对：开闭数量一致。
   - 检查旧编号、旧归属词、旧图号和悬空 `§` 引用。
   - 检查 U+FFFD、畸形 Markdown 表格行（尤其 `^||`）、重复标题和明显截断。
   - 对关键内容做计数或逐项探针，不凭“看起来完整”判断。

3. **核对变更范围**
   - 运行 `git status --short -- <目标文件>` 和 `git diff --check -- <目标文件>`。
   - 用 `git diff --stat -- <目标文件>` 与任务范围比对；工作区总 diff 很大时，不把总 diff 误当成本轮改动。
   - 若有快照，逐行核对删除内容：每条丢失行必须能解释为有意重写、迁移或删除。

4. **修复后再判定完成**
   - 发现格式残留（如多一个表格前导管道）先修复并重跑全量扫描。
   - 只有所有验收项都有机械证据时，才向用户确认“已完成并提交”；未完成则继续修复，不提前提交。

5. **安全提交**
   - 先确认目标文件确实是本轮要提交的文件。
   - 使用 `git add -- <目标文件>`，再提交明确的单一主题 message。
   - 若 Git 报 `index.lock`：先检查是否存在活跃 Git 进程；仅当锁文件确认是陈旧文件时删除，再重试一次。不要无条件删除锁，也不要在锁存在时反复提交。

6. **提交后验证**
   - 用 `git show --stat --summary HEAD` 确认提交只包含目标文件。
   - 用 `git show HEAD:<目标文件>` 重新读取提交版本，复跑 Mermaid、旧编号、乱码、表格和关键章节探针。
   - 用 `git status --short -- <目标文件>` 确认目标文件干净；若仍有差异，说明提交前后还有未提交改动，不能宣称收尾完成。

## Failure boundaries

- **完整性问题**：先从磁盘和 Git 版本对账，不能凭编辑器显示判断内容丢失；编辑器旧缓冲不是回填依据。
- **格式问题**：局部补丁后仍要跑全章扫描，因为后续大段替换可能重新覆盖已修复的导语或图块。
- **锁问题**：锁文件是并发状态信号，不是可以直接绕过的提示；先辨别活跃进程和陈旧锁。
- **提交范围问题**：目标文件 clean 只代表该文件无未提交差异，不代表整个工作区 clean；汇报时分别说明两者。

## Output contract

收尾汇报只给三类证据：

1. **交付**：目标文件、提交哈希、提交主题。
2. **验证**：关键机械探针结果和目标文件工作区状态。
3. **风险**：仍存在的未提交无关改动或未验证项目；没有风险时明确写“无”。

不要把“尝试过的命令列表”冒充完成证据，也不要在提交失败后给出成功式汇报。
