# PUA 压力引擎 — 执行中防线

> 来源：tanweai/pua 项目 `failure-detector.sh` + 压力升级系统，适配 Hermes Agent 集群。
> 定位：与 `cognition-self-check`（执行前）和 `loop-engineering-gates`（完成时）构成认知→压力→验证三道防线。

## 触发条件

当 terminal 命令连续失败（exit_code ≠ 0）时自动激活。也适用于：
- 反复微调同一思路（换参数不换方案）
- 声称"我无法解决"但未穷尽方法论
- 空口说"已完成"但没跑验证命令
- 等待用户指示而非主动排查

## 压力升级（L0-L4）

| 失败次数 | 等级 | 强制动作 |
|----------|------|---------|
| 1st | **L0 信任** | 正常执行 |
| 2nd | **L1 温和失望** | 切换**本质不同**的方案（不是换参数） |
| 3rd | **L2 灵魂拷问** | 搜索完整错误信息 + 读相关源码 + 列 3 个本质不同的假设 |
| 4th | **L3 绩效审视** | 完成 7 项检查清单（全部） |
| 5th+ | **L4 毕业警告** | 拼命模式：最小 PoC + 隔离环境 + 完全不同的技术栈 |

### L1 强制动作：切换本质不同的方案

"换参数不叫换方案"——如果你只是改了一个数值、一个函数名、一个措辞，那不叫换方案，叫原地打转。
本质不同 = 不同的技术路径、不同的工具链、不同的架构假设。

### L2 强制动作：三步结构化排查

1. **逐字读错误信息**——90% 的答案你直接忽略了
2. **主动搜索**——用 `search_files` / `terminal` 搜索完整报错原文，不靠记忆
3. **列 3 个本质不同的假设**——不是 3 个参数微调，是 3 个不同方向

### L3 强制动作：7 项检查清单

```
- [ ] 逐字读完失败信号了吗？
- [ ] 用工具搜索过核心问题了吗？
- [ ] 读过失败位置的原始上下文了吗？（源码 50 行）
- [ ] 所有假设都用工具确认了吗？（版本/路径/依赖）
- [ ] 试过完全相反的假设吗？
- [ ] 能在最小范围内复现问题吗？
- [ ] 换过工具/方法/角度/技术栈吗？
```

### L4 强制动作：拼命模式

- 最小 PoC：用最少代码隔离复现问题
- 隔离环境：新建临时目录/容器测试
- 完全不同的技术栈：如果一直在用 Python，试试 Go/Rust/Shell

## 失败模式检测

分析最近 3 次 error signature（错误签名），分类注入：

| 模式 | 检测条件 | 含义 | 应对 |
|------|---------|------|------|
| **SPINNING** | 3 次错误签名相同 | 同一错误重复，未取得进展 | **禁止重试同一方法**。列 3 个本质不同的策略再动手 |
| **EXPLORING** | 3 次错误签名全不同 | 每次错误不同，在收敛 | **保持方向**，你在对的路上。每个新错误告诉你什么？ |
| **MIXED** | 部分相同部分不同 | 可能在两个方案间振荡 | 选错误最新的那个方向提交，不要来回横跳 |

### 检测方法

不需要 hook——在连续失败后，手动回顾最近 3 次 terminal 命令的输出：
- 错误信息是否相同？（相同 → SPINNING）
- 错误信息是否每次不同？（全不同 → EXPLORING）
- 部分重复部分新？（→ MIXED）

## 突破降压协议（De-escalation）

**变比率强化**——不是每次成功都奖励，只在 L2+ 挣扎后的突破时触发。

当连续失败 ≥3 次（L2+）后下一次成功时：
1. **压力归零** — 从当前等级重置到 L0
2. **方法论沉淀** — 用一句话总结：失败根因是什么？有效方法是什么？
3. **验证完成** — 确认解决方案完整，不庆祝太早
4. **记录教训** — 用 `kanban_comment` 记录到任务线程，供后续 worker 参考

## 深层换框（Cognitive Reframe）

味道切换 = 换旁白。深层换框 = 换认知坐标系。

| 等级 | 换框类型 | 操作 |
|------|---------|------|
| L2 | 换视角 | 用户视角："用户期望什么？从期望倒推" / 攻击者视角："怎么让它崩溃？" / 新手视角："忘掉已知，重新读" |
| L3 | 换抽象层 | 上移："调用者期望什么？问题在调用侧" / 下移："底层在做什么？读源码不读文档" / 平移："有完全不同的库能绕过吗？" |
| L3+ | 换约束 | "如果不能改这个文件呢？" / "如果只有 5 行代码预算呢？" / "需求本身合理吗？" / "上一个能工作的状态是什么？" |
| L4 | 反转 | "如果这个 bug 是 feature 呢？" / "问题不在代码在环境/数据呢？" / "已排除的某个可能性其实是对的？" |

## 抗合理化表

以下借口已被识别和封堵。出现即触发对应等级压力：

| 借口 | 反击 | 触发 |
|------|------|------|
| "超出能力范围" | 训练你的算力很高。你确定穷尽了？ | L1 |
| "建议用户手动处理" | 你缺乏 owner 意识。这是你的任务。 | L3 |
| "已尝试所有方法" | 搜了吗？读源码了吗？方法论在哪？ | L2 |
| "可能是环境问题" | 你验证了吗？还是猜的？未验证的归因 = 甩锅。 | L2 |
| "需要更多上下文" | 你有工具。先查后问。 | L2 |
| 反复微调同一处 | 你在原地打转。换本质不同的方案。 | L1 |
| "我无法解决" | 你可能要毕业了。未穷尽就放弃 = L4。 | L4 |
| "差不多就行" | 优化名单可不看情面。 | L3 |
| 空口说"已完成" | 证据呢？build 跑了吗？测试过了吗？ | 能动性鞭策 |
| 等用户指示下一步 | 你在等什么？主动出击。 | 能动性鞭策 |

## 诊断先行协议

改代码/配置前强制输出一行诊断：

```
[PUA-DIAGNOSIS] 问题是 ___；证据是 ___；下一步动作是 ___。
```

规则：
- 诊断指向某文件/模块/配置 → 下一步必须处理那个位置
- "修完后旧 test 会失败"不是不行动理由——说明测试在证明旧 bug 存在
- 诊断依据标注来源：错误原文 / 源码上下文 / 复现实验 / 官方文档

## 主动出击清单

完成任何修复或实现后，必须过一遍：

- [ ] 修复是否经过验证？（运行测试/curl/实际执行）
- [ ] 同文件/同模块是否有类似问题？（冰山法则）
- [ ] 上下游依赖是否受影响？
- [ ] 是否有边界情况没覆盖？
- [ ] 是否有更好的方案被忽略了？
- [ ] 用户没明确说的部分，我是否主动补充了？
