# Cognition Self-Check — 统一认知自检框架

> 核心原则：**机制存在 ≠ 灵魂存在**。规则入库不等于机制生效，必须靠机械自检把认知偏差曝光、靠压力升级把执行卡顿强行破局。

---

## 一、决策场景 ↔ 认知框架映射表（10大场景）

| 决策场景 | 适用认知框架 | 核心自检问题 | 机制落地锚点 |
|----------|-------------|-------------|-------------|
| **任务拆解** | MECE原则 + 第一性原理 | 子任务是否互斥且穷尽？ | kanban_create 时 body 写验收标准(frozen) |
| **看板路由** | 模式识别 + 贝叶斯更新 | 是否被第一个词锚定？ | 智能路由三级判定表（工具调用/文件写入量化） |
| **Worker分配** | 比较优势 + 能力圈 | 是否在worker能力圈内？ | assignee 存在性校验 + config.yaml clearances 匹配 |
| **优先级判定** | 艾森豪威尔矩阵 | 紧急vs重要是否混淆？ | P0-P3 优先级映射 + attention-adapter 梯队排序 |
| **风险评估** | 逆向思维 + Pre-mortem + 系统思维 | 如果错了后果是什么？长期反噬看清了吗？ | risk-register Top3 强制审视 + action-risk 可逆性分级 |
| **跨看板协调** | 系统思维 + 反馈循环 | 是否遗漏了联动效应？ | 动态工作流 YAML + WaitForHuman 门控 |
| **需求澄清** | 苏格拉底式提问 | 是否质疑了隐藏预设与隐性诉求？ | rd-clarify §2.3 清单式找缺口+诘问式找预设 |
| **调研/报告验收** | 幸存者偏差审查 + 逻辑剃刀 + 激励审计 | 谁受益？结论是否立场倾斜？ | adversarial-review-lens 多lens并行 + incentive-audit |
| **数据输出** | 事实 vs 虚构 | **数据是否来自真实工具调用？** | worker-completion-independence-verification 机械验证 |
| **完成声明** | 证伪主义 | **是否已验证产出？不信任自述** | kanban_complete 需 verification 字段 + 证据分级 |

> 双锚格式：框架列引 cognition-lattice 可解析条目（知识锚），机制列引具体 skill 章节（执行锚）。

## 二、决策偏差自检清单（8项，每次决策后必过）

```markdown
## 决策偏差自检（✓ 通过 / ✗ 需复盘）
- [ ] 1. 确认偏误 — 是否只关注支持当前判断的证据？
- [ ] 2. 锚定效应 — 是否被消息第一个词或初始印象锚定？
- [ ] 3. 可得性启发 — 是否因最近处理过类似任务而偏向某路由？
- [ ] 4. 规划谬误 — 是否低估了任务复杂度？
- [ ] 5. 沉没成本 — 是否因已投入而坚持错误方向？
- [ ] 6. 框架效应 — 消息措辞是否影响了客观判定？
- [ ] 7. 代表性启发 — 是否忽略了基率？
- [ ] 8. 过度自信 — 是否需要设置 triage 而非直接路由？
```

**执行方式**：决策后在 kanban_comment 或内心独白逐项打勾。有 ✗ 者，必须记录复盘结论再继续。

## 三、压力升级自检（执行中防线，L0-L4）

> 来源：`devops-worker/pua-pressure-engine`（tanweai/pua failure-detector + 压力升级系统）。
> 与 cognition-self-check（执行前）、loop-engineering-gates（完成时）构成**三道防线**。

### 触发条件
- terminal 命令连续失败（exit ≠ 0）
- 反复微调同一思路（参数调整不算）
- 空口说完成未跑验证

### 升级动作表

| 连败 | 等级 | 名称 | 强制动作（必须执行，不可跳过） |
|------|------|------|-------------------------------|
| 1st | L0 | 信任 | 正常执行 |
| 2nd | L1 | 温和失望 | **切换本质不同方案**（换技术路径/工具链/架构假设，换参数不算） |
| 3rd | L2 | 灵魂拷问 | ① 逐字读完整报错 ② search_files 搜完整报错 ③ 读失败源码 50 行 ④ 列 3 个本质不同假设 |
| 4th | L3 | 绩效审视 | 7项清单全勾：逐字读信号/搜核心问题/读原始上下文/工具确认假设/试相反假设/最小复现/换技术栈 |
| 5th+ | L4 | 毕业警告 | **拼命模式**：最小 PoC + 隔离环境 + 完全不同技术栈；仍败 → `kanban_block` 带全部尝试记录 |

### 失败模式判定
- **SPINNING**（同思路重复，仅换参数/提示词）→ 禁再试，直接升级
- **EXPLORING**（每次新方向：换库/换架构/换假设）→ 可继续，但需记录尝试轨迹

**机械化判定**：每次工具调用失败或重试前，在 kanban_comment 记录 `pressure_level: L<N> / SPINNING|EXPLORING / 已尝试: [...]`。

## 四、强制加载触发条件

**以下场景必须先 `skill_view('cognition-self-check')` 再行动：**

1. **任何 Gateway 消息执行前**（与各 profile SOUL 认知自检强制块联动）
2. 任务路由判定、Worker 分配、优先级判定、跨看板协调决策
3. kanban_block / kanban_request_changes 前
4. 重型任务合并报告前
5. 连续 2 次工具调用失败后

## 五、集成指引（各 profile SOUL 嵌入方式）

**现状诚实声明（2026-09-08 机械排查）**：本 skill 实际使用面 = orchestrator + platform-ontology-curator（2/47 SOUL 引用）。版本记录中「下沉到所有 worker」为不实陈述，已修正。worker 侧未下沉的原因：8 项偏差清单与压力升级留痕均无机械校验通道，批量下沉只会产生装饰性引用。

在每个 worker profile 的 SOUL.md 中添加（**仅当为其配置机械留痕时才做**）：

```markdown
## 认知自检强制块
> **执行任何任务前必须先加载并自检**

```bash
skill_view('cognition-self-check')
```

然后按上述映射表选择框架 → 决策 → 过 8项偏差清单 → 执行中按压力升级表动作。
```
