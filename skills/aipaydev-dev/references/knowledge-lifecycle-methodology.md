# 知识生命周期方法论（Knowledge Lifecycle）

> 来源：京东技术公众号《拆解京东海博 AI-Native 落地保障：海博团队 AI 知识库能力建设》（2026-09-24，作者 徐双双，[链接](https://mp.weixin.qq.com/s/rNox2XcWvgt2zdwGlVmfAg)）。组织级 AI 知识库实践：知识生产（历史代码结构化）→ 消费（按需读取管线）→ 沉淀（蒸馏回库）→ 防腐（过期治理）全生命周期，附 AB 实验对照。
> 证据分级：OKF 规范要点=B（[Google Cloud 官方博客](https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing) 一手直查，2026-09-24 核验）/ 机制描述=B（官方公众号自述）/ AB 实验数字与文档产量=C（文章自报，不可外部复核，引用时须标注"文章自报"）。
> 纪律：守决策 40 吸收边界——只吸收机制，不引依赖、不搬装配叙事（上游 build-* 技能、文档产量流水账、京东内部栈 JSF/JMQ/京ME 均不进载体）；守决策 26/27——门禁 55 不增、复杂度预算不增。各环节的动作协议统一在本文定义，不新增门禁或结构。

## 一、定位：把"上下文经营"拆成生产、消费、沉淀、防腐四阶段协议

swarm-yuan 的总闭环（探查→生成→执勤→指纹感知→局部更新）覆盖知识全生命周期；各环节的动作协议统一在此定义为四阶段协议，落点见各节：

| 段 | 上游机制 | swarm-yuan 既有落点 | 本节定义 |
|----|---------|--------------------|-----------|
| 生产 | 知识编译前移到维护期；只写可查证事实 | 生成流程 Step 4 探查（exploration-guide §D）；溯源三级标记（memory-persistence.md §知识溯源） | 前端页面知识三角；待确认事项清单回填协议 |
| 消费 | 6 步读取管线（摘要优先/追链/分组注入） | 开发工作流 ②探查（先查配方再查地图） | 读取协议六步化增注 |
| 沉淀 | 两源蒸馏 + 人工确认门 | 生成流程 Step 12 memory-writeback；问题沉淀三载体；mark-active 三关核验 | 三维蒸馏对账注记 |
| 防腐 | 生命周期四步 + 过期三态 | 指纹 --diff；reference-manual last-good 红线（骤降 >50% 拒写） | 过期三态处置（续期/降级标注/归档） |
| 验证 | AB 实验对照（带库 vs 裸代码） | verifier 司法理念 | 目标技能价值对照法 |

## 二、生产段：编译前移 + 诚实抽取 + 页面三角

**论断：瓶颈在知识生产，不在检索。** 上游对向量 RAG / GraphRAG / Agentic Search 三范式的裁决是"重心都在运行时怎么检索得更准，但真正的卡点在知识源头"——期望知识结构化、绑定关联、精确定位到 file:line、随代码更新。对策是把"知识编译"从运行时前移到维护期：入库时就消化、重写、组织，运行时只剩导航+摘录。swarm-yuan 的生成流程 Step 4 探查期一次生成、开发工作流只消费不重构，正是同一判断的既有实现（理念层"先认识，再行动"的外部佐证）。

**抽取纪律（与溯源三级标记同构）**：只写能从代码查证的事实，查不到的宁可留白绝不编造；读不懂的业务语义显式标记交人工补全，再抽样核对纠错。swarm-yuan 对应物：extracted / inferred / ambiguous 三级标记（memory-persistence.md）+ 多源矛盾裁决序（exploration-guide）。**待确认事项清单回填协议**：裁决序走到"并存标注"仍不能定的项，集中落到 `notes/` 待确认事项清单（等懂业务的人回填，回填后按裁决序重新转正），不允许散落在各文档的"待验证"字样里自然蒸发。

**前端页面知识三角**：前端知识生成的三个必答——操作（页面有哪些按钮/入口）、调用（每个操作调哪些 API、**真实入参在调用点反推**——前端常只透传一个参数对象，光看 API 定义抽不出字段）、权限（什么角色/条件可见可点、无权限如何降级提示）。微前端另需单独理清主子应用拆分与通信。落点：exploration-guide「Node.js / 前端」探查要点。

## 三、消费段：6 步读取协议

上游 `/okf-knowledge-read` 把"读知识库"协议化为六步，每步有明确的收敛动作。开发工作流 ②探查的通用读法即此六步协议（基础指引：先查 recipes 配方与 §A 同类功能，再按 reference-manual 地图定位；落点：SKILL.md 第五层开发工作流 ② + template-spec workflow 节点②）：

| 步 | 动作 | swarm-yuan 映射 |
|----|------|----------------|
| 0 | 识别意图：问的是业务概念 / 服务契约 / 数据流 / 架构决策？ | 决定先查 recipes（概念/契约）还是边集（数据流）还是特征卡（决策） |
| 1 | 发现知识库：定位目录，读 index + 类型注册表 | reference-manual 地图 + 构件/接口/store 表的 § 锚 |
| 2 | 匹配概念：粗筛（grep）+ 精筛（语义）锁定条目 | relations-query.sh 按实体/字段反查 + 地图定位 |
| 3 | 加载文档：**摘要优先，不够再读全文** | 表格行优先；表格不答再下钻源码 file:line |
| 4 | 追踪链接：沿关联补齐（实体→服务→数据流） | relations.jsonl 边集一跳/两跳 |
| 5 | 分组注入：按类型分组，注入上下文 | spec §24 架构映射按层归位 |

核心收益是 token 经济：摘要优先 + 分组注入避免"一次性加载几百份文档撑爆上下文"，与 3 层渐进式检索（memory-persistence.md）同一纪律。

## 四、沉淀段：两源蒸馏 + 三维对账 + 人工确认门

上游沉淀协议：需求完成后两个知识来源——**master 代码（最终事实）+ 过程产物（spec/TRD/沟通沉淀）**——一起蒸馏回库；蒸馏后**不直接落库，先人工确认再合并**，AI 不擅自覆盖，人把最后一关。三维蒸馏对账（业务/项目知识、开发经验、人维度经验）与 swarm-yuan 既有通道的对齐：

| 上游蒸馏维度 | swarm-yuan 落点 |
|-------------|----------------|
| 业务/项目知识（规则、决策、影响面、术语、边界） | reference-manual 单条更新 + 特征卡演化 |
| 项目开发经验（坑、根因、可复用方案、约定） | 问题沉淀三载体（清单/配方/规则） |
| 人维度经验（选型背景、评审反馈、协作约定） | decisions.jsonl 留痕（trace-log --decision 五要素） |

人工确认门的 swarm-yuan 同构物是 `--mark-active` 三关核验：AI 产出的知识须经真实性抽样才激活，未核验的知识不进执勤面。

## 五、防腐段：过期三态处置

上游生命周期四步：建档（每条知识绑负责人）/ 蒸馏反哺 / 冲突确认 / **过期治理**。过期治理按知识置信度三态：有效→续期；部分失效→**降级**（标注后保留待重探查）；完全失效→**归档**（不删，可追溯）。

swarm-yuan 反馈回路的两态基线：正常→单条更新；骤降 >50%→last-good 红线拒写保留旧清单。红线防的是探查失败污染，三态防的是**条目级陈旧**——两者正交。反馈回路并入三态处置：指纹 --diff 感知变化后，受影响条目按核实结果三处置——仍成立→更新（续期）；证据源已变但新证据不足→条目标注降级（degraded，引用时须声明待核）；证据源已消失→移入归档区（reference-manual 末尾已归档节或 notes/，不物理删除，保留 valid time 历史）。与双时态注记（exploration-guide 矛盾裁决节）同构：归档不是抹除历史有效性，是关闭 recorded time。

## 六、精准回归：锚点反查分级

上游精准测试：用例挂业务锚点与代码锚点（接口/实现文件/表），git diff 进来后四路反查，输出分级回归范围——**必跑**（diff 文件 ⊆ 用例锚点直接命中）/ **应跑**（改了接口→链路定位→反查引用它的用例；改了表/topic→反向视图→用例）/ **建议跑**（命中接口所属业务链→拉出整链用例）。价值双面：只跑真正相关的（精准）+ 靠反向索引与链路扩散兜住"改 A 表却影响 B 接口"的隐蔽影响面（不漏）。

swarm-yuan 落点：spec §19 测试左移的"回归范围"字段携带分级推导协议——以 relations.jsonl 边集为反查底座（import 边=直接命中、接口/实体反查=应跑、配方可归链=建议跑；**字段改名若暴露于 API JSON 即属接口命中**——含前端调用点/fixtures，契约面同口径），`--impact` 的 diff 消费方反查（>3 warn）是它的门禁侧镜像。分级是 AI 判断引导协议，不新增 check_*（决策 27）。

## 七、粒度决策与 AB 佐证

**粒度决策**：上游采纳 OKF（[Open Knowledge Format](https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing)，Google Cloud 2026，v0.1 开放规范；京东文章转述）——一概念一 Markdown 文件、YAML 头 `type` 唯一必填、index.md 渐进披露 + log.md 变更追溯、跨概念普通链接成图。"宽容消费"（字段不全/链接失效降级为普通文档不报错）为文章转述，官方博客未明示（仅 type 必填隐含）。swarm-yuan 的裁决：目标技能 references 走**单文件地图模式**（reference-manual 表格化 + § 锚路由）而非 OKF 原子文件树——单仓研发场景下地图模式的计数核验（inventory-verify 表锚对账）与 last-good 红线都建立在表格行上，原子化会拆断这两条既有执法线。OKF 粒度作为**知识组织光谱的另一端**登记：当项目知识长到单文件地图撑爆按需读取（摘要优先失效）时，才考虑按 OKF 原子化拆分，且须保住计数核验与红线两条执法线。

**AB 佐证**：上游验证法——同提示词、同需求、同仓、同方法论，两组子代理并行（A 用知识库 / B 仅代码），度量耗时/上下文来源/可溯源性。文章自报：A 组 542s vs B 组 967s（≈44% 提速），A 组 8 篇结构化知识+3 个源码文件 vs B 组 16 个源码文件，且 A 组多发现两个隐藏阻塞点（跨仓消费端缺自动重试、配置白名单门禁静默失败）。数字不可外部复核（C 级），但**方法本身**是目标技能价值验证的现成范式：同一需求"带目标技能 vs 裸 AI"对照，可复用于 swarm-yuan 自身的有效性叙事。
