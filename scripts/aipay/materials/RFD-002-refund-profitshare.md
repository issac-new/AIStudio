# RFD-002 收单商户小程序收银台售后与分账需求说明书

> 需求编号：RFD-002　｜　类型：增量需求（基于已交付的 RFD-001 多端小程序支付收银台）
> 提出方：某连锁茶饮品牌商户（收单商户）＋ 平台运营
> 转办：BA（bella）→ 产品（fanfan）
> 一句话需求：在已上线的收银台（v1.0.0-cashier）之上，增加**退款**与**商户分账**两项
> 资金能力，双端（微信小程序 / 支付宝小程序）一致可用，且不产生资损。

## 1. 背景

RFD-001 已交付统一下单、双端调起、回调验签、超时关单与对账支撑，商户接入后日均
交易约 4 万笔。上线两个月后商户提出两类刚性诉求：

1. **售后退款**：门店偶发制作失败、原料缺货、消费者临时取消，需按订单整单或部分
   退款；目前只能走人工线下打款，商户财务与平台对账两侧都不闭环。
2. **分账**：商户采用"总部统一收款 + 门店/加盟商分成 + 平台服务费"的经营结构，
   需要在交易确认后把钱按约定比例分给门店主体与平台，并能在争议时冻结分账。

商户明确要求：退款与分账必须**原路退回 / 实名接收方**，任何一笔钱都不能出现"系统
记的数与渠道实际到账不一致"。

## 2. 目标

1. 支持整单退款与同一笔支付的多次部分退款，退款结果可查、可对账、可重放通知。
2. 支持按比例向多个接收方分账，支持分账冻结与解冻，未分账余额在时窗到期后自动归还商户。
3. 双端一致：同一套 BFF 接口覆盖微信与支付宝两渠道，渠道差异在 csw-channel-* 内收敛。
4. 资金安全：任何退款/分账请求在受理前完成金额与状态校验，超限、重复、跨单一律拒绝
   并可追溯。

## 3. 依据的公开技术手册（合规引用）

- 微信支付（财付通）商户平台开发文档（pay.weixin.qq.com 文档中心）：
  - 退款申请：`POST /v3/refund/domestic/refunds`（`out_refund_no` 幂等；
    `amount.refund` / `amount.total` / `amount.currency`；可传 `notify_url`）
  - 退款查询：`GET /v3/refund/domestic/refunds/{out_refund_no}`
  - 分账：`POST /v3/profitsharing/orders`（`receivers[]`：`type=MERCHANT_ID` /
    `account` / `amount` / `description`；`unfreeze_unsplit` 控制剩余解冻）
  - 分账查询：`GET /v3/profitsharing/orders/{out_order_no}`
  - 解冻剩余资金：`POST /v3/profitsharing/orders/unfreeze`
  - 回调验签：微信支付平台证书 + `Wechatpay-Signature` 头（与 RFD-001 一致）
- 支付宝开放平台文档（opendocs.alipay.com）：
  - 退款：`alipay.trade.refund`（`out_request_no` 幂等，支持多次部分退款）
  - 退款查询：`alipay.trade.fastpay.refund.query`
  - 分账/结算：`alipay.trade.order.settle`（`royalty_parameters[]`：`trans_out` /
    `trans_in` / `amount`；`settle_no` 关联）
  - 分账查询：`alipay.trade.order.settle.query`
  - 签名 RSA2（SHA256WithRSA），验签使用支付宝公钥
- 平台侧约束（以渠道正式开通结果为准，本文按现行公开文档默认值描述）：
  - 微信分账默认最高分账比例 30%，且需商户号预先添加分账接收方关系；
  - 微信分账时窗自订单支付成功后起算，逾期未分金额默认自动解冻给商户；
  - 支付宝交易分账/结算能力需签约对应产品，分账比例上限与产品码相关。

## 4. 角色

| 角色 | 说明 |
|---|---|
| 商户运营 | 配置分账规则（接收方、比例）、发起退款、查看售后与分账结果 |
| 门店 / 加盟商 | 分账接收方，需已完成渠道侧接收方关系建立 |
| 消费者 | 在商户小程序内查看退款进度与结果 |
| 商户系统 | 调用 BFF 退款/分账接口，接收结果通知 |
| 平台运营 / 财务 | 核对资金台账，处理不平与争议冻结 |

## 5. 功能需求

### F1 退款申请与受理（BFF → pay-core）
- 入参：`merchantId + outTradeNo + outRefundNo + refundAmount + reason + operator`。
  `outRefundNo` 由商户侧生成并作为幂等键。
- 受理前校验：原支付单存在且处于 `SUCCESS`；`refundAmount` ≤ 可退余额；同一
  `outRefundNo` 重复提交返回首次结果（不重复调渠道）。
- 部分退款支持同一支付单多次发起，累计退款额不得超过支付总额（含在途未终态金额）。
- 退款单状态机：`INIT → REFUNDING → SUCCESS / FAILED / ABNORMAL`（ABNORMAL = 渠道
  结果不明，须人工或定时查证转终态）。
- 原路退回：退款出账账户与渠道与原支付单一致，不允许指定替代收款方。

### F2 渠道退款适配
- csw-channel-wechat：V3 退款申请、退款回调验签与解密、退款查询；金额单位为分。
- csw-channel-alipay：`alipay.trade.refund`、退款查询；金额单位为元（两位小数），
  `out_request_no` 承载幂等；同一笔交易多次部分退款。
- 两渠道金额单位、幂等字段名、通知报文结构差异**必须在本层收敛**，BFF 对外契约保持
  RFD-001 §5.3 冻结的 snake_case 风格不变。
- 渠道通知丢失时以主动查证兜底；查证与通知到达同一结果时必须幂等收敛，不得二次入账。

### F3 分账（比例、时窗、冻结解冻）
- 商户可按订单配置多个接收方（门店 + 平台服务费），每个接收方给金额或比例。
- 受理前校验：分账总额 ≤ 订单可分账金额；接收方已在渠道侧建立关系；比例合计 ≤ 100%
  且 ≤ 渠道允许上限。
- 支持先冻结后分账（争议订单）、以及解冻剩余资金把未分部分归还商户。
- 分账须在渠道允许的时窗内完成；逾期未分金额的归属与自动解冻行为需与渠道文档一致，
  并在系分中显式写明本系统看到的终态。

### F4 售后与分账的资金一致性
- 每笔退款、每笔分账生成独立资金流水记录，与原支付单、渠道流水号双向可追。
- **已部分分账的订单再发生退款时，可退余额的口径必须先定义清楚**（是否需先向接收方
  回退分账 / 是否允许商户账户垫资），否则存在资损风险。
- 日终对账：渠道账单与本系统流水按订单/退款/分账三个维度核对，不平即告警并可锁定
  该商户的出账类操作。

### F5 小程序端售后入口（双端）
- 消费者在订单详情页可发起/查看退款进度（展示受理中、成功、失败三种状态与原因）。
- 微信端与支付宝端使用同一 BFF 查询接口，宿主端差异仅在展示层。

## 6. 非功能需求

| 维度 | 要求 |
|---|---|
| 幂等 | 退款、分账均以商户侧请求号为幂等键；重复与并发提交不产生二次资金变动 |
| 一致性 | 资金流水与状态机变更同事务或最终一致并可查证，禁止"先返回成功再落库" |
| 防资损 | 金额、状态、时窗、比例四项前置校验缺一不可；超限直接拒绝并留痕 |
| 合规 | 退款原路退回；分账接收方实名；操作留痕满足审计取回（≥ 6 个月可查） |
| 性能 | 退款受理 P99 ≤ 1.5s（不含渠道异步到终态）；分账受理 P99 ≤ 2s |
| 可观测 | 每笔资金操作可按 `outRefundNo` / 分账单号 全链路追踪到渠道请求与响应 |
| 灰度 | 支持按商户白名单开启分账，退款可全量灰度回滚到线下流程 |
| 兼容 | 不影响 RFD-001 已上线下单/回调/关单链路与既有 BFF 契约 |

## 7. 验收标准

1. 整单退款：支付成功订单发起全额退款 → 渠道受理 → 通知或查证转 `SUCCESS`，
   消费者侧到账，资金台账新增一条与渠道一致的退款流水。
2. 部分退款：同一支付单连续发起两笔部分退款，累计不超过支付额；第三笔若超限被拒绝，
   返回明确错误码且不留资损流水。
3. 幂等：同一 `outRefundNo` 并发提交 5 次，渠道侧只发生一次退款，5 次返回同一结果。
4. 通知重放：同一退款回调重复投递 3 次，系统状态与流水不发生变化。
5. 分账：配置"门店 20% + 平台 5%"的订单支付成功后完成分账，两接收方金额与比例一致，
   分账查询可取回终态。
6. 冻结解冻：争议订单先冻结、后解冻剩余资金，未分部分归还商户，全程可追溯。
7. 越权/超限：未建立接收方关系的分账请求、比例超渠道上限的请求，均被前置拒绝。
8. 对账不平：构造一条渠道有而本系统无（或反之）的记录，日终对账能识别并触发锁定。
9. 双端一致：微信端与支付宝端在售后入口上看到同一状态口径，BFF 契约字段风格不变。
10. 回归：RFD-001 的下单、调起、回调验签、重复回调幂等、超时关单、契约一致性六域
    测试全部保持通过。

## 8. 范围外（本期不做）

- 跨境分账、外币结算、营销资金（代金券/立减）的分摊与回退。
- 平台垫资退款（先用平台资金退给消费者再向商户追偿）。
- 分账向消费者退款（接收方资金回退）的全自动编排——本期只做到人工发起。
- 商户自助修改历史分账规则、批量补分账工具。
- 线下门店 POS、H5 / App 端收银（本期仅双端小程序）。

## 9. 待澄清（BA 初稿已识别，需产品与架构确认）

1. **已分账订单发生退款的资金回退路径**：是先向接收方发起分账回退再退款，还是允许从
   商户待结算资金中扣划？两者时延与失败处理完全不同，商户财务口径需确认。
2. **可退余额的定义**：是否扣除"在途退款"与"已冻结分账"？定义不同会导致超限放行或误拦。
3. 微信与支付宝**分账时窗的具体天数**与逾期自动解冻的确切行为（渠道文档口径不同），
   需要确认本系统以哪一侧为准并写入设计。
4. 分账比例上限（默认 30%）在商户已申请提额的情况下如何取值——固定常量、配置项，
   还是渠道查询返回？
5. 部分退款的最小金额与币种精度（微信按分、支付宝按元两位小数）在 BFF 层统一的口径。
6. 退款是否需要商户侧二次审批（当前 F1 假设操作员发起即受理，商户集团要求大额需审批）。
7. ABNORMAL（结果不明）态的查证时限与人工介入阈值未定，涉及资损敞口时长。
8. F5 消费者自助发起退款的开放范围（本期是否只允许商户侧发起、消费者只读进度）。
