# Harness、Loop Engineering、Graph Engineering：如何选择，如何评估

先给结论：Harness、Loop Engineering、Graph Engineering 不是三选一。把它们放在同一张候选方案表里，再问“哪个更先进”，很像拿机房门禁、函数调用栈和业务流程图比赛谁更会写代码。它们解决的是不同层面的控制问题。
一个文章生产 Agent 足以说明这种差异。它需要研究来源、核验证据、写作修订、编辑审批、发布和通知。模型能把一段文字写出来，不等于系统能保证来源被核验；能通过多轮修订，不等于发布超时后不会重复提交；能画出工作流，也不等于工具权限、状态存储和轨迹评估有了边界。可靠执行需要三个对象协作，而不是替换。

![img](https://mmbiz.qpic.cn/sz_mmbiz_png/lIfJGW1r7cBlicGSffZCmrCia73uKIJBBleib9F0fv7xlTicgd9gRkvRIGqugWGgBKGKWWYian6ZZ8Bs5Ll3qG0U7nlDtstkN8jV69ytLWYcPzLY/640?wx_fmt=png&from=appmsg)

封面中的“数据回流、经验沉淀、质量闭环”不是装饰性口号：运行轨迹中的失败样本、人工修订原因和副作用事件，应经过脱敏后进入回归任务集和策略复盘；它们只能支持后续评估和治理改进，不能直接当作模型能力提升的证据。

## 三者的正确关系：嵌套，不是竞争
 Harness可以 定义为统一的可信运行边界。它承载模型和工具适配、权限、预算、上下文、状态存储、轨迹、评测和副作用隔离。具体系统中，这些能力也可以由多个独立服务提供，但必须通过明确接口纳入同一治理边界。没有这层边界，Loop 和 Graph 容易直接碰到外部系统，模型的临时决定就可能绕过权限和预算。
Loop Engineering 是阶段内闭环。它处理行动、观察、验证、修复和停止：当前阶段是否还要检索一次、草稿缺少引用时修哪里、连续几轮没有进展时何时终止。Loop 的主人是运行系统，模型只能在约束内提出下一步候选动作。
Graph Engineering 是阶段间拓扑。它处理节点、边、条件路由、并行、Join、人工门、检查点、恢复与补偿：研究冲突后去核验还是人工门，审批拒绝后回到哪一个草稿版本，发布结果确认已执行时为什么只能跳过。

![img](https://mmbiz.qpic.cn/sz_mmbiz_png/lIfJGW1r7cDO5otZmlFxpyF4t5DNaibErWVhl7sClxbuzHEw89IQKKmia3uITC3mzq8fewoIciaPFznfPbfwbTKibeKL7lnDh5llpEzBhrfjSTs/640?wx_fmt=png&from=appmsg)

图中的“承载”表示 Harness 为 Graph 和 Loop 提供共同的权限、预算、状态与轨迹上下文；“编排”表示 Graph 只决定允许的阶段和边；“推进”表示 Loop 在当前节点内反复执行行动、观察、验证、修复和停止。右侧的研究、核验、写作、审批、发布只是同一业务链上的阶段示例，不代表每个节点都必须包含 Loop。
最常见的生产组合是：Harness 承载运行边界，Graph 编排研究、核验、写作、审批和发布，写作或研究节点内部运行受控 Loop。单节点任务也仍然需要 Harness；多阶段任务并不必然让每个节点都有 Loop；只有出现多轮行动、观察和修复时，Loop 才值得引入。

## 用同一任务看三种执行模型
比较必须固定任务、输入约束、来源集合、模型和工具版本、预算、并发条件、成功定义和副作用规则。否则“图工作流更好”或“循环更灵活”只是把不同任务的结果放在一起讲故事。
统一 Running Case 是：基于来源约束研究一个技术主题，核验关键 Claim，生成草稿，处理修订，取得审批，然后发布并发送通知。下面三种模型都面对这同一条任务链。

![img](https://mmbiz.qpic.cn/sz_mmbiz_png/lIfJGW1r7cCuVlC3Lf8vLXEibwsYegLOQs3QsQdAM21gFvSLczyHDR3YgmLmChJHpbkmaf7KTsFib7rz964P0EmZ57pjlrP9loJj5h7dzU4gw/640?wx_fmt=png&from=appmsg)

三种模型必须共享同一个 run_id 输入快照、同一来源集合和同一成功判定。一次生成只允许一次模型决策；受控 Loop 只增加阶段内轮次；Graph+Loop 才增加显式阶段边、人工门和恢复路径。图中“无法表达审批与恢复”指没有结构化状态和路由证据时难以证明这些控制，不是说任何单次调用都绝对不能外接审批服务。
一次生成模型只有一个模型调用和有限工具动作。它适合范围小、无副作用、没有修复需求的任务，例如生成一段内部摘要。它的优点是简单，缺点是“模型说完成了”很容易被误当成完成证明。
受控 Loop 模型能在一个阶段内检索、观察、核验和修复。例如一份草稿缺少来源时，Loop 可以补证据再重写，并在轮次、时间或成本预算耗尽时停止。它改善了阶段内质量，却不天然解决多阶段路由、并行汇合、审批版本和发布恢复。
Graph 加节点内 Loop 模型将研究、核验、写作、审批和发布拆成显式节点。Graph 规定结果只能进入被声明的后继；写作节点内部仍然使用 Loop 修复局部问题；Harness 统一约束所有模型和工具调用。在阶段边界、审批和副作用恢复确实存在时，它通常带来更强的治理能力，同时也带来更多状态、契约和运维成本。

这个矩阵并不意味着 Harness 只能做底层能力，或者 Graph 不能调用验证器。它强调的是主责任：当一个问题无法解释时，先判断缺的是运行边界、阶段内闭环还是阶段间拓扑，再补对应层级的机制。
表格中的“恢复责任”要进一步拆开：Harness 提供状态存储、隔离和幂等基础设施，Graph 保存跨阶段的 Checkpoint、路由、补偿和人工接管语义，Loop 只负责当前阶段内尚未完成的动作。Checkpoint 至少应保存 checkpoint_id、last_applied_event_id、state_version、Graph 版本、Event Schema 版本、projector 版本和 recovery_lease。同一 run_id 同时只能有一个恢复写入者；可用带过期时间的租约、乐观版本号或单写者队列实现，租约失效或版本冲突时必须停止写入并重新读取最新 Checkpoint。事件追加、状态投影和游标推进要么原子提交，要么使用 Outbox、乐观锁和幂等投影，避免漏事件、重复投影或旧状态覆盖新状态。

## 评估不能只看最后一篇文章
最终文本通过人工阅读，只能说明结果看上去可用，不能证明它经过了正确路由，也不能证明发布失败后没有重复执行。评估至少分成四层，每层使用不同证据。

![img](https://mmbiz.qpic.cn/sz_mmbiz_png/lIfJGW1r7cA8x5XLUsReGZJEEpuTRZ7fI4xOP4bjbFiblYgDKf0nLw4KrgB2DHkE3UmJcWcuP1490KyGiaQdENvMKgtF2yTYb4ibbyBxnwaPpE/640?wx_fmt=png&from=appmsg)

结果质量包括关键 Claim 的证据覆盖、引用有效性、结构约束、事实冲突和人工接受度。它关注产物是否可用，不把模型自评当作事实证明。
执行质量包括验证 Outcome 是否被正确处理、未声明路由是否被阻断、Loop 是否在预算内停止、并行 Join 是否保留冲突、Human Gate 是否绑定正确版本。它关注控制流是否遵守契约。
资源效率包括模型轮次、工具调用、等待时间、并发数量和预算消耗。少调用不一定更好：为了压低轮次而跳过核验，通常只是把风险转移到发布后。
治理质量包括权限拒绝是否生效、人工决定是否可追溯、Checkpoint 是否可恢复、副作用是否去重、阻断状态是否可解释。一个任务即使完成了，只要重复发布或无法解释审批依据，治理分仍应是失败。
四层指标必须有固定口径，不能只报一个“成功率”：
指标
计算口径
统计注意事项

重复副作用率

## 三个失败场景，比成功演示更能区分架构

![img](https://mmbiz.qpic.cn/mmbiz_png/lIfJGW1r7cDtETjroibHfTOiao9U78rj7Yowvd36xnXTX3wlAVHhjIiaUL97NKAcU7rGvMOvNVWLWoy08J5Ga25M2tEjeOStk1viaAUXmJKxVbg/640?wx_fmt=png&from=appmsg)

第一个场景是研究结论冲突。一次生成往往只会选择一个看似合理的答案；Loop 可以再次检索，但缺少明确 Join 规则时，仍可能把冲突压平；Graph 可以让冲突结果进入核验或人工门，并记录选择的依据。这里需要观察的是来源指纹、冲突路由和人工介入，而不是最终段落是否流畅。固定断言应包括：冲突分支不能直接进入发布；Join 必须保留分支身份、输入指纹和冲突原因；人工门决定必须绑定当前证据版本。
第二个场景是编辑拒绝草稿。Loop 擅长根据修订意见修改文本，但它需要知道被拒绝的是哪个版本。Graph 将审批决定绑定 Artifact 版本，revise 指向修订节点，reject 阻断，approve 才允许进入发布。这里需要观察的是版本关系、授权范围和路由轨迹，并断言新草稿不能复用旧审批；输入快照、Artifact Revision 或 state_version 变化后必须重新审批。
第三个场景是发布超时。Harness 提供幂等键、状态存储和外部查询边界；Graph 根据副作用账本的三态结果决定动作：confirmed_executed 跳过发布，confirmed_not_executed 在预算内重试，unknown 进入查询、对账或人工门；Loop 最多只能帮助某个阶段在受限预算内重试查询。普通超时、not_found 或最终一致性延迟不能单独证明未执行。这里需要观察的是重复副作用率、恢复成功率和未知状态的人工接管率。

## 选型从任务结构和风险开始

![img](https://mmbiz.qpic.cn/sz_mmbiz_png/lIfJGW1r7cCL8IoLBRJf5QuEoR7TRicf1LDzvZ1ZXz4dcxPo21AhETfg3MoYGwNfOticEZ4VAJvIhl1tCX5SOvc2N6JgMKeXjicqp0edZz7feU/640?wx_fmt=png&from=appmsg)

可以用四个问题快速收窄范围：任务是否只有一个阶段？阶段内是否存在工具调用后的观察和修复？是否存在并行、条件路由、审批或跨阶段恢复？是否会产生发布、写入、扣费、通知等外部副作用？这里的“阶段”指具有独立输入、Outcome、预算或责任人的可恢复单元，而不是任意函数调用；只有跨阶段存在多条允许路径时，才需要 Graph。
单阶段、低风险、无修复任务，先建立 Harness 与最小验证即可。单阶段但需要反复行动和修复的任务，在 Harness 内增加受控 Loop。单阶段但存在发布、写入、扣费或通知等副作用时，仍必须具备幂等键、状态查询、审计和人工接管；这不自动意味着要引入 Graph。多阶段、存在并行汇合、人工决策、版本关系或跨阶段恢复的任务，需要 Harness 加 Graph，并在需要多轮推进的节点内嵌 Loop。
架构复杂度不是勋章。用 Graph 包装一次纯文本摘要，可能只是把可读性换成状态样板；用无限 Loop 承担审批、发布和恢复，又是在用临时性换取后期事故。选择的目标是把复杂度放在真实存在的复杂度上。

## 把选型变成可回归的评估闭环

![img](https://mmbiz.qpic.cn/mmbiz_png/lIfJGW1r7cAflsJBHsuHGMID31DB2EZicF1nEde62oFZre8r3jCukyic8gUib6ezFqfEsiaxTRfgbL0NFxF9WRXDQaXQjSD991cDficFPRTaxVMY/640?wx_fmt=png&from=appmsg)

生产环境不应只运行一次成功案例。为统一任务集保留正常样本、缺证据样本、来源冲突样本、审批拒绝样本、发布超时样本和状态版本变更样本。每次修改 Prompt、模型、工具、路由或权限策略后，分别比较四层指标，并保留差异原因。
图中的生产组合按四条线阅读：Harness 提供模型适配、工具权限、预算控制、状态存储、轨迹评测和副作用隔离；Graph 依次编排研究并行、证据核验、写作节点、Human Gate 与发布通知；审计事件记录输入版本、Artifact 版本、验证 Outcome、边选择和恢复决定；恢复机制通过 Checkpoint、查询证据、跳过已确认执行动作或人工接管来处理异常。图中的“跳过已提交”是版面上的简化标签，工程判断必须以 confirmed_executed 为准，不能把“请求已发出”等同于“外部动作已完成”。底部四层评估分别消费这些事件，而不是只读取最终文章。
控制流测试使用固定输入、模型 stub 和工具 stub，验证 Outcome 路由、预算停止、Join、Checkpoint 恢复、版本绑定和副作用去重；它不等于模型能力评测，不能据此推断事实知识、写作质量、推理能力或泛化能力。模型能力需要独立测试集、评分标准和模型版本记录。每次修改 Prompt、模型、工具、路由或权限策略后，都应固定数据集、并发条件、预算版本和统计时间窗口，保留指标差异原因。
Harness、Loop 和 Graph 的组合不是终点，而是让评估对象稳定下来：同一输入版本走了哪些节点，哪一轮验证改变了草稿，人工批准了什么，副作用何时提交，恢复凭什么跳过。轨迹可能包含 Prompt、工具输出、业务数据和人工审批内容，生产系统应做字段脱敏或加密，配置访问控制、保留期限和删除策略，并记录谁查询过哪些审计数据。这样，系统改进才能从“感觉更聪明”变成一组可讨论、可复现、可治理的工程证据。

## 总结
Harness 解决可信运行边界，Loop Engineering 解决阶段内闭环，Graph Engineering 解决阶段间拓扑。它们不在同一层级，因而不应被迫做互斥选择。任务越接近真实业务，越需要同时控制模型行动、阶段转移、人工责任和外部副作用。
真正有效的选型从任务结构出发，并以多层评估收束：结果是否可用，执行是否遵守契约，资源是否受控，治理是否能解释和恢复。把这四个问题都回答清楚，才有资格说一个 Agent 系统变好了。
