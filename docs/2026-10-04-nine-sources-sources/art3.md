# Pi 1.0 解析

AI ENGINEERING

# Pi 1.0：极简 Harness，开始管理复杂性
工具按需发现，模型动态路由，长任务有了独立的持久执行底座。
全文 3597 字  /  阅读约 8 分钟

2026 年 10 月 1 日，Earendil 正式发布 Pi 1.0，同时推出实验性包 Pi Durable。
如果只看功能清单，这次更新像是给终端编程助手补上 MCP、模型路由和全屏界面。但把发布说明、版本记录和运行机制放在一起，会看到一个更值得关注的变化：**Pi 正在把工具、模型、上下文和执行状态，变成可以组合、可以追溯的运行时能力。**
Harness 可以理解为模型之外的执行底座：它准备上下文，提供工具，驱动模型与工具之间的循环，并保存会话状态。模型再强，也要靠这层底座把一次回答变成能持续推进的工作。
Pi 仍强调极简。这次值得讨论的，正是它如何承接复杂需求，以及把复杂性放在哪里。
PART 01

## 先看时间线：1.0 是收束点

官方发布说明列出七项核心变化：Codemode、虚拟模型、延迟工具加载、Anthropic 缓存预热、会话中途的系统消息、新 TUI 主题，以及默认全屏。
这些能力并非全部在 10 月 1 日首次出现。
9 月 29 日的 0.99.0，已经引入 Codemode 与 MCP、虚拟模型、分类器模型和默认系统主题；9 月 30 日的 0.99.2，进一步优化 MCP 工具发现与连接方式。到了 1.0.0，新增重点包括 Codemode 提示词瘦身、图片生成、默认全屏、MCP OAuth 加固和启动信息控制。
因此，理解 Pi 1.0，要看这一轮连续变化。只比较最后一个版本差异，会漏掉主要设计；把整轮能力都称作“1.0 当天新增”，又会误读时间线。
终端体验也有明确变化：全屏成为默认模式，希望保留终端原生滚动历史的用户，可以使用 `--tui-mode regular`。不过，对构建 Agent 的人来说，更重要的部分在执行底座。
PART 02

## Codemode：让工具调用可以组合

传统 Agent 往往逐个调用工具：模型发起调用，读取结果，再决定下一次调用。处理几十个 Issue 或多组检索结果时，中间数据不断进入上下文，也不断触发模型往返。
Codemode 提供了另一种编排方式：模型写一段 JavaScript，在 QuickJS 沙箱里调用工具，完成并行、过滤与聚合，再把脚本输出交回模型。
它不是所有安装默认开启的工作方式。配置 MCP 服务器会自动启用 Codemode，也可以在 `defaultTools` 中显式加入 `+codemode`。开发者可以先从批量读取、检索和分类这类场景验证，再决定哪些流程适合交给脚本组织。
这个沙箱没有 Node API，也不能直接访问文件系统、网络或定时器。脚本通过已提供的工具与模型接口接触外部系统。它的职责很具体：把一组调用组织成局部流程。
例如，官方 MCP 文章演示过一个工作流：从 Linear 拉取 Issue 和评论，用 Jev 判断评论者的情绪，再输出筛选后的条目。读大量数据、逐项分类和排序都在脚本里完成，模型最终接收的是整理结果。
让中间数据留在编排层
原始结果不必全部进入模型上下文。模型提出处理方法，代码完成批量操作，再把值得继续推理的结果交回来。

1.0 又压缩了 Codemode 的说明开销。官方 changelog 给出的例子是：启用默认工具和 Codemode 的 GPT-5.6 请求，提示词从约 5,300 tokens 降至约 3,300 tokens，减少约 40%。
**这个数字描述的是特定配置下的提示词体积，不能直接换算成所有任务节省 40% 费用。** 实际成本还受模型、输出长度、缓存命中和工具结果影响。
代码编排也不会消除副作用。脚本失败前已经完成的工具调用不会自动撤销；并行读取很自然，并行写入则需要任务本身允许。它省下的是不必要的往返与上下文，不会替开发者决定执行边界。
跨次调用的小状态可以用 `store()` 保存，比如条目 ID、游标或摘要。成功脚本的写入会进入会话记录，恢复和分支沿各自路径读取。这种存储有容量限制，适合衔接流程，不适合囤积整批原始数据。
PART 03

## MCP 与延迟加载：工具说明也要占预算

Pi 曾明确把 MCP 留在核心之外。Earendil 在 9 月 29 日的官方文章中解释了转变：为 MCP 增加的工具元数据、发现方式和编排环境，同样有利于 Jev 等能力接入。
于是，Pi 原生支持 stdio 和 Streamable HTTP MCP，并提供 OAuth。更关键的是，接入服务器不再意味着立即把全部工具说明塞进上下文。
Pi 为工具提供五种 exposure，也就是工具的暴露方式。官方文档区分了“模型可以发起调用”和“其他工具可以嵌套调用”这两条路径：
●`direct`：激活后向模型声明，也允许其他工具调用。
●`model-only`：激活后向模型声明，但不允许其他工具或 Codemode 嵌套调用。
●`codemode`：注册后即可被代码调用，通常不直接向模型声明。
●`deferred`：具备代码调用能力，但不预先列入 Codemode 说明；可由工具搜索发现并激活。
●`hidden`：保留注册，撤回可访问性。
这里尤其要注意：`model-only` 不等于“模型看得见却不能执行”。它限制的是嵌套调用路径，适合编排工具或需要询问用户的工具。
MCP 还有一层配置映射。默认 `codemode` 暴露方式的 MCP 工具按需发现，脚本可以使用 `searchTools()`、`describeTool()` 和 `describeNamespace()` 获取必要说明，模型侧则可通过 `tool_search` 加载工具。
从 0.99.2 起，没有 `direct` 工具的 MCP 服务器不再阻塞第一次提示词请求。连接在后台建立，真正搜索或调用时才等待。服务器在系统提示中以简短摘要出现，避免完整 schema 常驻。
对连接大量服务的 Agent，这是一条直接的工程原则：**工具说明本身也是上下文，应像其他运行资源一样按需分配。** 服务器返回结构化数据，代码才更容易组合；只返回一大段文字，仍会把处理压力推回模型。
PART 04

## 虚拟模型与 Jev：把路由放进每次请求

Virtual Models 允许扩展注册一个看起来像普通模型的入口，比如 `router/auto`。用户选中这个入口，扩展在每次请求前决定实际使用的模型和思考级别。
路由输入可以包含会话消息、上一次物理模型、当前阶段，以及请求属于用户输入、循环继续还是重试。它因此能处理的不只是“这个问题发给哪个模型”，还包括“同一任务推进到这里，该由谁继续”。
Pi 1.0 发布页演示了一条路线：Claude Opus 负责规划，Jev 判断何时进入实现阶段，随后切换到 GPT 6 Luna；`/session` 再按物理模型展示成本与缓存使用情况。这是官方演示的扩展方案，并非所有会话默认开启的自动路由。
Jev 在这里承担的是明确判断。Pi 的模型目录区分聊天、分类器和图片模型，支持 TypeSafe 的 `jev-latest`，也支持把 llama.cpp 模型用于分类。分类器面对 JSON 状态回答类型明确的问题，返回选择、布尔值或分数，以及概率。
这种分工很适合工程化：大模型理解开放任务，分类器判断阶段或条件，代码根据结果组织下一步。但分类器仍可能判断错误，关键决策需要阈值、回退和可观察记录。
成本也不能只按模型单价计算。分类调用会增加首 token 前的延迟，跨模型切换会失去原模型的提示词缓存。官方路由文档建议在循环继续和重试时尽量保持模型连续性。虚拟模型在 0.99.0 changelog 中还标为实验性能力，采用前应验证自己的路由策略。
1.0 的 `models.generateImages()` 则把图片生成接入了 Codemode，调用使用会话凭据，相关用量纳入会话统计。不过，脚本可以执行分类和图片模型，**聊天模型仍不能通过这套 Codemode 接口直接运行**，不宜把它想成任意模型都能随意嵌套的统一入口。
PART 05

## 动态上下文：记录变化，也处理缓存代价

当工具会动态加载、扩展会热重载，系统提示词也需要表达“什么时候发生了什么变化”。否则，恢复历史时很难解释模型当时具备哪些工具、接收了哪些规则。
Pi 会在第一条系统消息中记录初始提示词与工具集，并在后续模型请求前，把工具和提示词变化追加到对应位置。这让上下文拥有时间顺序，也让会话恢复和分支保留更清楚的运行轨迹。
“上下文版本化”可以作为理解这种设计的概念，但它是对机制的归纳，并非发布清单中的独立产品名称。
缓存收益取决于模型供应商。支持会话中途系统与工具变化的接口，可以增量表达变化；不能表示这种转换的接口，则接收完整的会话检查点，可能使缓存前缀失效。动态变化和缓存保留之间，需要供应商适配层处理。
Anthropic 缓存预热是另一项配套能力。Pi 默认在活跃运行中预热，只有模型声明缓存寿命，且预计可避免的未命中成本至少达到 0.05 美元时才执行。刷新产生的用量计入会话统计，但不进入模型上下文。
这几项设计可以连起来看：稳定内容尽量复用，工具说明按需发现，中间结果在代码里消化，变化按发生位置记录。上下文成本开始进入执行底座的日常管理。
PART 06

## Pi Durable：恢复能力有了独立边界

Pi Durable 与 Pi 1.0 同日发布，但它是独立的实验性框架。终端编码 Agent 继续面向一个人驱动的工作方式；Durable 则面向长任务、多入口和多人可以操控的 Agent 应用。
它把 Harness 拆成存储、会话与任务执行机制。内置存储包括内存、SQLite 和 JSONL，也允许开发者实现自己的后端。需要跨进程恢复时，应选择真正持久化的存储，不能把内存后端当作同等保障。
最关键的变化是：模型请求、工具调用和上下文压缩，都作为任务执行。任务在步骤之间保存 checkpoint；进程中断后，新进程打开同一份存储，找回未完成任务，从最近检查点继续。
但恢复不是把所有操作无条件重做。被截断的模型请求会重新发送，部分回答保留在记录中并标为中止；中断工具只有声明可安全重跑时才会再次执行，否则把中断状态和已有输出交给模型处理。
持久执行需要三种不同保证
✓任务进度有检查点，重启后知道工作停在哪里。
✓重复提交有 requestId，客户端重试可以找回原提交。
✓外部副作用有安全重放声明或业务幂等键，避免重试造成重复操作。

**提交去重不等于外部操作恰好执行一次。** 官方支付示例也显式使用幂等键；发通知、扣款、部署等动作，仍要在工具和业务系统里定义恢复方式。
Durable 的长对话同样依赖压缩：旧消息保留在存储，模型使用当前上下文和摘要；后台压缩到下一轮边界再接入。这不是无限大的上下文窗口。当前设计还要求同一份存储由一个进程持有，多个客户端连接该进程，不能直接视作多进程共享写入方案。
从构建 Agent 的角度看，Pi 1.0 与 Durable 最有参考价值的，是这些边界：工具何时进入上下文，模型何时切换，变化如何记录，失败以后哪些步骤可以继续。
极简底座是否足够，最终要看它能不能把这些问题交代清楚。Pi 的这轮更新，给出了值得验证的具体实现。
