## 3. 波次安排（在途 worktree ≤ 3）

- **波 1（契约）**：X0 ∥ X1 ∥ X2。纯服务端与共享组件，不动路由，可在任何窗口推进。
- **波 2（B 骨架＋A/C 壳）**：B1 ∥（X3）∥ C1。X3 量小插队。
- **波 3（B 签批量）**：B2 → B3 ∥ B4 → B5 ∥ B6；B8/B9/B10 随 B 尾段。B7 等 journal 积累自然排后。
- **波 4（A ∥ C 主体）**：A0 → A1 ∥ C3；A2/A3 ∥ C4/C5；A4/A5/A6 ∥ C6/C7/C8。A7 ∥ C9。
- **波 5（E 收尾）**：E1 → E2 → E3 全过后跑终验。（原波 5「D 镜头」已随 D 波解体取消）

每张工单=一个 feat/<slug> 分支（worktree 位置随仓库既有惯例），验收门逐条过后 `--no-ff` 合 main，对账总表对应行号勾销。

## 4. 部署窗与轮次协调

1. 所有 inject（补丁注入与 UI 换装）只在**无轮次在跑的部署窗**执行；run21 开轮即冻结全部 inject，批次在 main 上等窗。
2. run21 开轮清单中的低风险迁移件（驱动侧改调 631/634/635/orgloop 端点的透传化）与本计划同源——同属部署窗工作，一次开窗一并执行，bash 侧只许透传不许重写语义。
3. TSV→产品存储迁移（X2 附带）为一次性动作，在部署窗执行并保留 TSV 只读降级档。
4. 终验：E3 后的一轮全量推演为产品面验收场——推演中心六签承载该轮观测，治理报告数据面与 UI 同值对照。
5. 阶段验收场（Q4 裁定）：用户每阶段走查**该阶段风险最高的屏**（B=监督面板真数据判读、A=inbox 把关、C=清偿门与关卡定义态、E=全量），走查清单按需求号逐屏打勾；走查走 dev 热更新不装机。监督面板/运行观测的真数据走查必须在一轮**在跑**时——B 面验收场=下一轮开跑前部署窗注入、开跑后走查。

## 5. 验证门禁（每张工单必过）

1. **单测**：新端点纯函数照 PR-0 模式；组件 VTU；`npm test` 全绿才许提交（测试与提交分两轮动作）。
2. **inject 重放**：补丁在纯基线重放零失败（部署窗执行）。
3. **浏览器走查**：`npm run dev`（8649）按工单动线清单走查并留帧；不默认装机，Electron 主进程类改动例外并如实标注。
4. **无锚不展示抽查**：每签抽一块展示内容核对条款锚；数字实测计算抽查（禁手编）。
5. **合并一致性**：新消费一律调端点/API；发现双实现=产品缺陷进清偿门开单，不静默。
6. **对账勾销**：行号即工单号，完成一行勾一行；双家/孤儿即时标红。
7. **文档与文案**：jargon-check HARD=0；页签文案中文说人话、术语全名首现。

## 7. 收尾纪律

每工单：feat 分支 → 验收门逐条过 → `npm test` 全绿 → 合 main（`--no-ff`）→ 对账行勾销 → 部署窗 inject 重放验证。每阶段末：回归测试（ia-views/governance-view/新增面）＋构建零错。本计划随裁决与详设修订同步升版；行号引用以 A-G 123 行对账总表为唯一正本。变更分级（Q5 裁定）：需求级变更（增删需求/改验收判据）=需求分析 §七 变更记录＋用户确认后生效；界面级微调随工单验收不走变更；新增「能力驱动」想法强制回答「锚到哪条 R」，锚不到不入期。

## 8. 不做什么

- 不动岛屿既定路线（IDE/BPA/本体/评测/技能治理只接入口与新约定装置）。
- 不做二级页签；不删任何功能（123 行全有新家，只有迁移与合并）。
- bash 原件退役不在本计划——退役判据（产品面走通一轮＋影子对照一轮）达成后另行评估。
- 不为重构打断在跑轮次；不为镜头层做角色专属路由（URL 稳定，视角随镜头变）。
