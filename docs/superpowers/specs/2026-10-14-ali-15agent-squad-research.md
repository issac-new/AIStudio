## 主旨三句话

唯一主旨：对照阿里文章逐条核对 SwarmStudio 的多 Agent 研发体系，结论是机制件覆盖度已高（15 项对照中 7 项已具备、3 项部分具备），真差距集中在回路的自动化程度与两个工具面，据此给六件编号改进项（A-F）待拍板。受众：SwarmStudio 产品决策者与维护者。读完促成：从 A-F 中圈定执行项与顺序。

## 1. 调研结论（文章说了什么）

文章主线一句话：编码提速提不动交付（20 个工作日里编码只占 2 天，编码提速十倍，全周期只省 1.8 天），因此把 15 个分工 Agent 组成小队接管「需求-实现-验证-反馈」全流程，再用「运行面 + 优化面」双面结构让小队越跑越好。对本仓有直接价值的八点：

1. **瓶颈定位**（§02）：瓶颈在需求确认、协作、验证、等待，不在编码。全流程视角是产品取舍的出发点。
2. **能力池 + Leader 调度**（§03）：15 个 Agent 组成能力池，Leader 决定先做什么、交给谁、完成后怎么检查、出错回到哪。
3. **失败三档回退**（§03）：测试不过，回原 Code Session 原地修；方案方向错，带失败证据回 Research/Explore 重做；反复不收敛，触发 Human Gate 请人判断。
4. **任务状态保留**（§03）：前手做了什么、为什么这样做、验证发现了什么，后手能直接接着用。
5. **跑通后的四类持续问题**（§04）：架构约束传不到位（要在已有 API 上扩展，Agent 却新增一个）；预料外输入；同坑反复踩；修 A 坏 B。后两类分别指向经验库与稳定考卷。
6. **三挡调优**（§05）：手动挡＝专家定 Rubric、坏例入集、实验对比；半自动挡＝系统出建议报告（Token 大户、低效步骤、持续报错工具）；自动挡＝经验库从轨迹提取经验、动态注入。
7. **Coding 调优两件事**（§06）：离线用 20 个专家 Commit 反生成需求建考卷，与专家实现对波；在线从轨迹积累同类问题 SOP、较优执行路径、工具调用反模式。
8. **两个关键做法与实效**（§06-07）：实现与验证分离（独立视角）；迭代保留上下文（带证据和历史尝试）。受约束场景先行，19 题中约 10 题与专家近似等价、5 题接近专家水平，交付周期从约一个月缩短到一周以内（阿里自报口径）。

## 2. 差距对照（文章 × SwarmStudio 现状）

## 3. 六件编号改进项（待拍板）

每项给一句话价值、落点、代价，倾向性建议在节末。

**A. 半自动挡建议报告**。价值：把「哪里在烧钱、哪里在绕路、哪个工具在反复报错」从人工翻轨迹变成一张自动报告，专家照单处置。落点：聚合既有数据（tokens 域、Eval costUsd、trace 工具错误、incident 报告）出三张 Top-N 清单，挂 RunTraceView 或 Eval Studio 报告面板，不新增采集面。代价：中（数据全在，聚合函数 + 一个 UI 面）。

**B. 经验库回路（最大差距，两步走）**。价值：解「同坑反复踩」与「跨轮知识靠人搬」两个问题。当前每轮记忆清零，经验只活在复盘人写的纪律条款里。B1 提取器：从 run 轨迹提取经验候选三形态（同类问题 SOP、较优执行路径、工具调用反模式），只出候选不改行为。B2 受控注入：治理审核后入库（版本化 + 出处标：源轮次、源轨迹），下轮派单随任务卡注入，注入留痕。代价：高（新回路，涉及从零纪律边界，见 §4）。

**C. 专家基线考卷生成器**。价值：调优有固定考卷。当前用例手写 + 坏例回流，文章补了第三来源：从真实代码库专家 Commit 反生成需求（含验收条件）。落点：gitActivity 域 + Eval 衔接，生成器只产题，跑题走既有 runner/judge/compare。改技能或配置后必跑该集（回归门禁）。代价：中。

**D. 架构约束注册表（约束卡）**。价值：解文章问题①在本文仓的同型痛点——约束（在哪扩展、别新增什么）散在方案文档，任务卡里没有，agent 自然挑当下最容易的路。落点：约束卡四字段（陈述、适用范围、来源锚、生效轮次），挂 ontology 域，派单时随任务卡注入，本体工作台加维护页签。与 /learn 的 convention 归宿分工：会话内人的偏好走 /learn，架构级规则走注册表。代价：中低。

**E. 失败路由表显式化**。价值：把三档回退（原地修、带证据回上游、人闸）从散件升为一张显式路由表：失败类型→回退点→携带物。锚点已齐：goalbudget 域三维触顶（步数、token、时限，custom/server/goalbudget/）可作「不收敛」判据，escalation 作人闸，熔断指纹作原地修。缺的是中间档（方向错→回上游调研）的机器路由。代价：低（多为正名 + 补中间档）。

**F. 交付周期分解面**。价值：把「编码只占 2/20 天」这笔账做成产品面。各阶段时长瀑布指出瓶颈段，支撑「下一轮提速投哪里」的决策。落点：报告链步条时长数据已有，聚合成瀑布图挂报告或看板。代价：低。

倾向性建议：D + A 先做（代价低、数据现成、直接对位文章两个最实的点）；C 其次（考卷是 B 的前置——经验有没有用，要靠固定题验证）；E 顺手；B 最大但两步走，B1 提取器只出候选、零行为风险，可先行，B2 跨轮注入等 D（注入通道）与 C（验证考卷）就绪后再上。

## 4. 设计决定与理由

- **从零纪律与经验库的边界（B 的核心论证）**：方案正本「污染防线」禁的是前轮运行态残留冒充本轮凭据（禁引前序轮 commit、卡号、event_id 作凭据），不是禁知识复用。经验库注入的是治理面受控资产：经审核、版本化、带出处（源轮、源轨迹锚）、注入留痕。边界写成一条纪律：经验注入物不得含「本轮实测」形态的凭据。commit 哈希、卡号、event_id 一律改写为「历史经验出处」形态。这样从零纪律的断言（各维度归零）不受影响，同坑复踩的代价下降。
- **半自动挡不新增采集面**：三清单的数据源全在既有面。采集面膨胀有教训——TTFT 插件轮新增打点通道后，真实会话落盘确认至今挂账。聚合优于新采。
- **专家基线复用 Eval 通路**：生成器只产题（需求、验收条件、专家 diff 出处），判分走既有 runner/judge/compare，不另起引擎。专家 diff 不当标准答案（开放题无唯一解），当「对波参照」供裁判参考。
- **约束卡与 /learn 的分工**：/learn 收会话内人说的偏好（三归宿判定已有）；约束卡收架构级规则（人工维护 + 本体联动）。两者共用派单注入通道。
- **自动挡降档为「候选 + 审核 + 注入」**：文章的「全自动提取注入」在本文仓降一档，人保留否决权。依据是本仓自己的教训：无人监督的自动行为修改会失焦（run14 回灌把 agent 回合刷成 PASS 十小时不落的干扰源事故）。出候选零风险，改行为必须过人。

## 5. 边界（不做的事）

- 本轮只调研 + 提案，未动任何代码；A-F 均待拍板后另开 feature 分支实施。
- 文章数字（20 天里编码 2 天、19 题约 10 题等价、周期约一月到一周内）是阿里自报口径，未独立验证，仅作叙事参照，不进产品断言。
- 不照抄 AgentCore/AgentLoop 的产品形态与命名：本仓已有对位件（Eval Studio、RunTraceView、incident 报告），吸收的是做法，不是改名。
- B2 跨轮注入涉及从零纪律条款，须先修订方案正本再动代码；run19 推演进行期间不动该条款。
