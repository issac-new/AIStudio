## 批准前六问

1. **决策**：两件。其一，治理面板上「读不到数据」的几处结论不再显示成好结果，读数与执法的实际状态一致。其二，一个流程节点（当作一个 AI 应用场景）在立结果合同之前，系统能不能如实回答「它该不该做、缺什么、谁签的字」。做的人是项目所有者（2026-11-28 指令「全做」），看的人是用治理面板与流程架构页的管理员。
2. **口径**：本批不含统计评分。场景准入只给「命中哪条规则、缺什么」的缺口清单与三态结论，不打分、不加权、不排序。基线、成本这类读数缺数据源时如实写「未知」或「不可用」，不补数。
3. **可逆性**：批 A 全部是读模型修复，回退提交即恢复旧读数。批 B 新增字段全部可缺省，存量流程节点不回填、不改写；准入结论是追加式记录，不覆盖历史。批 A3 改变一条既有测试的口径（治理姿态「未配置」从显示关改为显示开），回退即恢复。
4. **署名**：实现会话对代码与验证证据负责；项目所有者对范围与验收负责。场景准入的「可进入试点」与「暂缓」由登录身份签署，署名取服务端登录身份，请求体同名字段不生效（沿用 `2026-11-24` 批一 D6）。
5. **停止条件**：出现下列任一情况即停并回退——批 A 任一修复让原有正确结论变错（库在且可读、确实为空时仍显示正常）；变异探针有未执行却被计为通过；批 B 的编辑器保存一次后丢字段；署名可被请求体冒填；与在途任务 `feat/workunit-framework-align` 的文件发生同文件双写。
6. **语法**：动了一条权限语法——场景准入的排除规则命中时，结果合同创建接口返回缺口清单（是否阻断创建见决策 D8）。动了考核语法里的「读数」部分（人机团队成功率从恒不可用改为按既定口径计算），不进任何绩效。不动预算语法与数据权属。

### 0.5 结果与证据

- 九层体检：检查项状态增加 `unavailable`（窗口内无事件可评）；层对象增加 `unevaluated` 数组；`score` 可为 `null`。
- 五流诊断：读看板库的五条信号在读不到时 `severity=unknown`、`value=—`、`detail` 写明「未找到看板库」或「看板库 N/M 个打不开」。
- 评分卡：`least-privilege` 与 `no-broad-permission` 两项的 `status` 随治理姿态读数变化，`evidence` 写出实际读数。
- 场景准入：接口返回每条规则的 `{ rule, verdict: 'hit' | 'clear' | 'undetermined', detail }`；签署接口返回追加后的记录。
- 每项修复都有先失败的用例与至少一个会变红的变异探针；变异探针驱动脚本放仓库外，运行后按摘要核对源码还原。

### 0.6 异常与恢复

- 未登录且未设 `AISTUDIO_LOCAL_OPERATOR`：签署接口返回 401。
- 登录身份不是在岗自然人：返回 400，问题列表写明。
- 治理姿态取数抛错：评分卡两项判「未知」并写明原因，评分卡接口本身仍返回 200。
- 看板库一个都没找到：五条相关信号判「未知」，写明「没有库不等于没有任务」。
- 回退：批 A 回退提交即恢复旧读数。批 B 新增字段可缺省，删除 `overlay/bpa-admission.json` 即清空签署历史。

### 0.7 验收反例

以下必须在测试中被拦住：窗口内没有工具调用时九层体检把对应检查项判缺失；看板库打不开或不存在时五流诊断显示「均有台账档」「无过载」；执法总闸未设环境变量时任一面板显示关；治理姿态健康时评分卡仍写死「部分」、总闸关时「权限不过宽」仍是通过；治理姿态取数抛错时评分卡接口报错；流程成熟度雷达把未打分的因素画成 0；用量库缺席时虚拟损益表显示成本 0；未登录签署被接受；请求体冒填签署人后记录里出现被冒填的名字；编辑节点名称后场景准入字段丢失；四条排除规则并入既有体检规则码；门函数被改成恒通过后测试仍全绿。

## 变更

### 批 A：读数不造假

**A1 九层体检**（`custom/server/harness/nine-layers.ts`、`custom/client/governance/components/NineLayersSection.vue`、`custom/client/governance/api/harness.ts`、`custom/client/governance/i18n.ts`）

「没有数据」分两种并分别处理：机制在位性（契约数、守卫在不在、文件在不在）为 0 即判缺失，不变；机制在、只是窗口内没发生事件（没有调用、没有失败调用、没有完成行、没有审计行）判「无法评估」，不计入分数的分母，不进差距与整改动作。本层没有可评估的检查项时 `score` 为 `null`，界面显示「—」。关键检查项无法评估时该层不得判「已覆盖」。另修同文件一处：发布门与界面验收两项全缺时原判「部分」，现判「缺失」。界面增加「无法评估」清单与记号；旧服务端不带 `unevaluated` 字段时界面从检查项状态推出清单。验收判据：窗口内无调用时工具层分数由改动前的 38 变为按已评估项计算；全缺输入九层分数均为 0。

**A2 五流诊断**（`custom/server/governance/org-diagnosis.ts`、`custom/server/governance/governance-analytics.ts`）

新增只读探针 `kanbanReadability()`，回答三态：一个看板库都没找到、找到了但有库打不开、全部可查。读看板库的五条信号（台账建档、在途过载、未指派任务、打回滞留、打回跟进）统一经 `kanbanSignal()` 输出：可查时按原逻辑给结论，否则整体给「未知」且写明读不到的原因。此前读失败被回退成 0，再被判成「均有台账档」「无过载」。`collectAssigneeStats` 的返回形状不变（它有十余个调用方）。验收判据：库文件在但打不开、以及完全没有看板库两种情况下，五条信号均为未知；库在且可查、确实没有任务时才是正常。

**A3 评分卡**（`custom/server/harness/ai-native-scorecard.ts`）

`least-privilege` 与 `no-broad-permission` 两项此前写死「部分」与「通过」，证据文案里的「角色工具矩阵 30/30」没有读数来源。现改为按治理姿态读数判定：执法总闸关，两项均不通过；有档案显式关闭审批，或一个档案都没读到，判部分；总闸开且已加载规则为 0，「权限最小化」判部分；其余通过。取数函数可注入，生产读 `collectGovernancePosture()`；取数抛错判「未知」并写明原因。同文件另修：两处目录计数此前未保护，目录不存在会让整张评分卡报错，现读不到判「未知」。

**执法总闸读数统一**（`custom/server/toolpipeline/enforce-gate.ts`、`custom/server/governance/posture.ts`、`custom/server/harness/nine-layers.ts`、`custom/server/managedsettings/managed-settings.ts`）

执法门的 `masterSwitchOn()` 判据是「部署侧锁定优先，其次环境变量显式为 0 才关，否则默认开」（2026-11-05 裁决）。治理姿态、九层体检、评分卡三处此前各自写「环境变量等于 1 才算开」，未设环境变量时执法在生效而面板显示关。现抽出纯函数 `toolEnforceOn(env, managed)` 作为单一事实源，三处同调。`managed-settings.ts` 增加测试隔离函数，读模型的测试不再读本机真实部署文件（它不认 `HERMES_HOME`）。验收判据：未设环境变量时治理姿态与九层体检都读到「开」；显式 0 读到「关」；部署侧锁定开时环境变量设 0 也读到「开」。

**A5 流程成熟度雷达**（`custom/client/bpa/components/BpaMaturityPanel.vue`）：九个因素全部打过分才画雷达图，否则显示「已打分 N/9」。

**A6 虚拟损益**（`custom/server/harness/virtual-pnl.ts`、`custom/client/governance/components/VirtualPnlSection.vue`）：用量库缺席时成本为 `null` 而非 0，界面显示「—」；看板交付数按与成本相同的天数窗统计；时间窗查询失败回退全表时在报告里标记，界面注明。

**A7 人机团队成功率**（`custom/server/capabilitypool/metrics.ts`）：按 `metric-defs.ts` 的既定口径计算——同时含人与 Agent 成员的结果团队中，结算结论为达成的团队数除以同口径已结算团队数。结果工作台未启用时如实标「未启用」。

### 批 B：场景准入与关卡

**B1 四条排除规则**（新增 `custom/server/bpa/bpa-admission.ts`，纯函数）：业务主责缺失（节点无在岗负责人）、无法提供基线（节点没有任何带数值基线的指标）、数据无合法依据（节点登记了敏感数据但没有合规结论）、重大影响无人复核（节点标为重大影响但没有复核人）。每条返回命中、未命中或无法判定，附缺口说明。规则码用自有类型，不并入既有九条体检规则的规则码。

**B2 准入三态结论**（新增 `custom/server/bpa/bpa-admission-store.ts`、控制器路由、`BpaAdmissionPanel.vue`）：结论取「可进入试点／需补条件／暂缓」。命中「业务主责缺失」「数据无合法依据」「重大影响无人复核」任一条，系统给「需补条件」并列出待补清单；未命中且基线规则未命中的，由人签署「可进入试点」或「暂缓」。记录含结论、触发的规则、待补清单、签署人（服务端登录身份）、时间、理由，追加式保存。

**B3 流程节点补字段**（`bpa-types.ts`、`bpa-controller.ts`、`BpaTreePanel.vue`、`api.ts`）：节点增加可缺省的触发条件、数据来源与新鲜度要求、数据合规结论、是否重大影响、复核人。编辑器与服务端的保存都要带上这些字段。

**B4 风险词表**（`custom/server/outcome/decision-matrix.ts`）：看板与评审面的语义词表新增业务动作词表（资金收付动作：付款、转账、汇款、打款、放款、扣款、退款、收款；数据类别：个人数据、个人信息、客户信息、敏感数据），命令面词表不动。词表取舍依据存量实测（3733 条标题，2026-11-28）：「支付」命中 143 条、其中 93 条来自名为 pay 的看板板，「结算」命中 75 条——业务域名词不收（域名词命中等于按部门贴高危标签）；资金动作词存量命中 0 条、「个人信息」命中 2 条（0.05%）。命中后果＝评审卡置顶计入高危数＋台账 risk=high＋治理总线事件升级，不设新门码、不连带判 one-way。原因见决策 D9。

**B5 合同基线**（`custom/server/outcome/settlement.ts`、`comparison.ts`）：结算建议给每条度量增加「较基线」读数；对照投影的行增加合同自带的基线。结算结论的判定不变。

**B6 问题记录**（`custom/server/eval/`）：另立一种来源类型承接告警与事故，不复用评测处置单；记录里抄入运行清单的版本锚点（模型、提示词指纹、权限模式、契约版本）。
