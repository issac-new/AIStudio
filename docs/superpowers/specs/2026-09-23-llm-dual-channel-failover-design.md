# LLM 双通道备份路由设计（推演环境 cc-switch 额度塌方的根治）

- 日期：2026-09-23（aipaydev 推演收口轮，环境类缺口产品化）
- 状态：上游能力设计（hermes-agent / cc-switch 侧），overlay 侧消费；本文定触发证据与交互契约
- 关联：推演报告 §四「环境类」、ISSUES-LOG cc-switch 双通道 403/401 事件
- 一句话：推演 12 编制 LLM 全靠单通道 cc-switch，额度窗两次塌方（403 打光 / 401 失效）让推演停摆数小时——备份路由不是优化，是推演的生存线。

## 一、触发证据（为什么立项，不是拍脑袋）

推演当晚真实事故链（ISSUES-LOG 在案）：

| 时刻 | 事件 | 影响 |
|---|---|---|
| 18:22 | chen 实例 cc-switch 主通道 403（额度窗打光） | 该 agent 停摆，任务队列积压 |
| 20:58 | chen 再撞 5 小时额度窗 403；同时备份通道 MGLM 令牌 401 | **双通道齐断**，诊断只能走 sqlite ro 查 providers/proxy_request_logs |
| 夜间 | cc-switch SRK 打光、MGLM 顶上恢复后 agent 未自动重叫 | 恢复后要靠人工补发纠偏消息才能续上 |

根因不是「额度不够」——额度永远不够。根因是：

1. **单通道硬依赖**：12 编制全押 cc-switch 单池，主备切换是人工的、事后的。
2. **无探活/无回退**：401/403 发生后没有自动降级到可用通道，恢复后也没有自动重叫。
3. **黑盒**：额度余量、切换状态对推演编排（导演脚本）不可见，只能事后翻 sqlite。

## 二、设计目标与非目标

**目标**
- 主通道（cc-switch）+ 至少一条备份通道（kimi-direct / MGLM / 其它），故障时**自动**切换，恢复后**自动**重叫。
- 通道健康与额度余量对编排层**可见**（主动探活 + 状态查询面），不靠事后翻日志。

**非目标**（诚实边界）
- 不做无限额度假设：备份通道也有额度窗，设计的是「有序降级+可见」，不是「永不失败」。
- 不碰上游模型调度内核：本设计只在通道选择层（gateway / cc-switch 边界）做路由，LLM 会话语义不变。
- overlay 不实现——能力在 hermes-agent / cc-switch 上游，本文是需求与契约，上游落地后 overlay 侧做开关与可观测性对接。

## 三、通道路由契约（给上游的需求接口）

```
通道链（优先级有序，示例）：
  1. cc-switch 主池（现状）
  2. kimi-direct 备份
  3. MGLM 备份
  ...
触发切换：
  - 403 额度窗打光 → 标记该通道冷却，流量走下一可用通道
  - 401 令牌失效 → 立即摘除（非冷却，需人工换令牌后恢复）
  - 连续 N 次超时 → 软摘除，探活恢复后自动归队
恢复：
  - 冷却期过 + 探活通过 → 自动归队，**恢复后自动重叫在途 agent**
    （治「SRK 打光 MGLM 顶上、恢复后 agent 须重叫」的坑）
可见性：
  - `hermes providers status`（或等价面）输出每通道：状态(available/cooling/down)、
    额度窗余量、最近一次切换时间与原因——编排层可轮询进 evidence。
```

## 四、与推演编排的接口（overlay/sim 侧消费）

- 导演脚本（aipay-scenario*.sh）在关键门禁前调用通道状态面，主备全断时**提前 fail-fast**（而不是让 agent 回合静默卡死）。
- evidence 采集（aipay-evidence.sh）把通道切换事件入台账，事后分析「哪次失败是模型问题、哪次是通道问题」。

## 五、验收口径

- 上游落地后：模拟主通道 403（测试桩），验证自动切备份、冷却归队、恢复重叫三步全自动。
- 推演复跑：人为掐断 cc-switch 一轮，推演不停摆（允许降级变慢，不允许停摆）。
- 本设计本身：本文即需求锚点；上游 PR 落地时对照 §三 契约逐条验收。
