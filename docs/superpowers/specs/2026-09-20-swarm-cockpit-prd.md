## 1. 产品概述

Swarm Studio 是面向软件研发全流程的智能驾驶舱：以 Matrix 为通信底座，以每个用户本机的 Agent 集群为执行单元，把需求分析、架构设计、开发实现、测试验证统一到「沟通协作 ⇄ 研发执行」双视图工作台。用户用 Matrix 账号登录后与真人、Agent、多 Agent 混合协作；每个账号绑定一个 Orchestrator，按能力标签调度本机 Agent；任务状态以房间事件流为准，全程可追溯（架构裁决 A/B/C，已批）。

与需求稿 §18 主表述的差异仅一处：「Swarm Studio 维护任务」细化为「Studio 各端从房间事件流投影任务」（裁决 A 落款），其余叙事不变。

## 2. 用户与角色

人员六种（需求稿 §4.1 全收）：产品需求分析、架构设计、开发、测试、团队管理者、普通协作者。

Agent 侧收敛为一张身份表（裁决 C 落地后，Agent 分两层）：

| 身份层 | 实体 | 举例 | 联系人与聊天中的呈现 |
|---|---|---|---|
| 集群账号（Matrix 实体） | 每用户一个 `@<用户>-agent`，Orchestrator 持号 | `@zhang-agent` | 独立联系人，树挂在所属用户下 |
| 附属 Agent（账号内虚拟） | 集群内按能力区分的执行体 | 需求分析、架构设计、编码、测试、评审辅助 | 消息徽章「张三的集群 · 编码 Agent」，不开独立账号 |

角色语义沿用需求稿：开发人员账号 = 其维护的系统职责集群入口（问题 5 裁决），集群携带模块能力标签（如 `module:payment`），产品侧按标签分发。

## 3. 核心用户旅程（贯穿案例：支付对账日报自动生成）

U1 产品发起需求。产品张三在沟通视图把业务需求发给本机需求分析 Agent → Agent 以 agent.message 回复拆解结果：5 张子任务卡片（parentId 挂同一案例，dueDate 按周排定）→ 按 capability 标签分发（账单模块 → 李四集群，报表 → 王五集群，测试 → 赵六集群）→ 各集群回执 received/started → 张三在任务决策栏看到「处理中 5/5」。完成标志：子任务事件链齐全且看板可数。

U2 设计评审与基线化。架构负责人收 design.md（git 制品指针）后发起 R2 评审卡片 → 李四、王五会签（signoffs 逐人呈现）→ 全员 pass → 文档随 G2 基线化，验收边界冻结进 frozenAcceptance。完成标志：R2 gate 事件 verdict=pass 且 signoffs 齐。

U3 开发人机协作。李四的编码 Agent 接开发任务 → 李四从 IDE 维度条进 /ide，任务上下文（需求、设计、聊天锚点）在侧栏 → codex 会话产出 diff → 李四点确认即发 R3 代码评审事件 → 提交回执回写，看板态变待评审。完成标志：diff 与 R3 事件同 taskId 可互溯。

U4 测试缺陷回路。测试 Agent 执行用例 → 失败即自动建缺陷任务（parentId 挂原任务）→ 李四集群修复 → 回归重测 pass → 赵六人拍板 R4 验收。完成标志：缺陷-修复-回归三段事件链 + R4 verdict。

U5 管理者驾驶舱。管理者开 ⚙管理台：项目进度、阶段阻塞、人员与 Agent 负载、逾期催办一览 → 对阻塞任务转派或重开。完成标志：统计数字全部可回溯到事件源（口径对照表）。

## 5. 关键业务规则（需求稿 §14 十五条，按裁决修订）

1. 登录一律 Matrix 账号；每账号绑定一个 Orchestrator（`@用户-agent`）。（已建）
2. 群聊可混合真人与 Agent；Agent 消息必须显徽章（agent.message）。
3. 任务可指派给人或 Agent；指派给 Agent 默认落其账号 Orchestrator，由 Orchestrator 按标签二次分派。
4. 任务状态变化 = 房间事件；看板与聊天只是投影（裁决 A）。
5. 需求与设计文档评审通过（R1/R2 + G2）才可作开发输入，验收边界随冻结。
6. 编码 Agent 修改代码前在 /ide 展示 diff；R3 门必须人确认。
7. 高风险操作（提交/推送/合并/删除/发版/关单）默认 HumanGate（§8 清单）。
8. 测试失败自动建缺陷任务并挂父任务；回归通过须 R4 人拍板。
9. 关键交付物一律挂任务或阶段（事件指针，不带制品本体）。
10. 管理者可看他人进展，受 Matrix PL 与 Studio 路由权限双重约束。
11. 任务/消息/文档/代码变更之间可互跳互溯（parentId、artifactRef、taskId 绑定）。

## 6. 非功能需求（需求稿 §12 浓缩）

| 维度 | 要求 | 验法 |
|---|---|---|
| 实时性 | 消息、Agent 状态、任务态、关键执行节点实时同步 | CDP 动线 + 事件断言（M-G sim 全链） |
| 可追溯 | 任务→需求、变更→任务、测试→需求、Agent 行为→日志四条链 | sim 证据导出三件套 |
| 可靠 | 消息可恢复、Agent 失败可重试、状态不脏写 | 幂等投影测试（31/31 先例）+ 打回重试路径 |
| 安全 | token 本地存储、代理权限交集、敏感操作人工审 | 权限负例测试 + always-allow 收口（M-A） |
| 扩展 | 新 Agent 类型/新阶段/新卡片类型可插拔 | 协议 schemaVersion 降级只读 + 开放枚举 |

## 7. 成功指标（v1 验收口径）

1. sim 全链（六阶段 × R1-R4 × 会签 × 打回 × 催办）断言通过率 100%。
2. 双真机真实小需求 G1-G6 走通且证据三件套（房间消息、git 图谱、工件）完整。
3. 评审门人机校验零漏放：bot 冒发任何 R/G 人审 verdict，读端 100% 忽略并告警。
4. 双端一致性抽测：同一任务在两台 Studio 投影状态一致（幂等投影保证）。
5. /ide 既有回归 21+ 项与 v12 壳层动线零回退。
