# 全流程推演方案与推演报告的本体论透镜分析

> **文档定位**：用本体论六要素（实体、属性、关系、规则、行为、事件）与六模块框架（统一业务词汇表/实体关系模型/业务规则与约束引擎/细粒度权限安全模型/全域数据源映射/`业务动作与工作流闭环`），对《全流程推演方案》V8.18 与 run15 推演报告做一次覆盖度诊断。参考材料：两篇本体论文章（《央国企数据本体建设核心方略》《2026 本体建模全景研究报告》）与仓内全部实现锚。本文只诊断与建议，不改正本；引用锚点均为文件路径与行号，可逐一反查。

主旨一句话：**这套推演体系在模块六（`业务动作与工作流闭环`）上已达到参考文章所述的终极形态并有实证，在「规则引擎」（模块三）上强而偏科，而整个语义层的地基——「统一词汇表」（模块一）与「数据源映射」（模块五）——是当前最薄弱的两块，报告层对本体的呈现近乎空白。**

## 一、为什么这个框架适用

两篇参考文章的共同判断：本体的价值不在描述数据怎么存，而在定义业务上「是什么、意味着什么」，并让 AI 在此之上走完「查询→推理→执行」的全过程。文章二给出的企业本体六层结构（类/属性/关系 + 规则/权限/动作）与本分析采用的六要素六模块框架同构。

全流程推演方案定义的系统恰是一个「本体驱动」的极端案例：15 个 AI 员工在 26 步主链上协作，靠的不是共享数据库，而是**共享语义**——判词、双凭证、问题单、六道关卡这些概念在所有 agent 之间必须一词一义，否则整个执法体系失灵。方案纪律里「术语首现给白话括注」「一词一义」「代号不入词表即 WARN」等条款，本质上都是在做语义治理。因此用本体论透镜看它，不是套用外来框架，而是给它已有的实践命名、并找出下一层的缺口。

## 二、六要素实证盘点

先确认六要素在方案与报告中的实物载体，再评估模块。每行给锚点。

| 要素 | 方案/系统中的实物 | 锚点 |
|---|---|---|
| 实体 | AI 员工（15 角色）、任务卡、看板、需求单（RFD）、关卡（G1-G6）、判词、问题单、证据帧、轮次（run）、技能 | 种子本体 16 实体类型（Agent/Human/Role/Squad/Task/Board/Gate/Patch/Repo/WikiPage…四类组织） | `custom/server/ontology/ontology-seed.ts` |
| 属性 | 任务卡字段（assignee/status/room 锚）、state.env 状态键（g1_frozen…report_done）、实体数据属性（name/model/scope，带 required 与情态） | `ontology-seed.ts` dataProperties；`state.env` |
| 关系 | 26 步 DAG 依赖、RACI 责任链、看板归属、playsRole/belongsTo 等对象属性 | 种子本体 12 对象属性（Domain-Range 显式）；方案 §2.9 责任总表 |
| 规则 | 六闸判据、QGate 45 门、研发自测门禁 56 项、纪律条款 1-43、SHACL 数据契约、六条公理 | 方案 §5.2/§5.3/§4.3；`ontology-validate.ts` |
| 行为 | 派发、认领即 spawn、结卡、审批（四态）、打回熔断、唤醒令、监控代行 | 方案 §3 步条；aipay-scenario.sh |
| 事件 | matrix 事件号、issues.log 行（ISSUE/DISP）、task_events（gate_blocked/column_transition）、approved.events、判词结论行 | 方案 §5.4 报告规范；run15 报告第 8 章 |

结论：六要素在系统内全部有实物载体且互相咬合（行为产生事件、事件受规则裁决、事件回写实体的属性）——这已经超出「有本体」的层次，进入「本体在执法」的层次。

## 三、六模块覆盖度评估

评级分四档：**实证**（有实现有运行证据）、**在构**（有骨架无运转证据）、**缺位**（无对应物）、**偏科**（局部强整体弱）。

### 模块一：统一业务词汇表 —— 缺位（六模块最弱项）

用户框架要求：全域术语唯一 ID、标准名称、别名、业务定义、归属部门。现状是三套词表并存且无一套满足要求：

| 词表 | 规模 | 有无唯一 ID | 有无别名 | 有无归属 | 位置 |
|---|---|---|---|---|---|
| 报告术语词表 | 59 条 | 无 | 无 | 无 | `simharness/mux/glossary.txt` |
| 方案导读词表 | 14 词条 | 无 | 无 | 无 | 方案总述 |
| 判词/结论行词表 | 三态+各闸判词 | 判词字面即 ID | 无 | 无 | 方案 §5.3/生成器 |

「同物异名」的实例在报告语言三规矩里被点名过（问题登记动作的写法曾有四种变体轮换，run15 词典卡片留有实测记录）。术语唯一 ID 与别名机制缺位，意味着「ISSUE 行」与「问题登记行」、「DISP」与「处置结论行」是否同一概念，全靠人读上下文判断——这正是文章二所说「每年超 58% IT 预算消耗在语义对接」问题的微缩版。

### 模块二：实体关系模型 —— 在构（中上）

已有：16 实体类型带四类组织法（协作主体/工作对象/知识资产/运行环境）、12 对象属性带 Domain-Range 约束、disjointWith 互斥公理、每条带国标情态分级（应/宜/可）、IRI 命名空间与版本快照回滚（`ontology-seed.ts` 头注与 `ontology-store.ts`）。

缺口一：**基数约束（cardinality）缺失**。用户框架点名「基数约束」——如「一个任务卡必须有且仅有一个 assignee」「一次推演恰有六道关卡」。当前对象属性只有 Domain-Range（值域类型），没有 minCardinality/maxCardinality，多值单值不可判。缺口二：核心实体覆盖不全——需求单（RFD）、判词、证据帧、轮次（run）尚不在 16 实体之内，而这些恰是推演域最高频的概念（它们目前只活在方案散文里）。缺口三：看板摄取只进四类实体（任务/执行人/依赖/运行清单），与种子本体 16 类相比摄取面窄。

### 模块三：业务规则与约束引擎 —— 偏科（约束强、推理弱）

强侧（约束校验，相当于 SHACL 形状门）有三层实证：写入即校验（error 拒写 422）、全量校验三档违规（`ontology-validate.ts`，19.7K 实现量）、结卡三路线（登记/执行式门 validatorExec 当场拦截/字面量门）——run15 报告与方案 §2.6.1 有完整判据与事件留痕（gate_blocked）。

弱侧（推理，相当于 SWRL/SPIN 规则链）没有对应物：「涉敏需求→G2 前置安全评审→SECURITY-GATE-PASS」这条规则目前由方案散文+驱动脚本 if 分支承担，不是本体里可查询的规则对象。用户框架说的「风险判定、合规校验自动化推理」，在现有系统里等价物是 QGate 45 门+判词语义，但它们游离于本体之外——判词规则无法被本体引擎反查「这条判据依据哪条公理」。

### 模块四：细粒度权限安全模型 —— 偏科（流程级强、数据级弱）

流程级（动作权限）已实证且相当细：审批四态（once/session/always/deny，超时 fail-closed）、看板围栏（assignee 必须匹配板级团队名单，09-26 实锤「填错=永远认领不到」）、五角色边界单一事实源（over-delivery 轮立）、涉敏安全评审四查。

数据级（属性权限）缺位：没有「角色 X 可见实体 Y 的属性 Z、其余脱敏」的机制。现有脱敏是路径级的（报告宿主环境脱敏把家目录替换为占位），不是本体属性级的。操作审计有（git 留痕+task_events），但审计对象是「谁动了哪张卡」，不是「谁读了哪个实体的哪个属性」。

### 模块五：全域数据源映射 —— 缺位（与模块一并列最弱）

已有的是一条单向通道：看板数据一键摄取进本体（`ontology-ingest.ts`，替换幂等，回执四计数），以及 @ontology 第八数据源（IDE 侧）。缺的是用户框架的核心物：**本体概念与物理载体的显式映射注册表**——哪个本体实体对应哪张表/哪些字段/哪个 API 端点/哪类非结构化文档。当前映射关系散在代码与散文里（如「任务卡↔kanban JSON」「轮次↔runs/<id>/state.env」「判词↔matrix 事件」都是约定俗成而非注册在案）。非结构化文档（分析稿/测试报告/复盘文档）完全在映射之外。

### 模块六：`业务动作与工作流闭环` —— 实证（六模块最强）

这是整套体系的设计中心，且已完整运转多轮：

- 规则触发动作：结卡校验违规→gate_blocked 拦截；两轮打回→熔断拒绝执行；涉敏标记→安全评审前置。
- 动作生成任务：判词通过→驱动推进下一步派发；违规聚合→治理冲突收件箱（kind=ontology，待裁决徽标「主动找人」）；结卡轮询环（watch）持续驱动。
- AI 从查询到执行：agent-bridge（`/api/ontology/agent-bridge/validate-task`，限本机回环+token）让 agent 直接调校验；hermes 认领即 spawn。
- 反馈环：run15 监控代行 8 次全部 DISP 留痕（唤醒令×3、安全修复链 1h08m、交卷令等）——「感知-决策-执行-反馈」四环全齐，且有台账可审计。

对照文章一的动态本体三层，本系统三层动态都有实证：对象层（看板摄取即时进本体、技能指纹感知局部更新）、逻辑层（方案按轮演进 V8.x、按轮注册表每轮规则真值、SHACL 版本快照回滚）、动作层（监控代行与自愈监督器）。对照文章二的 Palantir 六层，规则/权限/动作三层的「动作」层是本项目最深的护城河。

## 四、报告层的本体呈现 —— 近乎空白

run15 报告正文「本体」一词仅出现 1 次（语义体检页签相关图注）。这意味着：本体层在系统里执法（拦了多少结卡、检出多少违规、摄取了多少实体），在报告里不可见。方案 §2.5 已定义「本体证据面」端点（spec/ingest/validate/watch/status/export 五个），但报告生成器没有消费它们。六模块的「可审计」价值（监管刚需，文章二驱动力第 5 条）因此在报告层落空——读者无法从报告回答「本轮本体层做了什么、拦了什么」。

## 五、与参考文章的路径对照

文章二推荐「中间向外」路径：从核心共识业务概念切入，先固化核心层再双向扩展。本系统的实际演进恰好符合：从任务/看板/关卡这些最高共识概念起步（看板摄取四实体），向上抽象出种子本体 16 类，向下细化结卡校验三路线——没有走「全域一次性建模」，也没有纯自底向上。这个路径判断对后续补缺口同样适用。

文章一的「机制嵌入」主张（本体标准刚性嵌入业务流程，一票否决）在本系统已有等价物：结卡校验的 blocking 档、写入即拒 422、审计 A7 无释义代号 WARN。补齐模块一/模块五时应沿用这个「治理内嵌」传统，而非另起台账。

| 序 | 建议 | 对应模块 | 依据 | 量级 |
|---|---|---|---|---|
| P0-1 | 术语表升维：glossary.txt 增加唯一 ID（如 `term:issue-row`）、标准名、别名列表、业务定义、归属（角色/部门）五字段；三套词表向它对齐，方案十四词表与判词表标注对应 ID | 模块一 | 同物异名已在报告层实测出现；词表是其余五模块的寻址基础 | 中（一格式迁移+回填） |

| P2-1 | 判词规则入本体：把六闸判据与 QGate 门禁登记为规则对象（引用 SHACL shape/纪律条款编号），使「判据↔公理」可反查；推理执行仍留在现有门禁，先做可查不做 SWRL 全量推理 | 模块三 | 推理弱是因为规则游离本体，先治可查性 | 中 |

## 七、总判断

这套推演体系用治理实践证明了参考文章的核心命题：AI 落地的前提是被理解而非被堆砌。它的独特贡献在于把本体做成了**执法层**（结卡拦截、写入即拒、熔断复议）而不只是描述层，并在动作执行上跑出了多轮可审计实证。它的真实短板在语义层的地基处——词汇无 ID、映射无注册、报告不呈现——这三件都不是能力问题而是登记问题，补齐成本低、复利高。按「中间向外」路径，下一步不是引入更重的推理引擎，而是把已有的 16 实体、59 词条、五端点这些存量资产编目成册（唯一 ID+映射注册+报告呈现），让语义资产从「系统内生效」走向「报告层可审计」。
