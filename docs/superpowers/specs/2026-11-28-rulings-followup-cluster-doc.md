**P1 建卡层的跨域检查**

- 结论：这道检查现在哪里都没有，没有现成的补丁可以收进本仓。技能文件本身是「怎样恢复这道门」的配方，内容完整，不该改写。

**P2 完成交接的键名**

- 宿主上的本体文件 `~/.hermes/profiles/_shared/02-org-orchestration/ontology.md` 是 v1.5（2026-11-22 用户拍板），写明运行时会把别名 `artifacts` 归一成 `artifacts_produced`、`decision` 归一成 `decisions`，补写项记入 `handoff_autofilled`。宿主运行时由补丁 `hermes-cq16-handoff-normalize.patch`（11-24 起并入 `hermes-kanban-consolidated.patch`）实现了这项归一。

**P4 并发 L0 基线**

- 宿主上两份配置（主配置与调度入口档位配置）都是 8 和 5。宿主上的看门狗脚本与仓内那份逐字节相同。
- 看门狗脚本里有三种说法：文件头写「L0 NORMAL 12/4（用户批准基线）」；常量 `LEVELS["L0"]` 是 8 和 3；`team/shared/profiles.yaml` 共享段与调度入口的配置模板是 8 和 5；根模板 `team/config.yaml` 是 8 和 3。
- 常量只在配置读不到时兜底：正常运行时脚本在降档那一刻从配置里读出当前值记作基线，回升时写回这个基线。所以实际生效的 L0 是 8 和 5。
- 另查实：网关内嵌的派单器并发设置是「启动时读一次，重启才生效」（`runtime/gateway/kanban_watchers_dispatcher.py` 的 `_DispatcherSettings` 说明）；脚本文件头与参照文档写的「改配置后 60 秒内生效」只对独立运行的派单循环成立。

**P5 两个「永不触发」的定时任务**

- `team/profiles/orchestrator/cron/jobs.json` 里 `skill-mining-weekly` 与 `ttvv-monthly-report` 的备注写「调度改为永不触发(2/31)，由统一 Loop 经 cron run 驱动」，存下来的表达式却是 2 月 29 日。宿主上这两个任务的表达式相同，下次运行时间是 2028-02-29。
- 用真实的排程库实测：不存在的日期（2 月 31 日）校验能过，但计算下次运行时间时报错，调度器存不进去；把「2 月 29 日」再叠加「周一」，按 cron 语义变成「2 月的每个周一」，更糟。所以用 cron 表达式做不到「永不触发」。
- 调度器支持的另一类排程「每隔 N 分钟」没有上限。用仓内调度器代码实测 `36500d`（100 年）：解析为 52,560,000 分钟的间隔，下次运行落在 2126 年。
- 不能用「暂停」：`hermes cron run` 会把任务重新置为启用并恢复原排程，而宿主上的统一夜间循环正是用 `hermes cron run <编号>` 驱动这两个任务的。
- 仓内这份登记是 10 月 28 日的参考快照（14 项），宿主上的活登记已有 21 项，改仓内快照修不了宿主。
