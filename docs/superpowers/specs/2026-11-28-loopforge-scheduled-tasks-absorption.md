## 一、这轮要你决定什么

### 1.1 三个决定性发现

**发现一：它的「查重、水位」两条经验是事故后补的，而本仓现在没有这个病情。**

文章正文把五个定时任务写得很顺，截图却是另一回事。调研任务读到 50 条 Issue，其中 43 条是机器人批量生成的（24 条架构优化单、19 条竞品调研单），真实反馈只剩 7 条。架构优化 PR 积压到 31 个，才加上「满 10 个立刻停手退出，连沙箱都不拉起」。同源仓库的代码、文档、配置里搜不到「水位」「无重构」「LGTM」「本轮无事可做」「单测补充」「架构优化」任何一个词，这些规矩只活在它线上平台的提示词里。

本仓的读数（2026-11-28 只读查询看板库）：73 个库共 2748 张卡，其中 `gap-register` 自动登记 258 张、`auto-decomposer` 77 张；标题归一后重复多出的卡 50 张，约占 2%；未完成卡合计 68 张。所以这条判「记档待定」并定触发条件，现在不建刹车。文章自己的话也是这个意思：别为了凑产出硬折腾健康的代码。

**发现二：红线只写在提示词里，这是它最不该学的地方；本仓有执行层强制，但有一处设计在空转。**

源码里有一条测试断言：定时任务的提示词必须明写「当前审批模式为「完全权限」」，且不得出现「每次确认」「供用户确认」（`internal/httpapi/assistant_schedule_test.go:129-131`）。也就是平台强制把定时任务切到完全权限档，主对话里选的确认档对它不生效，「不合入、不直推主干」全靠提示词第一行。本仓 `AGENTS.md:64` 明写「权限与沙箱不能只靠提示词，边界上的确定性检查优先」，宿主侧创建定时任务时还会扫描提示词里的危险命令（`vendor/hermes-agent/cron/prompt_scan.py:1-16`）。

空转的一处：`custom/server/autosched/automation-schedule.ts:25-36` 的「到期自停＋无人值守授权」判定，全仓只有它自己的测试在调用，没有生产调用点。接进去还是退役，需要你裁决（决策 D3）。

**发现三：现在值得做的只有一件小事，给「测试没有有效断言」补一道机检。**

文章的审查清单把「新增逻辑缺少单测，或测试没有有效断言」列为必须打回的情形，但 LoopForge 自己没有机检，靠模型判断。本仓也没有这道守门。仓外粗扫的读数：1319 个测试文件、10680 个用例，词法上没有任何断言的 20 例。逐条判读：6 例是粗扫误报（用例标题的字符串里嵌着 `test(` 字样，或正则字面量里的花括号扰乱了括号配对）；10 例靠「不抛异常即通过」的 `execFileSync`，或靠同文件里带断言的辅助函数，属合法，例如 `custom/server/governance/__tests__/governance-contracts.test.ts:47-49`；1 例是有意不断言的校准探针；真坏样本 3 例。真坏样本是 `custom/client/loop/__tests__/saas-store.test.ts:26` 与 `:50`，注释写着「验证建表语句被查询」「验证连接池已结束」却没有断言；以及 `simharness/tests/mechanism-behavior.test.ts:252`，标题写了三条行为，函数体只造了夹具文件就结束。有真实坏样本，守门就有效力可证。

### 1.2 其余参考

- 宿主侧的定时任务比 LoopForge 完善得多，这一面不需要向它学。工具集可以收窄（`vendor/hermes-agent/cron/jobs.py:1684-1691`），连续失败默认 3 次提醒人（`vendor/hermes-agent/cron/scheduler.py:138-160`），执行记录带触发来源（`vendor/hermes-agent/cron/executions.py:249-263`），错误按特征归并成事件（`vendor/hermes-agent/cron/incidents.py`），供应商配额窗口关闭时把下次触发挪到恢复点（`vendor/hermes-agent/cron/quota_hold.py:1-9`）。
- 产品内的工作流调度器代码完整（时区、上轮未完则跳过、停机错过的触发跳过、可指定起始节点，`vendor/hermes-studio/packages/server/src/modules/studio/services/workflow/schedule.ts:139,188-190,203`），线上四张表都是 0 行。
- 独立评审「评审者不参与实现」本仓已有更严的等价物：作者、冷读审阅者、裁决人三角色分离（`docs/superpowers/specs/2026-11-19-independent-review-protocol.md:71-73`）。
- 「从这里重跑」与打回携带上游产物，是首轮规格明示延后的事项（`docs/superpowers/specs/2026-11-16-loopforge-sop-trust.md:171`）。LoopForge 为此有一整套字段：打回到哪个节点、失败后是中止还是打回、重做是定点修还是整段重来、携带哪些产物、最多尝试与最多打回次数（`internal/domain/workflow.go:73-80`）。
