# SwarmStudio 需求分析（重论证正本）

日期：2026-10-16
状态：v1——待用户评审，评审通过即需求冻结（本产品自己的「G1 需求冻结」）
上游：全流程推演方案正本（`2026-10-05-mux-v8-fullflow-plan.md`，26 步主链/六闸/交付物/责任总表）
取代声明：2026-10-16 用户裁定「设计并没有定稿，从头开始再论证」——此前总设计定稿、四件实施级详设、实施计划**全部降级为候选方案**，以本文冻结后的需求为唯一上游重新审定。

## 〇、结论先行

1. SwarmStudio 界面的第一用户是**主管（用户本人，总指挥）**：20 轮推演中用户手工做的每一类动作（每 20 分钟手动观察一窗、手动查运行状态、人工放行关卡、人工发收尾指令、人工处置代偿与密钥）就是被反复验证的真实需求。AI 工作者不点界面——他们的「界面」是 Matrix 消息与看板 API；界面是给人监督与决策用的。
2. 由此提炼出**14 条功能需求＋8 条非功能需求**，每条带事故或用户指令的证据锚。候选设计大部分经得起这份检验（三中心归位、推演中心六签、治理问责面、设置三页），但有**两处真缺口**（密钥治理无家、容量风险只读不提醒）和**一批无使用实证的推测性设计**（角色镜头层、四类锚全量检索）需要降级或后置。
3. 此前设计流程的方法论错误要承认：先做了功能盘点与归属对账，后补产品定位，**从未做过需求分析**——「123 行对账」保证不丢既有功能，不保证该做的都在。缺口两件即是证据。正确顺序应是：需求冻结 → 架构与界面重审 → 再谈开工。

## 一、用户与使用场景（谁是用户，拿证据说话）

| 干系人 | 真实使用证据（锚） | 需要界面做什么 |
|---|---|---|
| **主管（用户本人，总指挥，核心）** | 影子观察会话「每 20 分钟一窗」手工盯轮（前会话标题即此）；run20 G2 悬置 12 小时靠人工研判放行（`2026-10-14` 复盘，runs/20261015-v8-run20/state.env.bak-rollback 实物在档）；每轮开跑手动过 prelaunch 十六项；run20 中段系统盘 96% 靠肉眼发现后手工清理 12.5GB | 一屏开车（状态/停滞/闸/代偿）、待我出手的事集中呈现、介入动作留痕、开轮降手工 |
| AI 工作者（15 编制 agent） | 派发词经 Matrix 下达、任务经看板 API 流转、证据在仓与日志（方案正本 §2.9 责任总表） | 不需要面向它们的界面；它们的产出要能被人反查 |
| AI 治理角色（闸口裁判/工单员/接棒员/监督器/哨兵） | 判词/journal/台账/审批事件均为其产物（humansim 631、orgloop 636 已产品化） | 是数据生产方；界面消费其产物并标注来源（provenance） |
| 运维（用户兼任） | 部署窗纪律、launchd 看守、密钥轮换（win10 迁移包泄漏后用户硬待办手工轮换，2026-10-14 复盘档） | 变更留痕、风险预警、部署安全 |
| 外部观演/评测（未来） | 报告多格式导出、demo 姿态（方案正本 §1.5） | 报告可信、演示路径清晰——本期弱需求，不驱动设计 |

**场景主轴**：一轮 20 小时量级的推演里，主管的完整工作循环是「开轮（手工过检）→ 周期观察（手工盯）→ 发现异常（手工翻日志定位）→ 介入决策（人工放行/打回/发指令）→ 收尾验收（人工对账报告）→ 复盘治理（人工处置问题单与代偿）」。**SwarmStudio 界面的存在理由＝把这个循环里的手工动作逐件产品化，同时不破坏诚实呈现。**

### 3.2 降级或后置（无使用实证或高频存疑）

| 候选设计元素 | 问题 | 处置建议 |
|---|---|---|
| 角色镜头层（旅程条/四维带/一人四镜头/四张角色首页） | 「一人四镜头」是设想未验证；四张首页是推测性便利设计，零新数据面的前提也意味着零新价值面 | 维持排期最后；需求冻结时决定去留（Q1） |
| 证据库四类锚全量检索 | 四类里高频的是事件号与提交号；卡号/房间号检索低频 | 先做两类高频，低频挂账（不删） |
| 场景编排深做（场景注册表数据化） | 依赖 R11 拍板 | 等 Q2 |

### 3.3 真缺口（需求有、设计无）

1. **密钥/凭证治理无家**：R13 的密钥半句在 7 个签里找不到承接——泄漏轮换靠手工清单（ACCOUNTS.md），治理中心无台账无轮换记录位。
2. **容量风险只读不提醒**：度量体检成本卡是只读数字；96% 事故的教训是「需要主动亮灯」而非「需要再看一张表」。
3. **主管收尾指令工具化**：精准三步收尾令（结论行＋翻卡＋禁再跑）目前人肉发——可作为 R5 介入卡的延伸动作模板，候选设计未覆盖。

### 3.4 方法论检讨（自我批判，记档防复发）

1. 顺序错了：先盘点归位、再补定位、宣布定稿——**需求分析缺席**。自家流程要求 G1 需求冻结先于设计，这次跳了级。
2. 对账完备≠需求完备：123 行保证「旧的不丢」，不保证「新的都在」——3.3 两件缺口即为实证。
3. 部分新增件立项理由写错：按「能力已落地」立项（D 组锚定补丁与端点），正确的理由应是需求锚——监督面板恰好有 R10 强锚（结论对、论据错也要改）。
