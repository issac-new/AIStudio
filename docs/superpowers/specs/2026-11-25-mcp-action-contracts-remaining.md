## 变更

一句话：把 `ekko-studio` MCP 服务里尚未登记的 44 个工具，按各自的副作用逐个定级并登记进动作契约，使它们在启用了闸门的档位里可以被智能体调用。

背景。代理运行时有一道动作闸门（`runtime/agent/action_gate.py`）。工具不在契约里登记，闸门就按默认策略「不可逆」拦下。此前只有交互服务（`ekko-studio-interaction`）的 10 个工具登记过（批二），其余三个服务——用法（`ekko-studio-use`，29 个）、浏览器（`ekko-studio-browser`，13 个）、接口（`ekko-studio-api`，2 个）——共 44 个工具都没登记，在 `orchestrator` 等启用了闸门的档位里全部不可用。

具体落地：

1. `team/profiles/_shared/action-contracts.yaml`：`actions` 表追加 44 条，按服务分三段，每条含 `side_effects`、`reversible`、`level`、`note` 四个字段。键是模型发出的工具全名。
2. 守门 `custom/server/ekko-ui/__tests__/ekko-ui-patch-wiring.test.ts`：把「注入态 MCP 脚本里每个工具都在契约有登记」这条断言，从一个服务扩到四个服务。
3. `docs/DESIGN.md`：补一段，写明这道闸门的实际语义与登记的后果（此前设计文档里没有它的位置）。

明确不在本批：

- 给任何工具加参数级契约（`arg_contracts`）。这是用户在三个做法里选 A 时明确放弃的（见 D2）。
- 给通用接口调用（`ekko_studio_api_request`）加接口白名单。那是产品改动，要在 MCP 脚本里实现。
- 改闸门本身的行为。

## 决策记录

- **D1：定级的依据是每个工具实际调用的接口与方法，不是工具说明的自述**。从注入后的 MCP 脚本里机械抽出每个工具的处理分支：调哪个接口、什么方法、有没有按 `action` 分支的子动作。工具说明只作旁证。定级标准有三条：只读的直通；只写本人本档位的数据、可撤销、不越出本机的直通；不可逆删除、越出本机、触及凭据或隐私、会再起一轮自主运行的，标为不可逆。
- **D2：只登记，不加参数契约（用户裁决，三个做法里选 A）**。调研中发现这道闸门的实际语义与字段名给人的印象不同，见 D3。由此有三个做法：A 只登记，44 个工具在启用闸门的档位里全部可用；B 登记并给 17 个危险工具加参数契约，让它们无论怎么调都被拦，代价是没有任何放行路径，而且「把白名单写成空的来全拦」是借校验器的特性，不是它的设计用法；C 折中，只读与可撤销的直接登记，五个「部分动作安全」的用白名单放行安全动作，其余 12 个危险工具暂不登记。用户选 A。理由（用户的裁决，非本规格推断）：这些工具本来就是产品的正常功能，由智能体在用户面前直接调用；把它们拦住，等于在启用闸门的档位里废掉删会话、起对话、操作浏览器这些日常能力。
- **D3：这道闸门是「登记闸门」，不是权限闸门（调研结论，用闸门代码实测）**。它只拦没登记的工具。对已登记的工具，`reversible` 与 `level` 只是分类标签，不构成拦截条件：源码里受控级别走的分支是「参数级契约校验」，参数合规就放行。既有的 `acp_send`、`delegate_task`、`memory`、`cronjob` 这些标为不可逆的动作，必填参数齐全时全部放行。它也没有「问过用户再放行」的路径。所以本批写进契约的「不可逆」只是如实标注该工具的副作用，不代表闸门会拦它。闸门模式：`action_gate.mode` 在 `orchestrator` 与 `skill-eval-sandbox` 两个档位是 `enforce`（真拦），其余档位未设，走默认的 `shadow`（只记录到 `~/.hermes/profiles/_shared/action_gate_shadow.jsonl`，不拦）。
- **D4：守门按服务全覆盖，键名与脚本逐字对应**。守门从注入态 MCP 脚本里抽出全部工具定义，要求每个工具都在契约里有登记。服务名在配置里用连字符（`ekko-studio-api`），上线时净化成下划线（`mcp__ekko_studio_api__…`），闸门拿到的就是这个净化后的全名，所以键必须逐字一致。以后新增 MCP 工具而忘了登记，守门当场变红。
- **D5：条目由脚本从 MCP 脚本生成，不手敲**。44 个键逐字一致是硬要求，手敲容易错一个字符就等于没登记。生成脚本先校验定级表与脚本里的工具名一一对应（无多无少），不一致直接退出。

## 任务卡

### 完成条件

在启用闸门的档位里，44 个工具逐一被闸门放行；契约里每个键都能在 MCP 脚本里找到同名工具，脚本里每个工具都能在契约里找到同名的键；守门在删掉任一条登记后变红。

### 输入与来源

工具名、所属服务、处理分支来自注入后的 `vendor/hermes-studio/bin/ekko-studio-mcp.mjs`；定级来自逐个读处理分支；契约正本是 `team/profiles/_shared/action-contracts.yaml`。

### 工作流边界

只改契约正本、守门测试与设计文档。不部署到宿主（`team/` 是脱敏正本，部署走它自己的通道）。

### 工具与副作用

无运行时副作用。契约是声明式数据，改它只影响闸门的判定表。

### 结果与证据

契约 44 条新登记；守门断言覆盖四个服务；闸门代码实测 54 个工具全部放行；见「验证」。

### 异常与恢复

改错了回滚这一个提交即可，契约没有迁移、没有状态。

### 验收反例

出现以下任一情形即判失败：契约里有一个键在 MCP 脚本里找不到同名工具（键写错）；脚本里有一个工具在契约里没有登记（漏登记）；删掉一条登记后守门仍是绿的（守门空转）。

## 验证

实测结果（2026-11-25）：

1. 闸门代码实测（`runtime/agent/action_gate.py` 的 `check_action_contract`，对注入后 MCP 脚本里的 54 个工具逐个判定，入参给空对象）：登记前（主干契约）放行 10、拦截 44——放行的正是批二登记的交互服务 10 个；登记后（本批契约）放行 54、拦截 0。对照组：未登记的假工具名 `…__ekko_studio_not_a_tool` 仍被拦，报 `not registered`——闸门的兜底没被破坏。
2. 契约 YAML 能被闸门加载器解析：动作总数 57 → 101，其中 `ekko_studio` 四个服务共 54（交互 10、用法 29、浏览器 13、接口 2）。
3. 守门（`ekko-ui-patch-wiring.test.ts`，动作契约段由 3 例扩到 4 例，全文件 14 例）：脚本里四个服务的每个工具都有登记；契约里每个键都在脚本里有同名工具；界面六工具在位且四服务登记数为 10/29/13/2；键不带连字符、四服务各有一段。
4. 变异探针两个方向：删掉 `use_session_delete` 一条登记 → 「每个工具都有登记」与「登记数量」两条断言变红；把 `use_usage_stats` 的键改错一个字符（`use` → `usx`）→ 「每个工具都有登记」「每个键都有同名工具」「登记数量」三条断言变红。两处还原后 14 例全绿，契约文件与备份逐字节一致。
5. 改动规模：契约 +233 −0（纯文本插入，没有解析重排）；设计文档 +8；设计索引重生成 0 problem（772 → 773 份）。
6. 合并档回归：见提交说明。

过程记录（诚实声明）：① 规格里定级表的「只读」个数初稿写成 21，核对生成结果后更正为 20（总计 44）；② 闸门实测脚本第一次把工具名拼成了 `…__ekko_studio_ekko_studio_browser_tabs`（前缀重复，脚本里的工具名本身已带前缀），54 个全被判为拦截——是测试脚本的错，不是契约的错，修正拼法后结果如上；③ 守门第一版从键里反解服务名时映射写错，被自己新加的断言当场拦下，改为直接比对完整键。
