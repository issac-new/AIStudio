导读：美团把近 200 个评测指标跑在真实业务上，数字站长业务的人机一致率做到了 99%。支撑它的不是某个聪明的裁判模型，而是一整套工程范式——Rubric 二元化、Pass@k 门禁、E2E 与过程双轨评测集、归因双路径。本文基于其公开技术资料（评测白皮书、WOWService 技术报告、KuiTest 论文等）做一次系统拆解，8 条工程启示可直接迁移到你自己的 Agent 评测上。

01 问题定义：传统评测范式为什么失效

Agent 评测与传统 ML 评测存在本质差异。传统 ML 评测回答「算得准不准」，大模型评测回答「模型能力强不强」，而 Agent 评测的对象是一个耦合系统：

System = Model + Prompt + Skill/Tool + Memory + State + Business Flow

在这个耦合系统里，单一输入的输出具有随机性：Temperature 采样、Tool 非确定性返回、多轮上下文漂移。因此传统「单跑一次比对 ground truth」的评测范式在统计上不成立。美团图灵团队将评测目标形式化为四层：

层级
评估对象
典型信号
Result
端到端交付物
任务完成率、交付物可用性
Trajectory
执行过程
规划合理性、步骤稳定性、Tool 调用序列
Efficiency
资源消耗
Latency、Token、步数、成本
Risk
安全与越权
越权操作、数据泄露、红线触发

▲ Agent 评测的四层目标：由表及里，Risk 层一票否决

关键结论：两个 Agent 终态都「正确」，但一个路径收敛可复现、一个靠搜索空间暴力采样命中——在 Result 层不可区分，在 Trajectory 层差异巨大。这就是 Trajectory Evaluation 取代 Response Evaluation 的根本动因。

02 一致性工程：人人一致 → 人机一致

主观评测的统计噪声是规模化的头号敌人。同一个客服回复，五个标注员能打出五种分。美团的工程解法分三步：

▍独裁者 + 背靠背标注

指定一名领域专家（「独裁者」）作为 Rubric 最终仲裁人，避免多人共识漂移；多人背靠背盲标，计算标注者间一致性；分歧样本回流独裁者修正，再扩散到全体标注者。

▍Rubric 下钻与二元化

把连续模糊评分（「口语化程度 0–10 分」）拆成二值断言集合：

 原 Rubric（不可对齐）：骑手外呼回复是否口语化？打分 0-10
↓ 下钻后（可对齐）
 C1：是否以「您」指代骑手？[是/否/未知]
 C2：是否使用「甭客气/明儿见」类词汇？[是/否/未知]
 C3：是否包含「吧/呢/那个」语气词？[是/否/未知]

统计意义：把序数回归降维成独立二分类，每个断言的 Cohen's κ 可单独监控；unknown 占比是 Rubric 定义不充分的诊断信号——unknown 多说明边界模糊，继续下钻。上线阈值：单条 Rubric 人人一致率 ≥ 85%，人机一致率 ≥ 90%。

▍量化收益

数字站长：人机一致率做到 99%；Beam 业务：二元化改造后 62% → 92%；指标规模：从冷启动 20+ 个，一年推全扩展到近 200 个。

03 评测集工程：三元组、双视图与四类资产

▍Task 的形式化定义

Task = (Problem, Reference, Metric & Rubric)

长程 Agent 阶段，Reference 从可逐字比对的字符串迁移为 Expected Behavior，评测依据 = Transcript（轨迹）+ Outcome（环境终态）。这里有个容易被忽略的定义：Outcome 以环境终态为准——航班 Agent 输出文本「已预订」不算通过，SQL 数据库里存在对应记录才算通过。

▍端到端视图 vs 过程视图

04 在线评测：三类指标联合诊断 + 归因双 Loop

▍三阶段灰度

影子模式（Shadow，真实流量旁路不生效）→ AB（分流验证业务指标）→ 巡检（Probe，持续探活）。巡检具备双重属性：评测属性（能力稳定性）+ 监控属性（信号沉淀供归因）。

▍三类指标联合判读

类别
指标
Availability
Skill/Tool 成功率、失败率、P95 超时率
Cost
Token 消耗、平均步数、单任务耗时
Behavioral
任务类型分布、Skill 调用频次分布、平均轮次

联合判读的威力：

 完成率降 5pp + 某个 Skill 失败率 2%→15% = 工程故障；
 完成率降 5pp + Skill 全部正常 + 「数据对比类」任务占比 10%→35% = 用户结构漂移，新场景能力不足。 

单看任何一类指标，都会误判归因方向。

▍归因双路径：Agent Loop 与 Rubric Loop

▲ Bad Case 归因双路径：修系统之前，先确认裁判没错

Bad Case 沿 Trace 归因后分叉：Agent Loop 修复 Prompt/Skill/路由/上下文，回测后上线；Rubric Loop 校验是否评测标准本身判错，判错则迭代 Rubric 并入库。

只走 Agent Loop 的系统，会把 Agent 优化成「迎合评测分布」而非「解决用户问题」——Rubric Loop 是防 reward hacking 的结构性机制。

05 WOWService：四步判分管线

WOWService（arXiv:2510.13291）上线后 11 项指标全面超越基座：不满意率 -27.53%，满意度 +25.51%。其自动评测管线非常值得抄：

▍评分尺度与四步管线

四档评分：-1（红线）、0（不满意）、1（满意）、2（优秀）。判分管线分四步：

▲ 四步判分管线时序：序数回归 → 并行二分类 → 冲突才仲裁

三个设计要点：

 ① 任务降维：把序数回归（4 档）拆成 3 个独立二分类，每个 judge 决策边界更清晰；
 ② 红线独立：-1 规则最复杂，单独判别避免污染其他档位；
 ③ 冲突仲裁：用更强模型处理边界样本，控制人工抽检成本。 

▍基座隔离评估

基座评估必须与系统工程/外部工具/KB 解耦：数据集来自线上真实流量清洗 + 人工构造，按难度/长度分层抽样，每样本跑 3 次取均值；指标用 total score / usability rate（2-3 分占比）/ perfect rate（3 分占比）。

▍智能体评估双视角

宏观看端到端任务完成效率；微观看轨迹级检查点（执行逻辑、关键中间态）。支撑设施：沙箱完整模拟业务生态（DB、用户模拟器、API、监控日志）。

评测权在转移：ChatAgent 时代的标注链路是「核心评测员 → 外包标注 → 机评对齐」；长程时代压缩为「核心评测员 → 机评对齐 → 规模化」。原因：轨迹信息密度高使人成为瓶颈、Skill 数量爆炸、基座模型能力跃迁。分工固化为：Human 管 Rubric 设计与标准对齐，AI 管规模化执行/初筛/回归，Platform 管沉淀/回放/告警/归因。

长程评测基建七项能力：全链路回放 / Case 管理 / 分层执行沙箱 / Rubric 驱动评测引擎 / 报告与归因 / 版本回归 / 准入准出门禁。

07 KuiTest：LLM 当 UI 测试 Oracle（ICSE 2025）

传统 UI 测试 Oracle 靠手写规则，跨平台（Android/iOS/鸿蒙 NEXT）适配成本极高，且现代 UI 缺陷（如「全部已读」误清空列表）无法用规则穷举。KuiTest 的命题：把 LLM 的人类通识直接用作 GUI Testing Oracle，实现 Rule-free 遍历测试。

两阶段分解——直接端到端判 bug 不可靠，拆成「预测 → 验证」：

Stage 1 组件可供性预测：GUI 截图 + View Hierarchy + SoM 标记 + OCR + 图标库检索 → 输出组件功能描述 + 预测点击后 UI 状态；
Stage 2 交互响应验证：先做像素 diff（无变化 → 标记「UI 无响应」），再让 LLM 判断实际响应 vs 预测响应。 

实验结论（美团 10 业务线）：两阶段方案准确率 86%、召回 85%，三阶段反而下降（额外语义提取让模型忽略 icon 颜色变化等细粒度 bug）；组件识别整体 95.5%，无文本 icon 纯 LLM 只有 13%，加图标库后拉到 95%。工业落地：6 个月 20 业务线、21 万+ Cases；鸿蒙 NEXT 1230 小时遍历检出 34 个有效异常；大前端回归巡检一年检出 140+ 异常。

最后是 8 条可以直接搬走的工程启示：

1. Rubric 二元化是人机一致的前提：序数评分不可对齐，二值断言 + unknown 诊断可对齐；
2. Pass@k 是长程评测的统计基线：单次结果不可作为门禁；
3. E2E 与 Process 集必须双轨：单轨必然在「找不到责任方」或「模块全绿但业务崩」之间翻车；
4. 归因双路径防 reward hacking：只修 Agent 不校 Rubric，系统会拟合评测分布；
5. 环境终态判定：文本声明 ≠ 任务完成，Outcome 以 DB/系统实际状态为准；
6. LLM-as-Oracle 要做任务分解：拆「预测 → 验证」两阶段，配合像素 diff 前置降本；
7. 门禁必须嵌入 CI/CD：脱离流程的质量门禁没有约束力；
8. 冷启动按最小闭环：观测 L1 + 评测集 L1 + 回测 L1 即可，成熟度由最短板决定。
