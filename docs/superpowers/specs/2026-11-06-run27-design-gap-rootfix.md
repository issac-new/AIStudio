## 决策记录

### 一、设计初衷 vs 实际（三条证伪判据的实测面）

1. **「分布式多 agent 按真实公司流程交付」**：六闸 6/6 全过，但净额口径下折扣显著——代偿台账 94 笔 open，其中 `dispatch-preset` 77 笔（派发词由脚本代演人类）、`nudge` 13 笔（提醒代演）、`card-walk-done/backfill` 4 笔（代走 done/代建卡）。**组织自派发在案 0 条**。设计要求的「含代偿/净额双行并列」此前**从未真正渲染**（只有一张代偿类型表），等于用含代偿口径冒充净额结论。本批已补渲染：净额行 = 六闸 5/6（G5 由 director-proxy 代批不计「过」）、已修 0/88、组织自派发 0 条。
2. **「高效并行」**：并行度实测 43%（run11 基线 ~50%），报告如实标注「未达验收线」。但**证伪判据「连续两轮低于基线」不可测**——run24-26 运行产物按轮清理，跨轮对照数据不存。属机制缺口（见设计优化 O1）。
3. **「可审计证据链」**：帧层大面积失效——`frame-no-visible-change` 170 条（去重后 **19 步**前后帧完全相同）、`frame-content-mismatch` 64 条（去重后 **8 步**内容与步骤不符）、`frame-capture-failed` 3 条。报告逐帧有徽章披露，但摘要仍称「58 图次·全部实拍」——摘要与徽章口径打架。本批已改为「实拍可核验 26 步 / 内容不符 7 步 / 前后零变化 19 步」。
4. **「问题单闭环」**：报告一级摘要称「88 键 / 待处置 0 / 处置完整循环率 100%」，同一报告 G6 节又列「105 条 / DISP 0 条 / 待处置 105 条」，代偿节另有 94 笔 open。三个数字各有口径（唯一键 / 事件流 / 代偿），但**并列呈现无时点与口径对齐**，外部读者只能读成自相矛盾。更关键：88 键中**已修 0**、观察 72、延后 16——「100% 完整循环」实为记账循环，非修复循环。本批已拆为双指标并显式标注口径。

### 四、设计优化（需用户裁决或下轮落地）

- **O1 指标留档**：每轮收尾把 6-8 个核心指标（时长/六闸/并行度/记账率/修复率/代偿分型/帧有效率）追加到仓内 `docs/governance/run-metrics.jsonl`，产物可清、指标不灭——否则「连续两轮低于基线」类判据永远不可测。
- **O2 修复率进判据**：当前 G6 判据是「问题单 100% DISP」，DISP 允许观察/延后 → 天然激励「记账代替修复」。建议 G6 增「修复率下限」或要求延后桶逐项带 owner+到期。
- **O3 帧采集位分级**：19 步"前后零变化"多为非 UI 步（CLI/仓库动作）。应给 STEPS_META 每步声明 `capture_kind=ui|repo|none`：ui 步必须前后有差异，repo 步采集产物文件快照替代截图，none 步显式留空并计入「声明无帧」——避免用同一张空白页凑 58 张图。
- **O4 证据豁免显式化**：r18 缺步（2/4）与非 UI 步应在 STEPS_META 声明 `no_dialog=true`，审计器据此判豁免，而不是靠"看起来合理"。
- **O5 双账本单源**：retro 文档的「待处置 N」必须引用报告同源 DISP 快照并标注时点（retro 冻结于 G6，DISP 归桶发生在 report 段）——或让 G6 判据延后到 report 段校验。
- **O6 组织侧交付质量**：G5 打回 FE 四缺（agent 漏修）、xiao 60 迭代烧尽、审批 5 分钟超时、30 张零交付卡——建议 defect 段强制 FE 侧独立复测签名，任务书按 30 迭代分片。
- **O7 代偿结构治理**：dispatch-preset 77 笔 = 「15 人组织」的派发面主要靠脚本代演。若要验证自组织能力，需把派发词生成从脚本移交给总监角色（PR-7），否则净额口径下组织能力长期为 0。
