## 0、怎么读这份文档

### 0.1 一页纸结论

这套系统不是三个产品，而是一套三层结构：人用什么、AI 怎么干、项目知识怎么长，各自有唯一载体，靠同一套证据纪律串起来。

| 层 | 载体 | 一句话职责 | 主要产物 |
|---|---|---|---|
| 产品面 | SwarmStudio（`overlay/` 注入 hermes-studio） | 人干活的驾驶舱：日常、推演、IDE 三模式 | 89 条路由、33 个阶段页签、382 条注入补丁 |
| 运行面 | hermes agent 运行时 + Matrix + kanban | AI 团队真正执行：编制、授权、派发、催办、审计 | 42 个 profile、28 块看板、审批与证据流 |
| 能力层 | swarm-yuan 生成的目标技能 | 把项目知识变成写代码前必须通过的约束 | 六段技能目录、56 个门禁、9 节点工作流 |

三条断言贯穿三层，任一层都可以拿它验收：

1. **证据先于声明**：完成=提交号+卡号双凭证；门禁、评审、发布都要可反查的锚。
2. **未配置不等于已治理**：inactive／partial／unavailable 如实标注，不拿“存在”冒充“生效”。
3. **只迁不删、只补不覆盖**：能力在归属面有正身才退役；技能供给、任务台账、决策记录只增不改。

四个数字先给结论：编制 15 人展开为 30 个 Matrix 账号、42 个 profile；SwarmStudio 累计 146 条用户决策；swarm-yuan 累计 50 条编号决策文本、56 个门禁；全流程推演已跑 21 轮、方案迭代到 V8.46。

## 1、系统定位

### 1.1 三句话

**产品面的目标是把“现状”变成一眼可读的画面。** 人不再在聊天框、终端、看板之间来回找，而是在一个驾驶舱里看到谁在干什么、卡在哪一步、证据在哪。

**运行面的目标是把“AI 干活”变成可编制、可授权、可追责的组织行为。** agent 不是聊天对象，是有岗位、有权限边界、有在途任务、有审计记录的团队成员。

**能力层的目标是把“项目知识”变成机器可执行的约束。** 组件在哪、依赖怎么连、这类任务该怎么拼，不靠人记，也不靠 AI 猜，写成清单、配方和门禁。

### 1.2 三层结构

三层之间是单向消费关系，不是并列的三个子系统。

```
产品面（人看与操作）
   │ 只读运行面数据：看板 / 审批 / 团队 / 运行态 / 证据
   ▼
运行面（AI 执行）
   │ 消费能力层产物：项目技能（约束、配方、门禁）
   ▼
能力层（知识生成）
```

| 维度 | 产品面 | 运行面 | 能力层 |
|---|---|---|---|
| 代码位置 | `overlay/custom/{client,server}`＋补丁 | `upstream/hermes-agent` 运行时＋Matrix | `~/lab/Swarm-yuan` 与安装态 `~/.zcode/skills/swarm-yuan` |
| 状态存储 | 读模型＋少量本地配置 | kanban SQLite、Matrix 房间、证据 JSONL | 目标项目内的 `.swarm-yuan/`、技能目录、门禁账 |
| 变化速度 | 周级（每轮 spec） | 日级（派发与执行） | 月级（版本与决策） |
| 权威判据 | 用户决策与走查 | 卡状态与证据 | facts.conf 与决策史 |

### 1.3 为什么是三层而不是三个产品

三条边界判据，用来判断一个新功能该放哪层：

1. **写入口唯一**：任务真值只在 kanban；技能只在能力层生成；UI 不建第二份任务表或第二份技能库。
2. **读模型不复制**：产品面通过端点读运行面，不在客户端存一份“影子数据”。团队、审批、看板、证据全部如此。
3. **不反向依赖**：能力层不知道产品面存在；运行面不引用 UI 组件；产品面可换皮而不动运行面。

违反任一条，就是历史事故的形态：双入口、双事实源、幽灵状态。§9 的缺口大多可归到这三类。

### 1.4 五条贯穿纪律

这五条不是理念，是每轮验收都能查的机械规则。

1. **证据先于声明**：双凭证（提交号+卡号）、四类锚点（事件 `$`／提交／卡 `t_`／房间 `!`）、append-only 台账。
2. **未配置不等于已治理**：策略未配置是 inactive、检测器缺数据显示 unavailable、静态能力标 partial。禁止“仪表盘显示已治理”。
3. **单一事实源**：manifest、阶段路径投影、工具契约、价目表、FIBO 正本，每个横切维度只有一处定义。
4. **执行面 fail-closed，读模型 fail-soft**：权限与沙箱边界拒绝优先；坏数据跳过并记名，不让一个坏文件拖垮整页。
5. **只增不改**：技能供给只补缺失、用户改过不覆盖；任务台账 append-only；决策记录保留被推翻的旧条并标注。

## 2、设计原则与历史教训

这一章是全系统的“为什么”。每条结论都对应一次真实事故或一次用户裁决；按它改代码之前，先看它踩过什么坑。

### 2.1 七条设计原则

| # | 原则 | 含义 | 来源 |
|---|---|---|---|
| D1 | 模式隔离，能力共享 | 日常/推演/IDE 共享技术组件，不共享导航与写入口 | 推演污染日常的实报 |
| D2 | 证据先于声明 | 完成、门禁、发布都必须有可反查的锚 | run15/run20 嘴炮与报告失真 |
| D3 | 单一事实源 | 契约、格式、口径、价目只在一处定义 | 多次双源漂移事故 |
| D4 | 未配置不装已治理 | inactive/partial/unavailable 如实标注 | 安全检查「仪表盘绿但无边界」 |
| D5 | 执行失败即关闭 | 权限与沙箱边界拒绝优先，绝不静默放行 | 安全整改裁定 |
| D6 | 只增不改 | 台账 append-only，用户改过的副本不覆盖 | 供给链与决策史纪律 |
| D7 | 真实素材优先 | 不造数据、不造截图、不造演示按钮 | 报告反凑数、假按钮整治 |

### 2.2 十二类反复出现的问题形态与根治机制

这是 21 轮推演与 4 个月开发的“事故模式库”。同一形态复发，说明上次只打了补丁没根治。

| 形态 | 表现 | 根因 | 根治机制 |
|---|---|---|---|
| 嘴炮不交卷 | 干完活不交证据 | 完成与交卷解绑 | 结论行三要素＋四步前置＋zero-delivery 检测器 |
| 静默失败 | Bash 无声死亡 | `set -euo` 坑族 | fail-visible 静态门禁＋崩溃可 grep 锚 |
| 容量饥饿 | 并发拒绝丢派发 | 串行闸与扇出失配 | 并发定标 30＋事件年龄锚 |
| 会话饥饿 | 连续极小输出空转 | 上下文压力 | 饥饿检测器＋换会话令 |
| 闸死锁/拆闸 | FAIL 后绕闸放行 | 派修链路断裂 | 禁拆闸（用户裁定）＋处置通道 |
| 代偿循环 | 程序代演人类动作常态化 | 产品能力缺口 | 代偿台账＋净额＋清偿门＋激励反转 |
| 报告失真 | 计数/叙事与台账不符 | 生成器不校账 | 审计熔断＋真值脚本单一判据源 |
| 判词盲区 | 只查文件存在不查结论 | 存在性判据 | 结论行行首匹配＋内容判据 |
| 派发令过长 | 理解成本大于完成成本 | 任务粒度过大 | 任务粒度纪律＋极简单步令＋派发词窄化 |
| 合并丢失/死锚 | 集成分支赛后删 | 溯源判据错 | 分支保留守卫＋内容判据 |
| 驱动误改 | 运行中编辑主脚本 | bash 惰性读取 | 驱动冻结＋监督器 owner 注册表 |
| 帧壳页/刷单 | 壳页同像素、重放刷单 | SPA 冷启动、记单无幂等 | md5 结构性锚定＋幂等键 |

### 2.3 被推翻或被替代的设计

产品形态不是一次设计出来的。以下八项曾正式采用、后被证据推翻；保留在此，防后人重走。

| 旧方案 | 新方案 | 推翻原因 |
|---|---|---|
| A 类导出可抽出 custom/ | 55 个修改文件全归 B 类 patch | 上游文件直接 import 新增导出，抽出反要改更多 import |
| patch 028 重写 KanbanView | 独立 SwarmKanbanView 路由 | 侵入式重写污染上游 |
| cockpit 三栏 → 六区域 IA | 单页驾驶舱 → 壳+四场景 → 两页并存 | 用户裁决“菜单太多” |
| LoopEngine.tick 五阶段 | GraphService 图引擎（双跑后退役旧引擎） | 图为唯一主干的架构裁决 |
| 三 State Store 一等存储 | 事件日志唯一事实源，Store 降为投影 | 审计与回放需求 |
| codex 集成底座 | zcode 源码底座 → Ycode | 用户两次裁定 |
| 共享专职 agent 命名 | 每账号实例化 `<user>-<agent-id>` | 编制表归一裁决 |
| “--force 挤下宿主”归因 | rendezvous 争用＋独立锁目录 | 首轮推演实测证伪 |

### 2.4 人机边界的三条主线

1. **从导演兜底到代偿记账**：早期脚本兜底一切，没有边界概念；中期立“监控代行边界”，四类可代行留痕、两禁区；V8.29 正式命名代偿，立台账、净额、清偿门与激励反转——停滞但如实登记的轮也是有效轮。
2. **介入清单三分类**：启动/结束面全姿态保留；审批模拟面按判据批退；待收紧面（预写派发词/代走板/代建卡/排期）standard 记台账、strict 禁用。
3. **FAIL 唯一出口**：闸 FAIL 只能真派修订＋复审，禁止绕闸；监督编排层子智能体全部只读。

### 2.5 调研吸收的六条判定原则

这六条决定“什么值得吸收、吸收到什么程度算落地”：

1. **标尺先行**：每项建议必须贴合六条产品标尺之一，落点一律在既有功能区内，禁新增一级页。
2. **需求侧校验**：吸收点须追溯到真实痛点或已知缺陷；优先补“会让演示出丑的面”。
3. **不做摆设件**：运行通道缺失时记档待环境，不做空 UI。
4. **核实优先于重造**：动手前先查是否已覆盖；“落库≠进产品”，接线与数据源闭合才算落地。
5. **许可与架构红线**：专有许可只搬概念；不迁移架构只借语义；不适用项逐条给理由与对应物。
6. **验证纪律**：产物 grep＋端点 200＋真浏览器走查三层验法；不确定即记“未核”。

## 3、产品面终态：SwarmStudio

### 3.1 定位与三类问题

SwarmStudio 用**模式隔离 + 机制约束**解决三类问题：人找不到东西、推演与日常互相污染、完成声明不可信。三条断言与兑现方式：

| 断言 | 兑现方式 | 复核入口 |
|---|---|---|
| 日常与推演共享能力，不共享导航与写入口 | 三模式切换、`/app/sim*` 独立导航域、`useDailyStageProgress` 只读看板、`domain-split` 结构守门 | 专题正本 §3／§5.5 |
| 一切“完成”都要证据 | 双凭证、四类锚点、append-only 台账、hash 链证据 | 专题正本 §5.2 |
| 判断权不交给执行者 | 六道质量门、FAIL 唯一出口、人工介入留痕、执行层 fail-closed | 专题正本 §5.3-§5.4 |

### 3.2 三模式信息架构

| 模式 | 入口 | 壳 | 侧栏 | 数据源 |
|---|---|---|---|---|
| 日常工作台 | `/app` | `IaShell` | 常用 5＋六阶段＋专题 4＋设置 | 看板／审批／Matrix／治理读模型 |
| IDE 工作区 | `/app/ide` | IDE 独立壳 | 任务栏／会话／文件／终端／审查／插件 | zcode 会话内核＋hermes 会话 |
| 全流程推演 | `/app/sim` | `IaShell` 推演侧栏 | 导演台／监督面板／运行监控／证据库／运行编排／推演设置 | 图运行时＋run-state＋journal＋证据 |

顶栏工作视图切换只改路由不改组件树。跨模式跳转必须显式标注“在推演中查看／回日常处理”，不允许静默改道——这是 2026-10-21 导演详情分流裁决的直接原因。

### 3.3 日常：六阶段与治理域

六个阶段沿一次交付的时间轴排列：①搭台 → ②需求 → ③设计 → ④开发 → ⑤验收 → ⑥治理，共 33 个单层页签。页签级归属分三态：单阶段、多阶段、全程。

| 阶段 | 主要工作面 | 关键页签 |
|---|---|---|
| ①搭台 | 组织、团队、账号、资产、智能体 | 组织/账号/团队/资产四页签＋工作流/本体/技能/平台配置 |
| ②需求 | 需求冻结、分诊、排期 | 需求池/冻结单/分诊/排期 |
| ③设计 | 系分、spec、方案评审 | 系分/Spec/评审记录 |
| ④开发 | 看板、任务、代码、分支 | 看板三签/任务抽屉/分支产物 |
| ⑤验收 | 测试、UAT、发布门 | 测试/UAT/发布准出 |
| ⑥治理 | 运营记录与处置 | 八签：评审治理/改进实验/度量检查/安全审计/关卡与流程/问题单/审计/文档 |

⑥治理承载“发生了什么、要处理什么”；设置七域承载“改什么”。2026-10-21 用户裁定后，GovOverlay 七区退役，能力入口直达归属面，三治理面收敛为两面。

### 3.4 全流程推演

推演是运行面执行协议在 UI 上的投影，也是这套系统唯一能端到端验证“AI 团队能否交付”的场地。

**协议本体**：26 步＋六道质量门。G1 需求冻结 → G2 架构评审 → G3 编码门禁 → G4 独立测试 → G5 发布准出 → G6 复盘。G5 三腿并行取证（集成真值／缺陷闭环／安全条件），只取证不判，终判单源。

**产品面入口**：

- 导演台建真实看板任务，3 秒轮询；待决人工闸可批准/打回。
- 导演 run 与 26 步 run 详情分流：`/app/sim/director` 走图运行时，26 步走原详情。
- G5/UAT 已建真状态机：G5 走 submit→approve/reject→release，事件落 `evidence/release-gate-events.jsonl`；UAT 按 AC 逐条判定，conditional/reject 必填理由。
- 监督面板读 journal 事件流；证据库按四类锚点检索。

**当前状态**：run22 于 2026-10-21 10:01 起跑，0.7.38 首轮，smoke 5/5 通过，在途；G4 已过（缺报告显形），G5 多轮、两轮熔断（阈值 2），P0 缺陷台架漂移修复中（SIM `runs/20261021-v8-run22/evidence/scenario.log`）。

### 3.5 IDE 工作区

### 4.3 多机舰队

## 5、能力层终态：swarm-yuan

### 5.1 定位：生成器，不是技能市场

swarm-yuan 对任意代码仓库跑一次，产出一个项目专属的研发能力技能。此后 AI 在该项目里写代码，先查组件、依赖和规矩，再动手。

它卖的不是可复用技能内容，而是“先懂项目、再写代码”的认知与约束生成流程。失败分两类、工具分两件：不懂规矩 → 门禁；想错逻辑 → 验证（真跑测试＋独立审查）。

### 5.2 八环链与三份实物

```
①认知项目结构与关系 → ②整理工程规范 → ③结合框架最佳实践与既有业务实现
→ ④形成组件库与拼装式开发模式 → ⑤吸收开发者实际研发习惯 → ⑥装配成目标技能
→ ⑦用目标技能完成日常研发/测试/验证/交付 → ⑧使用中按具体问题迭代成长 →（项目演进回①）
```

①的产出是三份可核验实物，是整个能力层的地基：

- **组件库清单**：组件/接口/数据三类，两列表（路径 + 说明与约束）。
- **关系边集**：import 边＋声明式映射边＋AI 补语义边；字符串耦合单独设防。
- **配方**：业务功能清单＋高频任务拼装序列，每配方五要素（触发场景/前置查询/复用件/胶水/门禁与验证）。

### 5.3 目标技能六段目录与九节点工作流

目标技能是薄产物：`SKILL.md`＋`workflow`＋`references`＋`assets`＋门禁配置＋`scripts`；随发文件 92 个（lite 档 46 个）。

九节点：①需求理解 → ②探查 → ③设计 spec → ④实施 plan → ⑤编码 → ⑥测试 → ⑦独立审查 → ⑧合入 → ⑨发布。每节点四要素：入口／参与方／门禁／产出物与调用追踪。

六阶段状态机映射：open=①②；design=③④；build=⑤；verify=⑥⑦；archive=⑧；operate=⑨。守卫：build 需批准 spec，archive 需 verify pass 且证据非空；AI 自我声明不改变持久状态。

### 5.4 门禁四层纵深

| 层 | 位置 | 机制 |
|---|---|---|
| L1 写时 | 宿主 hooks | 统一判据 `spec-first-bridge`，命中阻断（exit 2）；已实测 Claude Code／Codex／ZCode 三家，另 5 家已渲染未实测 |
| L2 提交时 | git pre-commit | `core.hooksPath`，与宿主无关；候选与批准正文都取实际暂存区 |
| L3 门禁时 | `check_spec_first` | 入核心门禁序列 |
| L4 流程准入 | 状态机 build 守卫 | 无批准 spec 不得进 build |

门禁本体 56 个：核心 11、架构 18、合规 19、advisory-only 6；标准档 29、全量档 50；闭合 56 = 50 + 6，50 = 29 + 19 + 2。三档 enforce（strict 21／warn 20／advisory 15 静态），四种结果（pass／fail／warn／skip），skip 明示跳过、不计 pass。

### 5.5 自演进纪律

1. **负向预算**：门禁 56 冻结、conf 变量 197/200；新增须等额删除。
2. **预算棘轮**：生成器侧档与分发面分离，分发面只留消费面。
3. **证据分级**：A=本机实测、B=官方一手、C=二手转述；C 级未经核实不得写入基线。
4. **决策史只增不改**：被推翻的旧决策保留并标状态；选择与反选择都留痕。

概念也受预算约束：未创建且未运行不得声称；概念落地要问责。

- 版本：v2.0 → v2.79 → v2.86 → v2.88.1（最新发布）；仓库已到 R130（未发版）。

## 6、跨域接口

### 6.1 五条契约

三域之间只有五条缝。任何新功能若跨越两域，必须落在其中一条上，否则就是私自搭线。

| # | 契约 | 上游 | 下游 | 违反后的典型事故 |
|---|---|---|---|---|
| 1 | 技能供给链 | swarm-yuan 生成的目标技能 | profile／推演树 | 双份技能库、用户改动被覆盖 |
| 2 | 能力发现与委托 | 能力上报＋身份/委托双清单 | 派发器与执法门 | 派活给无权限 agent、提权 |
| 3 | 任务与证据 | kanban 卡＋证据 JSONL | 看板/审批/推演 | 幽灵任务、报告反查不到 |

| 5 | 推演验证 | 图运行时＋26 步＋G5/UAT | 导演台/监督/证据库 | 静默改道、闸键与证据脱钩 |

### 6.2 技能供给链

```
swarm-yuan 生成项目技能（如 aipaydev-dev）
   → simharness/skills/（推演装载清单）
   → 中央 manifest skill-provisioning.json（唯一期望源）
   → hermes profile install / skills install（git 分发包）
   → _shared/ops/provision-pull.sh（每日 06:40 多机同步）
```

- manifest 匹配优先级：精确名 > 最长后缀 `*x` > 最长前缀 `x*` > `*`；缺失时报告 `source=builtin`，供给端点拒绝执行。
- 供给只补缺失、默认干跑、执行需 `confirm:true`、写台账、可回滚；用户改过的副本绝不覆盖。
- 两种 manifest 不混：`skill-manifest.json` 是产物元数据；`skill-provisioning.json` 是“角色→期望技能”的期望源。
- 扫描只数 `SKILL.md`、跟随符号链接。早期“中位 6 个技能”的误判正是手工数不跟随链接；实测中位 296（8-563），orchestrator 309。

### 6.3 能力发现与委托

- 每机每日生成 `capability-reports/<machine>.json`（单机约 340KB），>48h 标 stale。
- 委托前查目录（把目录摘要注入委托词）尚未做，是明确挂账。
- 委托边界用否定式合成；委托只能收窄。
- 身份与委托双清单同时放行才放行；未登记身份沿用既有链。

### 6.4 任务与证据

- 卡是唯一真值：assignee 填账号短名，填错永远认领不到；板外 assignee 拒认领。
- 依赖用 `task_links`（DAG）；认领走 CAS。
- 完成双凭证：提交号＋卡号；报告类卡无锚定级 warn。
- 证据四类锚点：事件 `$`、提交、卡 `t_`、房间 `!`。发布门与 UAT append-only。

### 6.5 治理与审批

- 审批单一契约 `GET /api/approvals/pending-summary`：`{total,command,review,enforce,byRisk,ts}`。
- 裁决独立落 `policy-decisions` JSONL，带 `policyRuleId`，不写 govbus 冲掉安全事件。
- 评审治理：按内容分风险档、审批绑定 head commit、互审 ≤3 轮、24h 回滚率熔断、夜间扫描显式开关。
- 安全审计：六阶段流水线，自证拒绝 409，复核人≠发现人，记录哈希绑定。
- 评测判分：S0 轨迹规则（必需工具／无死循环／冗余步上限），死循环按“同名同参”判定。

### 6.6 推演验证

- 图运行时三态 `GRAPH_ENGINE=legacy/shadow/on`；事件日志 SQLite 是单一事实源。
- 26 步与六闸由 harness 驱动；G6 键统一 `retro_done@步24`。
- 发布门与 UAT 独立 append-only，不改 run-state 闸键。
- 导演 run 与 26 步 run 分流，不造第二份 run 视图。

### 7.5 推演 21 轮的终态结论

- **方案演进**：V1.0（20 步首通）→ V5（契约层冻结：26 步/六闸/模板，唯一正本制）→ V8（五部分分离重写）→ V8.46（治理结果层）。约 43 个版本号。
- **纪律**：编号至 80，79 条正文，只增不改；每条带事故日期与 run 实锤。
- **关键轮次的教训**：
  - run8：Bash 六型静默死亡＋报告零截图 → 静态门禁＋三载荷挂驱动。
  - run9：唯一 6/6 全首过，但 NVMe 脱挂 8.5h、SPA 壳页 → 差异审计 P1-P16。
  - run11：容量风暴丢 400+ 派发 → 并发定标 30＋事件年龄锚。
  - run15：24 帧同像素＋安全闸时序死锁 → 帧 md5 锚定＋裁决 A。
  - run19：G4 把写 FAIL 的报告当过闸 → 判词语义重写（纪律 52-56）。
  - run20：往轮产物冒充 4 件、死锚 13 件、代偿 179 笔 → 真值三件套＋report_truth.py。
  - run21：派发词全角标点 17 连崩、监督器重生环境差异 → 当晚全根治，纪律 76-78。
- **净结论**：推演的价值不在“跑通”，而在每轮把一类失败形态转成机械门禁。21 轮共沉淀 12 类问题形态（§2.2）与 30 项 prelaunch。
