# NCWK 产品正本

> 三域产品：SwarmStudio（产品面）× hermes agent teams（运行面）× swarm-yuan（能力层）
> 版本：2026-10-21 R1｜核实日：2026-10-21
> 本文只写**产品是什么、给谁用、能做什么、现在到哪一步**。怎么实现、为什么这样设计、踩过什么坑，见《NCWK 设计正本》。

## 0、怎么读

### 0.1 一页纸结论

NCWK 是一套让“人指挥 AI 团队交付软件”的工作系统。它把三件事装进一个体系：

- **人怎么看**：一个驾驶舱，三种工作模式（日常、推演、IDE），看到谁在干什么、卡在哪、证据在哪。
- **AI 怎么干**：一个有编制、有权限、有任务、有审计的 AI 团队；15 个岗位展开为 30 个账号、42 个智能体，共用 28 块看板。
- **项目知识怎么长**：一个生成器，对任意代码仓库生成项目专属开发技能；AI 写代码前先查组件、依赖和规矩，再动手。

三个数字先给结论：编制 15 人／30 账号／42 智能体；产品面累计 148 条用户决策；全流程推演已跑 22 轮，run22 于 10-22 收官（六闸全过）。

## 1、产品定位

### 1.1 一句话与三句话

**一句话**：把人、AI 团队、项目知识装进同一个驾驶舱，让 AI 团队按编制、按证据、按门禁交付软件。

**三句话**：

1. 产品面让“现状”一眼可读：人不再在聊天框、终端、看板之间来回找。
2. 运行面让“AI 干活”可编制、可授权、可追责：agent 是有岗位、有权限边界、有在途任务、有审计记录的团队成员。
3. 能力层让“项目知识”变成写代码前必须通过的约束：组件、依赖、配方、门禁都由生成器产出，不靠人记、不靠 AI 猜。

### 1.2 解决的三类问题

| 问题 | 表现 | 产品的解法 |
|---|---|---|
| 人找不到东西 | 群聊、看板、终端、文档各说各话；同一任务五处呈现 | 三模式驾驶舱＋唯一看板＋审批收件箱＋全站检索 |
| 推演与日常互相污染 | 模拟环境的消息/任务/配置渗进真实工作 | 日常与推演共享能力、不共享导航与写入口；两套数据隔离 |
| 完成声明不可信 | 说做完了但找不到证据；报告漂亮但数字对不上 | 双凭证（提交号+卡号）、人工闸、证据库、机械审计 |

### 1.3 用户是谁

**第一用户是主管（总指挥）**，不是 AI 工作者。AI 工作者的“界面”是 Matrix 消息与看板 API；产品界面是给人监督与决策用的。

典型使用者：

| 角色 | 用产品做什么 |
|---|---|
| 主管／总指挥 | 看全景、做审批、拍板方向、验收结果 |
| 业务分析／产品 | 需求冻结、排期、验收标准 |
| 架构／研发 | 看任务、看分支、进 IDE 编码、处理评审 |
| 测试／安全／运维／审计 | 独立测试、安全检查、发布与复盘、合规取证 |

## 2、产品全景

### 2.1 三层能力，一个体验

```
人 → 驾驶舱（产品面）
        ↓ 派活 / 审批 / 看证据
     AI 团队（运行面）
        ↓ 按项目技能与门禁干活
     项目知识（能力层）
```

对用户来说，这是一条连续动线：在驾驶舱里定事 → AI 团队认领并执行 → 每一步留下证据 → 人审批或验收。

### 2.2 产品能力清单（用户视角）

| 能力 | 用户能得到什么 |
|---|---|
| 日常交付 | 从需求到验收的六阶段工作台，看板、审批、沟通、文档一处闭环 |
| 全流程推演 | 在隔离环境里完整演练一次交付，六道质量门卡关，产出可审计报告 |
| IDE 工作区 | 在一个工作区里看任务、开会话、改代码、跑终端、审变更；支持本机编码工具 |
| AI 团队 | 15 个岗位、30 个账号、42 个智能体；派活到人、卡在板、证据在库 |
| 技能供给 | 项目专属开发技能自动装到每个岗位；用户改过的不覆盖 |
| 治理与审计 | 评审分级、安全审计、工具策略、告警与巡检；关键动作可反查 |
| 专题工作台 | 流程架构（BPA）、本体（含 FIBO 金融本体）、评测、技能治理 |

## 3、产品面：人用的界面

### 3.1 三种工作模式

| 模式 | 入口 | 用来做什么 |
|---|---|---|
| 日常工作台 | `/app` | 今天的活：看板、审批、沟通、阶段页、检索 |
| IDE 工作区 | `/app/ide` | 写代码与审查：任务、会话、文件、终端、变更、插件 |
| 全流程推演 | `/app/sim` | 演练一次完整交付：导演台、监督、运行监控、证据库 |

顶栏切换只换视图不换心智：跨模式跳转必须明确标注“在推演中查看／回日常处理”，不会静默把你带到另一个世界。

### 3.2 日常：六个阶段

| 阶段 | 人在这里做什么 |
|---|---|
| ①搭台 | 建组织、账号、团队、资产；配工作流、本体、技能、平台 |
| ②需求 | 收需求、冻结范围、分诊、排期 |
| ③设计 | 写系分与 spec、做方案评审、留评审记录 |
| ④开发 | 看看板、领任务、跟分支、查产物 |
| ⑤验收 | 跑测试、逐条 UAT、过发布门 |
| ⑥治理 | 评审治理、改进实验、度量检查、安全审计、问题单、文档 |

共 33 个单层页签。治理是“发生了什么、要处理什么”，设置是“改什么”，两面分工不重叠。

### 3.3 全流程推演

推演是把真实交付完整走一遍的场地，26 步、六道质量门：

| 门 | 人看到什么 |
|---|---|
| G1 需求冻结 | 验收标准、范围外清单、影响面、涉敏评估都齐了才开工 |
| G2 架构评审 | 设计五要素、爆炸半径、验证计划、备选方案都摆出来 |
| G3 编码门禁 | 有设计才编码；需求-代码-测试一一对应；测试记录随分支 |
| G4 独立测试 | 测试的人不是写码的人；缺陷报修验闭环；只认本轮证据 |
| G5 发布准出 | 七项证据、回滚方案、灰度节奏、人工闸 |
| G6 复盘 | 三段式复盘、行动项、问题单回写、经验入记忆库 |

推演产出：一份可审计报告＋证据库（截图、对话、操作、台账）。导演台可以建真实任务、3 秒刷新、批准或打回人工闸；启动与人工闸有真实通知。**run22 已收官**（10-21 10:01→10-22 05:32，约 19.5 小时）：六道门全部通过，发布门经真实打回后补齐，165 条问题单、58 条处置留痕。

### 3.4 IDE 工作区

一个任务导向的编码工作区，不是聊天页：

- 双模式：**编程**（写代码）与**工作**（非仓库任务）。
- 23 个页签：任务栏、会话、文件、终端、审查、插件、沟通（完整 Matrix 客户端）等。
- 本机编码工具可直接拉起：zcode、DeepSeek Harness。
- 用量与上下文：本机 zcode 会话的 token、成本、逐轮趋势、上下文构成、压缩事件。
- 电脑操作（CUA）：默认关闭，显式开启；凭据成对注入。

### 3.5 专题四岛

| 岛屿 | 用来做什么 |
|---|---|
| 流程架构 BPA | 流程定义、节点、执行视图；架构清单与 PCF 映射 |
| 本体 | 五要素建模、实例管理、词表；FIBO 金融本体 37 概念、12 官方域、4 个真实场景、逐条来源 |
| 评测 | 评测集、运行、红队、校准、处置链；失败样本回流 |
| 技能治理 | 技能目录、供给对账、舰队能力发现、使用读数 |

### 3.6 设置与权限

设置七域，覆盖账号、团队、模型、平台、通知、界面、集成。权限分层：超级管理员、领导层、普通成员；团队页有独立的负责人判定。

## 4、运行面：AI 团队怎么被使用

### 4.1 团队

| 项 | 数字 | 说明 |
|---|---|---|
| 编制 | 15 人 | 主管、业务分析、产品、架构、研发×4、测试×2、安全、运维、审计 |
| 账号 | 30 个 | 每人一个人类账号＋一个 AI 助理账号 |
| 智能体 | 42 个 | 14 个调度器＋28 个执行 agent |
| 看板 | 28 块 | 每人 2 块（主管不建板） |

每个智能体有岗位、能力边界与权限。任务责任以卡上的负责人为准，看板只是视图。

### 4.2 派活与执行

- 人把活派到某个人，卡进入他的看板；AI 助理认领并执行。
- 并发上限 30；一轮里可以按模块并行（系分 4 路、编码 6 路、测试+集成 3 路）。
- 派活有里程碑：开发要按节点报进度，测试首个用例就要提交，报告先出首片。
- 卡住会被催：先唤醒，再要验证账本，再按 1→2→3 重催，三次不交付建议换人。
- 完成后要交证据：提交号＋卡号。

### 4.3 审批与人机边界

- 14 个人工介入点全部进审批收件箱，批准/打回留痕。
- 推演里的模拟审批与真实审批是两条有意保留的通道，互为兜底。
- 程序不能替人做决定：代做的人类动作要记代偿台账，净额单独呈现。

### 4.4 技能与能力

- 每个项目有一套专属开发技能；按角色的期望清单自动装到对应智能体。
- 供给只补缺、不覆盖用户改动；默认演练，确认才执行；可回滚。
- 多机时走中央仓每日同步；每台机上报“谁有什么能力”，形成舰队能力视图。

### 4.5 治理与审计

- 评审按风险分级，重要改动要人审、绑定具体提交。
- 安全审计走六阶段：覆盖账本、对抗验证、三态结论（确认/待验证/已否决）、独立复核；审计面已扩到代码仓（密钥/依赖声明/危险 API）。
- 工具调用可加策略：严格模式下未明确允许的一律拒绝；高风险命令可进 OS 级沙箱执行。
- 巡检 31 个检测器，异常进治理面板，不发群；新增会话耗尽检测（长跑会话只应答不出活的识别与换会话建议）。
- 线上失败可转回归样本：从 IDE 轨迹挑一个会话或节点，转成可重复判分的题目，区分原证据复现与新证据修复。

## 5、能力层：项目知识怎么长

### 5.1 它给用户什么

对任意代码仓库跑一次，产出一个**项目专属开发技能**。此后 AI 在这个项目里写代码，会先查组件、依赖和规矩，再动手。

它不是技能商店：不发别人写好的通用技能，而是按你的仓库现场生成。

### 5.2 产出什么

- **组件库清单**：组件、接口、数据三类，每项带路径与约束。
- **关系边集**：谁依赖谁、映射关系、语义关系。
- **配方**：业务功能清单＋高频任务的拼装步骤（先查什么、复用哪个件、补什么胶水、过哪些门禁）。
- **目标技能**：六段目录，随项目一起走；含门禁、模板、脚本、参考文档。

### 5.3 怎么用

编程时的九步：理解需求 → 探查 → 写 spec → 拆任务 → 编码 → 测试 → 独立审查 → 合入 → 发布。每一步都有对应门禁与产物。

### 5.4 凭什么可信

- 56 个门禁：核心 11、架构 18、合规 19、观测 6；按项目档位启用。
- 写代码前、提交前、门禁时、流程准入四层拦截。
- 规范、证据、决策都留痕；数字有单一事实源，不手抄。

## 6、典型工作流

### 6.1 从 0 到 1 搭一套

1. 在 ①搭台建组织、账号、团队与资产。
2. 配工作流、本体、技能来源与平台参数。
3. 选项目，生成项目专属技能并分发到岗位。
4. 建第一块看板，派第一个任务，验证闭环。

### 6.2 日常交付一天

1. 打开工作台，看“待我出手”的审批与阻塞。
2. 看板看谁在干什么；把新任务派到人。
3. 处理审批：批准/打回，留理由。
4. 阶段页看当前阶段进度与产物。
5. 收工时看今日完成与证据。

### 6.3 跑一轮推演

1. 在推演区选场景与卷子（需求、验收标准、模块集）。
2. 起跑前检查 30 项前置（环境、账号、看板、采集链、台账）。
3. 导演台看进度与人工闸；监督面板看研判与停滞。
4. 六道门逐一过；G5 三路取证、只判一次。
5. 收官出报告与证据库；复盘行动项回写。

### 6.4 在 IDE 里改一个任务

1. 从任务栏选任务，工作区跟到该任务。
2. 看简报与相关消息，开会话。
3. 改代码、跑测试、提交；证据自动挂到任务。
4. 发起审查，处理评论，合入。

## 9、路线

### 9.1 近期（一周）

1. run22 收官：把 G5/UAT 完整走一遍，报告与证据归档。
2. 安全观察期累积数据，不急于切换阻断。
3. 修完能力层三处口径债。

### 9.2 中期（一月）

1. 派活时自动带能力摘要。
2. 工作台首载优化与僵尸视图清理。
3. 技能缺口补齐：53 个无源技能补库或从清单删除。

### 9.3 长期

1. 一键开轮：开一轮推演变成一次点击。
2. 自组织闭环：AI 自己干活，人只管审批；成功标准是闭环了多少产品缺陷。
3. 经验回流：问题单关闭即回流回归库。

## 10、验收标准（用户视角）

一条能力算“可用”，必须同时满足：

1. **看得见**：在归属页面有入口，不是只有 API。
2. **点得通**：真实数据、真实动作，不是演示按钮。
3. **有证据**：完成后能拿提交号与卡号反查。
4. **说得清**：界面文案说人话，不出现机读噪声。
5. **可回退**：改动可还原，用户改过的东西不被覆盖。
