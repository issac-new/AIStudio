# SwarmStudio 并行能力基础化设计要求（Spec）

- 日期：2026-10-09
- 状态：已确认方向（用户指令记录），设计细化随 B 轨三期展开
- 来源：用户原话——「并行能力是 SwarmStudio 的基础能力。无论是需求分析、方案设计、代码研发、质量测试、报告编写工作，都要进行动态规划和拆解、组合。提高效率。」

## 1. 主旨（三句话）

并行不是某个环节的加速手段，而是平台级基础能力。所有工作类型在派发时默认走「动态规划 → 拆解 → 并行执行 → 组合归一」四步，而不是默认单人串行。衡量标准：同等任务量下墙钟时间显著缩短，且证据链与责任边界（RACI）不因并行而模糊。

## 2. 五类工作面（全覆盖，不限于研发）

| 工作面 | 拆解维度（示例） | 组合归一物 |
|---|---|---|
| 需求分析 | 按业务域/AC 组拆分系分任务 | 合并的概设契约（单一事实源） |
| 方案设计 | 按模块/接口边界拆设计任务 | 架构设计文档 + 接口契约对齐记录 |
| 代码研发 | 按应用/组件/分支拆 DEV 任务 | integration 分支合并 + 冲突收口 |
| 质量测试 | 按用例域/组拆执行任务 | 测试报告（执行人汇总，结论行唯一） |
| 报告编写 | 按报告章节/受众拆编写任务 | 合并器产出的正本（双正本制） |

关键点：五类工作的拆解粒度与并行度由**工作量估计（estimate）+ 扇出上限**动态决定，不是固定模板。B 轨二期已落的 estimate 落库+派发加权（main 418fe874）是本要求的计算基础。

## 3. 机制要求（四步闭环）

1. **动态规划**：任务进入时估计工作量，>1 人日阈值即触发拆解评估（纪律 31 的推广形态——从研发推广到全部五类）。
2. **拆解**：按上表维度拆为可独立执行的子任务，每个子任务有明确 owner、验收物、RACI（R 唯一，结论行/归一物只由 R 出）。
3. **并行执行**：子任务同时派发（图驱动派发，扇出受容量闸约束）；执行者之间物料共享先行（如用例文件先 push 共享再分头跑）。
4. **组合归一**：R 收集并行结果，汇总为唯一归一物（报告/合并分支/契约文档）；并行不改变「结论行唯一」「不许谎报」纪律。

## 5. 边界与不变量

- 并行不得破坏：RACI 责任唯一、结论行唯一、不许谎报、证据链完整（并行执行的结果必须可追溯到执行者与命令）。
- 拆解有成本（协调/合并开销）：工作量估计低于阈值或强耦合任务不强行拆（拆解开销>收益时不拆，如实记录）。
- 容量闸与扇出上限仍是硬约束：并行度上限=闸值-在途占用。
