# 驾驶舱 · 沟通协作 · IDE 工作台——UI/功能/操作序列全面复盘（2026-10-03）

**结论**：三大核心动线（任务处理 / 会话协作 / 运行追溯）的跨界面联动是连贯的——101 处跳转点的目标地址高度收敛（任务→看板抽屉或 IDE 工作空间、会话→会话画布、运行→运行详情），搜索、通知、管理台行操作都能一步到位。主要问题集中在两处：**职责界面重叠**（管理面四套并存、同一任务五处呈现、注意力计数四套口径）与**术语晦涩**（「饲料」实为带推荐码的外链、「工作流」一词双义、AGENTS 混编等）。本轮已落地 3 处术语澄清（含外链诚实化），另 7 项设计分叉以菜单形式待裁决。

证据基座：101 处跨界面跳转点全量测绘（`custom/client` 源码级）、术语词条对账（zh/en 双语）、14 组浏览器动线实测（`scripts/regression/ux-flows.mjs`、`ux-deep.mjs`，隔离链 8689）。

## 一、职责界面：清晰度主战场

### 1.1 现状职责图

| 界面/入口 | 实际职责 | 承载内容 |
|---|---|---|
| 沟通协作（/app 三栏） | 会话协作主战场 | 左栏导航+会话流、中栏会话画布、右栏任务·决策 |
| IDE 工作台（/app/ide） | 编码执行主战场 | 任务侧栏三段、会话窗格、编辑器/终端/文件、键位卡 |
| 看板（/app/board 9 页签） | 任务与治理工作面 | 看板/追溯矩阵/三账与体检/全链路追踪/组织与知识/台账与规则/审计与变更/文档评审/驾驭工程 |
| 管理台（⚙管理浮层 7 分区） | 跨域对象管理 | 任务/会话/员工/智能体/团队与通道/评审/统计 |
| 收件箱（/app/inbox） | 审批裁决 | 待审聚合 + 审批历史（批准/打回返工） |
| 概览（/app/dash 三卡） | 聚合仪表 | 我的待办/评审闸口/交付进度 |

### 1.2 职责重叠问题（按影响排序）

1. **管理面四套并存**：「员工/团队与通道」在管理台、「组织与知识」在看板页签、「账户管理」是独立入口——三处管人；「任务」在管理台任务表与看板两处各一整套 CRUD；「评审」分布在管理台评审、收件箱、文档评审、审计与变更四处。新用户（甚至老用户）需要记忆「哪类对象去哪套管理面」，而边界并没有硬规则。管理台浮层里自带一段使用说明（「管理台覆盖全屏；实时徽章进列表，历史跳『运行·历史』，操作在行上」）——**需要注记才能用的界面，本身就是职责不清晰的自证**。
2. **同一任务五处呈现**：看板卡片、管理台任务表、右栏「任务·决策」（等我/需关注/挂接任务/任务动态四段）、概览「我的待办」、注意力条 chip。五处的计数口径与筛选语义各不相同（见 1.3），状态操作也分散（右栏改派/去处理、看板抽屉、管理台行操作）。
3. **注意力/状态计数四套口径**：顶栏「任务 29」（开放态）、通知徽标（决策+消息未读）、右栏「需关注 27」、注意力条（受阻类）。数字相近而含义不同，同屏并列易互相打架——此前「在线 3 vs 暂无内容」的割裂（上一轮 F6 修复）就是这类口径分裂的实例。
4. **顶栏四个状态弹层交互模型各异**：任务 chip→右锚态势面板、通知→右锚下拉、日程→全屏模态、在线→右锚下拉。功能可懂，但四种弹层形态（面板/下拉/模态）交替出现，学习成本偏高。

## 二、联动连贯：底子好，四处毛刺

### 2.1 连贯性良好的动线（实测通过）

- **任务动线**：注意力条/通知/右栏/概览/日程/运行详情 → `看板?task=`（抽屉）或 `/app/ide?task=`（IDE 工作空间）——入口六处、落点两种，语义一致。
- **会话动线**：搜索→会话画布（实测 `#/app/s/chat/mul3dtaokagker`）、通知消息→房间、管理台会话行→房间/会话画布、左栏会话→中栏画布。
- **运行动线**：`运行·历史`/运行详情/RunTrace（全局时间线）互链完整；RunTrace 有全局入口（右栏「全部时间线」）。
- **管理台行操作**：详情（右栏就地展开）/ ⌨（IDE）/ 历史（RunTrace）三键分工明确，实测全部到位。
- **视图切换状态保持**：沟通协作 ↔ IDE 往返后会话上下文仍在（实测两向均保留）。

### 2.2 毛刺与断点

1. **「＋ 新任务」只跳看板不开建卡表单**（`WorkbenchView.onNewTask` 只做路由跳转）。按钮语义承诺「新建」，落点却要用户再找列头「+」——操作序列断一拍。
2. **概览三卡整体点击无落点**：只有卡内行（`ov__row`→收件箱/看板/任务）可点，卡片容器不可点、行是小目标区。信息可下钻但点击面太小（Fitts 定律反例）。
3. **视图切换不带 URL 上下文**：`IaViewSwitcher` 直推 `ide.shell`/`ia2.collab`，会话/任务上下文靠 store 恢复（功能上成立），但 URL 不可复制分享当前 IDE 任务态（与看板页签 URL 回写的努力方向不一致）。
4. **注意力条 chip 无 taskId 兜底跳 `/app`**（`IaGlobalTop`）：普通态 chip 若查不到任务即原地打转，无任何反馈。

### 3.2 待裁决的晦涩词（改动牵动交互语义，列菜单见 §六）

- 右栏四分法「等我 / 需关注 / 挂接任务 / 任务动态」：四个近义任务清单并列，区分靠使用经验。
- 评审词族「评审闸口 / 待裁决评审 / 待审 / 审计与变更 / 文档评审」：五个"评审"概念并存。
- 治理黑话「三账与体检 / 驾驭工程 / ekko 运维」：对产品技术研发人员不自明（三账=进度/风险/资源账？）。
- 「等您操作（RACI）」：RACI 矩阵术语直接上卡片，未接触该方法论的用户不可读。

## 四、研发工作习惯适配

**做得好**：IDE 侧键位基建完备（`IdeKeymapCard` 快捷键管理 + ⌘K 命令面板 + 用户覆盖与冲突检测、终端 ⌘B detach 真离会、分屏对照 ⇔、侧问 /btw、后台任务 ⏱）；URL 深链体系完整（看板 ?tab=&status=&task=，且并行轮已补页签 URL 回写）；一屏信息密度高、等宽字号呈现任务号/用量；搜索（⌘ 域）直达会话全文。

**不对称/短板**：
1. **沟通协作侧无命令面板**：⌘K/键位卡只在 IDE 壳内；沟通协作视图只有搜索框，两壳能力不对称。
2. **审批一键直通**：「批准/打回返工」直接执行、无确认层、无撤销（`ApprovalPanel.decide` 直调 API）。评审是治理决策动作，误触代价高——研发工具惯例是不可逆动作要么确认要么可撤销。
3. **模型切换死态提示出口单一**：「当前模型不可用（aim）…请重新选择后继续」只有「去设置重选」一个出口，且长期驻留（诚实态设计，但操作序列绕远）。
