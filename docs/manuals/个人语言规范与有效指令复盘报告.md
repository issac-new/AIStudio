## 二、你的语言规范（从指令中归纳的隐性标准）

以下 8 条规范按你的历史指令频次和强度排序，每条附原文锚点（编号对应 `quality_language_mindset_directives.jsonl` 中的消息序号）。

### 规范 1：说人话，禁黑话（出现 ≥20 次）

> "可以有专业术语，但不能有莫名其妙的缩略语黑话，要符合人的阅读和认知习惯" (#148/#149，同文下发两套系统)
> "AI味有些重 不像自然语言和形式语言的表达，黑话和缩略语 不知所云 语句也不通顺" (#176)
> "PPT看不懂，信息太密，不要有太多黑话和脚手架、过程性内容，要把事情讲清楚" (#164)
> "对类似这样的黑话都用人话来说，进行PPT全面排查整改" (#20)

**标准细化**：
- 术语首现必须定义："所有术语概念第一次出现必须要有定义说明和解释，也要消除彼此间的歧义和冲突" (#42)
- 费曼检验："要能让没有过程背景知识的人可以一眼看懂，这也是费曼那句话的思路" (#38/#42)
- 判例：§5.5、precheck.sh --all-full、7维度 这类内部代号在汇报产物中必须展开 (#20)

### 规范 2：结构严密——衔接、递进、无孤立内容（出现 ≥30 次）

> "各章节之间要有衔接对应关系 不应存在孤立内容，否则逻辑有严重缺陷" (#171，发出 2 次)
> "我要的是从理念、设计、架构、实现、使用、引用5层逻辑，环环相扣、逐层递进、与事实相符，且整体协调统一的一份完整文档" (#61/#64/#112，发出 5+ 次)
> "全文要按照完整的故事逻辑的层次及顺序来讲" (#170)
> ""道、法、术、器、势"的逻辑递进展开关系没有体现出来" (#93)

**标准细化**：
- 五层递进链：理念→设计→架构→实现→使用→引用
- 论证充分性："为什么需要这样做，以及这样做是有效的充分及必要性论证" (#172)
- 图文配比："图形为主 文字为辅，多图 少字 要有逻辑、有结构、有层次、有关系，有论点 论据 论证支撑" (#6)；反向判例"图少 文字多 认知负载过重" (#4，发出 3 次)

## 三、有效指令模式库（你的高产出指令句式）

### 模式 A：标准否决式（最高频）
```
[产物定位] + [具体缺陷] + [隐含标准]
```
例："设计文档不要有脚手架内容" / "图少文字多 认知负载过重，请对正文进行重构调整"
**有效原因**：缺陷具体可验证，AI 可机械对照整改。
**失效变体**：只说"优化下"——你在 822 条中约有 40 条此类，后续多需追加补充指令。

### 模式 B：五段递进式（复杂产物定义）
```
我要的是从理念、设计、架构、实现、使用、引用5层逻辑，环环相扣、逐层递进、与事实相符，且整体协调统一的一份完整文档
```
**这是你打磨出的最强指令模板**，重复使用 ≥5 次，覆盖 PPT/skill/设计文档三类产物。

### 模式 C：方法论枚举式（系统性体检）
```
依据第一性原理、四个导向（价值/目标/问题/结果）及自举能力、金字塔结构化思维，基于MECE原则、实用主义思想、图尔敏论证模型、麦肯锡七步工作法，审视检查当前X设计及实现中存在的问题，进行修复
```
**注意**：此模式你发出 2+ 次，但后续出现"不要生搬硬套"的回撤（#95、#151）——方法论枚举对 AI 是双刃剑，点名框架容易诱发教条映射。改进用法：框架名 + "隐含内在逻辑关系，不要硬靠词"的否定性护栏。

### 模式 D：分层编号式（多点反馈）
```
1、…… 2、…… 3、…… 4、…… 5、……
```
例：#161 PPT 调整思路 4 条、loop graph 改进 5 条。
**有效原因**：每点独立可验收，AI 不会漏项（对照你"每一轮排查都有丢的"的挫败，编号式是有效的对抗手段）。

### 模式 E：制度宣告式（规范成文）
```
X 的所有日常工作，要建立……规范，可以……但不能……，要……也不能……
```
例：#148/#149 语言规范同文下发 hermes + zcode。
**特征**：以"所有日常工作"限定范围，用"可以A但不能B"的让步句式给出边界。

### 模式 F：锚点校正式（事实纠偏）
```
文档指的是：<绝对路径>，PPT指的是：<绝对路径>
```
**有效原因**：消除指代歧义。你在 AI 理解错"哪个文档"后发展出的补丁式指令。

### 模式 G：目标循环式（长任务）
```
/goal + [完成X的复盘及所有工作的改进重构，直至完成所有]
```
**特征**：用"直至完成所有"封死提前收工的口子。

## Methodology

- **采集**：只读访问 `~/.hermes/profiles/orchestrator/state.db` 与 `~/.hermes/state.db`（messages 表 role='user'）、`~/.zcode/cli/db/db.sqlite`（session_input 表 kind='sendText'，比 message 表更干净——后者混入子代理上下文）、`~/.claude/projects/*.jsonl`（type='user' 且非 isSidechain）
- **补充采集（v1.1）**：`~/.cc-switch/cc-switch.db`（session_log_sync 证明客户端覆盖面；proxy_request_logs 无正文确认排除）、`~/Library/Application Support/Antigravity/User/globalStorage/state.vscdb`（trajectorySummaries protobuf 解码出 8 条 trajectory 元数据）、`Antigravity/User/History/`（恢复 2 份用户手写需求文档）、`~/.gemini/`（确认会话正文已删）
- **过滤**：剔除系统注入（[CONTEXT COMPACTION]、[ASYNC DELEGATION]、kanban 通知回显 [✔/⏸]、雷达自动 prompt、"继续"类短确认）
- **分类**：指令类判定 = 指令动词开头 OR 核心质量词≥2 命中 OR 约束词+质量词；调研类单列不纳入本复盘
- **已知偏差**：①正则分类对反讽/混合句有误判（~5% 人工抽查误差）②Claude Code 样本量小（16 条指令类），其风格结论代表性弱 ③ZCode message 表的 role=user 含大量子代理注入，故采用 session_input 表为准 ④Antigravity 8 条 trajectory 仅标题级素材（正文在 Google 云端），Gemini CLI 正文已删——这两源对语言规范归纳的贡献度低于四大主源 ⑤去重以「去空白后前 100 字符」为键，跨源同文重复指令（如语言规范同发 hermes+zcode）保留双份但已在正文标注
- **原始数据**：`instruction-retrospective/` 目录下 6 个 jsonl 文件保留全量语料，可复查
