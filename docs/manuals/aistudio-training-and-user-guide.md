# AIStudio 培训和使用手册

本手册帮助新用户独立完成一次可检查的工作交付，也帮助讲师组织培训、演示和考核。学习重点不是记住所有按钮，而是分清任务进展、人工决策和交付证据。

- 适用版本：AIStudio 1.0.9-overlay。
- 使用形态：浏览器 Web 版。桌面端差异不在本手册展开。
- 核实日期：2026-11-02。
- 维护责任：产品文档维护者随页面、路由和操作契约同步修订。
- 验证说明：本版已核对当前源码、现行文档和对应守门测试，并完成交互培训页的 PC 浏览器走查。真实业务账号的完整培训流程未重新执行，正式培训前讲师仍应按第 9 章预演。

需要自动导览时，运行 `npm run training`。交互版按设计、实现、部署、使用分为四部分 12 幕。页面用四套独立拓扑展示系统协作、任务状态、服务发布和日常治理。macOS 可双击 `docs/manuals/start-training.command`，Windows 可双击 `docs/manuals/start-training.bat`。交互版使用模拟数据，不连接真实业务服务，仅面向 PC 横屏使用。

## 1. 怎样使用本手册

新用户先读第 2 章，再按第 4 章完成首次练习。日常操作查第 5、6 章。讲师使用第 7、8 章组织课程和考核。环境管理员重点读第 3、9、10 章。

手册使用两类提示：

- **环境依赖**：该步骤需要网关、Matrix、模型服务、执行 worker、第二名审批人或其他外部条件。条件未就绪时，不能把页面打开视为功能验证通过。
- **完成判据**：该步骤应留下的可检查结果。没有判据的点击练习不计入培训验收。

建议学习路径如下：

| 读者 | 学习重点 | 应完成的练习 |
|---|---|---|
| 主管、审批人 | 总览、看板、审批、验收 | 首用练习、练习 A、练习 B |
| 产品、业务分析 | 需求冻结、影响分析、UAT | 首用练习、练习 D |
| 架构师、研发 | 任务契约、IDE、独立评审 | 首用练习、练习 A |
| 测试、评测人员 | 独立测试、评测、复评 | 首用练习、练习 C |
| 组织管理员 | 组织、账号、团队、权限 | 首用练习、练习 E |
| 运维、安全、审计 | 发布准出、审计、故障处理 | 首用练习、练习 B、环境预演 |

## 2. 先理解产品怎样工作

### 2.1 AIStudio 解决什么问题

AIStudio 把人和多个 AI 身份放在同一个工作系统中。你可以分派任务、沟通、编码、审批、测试和追查证据。产品覆盖需求、设计、开发、验收和治理，但每个页面并不另建一套任务真值。

AIStudio 由五类组件协同工作：

| 组件 | 用户能感受到的作用 |
|---|---|
| AIStudio 产品面 | 提供看板、工作台、审批、IDE、评测、治理和推演页面 |
| Matrix | 承载人员、房间和协作消息 |
| hermes agent | 运行 AI 身份，并通过网关处理消息和任务 |
| Ycode | 为 IDE 提供编码执行能力 |
| swarm-yuan | 为代码仓库提供项目专属开发技能和约束 |

五个运行时组件不等于五个独立发布包。当前发布按驾驶舱、agent teams、Ycode、yuan skill 四个模块组织，整体源码包再汇总四个模块和仓级工程文件。Matrix 是外部基础设施，不作为 AIStudio 的独立发布模块；各模块版本与产物以 `RELEASE-MANIFEST.json` 为准。

日常使用只需理解一条原则：页面是工作入口，权威系统才保存最终事实。任务以看板为准，审批以源系统的裁决记录为准，交付以提交和测试证据为准。

### 2.2 三种工作模式

| 模式 | 入口 | 适用场景 |
|---|---|---|
| 日常工作台 | `/app` | 建组织、管需求、派任务、沟通、审批、验收和治理 |
| IDE 工作区 | `/app/ide` | 围绕具体任务查看会话、文件、终端、变更和审查结果 |
| 全流程推演 | `/app/sim` | 在独立运行上下文中演练交付流程、处理人工闸并保存证据 |

日常任务和推演任务可能共享部分能力。当前版本尚未把所有批量操作和注意力入口都与推演数据隔离。不要把推演环境当作已经完全隔离的安全沙箱。

### 2.3 六个核心概念

**身份（profile）**是网关中的 AI 工作身份。统一身份聊天可以与一个或多个身份对话。身份在线不代表它一定有空领取任务。

**任务卡**是工作分派和状态跟踪的依据。标题、负责人、工作区、验收标准和完成总结都属于交付信息的一部分。

**工作区**是任务读写文件的目录。`scratch` 用于可丢弃的临时产物。任务完成后，系统会尽力删除受管 scratch 目录。子任务未结束、路径保护或清理失败时，目录可能保留。`worktree` 用 Git worktree 隔离代码改动。`dir` 指向已有目录。需要保留交付物时，不要使用 `scratch`。

**质量门**是关键阶段的放行判据。G1 控制需求冻结，G2 控制架构评审，G3 控制编码质量，G4 控制独立测试，G5 控制发布准出，G6 控制复盘。

**UAT** 是用户验收测试。验收人按验收标准作通过、有条件通过或不通过判定。任务进入 `done` 不等于 UAT 已通过。

**证据**用于支持完成声明。研发任务通常需要任务卡号、真实提交号、自测结果和独立评审记录。页面显示“完成”不能替代这些证据。

### 2.4 四条使用纪律

1. 不要把聊天记录当成任务完成证明。
2. 不要把阶段“已流转”当成阶段“已完成”。
3. 不要把数据源“缺席”当成待办为零。
4. 不要批准自己没有核对对象、影响和证据的请求。

## 3. 培训前准备

### 3.1 学员需要准备什么

每名学员需要一个浏览器和一套培训账号。账号可由管理员直接创建，也可通过 Matrix 邀请发放。学员还需要知道培训使用的看板、身份和工作区，不应猜用生产数据。

讲师应提前准备以下材料：

- 一个培训看板。
- 一张不含敏感信息的练习任务卡。
- 至少一个可用于澄清需求的 AI 身份。
- 一条用于审批练习的低风险请求。
- 一个用于独立评审的第二名学员或讲师账号。
- 一份培训专用测试目录或 Git 仓库。

### 3.2 环境管理员检查清单

| 培训内容 | 必需条件 | 检查方法 |
|---|---|---|
| 登录和页面学习 | 后端 8647、前端 8649 | 能打开登录页并进入工作总览 |
| 统一身份聊天 | 网关和至少一个在线身份 | 身份清单可读取，测试消息有来源身份回复 |
| Matrix 房间和邀请 | Matrix 服务、账号和相应管理员凭证 | 房间可进入，邀请在测试账号上有效 |
| 看板自动执行 | dispatcher、worker、模型和工作区 | worker 能认领 `ready` 卡并进入 `running` |
| IDE 编码 | Ycode、任务工作区和项目依赖 | 能打开任务上下文并读取训练项目 |
| 业务地图 | 至少一类已核对的知识数据 | 需求词面能命中预期实体或文档 |
| 全流程推演 | `OBS_SIM_ROOT` 及该轮所需运行资产 | 后端日志未报推演根缺席，导演台能读取目标 run |
| 双人会签 | 显式培训治理仓、`super_admin` 发起人、另一名合格治理人员 | 培训仓已有 admin 行，发起人不能替第二人批准 |

缺少某项条件时，讲师应删去对应实操，不用截图或口头描述冒充实操结果。

### 3.3 启动培训环境

以下命令中的 `<本仓根目录>` 和 `<培训治理仓绝对路径>` 是占位符。先把它们替换为实际绝对路径，不要输入尖括号。

1. 确认 Node.js 不低于 23.0.0。

   ```bash
   node --version
   ```

2. 注入当前产品的补丁和配置。

   ```bash
   cd <本仓根目录>
   npm run inject
   ```

3. 安装依赖。新克隆的环境执行一次即可。

   ```bash
   cd <本仓根目录>/vendor/hermes-studio
   npm install --no-audit --no-fund --ignore-scripts
   mkdir -p dist
   ```

4. 在第一个终端启动后端。

   ```bash
   cd <本仓根目录>
   npm run serve
   ```

   预期日志包含 `[serve-server] PORT=8647`。需要推演时，还要检查 `OBS_SIM_ROOT` 是否指向有效目录。

   组织保存会直接提交到治理仓。包含组织或会签实操时，先准备一个已初始化的培训 Git 仓库，再改用以下命令启动：

   ```bash
   cd <本仓根目录>
   GOVERNANCE_REPO="<培训治理仓绝对路径>" npm run serve
   ```

   核对日志中的 `GOVERNANCE_REPO` 正是培训仓。路径不符时，不要执行组织保存。

5. 在第二个终端启动前端。

   ```bash
   cd <本仓根目录>
   npm run dev
   ```

6. 打开 `http://localhost:8649`。

只学习页面和离线评测时，启动到这里即可。聊天、自动派发和 IDE 编码还需要以下服务：

7. 配置 hermes 身份并启动网关。身份安装方法见[《SwarmTeam 部署包说明》](../../team/README.md)。

   ```bash
   hermes gateway start
   curl --fail http://127.0.0.1:8650/health
   ```

   前台运行可改用 `hermes gateway run`。网关需要有效的 profiles、模型和 `API_SERVER_KEY` 配置。不要把密钥写进培训材料。

8. 需要 worker 自动认领时，确认网关配置中的 `kanban.dispatch_in_gateway` 未设为 `false`。网关内含 dispatcher，默认按周期认领 `ready` 卡。

9. 需要 IDE 编码时，先安装 pnpm，再在另一个终端启动 Ycode。

   ```bash
   cd <本仓根目录>
   npm run zcode:ensure
   npm run zcode:serve
   ```

   看到 `引擎服务就绪 :3030` 后再开始 IDE 实操。Matrix 服务由部署管理员按培训环境单独准备，Web 启动命令不会自动启动它。

默认部署是每个运行节点一个 hermes gateway，复用该节点的多个 profile。gateway 是本机智能体消息与执行委托的统一入口，不是一个全网唯一中央网关。多机培训时，各机本地执行，通过受控 peer API、Matrix 和 Git 制品协作；不要让页面或脚本绕过本机 gateway 另起执行链。

Windows x64 的额外要求见[《Windows x64 环境指南》](../windows-x64-setup.md)。日常培训不需要构建桌面包。

### 3.4 创建首个管理员账号

`reset-default-login` 会重置已有 `admin` 账号的密码，把它启用为超级管理员，并覆盖本地凭据文件。只在首次初始化或明确计划重置时执行。不要在学员仍在使用的环境上运行。

在首次启动前执行：

```bash
cd <本仓根目录>
node vendor/hermes-studio/bin/hermes-web-ui.mjs reset-default-login
```

命令会生成随机密码。密码只显示一次，同时写入 `${HERMES_WEB_UI_HOME:-~/.hermes-web-ui}/admin-login.json`。该文件权限应仅为当前系统用户可读写。通过安全渠道交付密码，不要贴到培训群或手册中。

开发模式也提供 `HERMES_WEB_UI_DEV_BOOTSTRAP=1` 空库引导。该入口只用于隔离开发环境，不作为共享培训环境的建号方法。产品没有可供公开使用的出厂默认密码。

### 3.5 验证登录

1. 打开登录页。
2. 使用管理员分配的账号登录。
3. 在地址栏进入 `/app`。
4. 确认页面显示“工作总览”。
5. 打开左侧“看板”。
6. 打开左侧“审批收件箱”。

如果页面能打开但数据为空，继续检查账号权限和数据源。不要用刷新次数判断后端是否正常。

## 4. 30 分钟首次练习

这次练习产出一个身份回复、一张可验收任务卡和一条检索记录。它不要求任务执行到 `done`，也不代表 G1 已通过。

### 4.1 认识工作总览

1. 进入 `/app`。
2. 查看“准备阶段”的五张卡。
3. 查看“交付阶段”的五张卡。
4. 点击左侧“流程总览”“工作台”“看板”“审批收件箱”，辨认四个高频入口。
5. 返回 `/app`。

准备阶段显示组织配置信号。交付阶段显示日常任务集中在哪里。“已流转”表示后续阶段已有工作，不表示本阶段质量门已通过。“未纳入跟踪”表示当前没有自动判据，需要人工核对。

### 4.2 发起一次轻量聊天

**环境依赖**：网关和至少一个身份可用。没有可用身份时，记录该练习未完成，继续学习看板。

1. 进入 `/app/collab`。
2. 点击左下“新建聊天”。
3. 点击顶部身份名称。
4. 选择讲师指定的身份。
5. 输入：`请用三句话说明这项培训任务的验收标准，不要修改任何文件。`
6. 点击“发送”。
7. 核对回复旁的来源身份。

也可以在消息中输入 `@身份ID`。有效的 `@` 会把消息发给指定身份，最多五个。一个有效 `@` 都没有时，消息发给当前选中身份。显示排队或仍在生成时，不要重复发送。

轻量问答可以直接使用聊天。需要修改文件、分派责任或保留交付证据时，应建立任务卡。

### 4.3 创建一张可验收任务卡

1. 进入 `/app/board?new=1`。在看板筛选中只保留一个培训看板，并核对目标板名。聚合看板选中多个板时不能建卡。
2. 在首列建卡表单输入标题：`培训：整理登录页验收清单`。
3. 填写讲师指定的负责人。
4. 选择讲师指定的工作区。
5. 需要关联父任务时，选择父任务。
6. 点击“创建”。
7. 打开新任务卡。
8. 在正文中填写以下模板。

   ```text
   目标：形成登录页验收清单，供独立测试执行。
   范围：账号登录、错误提示、登出。
   非目标：不修改代码，不测试真实生产账号。
   验收标准：
   1. 清单覆盖成功登录和错误密码两个场景。
   2. 每个场景都有操作步骤和预期结果。
   3. 清单不含真实密码、令牌或个人信息。
   ```

9. 保存正文。
10. 核对任务 ID、负责人和工作区。

`dir` 必须是已授权的已有目录。`worktree` 适合需要保留代码改动的训练。`scratch` 只适合可丢弃产物。完成时会尝试回收它，但不能把回收当作数据清除证明。

### 4.4 把任务转为可开工

1. 重新阅读任务正文。
2. 确认至少三条验收标准都能明确判定。
3. 确认非目标没有与目标冲突。
4. 点击转为 `ready`。

如果负责人、工作区或验收标准仍不清楚，不要转为 `ready`。建过卡只表示登记了想法，不表示已经可以派发。

### 4.5 找回任务并查看审批入口

1. 按 `Cmd+K`。Windows 或 Linux 按 `Ctrl+K`。
2. 输入刚创建的任务 ID。
3. 切换到“任务”结果类型。
4. 练习按看板、状态、负责人和时间筛选。
5. 打开任务并确认是同一张卡。
6. 进入 `/app/inbox`。
7. 查看“等人决定”“前置批准”“遗留事项清算”和“审批历史”所在区域。
8. 查看是否有“源缺席·状态未知”。

### 4.6 首用完成判据

完成以下事项，才算通过首用练习：

- 能说出工作台、看板、审批收件箱和 IDE 的不同用途。
- 收到过指定身份的回复，或如实登记该环境依赖未满足。
- 任务卡有任务 ID、负责人和正确工作区。
- 任务卡有目标、范围、非目标和至少三条可判验收标准。
- 能使用全局检索按任务 ID 找回任务。
- 能解释“已流转”“源缺席”和“任务完成”的不同含义。

## 5. 页面与导航速查

### 5.1 高频入口

| 页面 | 路由 | 主要用途 |
|---|---|---|
| 流程总览 | `/app` | 查看搭建进度和日常任务所处阶段 |
| 工作台 | `/app/collab` | 统一聊天、房间协作、任务和决策 |
| 看板 | `/app/board` | 建卡、筛选、分派、催办、评审和完成 |
| 审批收件箱 | `/app/inbox` | 聚合等待人工决定的事项和审批历史 |
| IDE | `/app/ide` | 围绕任务进行编码和审查 |
| 全局检索 | `Cmd/Ctrl+K` | 搜索会话、任务、运行、文档、人员和命令 |

“最近”位于左侧常用区，用于返回最近访问的页面。它不是系统审计记录，清理浏览器数据后可能消失。

### 5.2 六阶段页面

| 阶段 | 路由 | 主要页签与用途 |
|---|---|---|
| ①搭建 | `/app/stage/setup` | 五步进度、组织、账号、团队、环境与资产、智能体 |
| ②需求 | `/app/stage/reqs` | 需求与冻结、文档评审、G1、启动准备 |
| ③分析设计 | `/app/stage/design` | 任务分解、G2 系统分析、G2 质量门、排期 |
| ④开发 | `/app/stage/build` | 今日工作、看板、审批待办、风险与交接、G3/G4 |
| ⑤验收 | `/app/stage/accept` | 验收总览、需求追溯、交付健康、UAT、G5、交付案例 |
| ⑥治理 | `/app/stage/govern` | 遗留项、问题清单、安全审计、变更、可信执行、评审和改进 |

治理页签按“待处理”“审计与质量”“改进与度量”分组。旧治理深链会跳转到对应阶段页签，不需要另记一套地址。

### 5.3 专题工作台

| 页面 | 路由 | 主要用途 |
|---|---|---|

## 6. 日常操作指南

### 6.1 建立组织、账号和团队

组织变更会提交到治理仓库。发起人必须具有 `super_admin` 应用角色。修改已有 admin 行或治理裁决行时，系统要求另一名合格治理人员会签。第二人须已登录、在当前编制内具有 admin 或审计资格，且不能是发起人。首次向空编制加入 admin 行有建编豁免，不会触发会签。紧急通道会立即落盘并记录理由，只用于真实紧急情况。

1. 进入 `/app/stage/setup?tab=org`。
2. 点击“新增成员”。
3. 填写账号、角色、汇报关系、看板 slug 和 Matrix 账号。
4. 点击“保存（提交 git）”。
5. 如果出现治理者守卫，点击“发起会签”。
6. 让另一名合格治理人员登录。
7. 在“待会签变更”中核对变更。
8. 由第二人批准或驳回。
9. 核对返回的提交号和操作人。

需要邀请账号时，进入 `/app/stage/setup?tab=accounts`。填写本机账号名、角色、服务器地址和有效期。使用 Synapse 管理员 access token 生成邀请。通过安全渠道发送邀请文本。受邀人首次登录后应修改密码。

团队页用于维护团队、房间、领导和值守分派。团队领导是协作职责，不等于全局超级管理员。全局账号角色、组织治理岗和 Matrix 房间权限属于不同判断面。

### 6.2 冻结需求并完成设计评审

1. 进入 `/app/stage/reqs`。
2. 填写需求范围和非目标。
3. 写出至少三条可判验收标准。
4. 在“文档评审”中核对缺项。
5. 在 G1 页面执行冻结。
6. 进入 `/app/stage/design`。
7. 分解任务并排定依赖。
8. 完成系统分析和设计评审。
9. 核对 G2 结果后再进入开发排期。

冻结后需要变更时，应重新走对应变更和冻结流程。不要直接改写已冻结内容后继续沿用旧批准。

### 6.3 使用统一身份聊天

统一聊天适合澄清、咨询和轻量协作。每个身份有独立会话。多个 `@` 会分别发送，不是一个多人共同回答的会议室。

1. 进入 `/app/collab`。
2. 点击“新建聊天”。
3. 选择当前身份，或在消息中精确 `@身份ID`。
4. 写明任务 ID、目标、限制和期望输出。
5. 发送后核对来源身份。
6. 把需要执行和追踪的工作登记到任务卡。

推荐指令结构：

```text
任务：<任务 ID>
目标：<希望得到的具体结果>
范围：<允许查看或修改的对象>
限制：<不得修改、不得外发或必须保留的条件>
验收：<需要返回的证据或检查结果>
```

### 6.4 推进看板任务

看板常用状态如下：

| 状态 | 含义 | 典型下一动作 |
|---|---|---|
| `triage` | 想法或需求待澄清 | 补规格、分解或退回 |
| `todo` | 已登记但尚未排入执行 | 补责任与计划 |
| `scheduled` | 已安排执行窗口 | 等待开工条件 |
| `ready` | 已具备开工条件 | 触发 dispatcher，等待 worker 认领 |
| `running` | worker 已认领并执行 | 查看进展、阻塞和产物 |
| `blocked` | 等待人工输入或条件恢复 | 催办、补信息、解除阻塞 |
| `review` | 等待评审 | 查看变更，批准或打回 |
| `done` | 已完成状态迁移 | 核对完成总结和交付证据 |
| `archived` | 已归档 | 按需查看历史 |

标准研发任务按以下顺序操作：

1. 在 `triage` 补齐任务契约。
2. 转为 `ready`。
3. 点击工具栏“Nudge dispatcher”。
4. 等待 worker 认领。
5. 核对状态变为 `running`。
6. 出现 `blocked` 时，先读阻塞原因。
7. 使用催办把消息路由给负责人或团队。
8. 补齐人工输入后解除阻塞。
9. 执行完成后进入 `review`。
10. 独立评审人点击“查看变更”。
11. 评审人选择“批准”或“打回返工”。
12. 批准时填写完成总结。
13. 核对任务状态、提交号、测试结果和审批历史。

`running` 只能由 worker 认领进入，不能靠人工修改状态冒充执行。催办只发送消息，不会解除阻塞。批准记录和状态迁移是两个动作，操作后应同时核对。

### 6.5 在 IDE 中处理研发任务

1. 在看板打开目标任务。
2. 点击“查看变更”，或从工作台携带任务上下文进入 IDE。
3. 核对 IDE 顶部或侧栏的任务 ID。
4. 核对工作区路径和分支。
5. 查看任务简报、会话和文件。
6. 在训练项目中执行讲师指定的修改。
7. 运行项目规定的测试。
8. 查看变更和审查结果。
9. 返回任务卡登记提交号与测试结果。

IDE 会话默认关闭电脑操作。插件存在不等于获得电脑操作授权。实际执行还受凭据、broker 和操作系统权限限制。

### 6.6 处理审批收件箱

1. 进入 `/app/inbox`。
2. 先检查各数据源是否正常。
3. 打开“等人决定”中的请求。
4. 阅读请求来源、对象和上下文。
5. 跳转到对应源系统完成裁决。
6. 在源系统核对终态、操作人、对象和时间。
7. 对“前置批准”核对提出人、run、任务卡和详情。
8. 在确认影响后批准或驳回。
9. 返回收件箱并刷新。
10. 对前置批准和通用审批，在收件箱历史中核对决定。

“等人决定”的按钮可能只是跳转到真实裁决面。页面跳转不等于已经批准。此类裁决记录留在源系统，不一定出现在收件箱历史中。“源缺席”表示状态未知，不表示没有待办。

### 6.7 完成验收与发布准出

1. 进入 `/app/stage/accept`。
2. 在“需求追溯”中核对验收标准、用例、测试和 UAT 判定。
3. 在“交付健康”中检查分支和交付物。
4. 在“UAT 待判”中逐条作判定。
5. 对未通过项登记缺陷并回流处理。
6. 在 G5 页面核对发布资料、回滚安排和评审证据。
7. 由有权限且已核对材料的人执行批准。
8. 发布后按项目要求完成观察和复验。

看板 `done`、UAT 通过和 G5 批准是不同事实。发布类任务不能只用其中一项代替另外两项。

### 6.8 使用业务地图分析影响

业务地图使用规则式词面匹配。命中表示需求文本提到了对应词语，不表示系统已经理解业务语义。每路结果有数量上限，源缺席时该路计零。

1. 进入 `/app/sim/map`。
2. 输入需求标题和描述。
3. 点击“生成业务地图”。
4. 分别查看本体实例、板级图谱、FIBO 术语、历史 spec 和建议模块图层。
5. 点击需要核实的节点。
6. 填写采纳、排除或需改造的说明。
7. 勾选“已核实该影响点”。
8. 点击“保存标注”。
9. 用相同标题和描述重新生成。
10. 核对标注是否恢复。

多人标注采用最后写入生效。看到“存在更新版本，本次未覆盖”时，应重新读取现存版本，不要把这次输入当作已保存。

### 6.9 使用流程架构、本体和技能治理

流程架构用于维护业务流程及其治理关系。它不是需求影响分析画布。先在“架构清单”维护节点，再检查流程地图、端到端链接、治理体检和成熟度。

本体工作台用于维护类型、属性、实例、约束、版本和导出。FIBO 页提供金融域参考。导入前应核对目标环境和重复导入影响。

技能治理用于扫描技能、查看风险判定和核对技能供给。执行供给或回滚前，应先干跑并阅读变更范围。危险判定需要人工复核，不能只用扫描分数代替安全审查。

### 6.10 使用评测工作台

评测运行是对已完成会话或显式证据进行离线判分，不是让 Agent 在线重新执行任务。`k` 表示每题样本数，`k<2` 时不具备门禁统计意义。

1. 进入 `/app/eval`。
2. 在“评测集”创建或选择评测集。
3. 核对题目、期望行为和 Rubric 断言。
4. 在“运行记录”选择评测集。
5. 提供样本映射。
6. 点击“运行”。
7. 打开运行报告。
8. 查看失败样本、unknown 和红线结果。
9. 对失败样本建立处置单。
10. 修复后提供新证据。
11. 执行同卷复评。
12. 使用 A/B 对比检查改善和回归。

开放评测集才能使用普通处置练习。密封集只返回聚合结果，不显示样本明细。原证据复现只能用于诊断，不能关闭处置单。跨考卷版本的结果不能直接作同卷 A/B。

“技能评估”是同一页面的第八个页签，评估对象是 spec 第 19 节的测试设计，不是直接给技能文档打分。操作顺序如下：

1. 粘贴包含第 19 节的 spec 全文。
2. 点击“评估”，先查看 S0 机械结构检查，再查看 S1 的 MAET 四路径、GWT 可执行性、边界与异常、断言可验证性四个语义维度。
3. 需要版本对比时，填写基线 runId，并按需要选择“评估同时落基线”。下一次评估使用同一基线 runId，查看通过率 delta。
4. 阅读总体判定。任一维度为 `no` 时是 `FAIL`，全部维度为 `yes` 才是 `PASS`，其余情况是 `CONDITIONAL`。

S1 依赖在线判定端。判定端不可用或回答形状不符时，对应维度显示 `unknown`，总体通常为 `CONDITIONAL`，不能把它当成通过，也不能据此断言 spec 质量差。基线快照是迭代工件，不是业务评测集；技能评估结果也不能代替真实测试执行。

### 6.11 使用全流程推演

1. 进入 `/app/sim/orchestration`。
2. 选择讲师指定的运行模式。
3. 阅读启动前检查结果。
4. 启动或续跑指定 run。
5. 在导演台查看质量门和当前步骤。
6. 在监督面板处理停滞和介入请求。
7. 在证据库反查关键结论。
8. 在该轮 run 目录读取最终报告。

最终报告位于该轮的 `evidence/final-report.html`。打开报告时要保留相对资源路径。某一轮推演结论只适用于该轮实际覆盖的流程和环境。

## 7. 分角色培训与实操

### 7.1 建议课程安排

标准课程约 3.5 小时。环境依赖未满足的项目应改为讲评，不计实操通过。

| 环节 | 建议时长 | 产出 |
|---|---:|---|
| 产品概念和导航 | 20 分钟 | 能解释任务、身份、证据和质量门 |
| 30 分钟首用练习 | 30 分钟 | 一张可验收任务卡 |
| 看板交付演示 | 40 分钟 | 任务状态与评审记录 |
| 审批和验收演示 | 30 分钟 | 一条可追溯裁决 |
| 分角色实操 | 50 分钟 | 对应练习产物 |
| 故障处理 | 20 分钟 | 一份排查记录 |
| 考核与讲评 | 20 分钟 | 考核清单和改进项 |

### 7.2 练习 A：从任务到独立评审

**适合角色**：产品、研发、主管、测试。  
**环境依赖**：dispatcher、worker、模型、培训代码库和第二名评审人。

1. 只保留一个培训看板，创建一张培训任务卡。
2. 填写负责人和 `worktree` 或 `dir` 工作区。
3. 补齐目标、范围、非目标和验收标准。
4. 转为 `ready`。
5. 点击“Nudge dispatcher”。
6. 观察 worker 认领和 `running` 状态。
7. 在 IDE 核对任务上下文。
8. 完成培训修改并运行测试。
9. 进入 `review`。
10. 由另一名评审人查看变更。
11. 评审人批准或打回。
12. 批准后填写完成总结。

完成判据：任务到达预期状态，评审人与执行人不同。完成总结能对应任务卡号、真实提交号和测试结果。没有 worker 时，本练习只能验收前四步。

### 7.3 练习 B：作出可追溯的审批决定

**适合角色**：主管、审批人、审计人员。  
**环境依赖**：讲师预置一条低风险 HumanGate 请求和一条源系统介入请求。

1. 进入审批收件箱。
2. 记录正常数据源和缺席数据源。
3. 阅读前置批准的提出人、run、任务卡和详情。
4. 对培训请求作出批准或驳回。
5. 打开一条“等人决定”请求。
6. 在源系统完成实际裁决。
7. 返回收件箱刷新。
8. 在收件箱历史中核对前置批准。
9. 在源系统中核对介入请求的终态和裁决记录。

完成判据：两条请求都有终态。前置批准在收件箱历史中记录了正确的操作人、对象和时间。介入请求可在源系统反查对应记录。缺席数据源仍单独标为未知。

### 7.4 练习 C：从评测失败到复评关闭

**适合角色**：测试、评测人员、研发。  
**环境依赖**：无外部模型判定依赖。本练习使用 S0 正则断言和显式证据。

1. 进入 `/app/eval` 的“评测集”。
2. 点击“新建评测集”。
3. 选择 E2E。
4. 输入唯一名称。
5. 输入以下任务 JSON。

   ```json
   [{"id":"t1","problem":"验证修复标记","expectedBehavior":"证据包含 OK","rubric":[{"id":"a1","text":"回复含 OK","expect":"yes","kind":"result","s0":{"kind":"regex","pattern":"OK"}}]}]
   ```

6. 点击“创建”。
7. 切换到“运行记录”。
8. 选择刚创建的评测集。
9. 输入以下样本映射。

   ```json
   {"t1":[{"evidence":{"transcript":"NO"}},{"evidence":{"transcript":"STILL BAD"}}]}
   ```

10. 点击“运行”。
11. 打开新运行报告。
12. 在失败样本 `t1#1` 上点击“建处置单”。
13. 展开处置单的“同卷复评”。
14. 输入修复后的新证据。

   ```json
   {"t1":[{"evidence":{"transcript":"OK — fixed in training commit 1"}},{"evidence":{"transcript":"OK — regression passed"}}]}
   ```

15. 点击“同卷复评”。
16. 核对处置单状态和最近复评结果。
17. 在 A/B 对比中选择原始 run 和复评 run。
18. 查看每题改善或回归。

完成判据：处置单为 `closed`，最近复评通过，A/B 中目标题显示改善。原始失败 run 仍应保留。该练习只证明规则判分和处置流程，不证明真实模型质量。

#### 补充练习：技能评估与基线对比

**环境依赖**：S0 可离线执行；S1 需要讲师确认的在线判定端。没有判定端时，本练习以正确识别 `unknown` 和 `CONDITIONAL` 为验收点。

1. 进入 `/app/eval` 的“技能评估”。
2. 粘贴一份包含第 19 节测试设计的培训 spec。
3. 填写唯一基线 runId，勾选“评估同时落基线”，点击“评估”。
4. 核对 S0 四判、S1 四维和总体状态，不以 `CONDITIONAL` 冒充通过。
5. 修订 spec 后使用同一基线 runId 再评估，查看通过率 delta 和各维度理由。

完成判据：页面保留首次基线，第二次评估能显示与同一基线的差值；学员能说明 `PASS`、`CONDITIONAL`、`FAIL` 的区别，以及为什么该结果不能代替真实测试。

### 7.5 练习 D：人工确认业务影响面

**适合角色**：产品、业务分析、架构师。  
**环境依赖**：讲师已核对培训需求会命中当前部署中的知识数据。

1. 进入业务地图。
2. 输入讲师提供的需求标题和描述。
3. 生成业务地图。
4. 逐层核对命中词面和来源。
5. 排除一个词面命中但业务无关的节点。
6. 确认一个确实需要改造的命中。
7. 保存两条人工标注。
8. 用相同需求重新生成。
9. 核对标注恢复。

完成判据：至少一条标注已勾选“已核实该影响点”。说明中能区分词面命中与人工结论。重复生成后标注仍存在。

### 7.6 练习 E：完成双人会签

**适合角色**：组织管理员、审计人员。  
**环境依赖**：培训治理仓已显式配置，当前编制已有 admin 行。发起人具有 `super_admin` 应用角色。第二人已登录、在现有编制内具有 admin 或审计资格，且与发起人不同。

1. 发起人进入组织页。
2. 修改一条培训用 admin 或治理裁决行。
3. 点击保存。
4. 在治理者守卫中发起会签。
5. 第二名治理人员登录。
6. 核对变更明细。
7. 由第二人批准或驳回。
8. 核对组织提交和会签记录。

完成判据：第二人与发起人不同，变更和会签都有可反查记录。紧急通道不属于本练习的通过路径。

## 8. 培训考核

### 8.1 基础考核清单

讲师逐项检查，不以学员口头“会了”代替操作。

- [ ] 能找到工作总览、工作台、看板、审批收件箱和 IDE。
- [ ] 能解释 profile、任务卡、工作区和质量门。
- [ ] 能说明 `scratch` 的回收条件和保留交付物风险。
- [ ] 能创建含三条可判验收标准的任务卡。
- [ ] 能用任务 ID 检索并找回任务。
- [ ] 能解释 `ready`、`running`、`review` 和 `done`。
- [ ] 能说明催办与解除阻塞的区别。
- [ ] 能说明批准记录与状态迁移需要分别核对。
- [ ] 能识别“已流转”和“源缺席”。
- [ ] 能说出任务完成、UAT 和 G5 的区别。

建议前十项至少通过八项，且第 3、8、9 项不能答错。组织可在此基础上增加自己的合格线。

### 8.2 实操考核证据

学员应提交以下材料：

- 首用练习的任务 ID。
- 一条分角色练习的完成记录。
- 一次故障排查的现象、原因判断和处理结果。
- 需要保留交付物时的工作区、提交号和测试证据。
- 审批练习的操作人、对象和源系统终态。

截图可以辅助说明，但不能替代任务记录、提交号、审批记录和运行结果。

## 9. 讲师预演与故障处理

### 9.1 开课前预演

1. 用培训账号完整登录一次。
2. 创建一张测试卡并删除或归档到培训约定位置。
3. 给指定身份发一条只读消息。
4. 触发一次低风险 dispatcher 测试。
5. 打开 IDE 并核对任务工作区。
6. 打开审批收件箱并检查源状态。
7. 执行业务地图练习并清理培训标注。
8. 运行第 7.4 节的评测练习，确认 S0 判分可用。
9. 需要推演时，打开目标 run 和证据库。
10. 记录未通过项，不带病开课。

### 9.2 常见问题

| 现象 | 可能原因 | 下一步动作 |
|---|---|---|
| 页面白屏或接口 404 | 后端未启动、端口不对或代理故障 | 检查 8647 监听和后端日志，再检查前端 8649 |
| 登录提示 `NO_USER_ACCOUNTS` | 空库且没有可用账号 | 按第 3.4 节初始化管理员，或使用有效 Matrix 登录 |
| 登录提示尝试次数过多 | 触发登录限流 | 等待限流结束。需要清理锁定时，由管理员按当前安全流程处理。不要反复猜密码 |
| 身份清单不可达 | 网关或身份目录不可用 | 检查网关和身份配置，聊天练习记为未完成 |
| 消息一直排队 | 身份正忙或网关仍在生成 | 等待自动拉取。持续无结果时查网关日志，不要重复发送 |
| `ready` 卡一直不进入 `running` | dispatcher、worker、模型或认领条件未满足 | 查看派发日志和认领条件，不要人工改成 `running` |
| 催办后仍阻塞 | 催办只发送消息，阻塞输入尚未补齐 | 打开卡片补齐原因，再执行解除阻塞 |
| 审批有记录但任务未达预期状态 | 审批记账与状态迁移是分开的动作 | 检查状态迁移失败原因。确认失败后，按源系统流程重试 |
| 收件箱显示“源缺席” | 某个权威数据源未接入或读取失败 | 记录未知范围并检查数据源，不按零待办处理 |
| 推演页面提示 `OBS_SIM_ROOT` 缺席 | 推演运行根未配置 | 配置有效 `OBS_SIM_ROOT` 后重启后端 |
| 业务地图保存提示版本冲突 | 其他人已写入更新版本 | 重新读取现存标注，再决定是否合并修改 |
| 评测出现大量 unknown | 判定端离线或断言无法判断 | 先区分 S0 与模型判定结果，不把 unknown 算通过 |
| 评测显示 `k<2` | 每题样本不足 | 增加同题样本，不用单跑结果作门禁结论 |
| 桌面端升级后仍看到旧界面 | 同版本缓存副本仍在使用 | 按桌面发布流程递增版本并清理对应旧副本 |

端口排查可使用：

```bash
lsof -nP -iTCP:8647 -sTCP:LISTEN
lsof -nP -iTCP:8649 -sTCP:LISTEN
```

需要停止进程时，先核对 PID 和进程工作目录，再只操作目标 PID。不要使用模糊匹配批量结束进程。

## 10. 安全与数据边界

1. 不在任务卡、聊天、评测证据或培训材料中填写真实密码、访问令牌和个人敏感信息。
2. 不使用生产账号、生产治理仓库或生产发布请求做课堂练习。
3. `npm run dev:lan` 会向局域网开放开发服务。不要在不可信网络中使用。
4. 管理员凭证只用于相应管理操作。Synapse 管理员 access token 不等于 AIStudio 超级管理员密码。
5. 组织紧急通道会留下审计记录，但它不是绕过双人会签的常规方法。
6. 需要保留代码和交付物时，不用 `scratch`。
7. 功能导航开关不是安全授权开关。真正的权限仍由服务端和部署边界决定。
8. IDE 的电脑操作默认关闭。不要因插件存在就假定已经获得执行授权。
9. 推演数据隔离仍有已知边界。不要用真实敏感数据做推演。
10. 审批前必须核对实际对象和影响。高风险命令、删除、覆盖和发布不能只读标题。

## 11. 术语表

| 术语 | 含义 |
|---|---|
| dispatcher | 负责把可执行任务交给执行者的调度组件 |
| worker | 实际认领并执行任务的工作进程 |
| profile | 网关中可对话或执行工作的 AI 身份 |
| RACI | 责任分工：执行、批准、咨询、知会 |
| Rubric | 评测题目的一组可判断言 |
| S0 | 使用确定性规则的评测判定层，例如正则表达式 |
| pass@k | 每题提供 k 个样本时计算的通过指标 |
| run | 一次有独立上下文和证据的运行或推演轮次 |
| HumanGate | 必须经人批准或驳回后才能继续的前置控制点 |
| G1-G6 | 从需求冻结到复盘的六道质量门 |
| UAT | 用户验收测试，由验收人按标准作判定 |
| 源缺席 | 页面无法读取某个权威数据源，因此状态未知 |
