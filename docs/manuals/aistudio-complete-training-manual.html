第一章 · 全局定位人定方向，机器守门，AI 干活

这句话不是口号，而是这套系统在 AI 员工变多之后唯一能站住的分工：人负责方向和例外，机制负责守门，AI 负责执行。质量不能指望模型自觉，只能指望每个“必须”都有机器检查、有证据、有阻断。

为什么规模一大，自觉就不够用了

一个人带两三个 AI 助手时，人可以盯着每一步，错了立刻拦下。当 AI 员工变成几十个、任务并行、跨团队交接，人已经看不过来：模型会漏跑测试、会把自己的推测写成结论、会在没有规格的情况下直接改代码。这些不是偶发失误，而是概率事件；只要次数够多，一定发生。

所以系统必须换一种可靠性来源：不依赖每个执行者都可靠，而依赖结构让错误必然被发现。规则不只要写进提示词，还要写成拦截：写文件时检查有没有规格，提交时检查分支和证据，构建前检查批准状态，发布前检查门禁和回滚。提示词是开环，违反可能没人知道；拦截是闭环，违反会被当场挡下。

一条硬纪律只写要求不给检查，等于没有要求。合法的写法是“开环提要求＋闭环兜底”：文档说清应该怎样做，机制保证做不到就过不去。

四论：凭什么相信这套机制可靠

机制不是零散规则的堆叠。系统论、信息论、科学方法论、控制论共同构成一套面向复杂系统的认识与行动方法：系统论解决“看清”，信息论解决“看准”，科学方法论解决“认识可靠”，控制论解决“行动有效”。四者通过“认识—信息—模型—行动—反馈”相互耦合，把认知转化为可验证、可执行、可持续优化的能力。

四论解决的问题在本产品里的落地
系统论看清边界与结构单仓四模块划界、六团队责任、组件清单与关系边集、门禁按族分层
信息论看准口径与噪声数字以单一事实源为准、跳过项单列、证据可度量、上下文预算与去重
科学方法论认识可靠可复现正反例 fixture、变异探针、独立审查、外部有效性边界
控制论行动有效可纠偏状态机准入、门禁阻断、返回码、趋势与再探查形成反馈

第二章 · 全景AIStudio 里都有什么，谁负责什么

AIStudio 是一个单仓工程：桌面驾驶舱、智能体团队、编码引擎、技能生成器四块在同一个仓库里，靠补丁与扩展层注入上游基线。对使用者来说，它是一套“人看板、AI 干活、机制留证”的工作系统。

四块拼图，各管一段

六个团队，六个责任面

团队不是组织架构图上的方块，而是六类“必须有人负责”的判断：需求能不能验收、工作有没有派对人、代码能不能审查、测试是不是独立、环境能不能恢复、批准是否有效。同一项任务会依次穿过这些判断。

产品面上，人主要在哪几处操作

入口做什么判断依据
/app 工作台看今天要处理什么：待办、评审、异常、发布汇总只是入口，结论回原始记录
/app/projects 项目项目状态、暂停与完成、负责人暂停只拦机器派单，不停在飞执行

三个常见误解

“看板 done 就是完成”

卡片状态是协作信号。真正的完成要有当前提交的测试、独立评审和合入记录；状态可以被人改，证据不能。

“门禁全绿就是质量好”

门禁只检查它擅长的那一面：词法、结构、流程、配置。算法错误、契约破坏、遗漏边界仍要靠真实测试与评审。

“AI 说修好了”

自述不是证据。要看当次命令输出、失败复现是否消失、有没有引入新问题；三者缺一，结论只能是“待核实”。

第三章 · 主线一件事怎么从想法走到发布

一项工作要穿过八个节点、四个阶段和六道质量门。每个节点都留下可复核的东西；没有证据的“完成”不算完成。

每一段必须留下什么

阶段做什么完成标志（可观察）失败时先查什么
需求与规格把一句话需求写成范围、验收条件、不做的事、风险和验证方法另一人能据此判断“做完没有”，不靠猜是否只有标题没有验收条件
派工选一张可开始的任务卡，确认负责人、目录、容量分配、认领、执行记录能连成一条线是否只有“已派发”没有认领
分支开发从最新主干建分支，先测试后实现，改动不越界测试与实现同分支，提交只含本任务是否直接改了主干或混入无关文件
分支测试运行目标测试与门禁，独立评审代码测试报告指向当前提交，评审人不是实现者是否拿旧提交的报告充数
主干合并核验前序证据、回滚方案与兼容性后合入合入记录可追溯，回滚步骤可执行是否跳过了批准或回滚说明
主干回归在主干重跑全量测试与适用门禁主干结果与分支结果分开记录是否用分支结果冒充主干结果
发布与复盘放行或冻结，取真实回执，登记遗留问题回执、观察负责人、行动项齐全是否只有“已发布”没有观察与回执

谁来批，批什么

批准不是点一个按钮。有效的批准要能回答：谁发起的、谁决定的、以什么方式决定、授权有多强、什么时候过期。代理批准能让流程继续，但不能算真人批准；这两本账必须分开记，否则“全部通过”会掩盖实际缺口。

给讲师的提问“这次发布是谁批的？他凭什么批？如果明天他休假，这个批准还有效吗？”三个问题能快速检验学员是否真的理解了批准链，而不是记住了界面位置。

把这一章压成一句话

一项工作能走到发布，靠的不是某个人记得住流程，而是四件事同时成立：对象清楚（任务、提交、测试、审批指向同一件事）、责任清楚（每一步有负责人和验收人）、证据清楚（每段结论能回到原始记录）、例外清楚（代理、跳过、豁免都单独记账并披露）。

后面的章节会反复用到这四个词。读第四、五章时，留意每个机制在补哪一块；读第六、七章时，留意每次失败是因为哪一块缺了。

第四章 · 深入机制swarm-yuan：把研发能力做成可执行的 SOP

SOP 是标准作业流程。所谓“研发能力的 SOP 化”，就是把资深研发脑中的判断，写成任何合格执行者照着做都能得到同样质量结果的步骤、检查与证据。swarm-yuan 不是代码生成器，它是这套 SOP 的生成器与执行器。

五项能力，形成一条链

能力对应实物能做什么不能外推成
① 标准研发能力standards-map.conf、industry-profiles/、rules.d/把标准条文映射到门禁，按行业与项目裁剪成可执行检查不等于自动合规、认证或覆盖全部法规
② 个性化研发能力17 项特征卡、mine-habits.sh、recipes.md、lessons.md把项目结构、书面约定、Git 行为与已验证经验固化为规则和配方不是模型微调；未记录的经验无法自动获得
③ 组织资产本体assets/ontology/、组件清单、relations.jsonl回答有什么、谁依赖谁、怎样复用；支持影响面反查不是完整数字孪生，也不是自动推理引擎
④ 标准研发流水线复用 spec、check_reuse、stable-diff、九节点、状态机约束最小单元与拼装方式，按四阶段推进交付不是全自动 CI/CD；语义是否“最小”仍靠人判断
⑤ 独立全面检查L1-L4、真实测试、评审、变异探针、ACP 证据分别验证流程、结构、行为与实现质量，形成发布证据全绿不等于业务正确或生产就绪

实现上分六层，一层喂一层

生成一套技能：Step 1—13

这十三步是“造工具”的流程，不是每天研发的流程。脚本负责枚举、复制、渲染和核验；AI 负责判断、填充和审查。只生成骨架不算完成，必须走完验证与激活。

阶段关键动作完成判据
1—5自检生成器环境；读规则与历史；三路探查结构、规范、代码组织；填 17 项特征卡组件、关系、配方有代码证据；P0 特征卡是具体值；统计事实经审读
6—9按档位生成骨架（lite / standard / compliance）；AI 填充项目内容；接门禁与宿主配置骨架无空泛模板话；# TODO:model 清零；只启用真正理解的配置
10—13跑核心门禁；独立审查并落记录；写回记忆；strict 终检后激活门禁有真实结果；评审人非实现者；清单、预算、完整性全过才 active

日常研发：九节点与研发四阶段

九节点是每天做事的路，四阶段是把它们分成四批验收。①需求理解、②探查、③写规格、④拆分计划、⑤分支编码、⑥测试、⑦独立评审、⑧合入主干、⑨主干回归与发布。前四步定方向，五到七在分支上完成，八合入，九在主干验证。

研发阶段包含节点为什么这样分批
分支开发⑤从最新主干起分支，测试与实现同分支，主干保持可发布
分支测试⑥⑦测试、门禁与独立评审都在分支完成，全绿才允许合入
主干合并⑧核验前序证据、回滚与兼容性，按授权合入
主干回归⑨合入后在主干重跑全量，发现并行改动的交互问题

状态机把九节点映射成六个状态：open（①②）、design（③④）、build（⑤）、verify（⑥⑦）、archive（⑧）、operate（⑨及发布后观察）。状态机只做逐级准入和状态更新，不会替你跑测试、合并或发布。

守门：59 道门、三档聚合、三种返回码

门禁检查的是词法、结构、流程与配置，属于“机械能判”的部分。当前共 59 道，按用途分成三档聚合：核心 --all 12 道、标准 --all-full 32 道、合规 --compliance-suite 19 道。配置变量 204 个（core 30、arch 126、compliance 48），数字以 assets/facts.conf 为正本。

返回码含义容易误读的地方
0没有 FAIL 或 ERRORWARN、advisory 与默认模式下的 SKIPPED 不阻断，所以“通过”不等于“全覆盖”
1业务 FAIL 或门禁自身 ERROR--fix-suggest 收集到 FAIL 也返回 0，只能看建议
2启动/配置错误，或显式 --strict-skip 下存在 SKIPPED不能一律解释成“部分跳过”

四层拦截各自守哪一段

层真实能力边界（必须讲清）
L1写文件时拒绝无规格修改宿主与 hooks 必须实际安装启用；草稿、未配置、缺库等情形会放行
L2提交时检查暂存内容与分支关联--no-verify 可跳过；配置或判定库缺失时 fail-open
L3门禁检查工作区、暂存区与未跟踪文件只有真的运行才生效；未启用、非 Git 仓库会 SKIPPED
L4进入构建前检查批准与规格不使用状态机就不触发；SPEC_REQUIRED=0 或库缺失会降级
不要过度承诺四层拦截是互补的纵深，不是密不透风的墙。它们能让“没规格就改代码”这类问题大概率被挡下，但挡不住业务逻辑写错、契约设计错和需求本身有歧义。那些必须靠真实测试、独立评审和业务验收。

能力边界，写在结论里

  • 不替代编码宿主、真实工具链，也不替代人的需求、架构和发布裁决。
  • 不是操作系统沙箱；权限与隔离由宿主和部署环境负责。
  • 门禁擅长词法与结构，算法错误、契约破坏和遗漏边界仍靠测试与评审。
  • 激活通过证明的是当次结构、清单与预算检查通过，不证明以后一直全绿。
  • fixture 通过证明检查能力，不证明真实项目的外部有效性；真实缺陷语料仍在采集。

标准怎么落到门禁上

standards-map.conf 用五列把门禁挂到标准条文：规则或门禁编号、CWE、GB/ISO 条款、ASVS5 小节、置信度。合规档分发这张映射，报告转换器把 CWE 与 GB/ISO 写进规则元数据，合规门校验矩阵完整性与字段合法性。

第七章 · 案例两个案例，看懂“完成”和“通过”的区别

第一个案例讲一轮真实推演怎样读账：流程完成不等于净额通过。第二个案例讲一次真实需求怎样走完流程：功能能跑不等于可以批准。

案例一：run28，两本账要分开看

run28 是一次完整推演：26 个步骤全部走完，耗时 44954 秒（12 小时 29 分 14 秒）。如果只看“六道检查全过”，结论会是 6/6。但其中一道检查由代理批准完成，扣除后净额是 5/6。两个数字都对，说的是不同的事。

现象正确读法容易被误读成
26 步完成说明流程范围走完了“质量已经达标”
含代偿 6/6六道检查都有结论，其中一道靠代理批准“六道全部真人通过”
净额 5/6扣掉代理批准后的真实通过数“系统有严重缺陷”或“和 6/6 一样”
open 65 / 已修 8/65未关闭问题数，与真正修复数是两个口径“65 条全部处理完”
报告 11/13、后续 13/14两个时点的覆盖，后续补证不能回写原报告“报告已经是 13/14”
讲师提问“如果领导只问一句‘这轮过了没有’，你怎么答？”合格答法是分两句话说：流程含代偿 6/6 走完，净额 5/6，其中 G5 是代理批准；另有 65 项未关闭问题、报告覆盖 11/13。不合格答法是单说“过了”。

案例二：订单编辑，功能对了仍可能被退回

需求是给订单加编辑能力：只能改可编辑字段，已关闭订单拒绝修改，未知订单返回不存在，改数据必须带分片键，前端只在非终态显示入口。测试全绿之后，评审仍然可能退回——因为分片键丢了、权限没判、回滚没写，这些不是“功能测试”能覆盖的。

检查面要看到什么只做表面验证的后果
正常路径可编辑字段更新成功，返回新版本只测 200，不测字段是否真落库
状态约束已关闭订单被拒绝，数据不变只看报错码，不查数据库是否被改
分片约束更新语句带分片键，只影响目标分片功能能跑，但全表扫描或写错分片
前端契约非终态显示入口，金额校验与创建同源只测函数存在，不测真实渲染
回滚出问题能按步骤退回上一版本只写“可回滚”，没有命令和负责人

验证检查是否真的有效：故障注入

测试全绿不等于测试有效。做法是故意注入两类故障，看系统能不能抓到：把状态条件去掉，制造并发覆盖风险；把分片键从更新语句里删掉，制造跨分片写。前者应该被业务测试抓到，后者应该被框架门禁抓到。如果注入后仍然全绿，说明测试或门禁没在真正检查。

# 只在隔离练习副本里做，做完立即还原
# 故障一：移除状态条件（CAS 退化）→ 期望并发测试变红
# 故障二：移除分片键（WHERE 只按订单号）→ 期望分片门禁变红
git diff        # 保存注入差异
git checkout -- .   # 还原（确认无未提交改动时）
git diff        # 还原后应为空
红线不得在真实业务仓注入故障；不得修改期望值来迎合故障；不得把未执行的套件记成通过。注入、变红、还原、复绿四段证据要成套保存。

第八章 · 验收学员交什么，讲师看什么

验收不看“讲得好不好”，看能不能拿出当次证据。作品齐全、证据对得上、边界说得清，才算通过。

学员要交的七样东西

  1. 生成包：目标技能路径、档位、入口文件、清单、激活报告、strict 与激活输出。
  2. 认知包：特征卡承接说明、组件清单、关系边集、至少一个五要素完整的任务配方、框架证据。
  3. 研发包：一个真实需求的规格、计划、分支差异、测试先行记录、评审记录。
  4. 证据包：门禁原始输出与返回码、逐门禁证据、跳过与警告的处置、构建与测试报告。
  5. 反馈包：一次结构或内容变化后的知识差异、局部重探查、清单复核、新指纹。
  6. 边界声明：未运行项、环境限制、外部有效性边界、离线与真实编码中未覆盖的部分。
  7. 认知说明：能指出三层投影与四论各自对应本次哪些记录，例如哪份门禁输出、哪条状态转换、哪次反馈更新。

只有文档没有命令输出，或只有退出码没有当次文件与测试证据，都不算完整作品。
