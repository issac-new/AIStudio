## 1. 最新方案要求怎样验收

### 1.1 26 步分七段，六闸不是六张装饰卡

| 阶段 | 步骤 | 必教内容 |
|---|---:|---|
| 序幕 | 1-4 | 账号分配、配置初始化、登录、环境冒烟 |
| 需求上锁 | 5-8 | 应用初始化、人员管理、G1、建群 |
| 需求分析 | 9-14 | 派发、任务分解、系统分析、分诊、四路系分、定稿 |
| 设计排期 | 15-17 | G2、系分收尾、排期 |
| 并行生产 | 18-19 | G3 编码、G4 独立测试 |
| 发布验收 | 20-21 | **先 G5 发布准出，再 UAT 用户验收** |
| 治理复盘 | 22-26 | 台账、合规审计、G6、IDE 介入、HTML 报告 |

逐步合格线以方案第五部分为准，不能只读步内叙事摘要。`docs/superpowers/specs/2026-10-05-mux-v8-fullflow-plan.md:414-421,2225-2238`

### 1.2 G4-E、G5、UAT 各回答什么问题

- **G4-E**：评测运行、红队、评估器三角、能力覆盖和评测集锚点是否满足当轮判据。PASS 置 `g4_eval_pass`，GAP 登记缺口后放行，FAIL 阻断 G5。GAP 不是 PASS。方案 `:824-846,1304,2280`。
- **G5**：测试证据、同 commit 可复现构建、依赖、具体回滚、灰度、用户向发布说明和 HumanGate 批准是否齐全。FAIL 即冻结发布。方案 `:852-878`。
- **UAT**：按 G1 冻结 AC 逐条给出证据和三态判词。通过、有条件通过、不通过不能混成一句“验收完成”。方案 `:880-901`。
- **完成契约门**：`complete_task` 前核对 receipt、证据路径、sha256 和 TAP/JUnit 计数。它只证明证据可重算，不替代 G3/G4 的质量判断。方案 `:1398-1407`。

### 1.3 等待时间也要形成产物

early-start 要求在闸门等待或熔断时并行形成三个幂等草稿：`prep_uat` 只收集 AC 与证据源，`prep_release` 准备发布说明和灰度表，`prep_retro` 预收集治理度量。草稿不提前代替正式判词，正式步骤再定稿。方案 `:2074`

### 1.4 全绿只是准入，不是充分成功

方案第五部分要求步骤与六闸记录真实、报告审计零 FAIL、必采证据达标、交付物全景清单全绿、问题单 100% DISP、测试门禁通过并完成报告持久化。standard/strict 还要看新发现并根治的缺陷和证据链完整性，不能把“26 步走完、六闸变绿”当成充分条件。方案 `:2496-2505,2882-2891`

### 1.5 run25 新增七条复盘纪律

1. capture 步键与采集器映射双向完备。
2. 审计缺口按自动修复、合规降级、内容补齐分类，同一缺口连续三轮不收敛就升级人工。
3. `report_done` 前核对 PART1 注册、行话 HARD=0、步 26 载荷已在场、数字与 issues.log 同刻一致。
4. 报告计数用生成时快照，审计锚定报告自身计数主张位，禁止全文首匹配。
5. 审计 FAIL 后重启必须覆盖缺口的上游采集位。
6. G1-G6 每道闸落键都发 delivery gate 事件，缺参不得杀驱动。
7. 方案改名或归档后全仓清扫活跃引用。

方案 `:2893-2903`

## 3. 为什么不能把本轮讲成“零缺陷全绿”

### 3.1 报告自己就有红黄牌和占位

- G4-E 是 GAP；评测处置链失败 2、已关 0、未关 2。
- 九层运行体检为 **覆盖 0、部分 1、缺失 8**。
- 技能专项帧为 0，复盘回灌文件缺席。
- 报告头部全量呈现覆盖为 13/15，步 2 还出现“载荷全缺（降级在案）”，多处使用“骨架占位·待补注册”。
- 六域审计中 L1、L2、L3、L5 为 warn，不是所有域都通过。
- 本轮 posture=standard，代偿台账 open 65 笔；“完整循环成立”属于含代偿口径，不等于净额无代偿。

final-report 第 0 章、第 2 章步 2、第 3—5 章。

### 3.2 “无未完成项”与后续台账必须分时点阅读

第 0 章写“还没完成的：无未完成项”。后续复盘与挂账台账却仍有：

- N01-N06 待做：真环境烧机、HumanGate 审批历史、发布门台账、评测数据通道、报告模板两节、DISP 闭环。
- N07-N09 观察：r18 op 注册、纪律硬断言评估、方案改名引用守门。

这不是允许把报告改写成“当时全部完成”或“后来毫无进展”。正确读法是：**第 0 章是该报告生成时的自述，后续复盘和清偿记录是另一时点的证据，二者必须带日期与来源对照。**

final-report 第 0 章；`docs/superpowers/specs/2026-11-03-run26-pending-batch.md:9-17,30-33`。

### 3.3 报告终态与复盘数字也不是同一快照

final-report 第 4 章为 33 个唯一问题键均有处置结论，其中观察 28、延后 5；复盘材料统计为 33 个唯一键、79 行，并指出 34 条问题单缺 DISP。它们属于不同整理时点和分母。培训时不能把各段数字相加，应回到该段标注的快照与统计口径。

final-report 第 4 章；`docs/superpowers/specs/2026-11-03-run25-full-retro.md:22-26`。

## 4. 哪些事故推动了真实修复

### 4.1 G2 环不是单纯“网络慢”

G2 环约 4 小时，包含 SFM 隧道 DNS 间歇断流、上游供应商熔断、725 恢复机制重复透传 `conversation_history` 的 kwarg 缺陷、监督器按错闸催办，以及熔断签名只看 integration tip 造成的 35 分钟复位盲区。后续形成补丁 726/729、监督器按闸分流、main tip 纳入签名和机制治理五件。

`docs/superpowers/specs/2026-11-02-mechanism-governance.md:5-20`；`docs/superpowers/specs/2026-11-02-chat-recovery-kwarg-fix.md:5-14`；`docs/superpowers/specs/2026-11-02-g2-breaker-evidence-main-tip.md:7-28`。

### 4.2 采集与报告链是最大成本

审计环共 36 轮，其中 16 轮来自错误重启起点，7 轮来自 PART1 未注册。`START_STEP=release` 跳过步 9 上游采集位，造成 25 分钟空转。后续把采集位前移、补齐映射、审计取数锚定终态单元格，并形成方案 §5.10 七条。

`docs/superpowers/specs/2026-11-03-run25-full-retro.md:5-39`；方案 `:2897-2902`。

### 4.3 容量恢复有效，但不等于限额消失

429 洪峰 56 次全部由恢复链消化，零死锁、零驱动退出，代价是每波等待 5-10 分钟。当前裁定是不把账号限额扩容列为整改项，只有恢复循环连续耗尽才升级为事故。不能把“自动恢复了”写成“外部容量无限”。

`docs/superpowers/specs/2026-11-03-run25-full-retro.md:26-27`。

## 6. 讲师怎样带读这份报告

1. **先看人读导读，再看闸和状态。**记录 RUN ID、posture、26 步、六闸、落键时间和代偿口径。
2. **再看 G4-E、G5、UAT 是否被混用。**GAP 不是 PASS，发布准出不是用户验收，UAT 三态要逐条回查。
3. **再看六域、问题单、治理结果和交付物矩阵。**warn、观察、延后、占位、缺失和 no_data 都要展开。
4. **区分当时快照与后续补流。**补拍、补录、补做和后续实测必须带日期，不回写历史判词。
5. **最后看挂账。**N01-N06、N07-N09、MP unit 85 红和真环境烧机未首跑仍是边界，不能用报告“无未完成项”覆盖后续台账。

讲师可让学员回答四个问题：

- 为什么六闸全过仍能同时有 G4-E=GAP？
- 为什么“无未完成项”不能替代后续 N01-N06 台账？
- 为什么 476 不能改写成 476/476 全绿？
- 为什么 run26 的补做和 MP unit 新红不能回填成 run25 的历史成绩？
