01 / CALIBRATION

先校准数字：59、53、32 各指什么

本页对应 yuan v2.100.1。数字以 assets/facts.conf 和 precheck 注册数组为准，不沿用过期注释。

59check_* 函数总数 = FULL 53 + advisory-only 6
32--all-full = 32 个 standard 序列成员（核心 12 + 架构 20）
204配置变量 = core 30 + arch 126 + compliance 48
门禁注册与执行序列
口径当前值怎样触发不能怎样解释
check_* 总数59注册表和三个聚合实现文件不等于单次交付必须执行的数量
CORE12--all不是旧文档的 11
STANDARD32--all-full不是 FULL 53，也不是旧值 29
COMPLIANCE19--compliance-suite未配置项可能 SKIPPED
FULL53ALL_GATES_FULL，供 --fix-suggest 等路径使用不是独立门禁总数，也不是 --all-full 的数量
advisory-only6各自 flag、宿主 hooks 或 loop-hook不在三个聚合执行序列里

FULL 53 的闭合关系是 standard 32 + compliance 19 + decision_audit/state_phase 2；再加上 6 个 advisory-only，才是 59。

02 / FILE BOUNDARIES

生成器、目标技能和 .swarm-yuan 运行态是三棵树

生成器负责“造技能”，目标技能负责“约束一个项目”，项目运行态负责“记录这次研发实际发生什么”。同名文件和同名目录不能互换。

目标技能目标项目技能目录下的 <项目>-dev/生成器出骨架，AI 填项目事实，升级器刷新通用文件自己的 SKILL.md、references、assets、scripts、rules.d 和宿主配置。
项目运行态<项目根>/.swarm-yuan/状态机、追踪、门禁、探查和恢复脚本state、tasks、notes、trace、decisions、gate 证据、指纹和恢复数据。
技能生成证据<目标技能>/.swarm-yuan/ 及技能根create、inject、upgrade、mark-activeactivation-report.json、effects/；技能根另有 skill-manifest.json 和 .swarm-yuan-version。

两个 .swarm-yuan 目录不能合并理解

项目根的账本正本是 trace.jsonl、decisions.jsonl、state.yaml 等。技能内的 .swarm-yuan/ 主要保存激活报告和框架注入效果。严格激活会先查技能内决策账本，再回退项目根及兼容路径；这是激活输入解析，不改变“项目账本正本在项目根”的运行时规则。

入库边界也由项目决定。运行态不天然等于临时垃圾。AIStudio 有意入库 .swarm-yuan/hooks/、部分基线和收据；不能按目录名统一删除或忽略。

生成落点有注册顺序

无既有技能目录时，默认生成到项目内 .agents/skills/。若已有受支持目录，则优先复用，顺序从 .agents/skills 开始，再到 .claude/skills、.codex/skills 等。第三个位置参数可显式指定目标目录。AIStudio 历史 .claude/skills/aistudio-dev 是项目特例。

05 / STRICT ACTIVATION

strict 激活是顺序执行的检查链，不是改状态字

--mark-active 只有在所有必需检查通过后才写 active。任何必需检查失败都返回 1 并保持 draft。

  1. 读取 SKILL 与当前状态SKILL.md 不存在直接失败；若不是 draft，报告无需标记并退出 0，不重跑激活检查。
  2. check_framework_globs防止框架已激活但 glob 全空、门禁实际不工作。
  3. check_spec_first_wiring防止 SPEC_REQUIRED=1 但 WRITABLE_DIRS 为空等失效配置。
  4. verify_completeness --strict检查占位符、workflow 要素、项目内容和决策记录。
  5. inventory-verify --strict带 TSV、path-check 和 stability-audit，核验清单计数、形态和登记路径。
  6. advisory 关系边集核验，再做最终预算relations 失锚只提示；预算是必需检查。
  7. 写 manifest 与 activation-report.json记录当次激活结果。
  8. audit-closure 提示后写 activeopen goal 只告警；最后才改 frontmatter 并解锁全量门禁。
两种非严格/建议路径不能误写成硬门。draft 下单独运行 verify_completeness（非 strict）可报告占位并返回 0；relations 和 audit-closure 在激活链中是 advisory。activation report 只证明当次激活通过，不保证后续项目永远全绿。

源码：scripts/generator/subcommands.sh:384-407,436-519,798-885。

06 / COMPATIBILITY & UPGRADE

历史兼容必须精确到记录和文件，不能泛化成放松 strict

SCHEMA_EPOCH：只豁免边界前的字段 schema

决策校验的 Python 主路径以 2026-10-28T00:00:00+00:00 为边界。它解决“新字段检查回溯误杀旧账本”，不是允许新记录缺字段。

决策记录的分期校验
记录类型实际校验
所有时期逐行必须是合法 JSON 对象；UserChallenge:incomplete 永远不能作为完整决策。
边界前，或 ts 缺失/不可解析按历史记录处理，不追溯后来新增的完整字段 schema。
边界后普通决策要求非空 type、ai_suggestion（或 suggestion）和 user_action。
边界后 UserChallenge除上述字段外，还要求 alternatives、missing_context、cost_if_wrong。

07 / STATE MACHINE

08 / SPEC-FIRST

L1-L4 共享判据，但触发时机和关联面不同

“有四层”不等于“任何环境都必然拦得住”。必须逐层核对实际安装、配置和当次调用。

spec-first 四层的实际行为
层实际触发与证据视图主要降级或绕过
L1 写时PreToolUse Write/Edit/MultiEdit 触及 WRITABLE_DIRS；查项目是否存在已批准 spec宿主未装/未启用、配置未实测、draft、非可写区、开关关闭、库/conf 缺失。Bash 的 rules.d 和推进态命令是相邻拦截面，不混称 spec-first 触发。
L2 提交时staged 触及可写区；特性分支按 staged ∪ branch 选 spec，正文取 Git indexgit commit --no-verify；draft、开关关闭、目录为空、库/conf 缺失会 fail-open。
L3 门禁时--all 或 --spec-first；特性分支按 staged ∪ branch ∪ untracked，正文取 worktree不运行就不生效；开关关闭、无目录、无判定库或非 Git 项目会 SKIPPED。
L4 流程准入state-machine.sh guard build，由 transition build 或 auto 进入 build 时执行；查已批准 spec 存在性不使用状态机就不触发；SPEC_REQUIRED=0 或判定库缺失会降级。
“已批准”是机器判据，不是人类签字。基础判据是 spec 含非占位“决策记录”段。真实人类评审仍要单独留证据。

L1 已有 Claude Code、Codex、ZCode 实证；Cursor、Gemini、OpenCode、Kimi-Code、Windsurf/Devin CLI 只有生成配置，尚未实证。生成配置不能写成已验证能力。

09 / PRECHECK

precheck 是累计汇总，不是首个 FAIL 即停

--all、--all-full、--compliance-suite 按注册数组串行执行，记录失败并继续后续检查，最后统一决定返回码。后续 PASS 不抵消前面的 FAIL。

bash scripts/precheck.sh --all                # 核心 12
bash scripts/precheck.sh --all-full           # standard 32
bash scripts/precheck.sh --compliance-suite   # 合规 19
bash scripts/precheck.sh --list-gates

GATE_RUNS_DIR=.swarm-yuan/gate-runs \
  bash scripts/precheck.sh --all-full
配置即命令。TEST_CMD、BUILD_CMD、MUTATION_CMD 会作为 shell 命令执行。只能使用受信任配置，不能把不可信仓库配置当成无害数据。

返回码必须结合输出判读

precheck 返回码与特殊路径
返回码当前语义
0无 FAIL/ERROR；WARN、advisory 和默认 SKIPPED 不阻断。--fix-suggest 即使收集 FAIL 也固定返回 0，只用于建议，不能当验收通过。
1业务 FAIL 或门禁自身 ERROR 的汇总失败；未知模式、非法 format 等部分 CLI 用法错误也返回 1。
2既可能表示配置、项目根或门禁实现完整性错误，也可能表示显式 --strict-skip 下无 FAIL 但有 SKIPPED。不能一律解释为“部分跳过”。

最终汇总分别显示 fail、warn、advisory、skip。skip 不计 warn，也不等于 pass。默认情况下有跳过仍可能返回 0，所以“通过”不等于“全部覆盖”。

gate-runs.jsonl 的字段和序号

GATE_RUNS_DIR 默认为空，JSONL 落盘默认关闭。--format json 或设置该目录会开启输出捕获，但只有目录非空才写 gate-runs。目录不可创建会告警并关闭落盘。

{
  "ts": "UTC 时间",
  "run": 1,
  "gate": "check_test",
  "status": "pass | fail | error | skip | warn | advisory",
  "ids": ["从检查输出提取并去重的 ID"],
  "duration_s": 3
}

run 按 JSONL 当前行数递增，是单门禁记录序号，不是整套套件共享的批次号。引用 gate-run#N 时，还要结合时间、执行命令和工作区确认它属于当次任务。

.gate-fail-flag 的清除权属于覆盖式运行

FAIL/ERROR 会写项目根 .swarm-yuan/.gate-fail-flag，供白名单拦截。只有 --all、--all-full、--compliance-suite 等覆盖式运行全绿才清旧标记；单个门禁变绿不能证明其它失败已修复。

源码：assets/precheck.sh:1255-1321,1338-1467,1879-1898,1969-1975,2031-2087；配置链：assets/precheck.conf:98-119。

10 / VERIFICATION

位置证明什么不能证明什么

11 / WORKER → ACP → ENGINE

worker→ACP→编码引擎：证据必须按层闭合

provider 名称、ACP 会话、引擎身份、技能调用和业务测试是不同事实。任何一层都不能替下一层签字。

人和 Kanban ↓ 任务、授权、规范 workspace Hermes worker-coder ↓ 先读代码与上游文档，准备项目技能，显式 cwd ACP / zcode-acp-server ↓ initialize → session/new → session/prompt → session/update 编码引擎（官方捆绑或 Ycode 分叉，须以身份字段区分） ↓ 技能工具调用、文件改动、命令与测试 worker 亲自复核 → Kanban handoff / 独立验证

worker-coder 要求技能准备先于 ACP 编码，首轮 prompt 带技能绝对路径；ACP 产出后，worker 必须亲自检查文件、语法、类型和测试。

当次交付要核对哪些字段

证据字段与证明范围

12 / R134 OFFLINE BOUNDARY

everything 不是完全气隙环境的“全内嵌包”

当前有效口径是 R134，R145“全内嵌”已撤销。everything 与默认档互补，不是互相包含。

源装不了的资料尽量内嵌完全气隙环境需提前把完整依赖同步到内部镜像，或接受诚实降级。
知识资产限本地或内部分发含第三方版权材料，公开分发前另做合规核对；gstack 浏览器默认 --no-browser，Chromium 离线不可引导。

13 / ACCEPTANCE

交付核对：每项都要对应当次证据

  • 目标技能通过 strict 激活，不是只有 draft 骨架；activation report 与当前技能目录对应。
  • 宿主发现技能和本次实际读取技能分别有证据。
  • 探查先查组件、配方和关系边集，没有凭印象重复造轮子。
  • spec、plan、worktree、分支和基线明确；⑤、⑥⑦、⑧、⑨顺序完整。
  • precheck 的 FAIL、ERROR、SKIPPED 分别解释，没有把控件数量、执行序列和通过范围混写。
  • L1-L4 按当前宿主和配置核对，没有把“生成配置”写成“运行实证”。
  • 测试有真实输出、负向和边界用例；需要时有变异验证；独立审查有 review-record。
  • ACP cwd、引擎身份、技能调用和当次回合分层对应；provider 名称没有替代 engineBinSource。
  • 离线包没有写成完全断网自足；Windows、气隙安装和版权边界已披露。

只有与当前任务相关的每一项都有证据，才能把该次研发交付写成完成。
