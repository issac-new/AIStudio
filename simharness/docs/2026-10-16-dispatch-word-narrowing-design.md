# 派发词窄化设计（PR-7 场景侧，2026-10-16）

> 定位：V8.34 方案「待收紧面 9/13/18（预写派发词）」的场景侧窄化件；strict 替代语义
> （派发改需求+期限交 PM 自主拆分）自 V8.29 起已在 `dispatch_in_room` 助手层在位
> （strict 姿态只发「自主组织」需求单，不预设拆分与人日），本文记录 standard 侧的
> 窄化路径与已落地件。

## 一、问题与张力（如实记录，不回避）

派发词预写是「驱动代演组织侧派单」的最大面（PR-7 问题描述：单轮 40+ 笔
dispatch-preset，fanfan-agent 的规划派发能力从未被考）。但它与用户 2026-10-15
同日裁定存在张力：

- **审计侧**（plan-doctrine-intervention-audit）：预写派发词=驱动替组织干活，
  自组织形态下应收窄；
- **交付侧**（task-granularity-root-cause-rule）：用户 10-15 拍板「任务书拆细」
  治「干完不交卷」——V8.32 完成定义四步、testlog 随首 commit 同步等纪律正是
  预写派发词的组成部分，是交付命的根子。

**化解（窄化的设计约束）**：窄化≠删细。收窄的对象是「枚举型代劳」
（本可由计划文档/任务卡承载的范围枚举），保留的是「纪律型内容」（完成定义、
边界、证据要求、结论行）——后者是用户亲自定的交付命方，动它就是回退 run20
的嘴炮治理。

## 二、四段结构（dispatch_task 助手）

```
派发词 = ①需求段（要做什么，一句话）
       + ②指针段（读哪些文档/卡——单一事实源，替代内嵌枚举）
       + ③纪律段（模板注入：testlog/defect-loop/PROGRESS/结论行）
       + ④验收段（结论行 AC + 期限）
```

- **指针替代枚举**：范围/用例/接口以 `docs/plan/<RFD>-schedule.md` 测试任务表
  +概设契约+任务卡为准（agent 本来就要读的三件），聊天消息不再内嵌复述。
  信息不丢失，只从易失的聊天消息移到持久的工件=单一事实源。
- **纪律段集中**：原散在各派发词里的 testlog/defect-loop/PROGRESS 条款收敛为
  一段模板（与既有 FRESH_NOTE/ACP_NOTE 模板变量同范式）。
- **strict 姿态**：仍由 dispatch_in_room 既有分支接管（需求+期限+AC，零预设）。

## 四、与 PR-7 产品侧的依赖（未落地部分）

场景侧窄化的完全体依赖 PR-7 三件产品件：

1. **pm-planning 技能产品化闭环**（输入=G1 冻结单→输出=结构化任务卡集）——
   任务卡的 body 是枚举的归宿，目前卡 body 由 agent 自写，结构化字段未产品化；
2. **autosched 与排期步对接**——排期产物由产品生成而非脚本，是指针段的
   权威源；
3. **任务纪律模板库**——纪律段作为可引用模板注入派发词（agent 自选），
   目前是驱动侧字符串模板（FRESH_NOTE/ACP_NOTE 已是雏形）。

**验收锚（PR-7 原文）**：一轮 strict 姿态中 fanfan-agent 自主完成拆分派发
（零 dispatch-preset）+编排面帧。

## 六、风险与回滚

- 风险：指针式派发依赖 agent 真去读计划文档——若 agent 不读，范围信息即失。
  缓解：本轮 5 片均保留「工作区+checkout 命令」的行动指引，且 AC 结论行不变
  （交付判据不依赖范围复述）。
- 回滚：`git revert` 本提交即恢复枚举式；dispatch_task 助手可保留不删
  （纯增量，无调用即零影响）。
