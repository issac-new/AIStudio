# 懒生成方法论（Lazy Generation）

> 来源：行者明灵《Harness实践：OpenSpec + Superpowers + CodeGraph + Ponytail + Caveman + RTK》上下篇（2026-09-16/17）+ [DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail) v4.9.0（MIT；141,551★，GitHub API 2026-09-18 A 级实测）。
> 证据分级：仓库元数据=A（本机核验）/ 性能数字=B（官方 benchmark 自述）/ 文章对照实测=C（二手信源）。
> 纪律：只引用方法论模式，不 vendor 上游 skill；守决策 26/27——门禁 55 不增，本文档为纯文档载体。

## 一、定位：给"拼装式开发"一个可执行的决策程序

理念层"新功能 = 既有稳定单元拼装 + 最小新增胶水"回答了**为什么**，但没回答**写入第一行新代码前按什么顺序找零件**。七层懒人阶梯把"先查再写"变成自动下探顺序，任何一层命中即停：

| 层 | 先问 | 通过判据 |
|----|------|---------|
| 1 | 真的需要存在吗 | 改写/砍掉需求能消掉就不写 |
| 2 | 代码库里已有吗 | 组件库清单 / recipes 配方 / §A 同类功能命中 |
| 3 | 标准库能解吗 | 语言标准库直接可解 |
| 4 | 平台原生能解吗 | 宿主 / 框架原生能力可解 |
| 5 | 已装依赖能解吗 | 包清单里既有依赖可解（不为一个函数引新包） |
| 6 | 一行调用能解吗 | 单行 shell / 一行库调用 |
| 7 | 都不中 → 最小可用实现 | 只写撑起**当前**需求的最小集，不为想象中的未来预留 |

**整合**：开发工作流 ②探查先查 recipes 与 reference-manual（层 2 的机器面）；⑤编码逐层下探，落到层 7 才允许新增代码。探查产物"可复用稳定单元清单"（exploration-guide §C ★必查）就是层 2 的组件库清单。

## 二、懒 ≠ 偷工（lazy, not negligent）

上游原话"The rule was never 'fewest tokens'"——懒人哲学裁的是**代码量**，永远不裁**正确性**。四类永不裁剪（与开发工作流 门禁下限同向）：

1. 验证与测试（尤其保护真实行为的测试，不为绿而删断言）
2. 错误处理与数据丢失保护
3. 安全检查与信任边界的数据校验
4. 无障碍与可观测性

目标技能执勤口径：任务路由（task-methodology-router）调的是**仪式复杂度档位**（小任务轻流程），门禁序列与安全铁律不随"任务很小"豁免。

## 三、证据与边界（诚实登记）

- 官方基准（B 级）：LOC −54%（单例峰值 −94%：日期选择器 404→23 行）、token −22%、成本 −20%、耗时 −27%；安全通过率 100%（对照组"朴素 YAGNI 提示词"95%）。
- **基线伪影教训（上游 issue #126，A 级）**：早先宣称的 −80~94% 总体数字系会话基线伪影，官方已澄清修正——**单例峰值 ≠ 总体均值**；本文档只引用修正后口径。与"缺失证据不显示为零"同族的估算诚实纪律。
- terse 模型可能因懒生成反烧更多 thinking token（净收益为负的场景真实存在）——按项目模型档实测，不默认开。
- **装完 ≠ 激活**：上游 skill 生效须宿主按内容哈希（trusted_hash）审查信任后激活——"装了≠生效"诚实族，目标技能 hooks 部署文档同口径披露。
