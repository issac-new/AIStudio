## 1. 五层元模型速查（实体清单）

| 层级 | 实体 | 对 swarm-yuan 探查的对应物 |
|---|---|---|
| 通用实体层 | 原则、约束、假设、需求、位置、差距、工作包、能力 | spec §1 背景/§5.6 版本约束/§5.7 安全约束；工作包→交付能力 = 任务→特征卡 |
| 业务架构层 | 驱动因素→目的→目标→测度→行动方案；产品/组织单元/业务能力/价值流/业务信息/施动者/角色/事件/功能/流程/控制/业务服务/服务质量/合同 | 探查的业务域识别；spec §1 目标链 + §18 领域知识 |
| 数据架构层 | 数据实体→逻辑数据组件→物理数据组件 | 探查的数据模型三层（ER 图→schema→物理表）；spec §10 数据设计 |
| 应用架构层 | 应用服务→逻辑应用组件→物理应用组件 | 探查的服务/模块划分；spec §7 后端/§8 接口 |
| 技术架构层 | 技术服务→逻辑技术组件→物理技术组件 | 探查的技术栈/基础设施；spec-template 技术选型 |

**纵向映射链**（BDAT 打通的关键路径，§24 逐层验证用）：

```
业务服务 →【被供应或被使用】→ 数据实体 →【被使用】→ 应用服务 →【被服务】→ 技术服务
数据实体 →【存在于/封装】→ 逻辑数据组件 →【实现】→ 物理数据组件
应用服务 →【通过……实现】→ 逻辑应用组件 →【实现】→ 物理应用组件
技术服务 →【提供/被实施于】→ 逻辑技术组件 →【实现】→ 物理技术组件
```

## 2. 双向语义动词体系（A→【动词】→B 模板）

所有架构关系用统一句式 `A →【动词】→ B` 表达，每条关系主动式+被动式双写（交付↔被交付、使用↔被使用、实现↔被实现、包含↔被包含、服务↔被服务）。写 spec §24 架构映射时沿用此模板——**模板统一 = 可读、可机器解析**（后续可加 lint）。

条件型/方式型关系用省略号占位（如"目标【按照……跟踪】测度"），不强行简化，保留语义精度。

## 3. 通用实体层的演进语义（差距→工作包→能力）

架构演进规划生成期必读文件：**差距**（当前态 vs 目标态的缺口）→ **工作包**（弥合差距的交付单元）→ **能力**（工作包的交付物，`工作包 →【交付】→ 能力`）。对应 swarm-yuan：§14 交付衰减分析（差距识别）→ §15 蓝图任务（工作包）→ 特征卡（能力沉淀）。填 §24 时若变更属演进类（迁移/升级/重构），须先写差距再写工作包。

## 5. 读图 SOP（架构图→结构化文本，8 步）

遇到"实体+连线+动词标注"类架构图（ER 图/C4 扩展图/BPMN 关系图），按序操作：

1. **切层**：按颜色/区域/泳道切成 3~6 层（关系只在层内+相邻层间识别，不在全图盲搜）；
2. **列实体**：每层实体清单+一句话角色定位；
3. **分组**：层内按语义角色分组（驱动类/资产类/主体类/载体类/治理类）——分组本身就是在识别关系簇；
4. **辐射穷举**：以每个实体为中心列出全部关联（先主动式），天然去重不遗漏；
5. **双向配对**：为每条主动关系补全被动式（图上只画一个方向也语义补全）；
6. **标注层间接口**：只识别层与层衔接实体的关系（如业务服务↔数据实体），控制复杂度；
7. **模板化输出**：统一 `A →【动词】→ B` 句式成文；
8. **建索引**：层末做动词去重汇总，文末做整体脉络总结（双层索引）。

**三重信号确认**（防视觉误判）：颜色判层、箭头方向判主被动、连线动词标签判语义——三者合一才确认一条关系。
