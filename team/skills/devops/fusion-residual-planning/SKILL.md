# 融合残差规划与设计文档同步

本 skill 处理「外部方法论已经完成初轮融合，但用户怀疑还有大量未落地内容」这一类任务。目标不是继续堆清单，而是把残差拆到原子机制，逐项判断该做、不该做、变形做还是延后，并把真正的状态同步进整体设计文档。

## 什么时候使用

- 用户追问「还有哪些没有落地」「全部落地了吗」
- 用户认为初轮融合结论过于粗、域级覆盖掩盖了子项漏项
- 需要规划残差的 NOW / 变形 / DEFER / NEVER，而不是照单全做
- 需要把已经执行的评测、门禁、验收纪律同步到总体设计文档

## 主流程

### 1. 先读全量事实，再谈残差

1. 读取源文档完整存档，按章节/编号建立原子机制清单；大文档必须分页读到末尾，不能只读摘要或片段。
2. 读取既有裁决矩阵、残差报告、深度规划和上一轮落地报告；它们是输入证据，不是新的事实源。
3. 机械扫描目标 `_shared/`、skills、评测基线、设计文档和 gap 台账，逐项找执行者、触发时机、判定口径与实测证据。
4. 记录每个原子项的状态：**等效**（已有且锚点完整）/ **已落**（本轮新增）/ **补落**（曾被域级结论遮蔽的漏项）/ **有意不落**（有边界和重新评估条件）。

域级「已覆盖」不能代替原子项核验；同一域中登记侧、发现侧、证据侧、迁移侧等子项必须独立判定。

### 2. 用五问做「该做/不该做」规划

对每个残差逐项记录论证链：

1. **语境匹配**：源机制依赖的团队规模、线上流量、训练管线或平台能力是否存在？不匹配则 DROP 或变形。
2. **单一事实源**：落地后是否会与现有协议、脚本或 skill 形成第二套口径？会则优先扩展既有事实源，不新建平行系统。
3. **执行面**：谁执行、何时触发、输出什么、谁裁决？只有 prose 没有执行面时，不能宣称机制落地。
4. **成本收益**：全量实现的维护成本是否超过对真实风险的收益？结构性不划算的完整引擎判 NEVER，而不是做一个空壳。
5. **可验证性**：能否构造坏样本证明它抓得到错？不能证明的机制至少变形成评测题、fixture 或可重复探针。

使用四档裁决：**NOW**（立即做）/ **变形**（换成适合本机语境的轻量形态）/ **DEFER**（附触发条件）/ **NEVER**（附失败理由与 reopening 条件）。

### 3. 把「落地」分成三种成色

每个执行结论都标成色，禁止笼统写「已落地」：

- **语义落地**：规则写进文档或 skill。
- **机制落地**：已有执行者、触发时机和判定口径。
- **效力落地**：坏样本或真实回归证明机制能抓住目标错误。

只到语义层写「提案」；到机制层写「可用」；到效力层才写「有效」。如果只完成前两层，交付中要明确缺哪一层及下一验证入口。

### 4. 设计文档只写终态，不复制调研过程

整体设计文档的更新顺序：

1. 先确定正本与事实源，正文写「规则是什么、为什么这样设计、如何执行、如何验证」。
2. 新机制用增量小节或增量段落接入，保留既有编号与外部引用；不要为方便重排旧章节。
3. 正文用大白话先讲规则，机制名、英文名和文件路径放在后面作锚点；不要让术语名充当句子主语。
4. 设计文档至少同步：关联机制段、资产清单/规模表、正文新节、附录术语、gap 台账或事实源指针。
5. 细节只保留在单一事实源；正文只能做摘要和指针，不能复制整套检查表。
6. 新建共享协议或规则文件后，回填共享规则指针索引，否则后续盘点会把它当幽灵资产或漏项。

### 5. 机械验收并人工复核

- 扫描旧口径数字和旧标题，确认零残留或逐项解释保留原因。
- 检查新节标题序、§ 引用、表格列数、资产索引和附录术语。
- 对每条关键锚点做一次上下文人工核对；Markdown 粗体、全半角标点和引号样式会造成脚本误报。
- 脚本报错先看实文再定论；脚本全绿也不能替代至少一条人工锚点抽查。
- 输出必须包含：原子项总数、四态数量、NOW/变形/DEFER/NEVER 数量、三层成色和未闭环验证项。

## 用户表达偏好

- 中文、严肃、直接；用户说「说人话」时先给一句能脱离术语独立理解的判断，再给机制名和路径。
- 汇报先讲结论和影响，不写过程流水账；按「改了什么 / 为什么这样取舍 / 怎么证明」组织。
- 不把「文档写了」说成「系统有效」；不把一个域的等效物扩展成全域覆盖。

## 典型坑

- **域级遮蔽**：一个子机制等效不代表相邻子机制覆盖；修法是回到原子清单重判。
- **伪落地**：把规则写入 skill 或设计文档就宣布完成；修法是补执行面与坏样本效力测试。
- **完整引擎冲动**：残差清单看起来完整就照单开发；修法是先过成本收益和可验证性，能变形就不造新基础设施。
- **双事实源**：为了表达清楚在多个文档复制细节；修法是事实源保留细节，设计文档只留摘要和指针。
- **验证脚本误报**：固定字符串没匹配到不等于内容缺失；修法是按实文排版核对，再修脚本模式。
- **并发覆盖**：共享文件被别的写入者改过后继续按旧内容 patch；修法是重读当前文件、合并新旧变化、再验证编号和锚点。
