# 跨章节衔接规范（章节之间的接口设计）

## When to Use

- 设计文档多章形成「机制→载体→运转」链时
- 用户说章节割裂、看不出组织和衔接论证关系
- 章节边界不清、图号交叉、接口表遗漏

## 核心原则：交接物 > 手术节

跨章节衔接不是写“本章承接上一章”，而是定义每章的交接物：

| 章节 | 交接物 | 说明 |
|------|------|------|
| **设计章** | **要求、边界、判定标准** | 明确要防止什么、检测什么、输出什么 |
| **载体章** | **载体清单、接线方式、失效检测** | 每节指向上游要求，并声明提供给下游的证据 |
| **运转章** | **证据类型、判定分支、回写动作** | 把运行输出连接回机制与载体 |

## 七步桥梁构建流程

### 1. 放置两类总图

- **载体章首**放「设计 → 实现 → 运转 → 回写」接口图；节点说明章节职责，不把它当正文替代品。
- **运转章首**放「输入 → 执行 → 证据 → 判定 → 回流」闭环图，并标明消费的是载体章输出。
- 回写边必须明确分别回到机制设计还是实现载体；否则反馈无法执行。

### 2. 写上下游导航句

章节开头第一段同时指向上游、声明下游：

```
本节承接 §X.Y（机制名称），输出的载体供 §Z.Z 使用。
```

每个实现小节至少指向一个设计小节，并说明它向运行小节提供什么证据；“编号对应”只能导航，不能替代依赖关系。

### 3. 写边界声明

每个小节末句必须写「本节不负责什么」或「由 §X 定义什么」。例如：

> 本节负责脚本与配置的接线，判定窗口与回滚策略由 §3.7 领域机制定义。

### 4. 用接口表固定依赖

| 上游设计 | 本节落地 | 下游运转 |
|------|------|------|
| §3.2 名册阈值 | 4.1 脚本阈值表 | 5.1 路由记录 |
| §3.3 治理节点 | 4.4 评审卡模板 | 5.2 差距登记 |

每行都写清上游机制、具体载体、下游消费物，不能只写“见 §X”。

### 5. 联动核对图号与引用

新增跨章节图后，全文扫描图题、图号和旧引用，确认图号连续、不重复、不悬空；图题统一使用：

```html
<p align="center"><b>图 X-Y　标题</b></p>
```

### 6. 不把章节编号当作逻辑

章节号只是导航。真正的逻辑由交接物和依赖边表达；若章节顺序与依赖顺序不同，必须在章节首部显式说明输入、输出和消费方。

### 7. 提交前机械验收

1. `cp <doc> /tmp/doc-pre-<tag>.md`，再用快照与 `git diff` 逐行核对，确认只保留计划改动。
2. 先做 Mermaid 源码验收：围栏成对、每块有合法图声明、关键节点和边标签在位。
3. 再做 Mermaid 全量渲染与视觉校对；源码通过不等于渲染通过。
4. 扫描旧图号、旧章节归属、悬空 § 引用、乱码和畸形表格行。

## 常见误区

- **只写“本章承接上一章”**：没有交接物，读者仍不知道上一章交出什么、这一章消费什么；改为要求/载体/证据/判定/回写的链。
- **接口表只写“见 §X”**：不能判断依赖是否真实接通；每行必须是上游设计 → 本节落地 → 下游消费。
- **只修正文不修图号**：新增总图会让后续图号与引用错位；图题、正文引用、目录和附录术语必须联动扫描。
- **只渲染新图**：其他图可能因编号或大段编辑被破坏；必须全量渲染。

## Output contract

交付时列出：总图位置、接口表位置、每章交接物、图号/引用扫描结果、源码与渲染两类验收结果。未完成渲染必须明确标为未验证，不得把源码合法性写成渲染通过。
