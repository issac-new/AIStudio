# 旧裁决重判编排（readjudication-orch）

orchestrator 侧编排手册：用户质疑「当时裁决的分析完善点有问题」（当时模型能力/前提过期）时如何组织重判。对账/重校正的完整方法论权威源=default profile 的 research-ledger-reconciliation（三轴：对账管落地状态、重校正管内容真伪、重裁决管判定质量）；融合落地对账=fusion-landing-audit；裁决矩阵四判定的方法修法=article-methodology-fusion 第 5 步。本件只存 orchestrator 编排层经验，防与 default 件双事实源漂移。

## 触发判别（先分层再派工）

用户质疑旧裁决时，先判质疑的是哪一层：
- 抄写/引用错（报告与源材料不一致）→ 重校正 recheck（重读内容真伪）
- 判断/前提错（分析本身浅/错/漏）→ 重裁决 readjudication（重判裁决矩阵本身）
- recheck 通过不代表判断层无缺陷，反之亦然——两轴正交。质疑措辞含「当时模型智力」「分析完善点」时必为判断层，勿用 recheck 结果搪塞。

## 试点先行，禁直接全量重派

先用 1-2 份裁决文档试点测翻案率，再决定是否扩大。实测基线（双裁决 60 行样本）：判断层严格翻案率仅约 3%——弱模型缺陷不在判断力，在声明-实存对账层。扩大前向用户报权衡：严格翻案约 3% 意味着每份预期再捞 1-2 条，修流程收益通常更高。

三类系统性缺陷（重判时重点排查）：
1. 等效印证过度声张——静态读判（文档 grep+实读）原理上看不见运行层漂移：配置被批量重生成静默洗掉、服务裸奔数周无告警。等效物在盘不等于等效物存活。
2. 语义落地虚报——机制落地有 grep 验收、语义落地默认没有，无验收的成色声明会注水。
3. 裁决产出无对账——同源双裁决并存、条数三处统计打架。

## 汇报纪律

- 翻案率双口径：严格翻案（判定本身变更）与广义翻案（翻案+升级+降级）差一个数量级，只报其一必然误导扩大决策。
- 合并裁决表分列：维持/真翻案/升级/降级，两口径翻案率并列。

## 派工契约（写进重裁决卡 body）

1. 注入「当时之后发生的新事实」证据包：前提失效类事件的实测锚点（端口探活/配置回读/新管线实战记录），worker 只重判不重查。
2. 原裁决文档零改动；翻案结论落独立 VERDICT 文件 + DATA-LOG 底稿。
3. 收卡独立验收=抽验翻案/降级条目的证据亲测复跑（端口 curl/落点 grep/逐行表计数核对），不信 worker 自报。

## 方法修法（待 default 侧落地）

以下四条是重判抽出的流程修法，权威落点=article-methodology-fusion 第 5 步与 fusion-landing-audit（default profile 所有，orchestrator 会话 skill_manage 拒写，需前台会话直改）：
- 等效印证必须附运行层探针：配置键 grep+端口探活+周期复扫，禁静态读判一次性判死
- 语义落地必须过 grep 验收+落点行级登记，验收不过不进成色声明
- 「集群无 X」类能力快照前提必须写失效条件；前提清单禁凭记忆枚举（可信边界/通信面类先 lsof 等实测盘点再列）
- 裁决矩阵落盘前机械自检：条数三方对账+同源文档查重

## Pitfalls

- 判断层翻案不等于处置变更：翻案分四级（判定变更/升级/降级/风险勘误），汇总时分开计；「落点声明时为真但今日不存活」是验证层勘误不是判定翻案。
- 落点声明不等于落点存活：keep 项重验时抽验今日存活（md5/行数/在盘），实体层无 git 跟踪的双层布局（symlink 指向的实体）最易静默丢失，数周无告警。
- 重裁决卡可能被路由到非指定板：gateway 重启窗口期 kanban_create 成功但写入落他板——目标板查无此卡时先循环扫全部板分库再定性（见 kanban-task-pickup-diagnosis），他板命中且 running 时禁重建（双跑），盯原卡等结果。
- DROP 层是最强层：整类否决零翻转是常态，翻案多因前提清单漏项而非语境判断方法错——重判火力优先给等效印证与成色声明条目，勿平均分配。
