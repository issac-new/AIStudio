# 验收证据与执行留痕纪律（orchestrator 侧 delta）

> **出处头**：验收纪律的权威源是 default profile 的 `worker-completion-independence-verification`（陷阱库 A-Z）与 `orchestrator-lessons`。本件是 orchestrator 自有目录的补充落点（skill_manage 拒跨 profile 写时的应急落位），只收三条新规则；待前台 default 会话把本件合入上述两件后，本件删除——防双事实源漂移。

## 触发

- 收到任何「卡已 done」回执（worker complete 或 dispatcher 代收）
- 自己写报告/验收块/汇报里的执行断言
- 要动常驻回归集（共享探针套件/判定代码）

## 规则一：执行记录只能转录真实回显（编制红线）

报告/验收块里的执行类断言——「实际跑通 ✓」「N/N PASS」「VERDICT=X」「rc=0」——只能来自当轮真实终端输出。

- **顺序不可倒置**：先跑出输出再写数字。把预期输出预填进验证块再回头补动作（先写报告后补跑）是假绿的根因形态：补跑一旦失败，带绿字的报告已进入交付链，用户和下游卡已采信。
- **可追溯判据**：验证块里每个数字必须能指回一条终端回显或产物文件；指不回的删掉或改写为「未验证」，动作未发生时写「待执行」。
- **复盘揭出后的修正不是只改数字**：把失败实录（哪轮失败、根因、修复）写回报告，时间线如实。

## 规则二：卡终态 ≠ 冻结验收达成——逐项对照生效层

收到 done 回执后，验收结论逐项对照**卡 body 冻结的验收标准**，不对照 complete summary 的交付描述。

- **机制**：系统侧关卡依据的是交付自述摘要；摘要可以如实描述一个与验收项不同类别的真实产物——验收项点名「堵 X 写入路径的门」，交付物是独立的旁路 CLI（产物真实、测试全绿、门却没装上），卡照样流到终态。
- **检测法**：逐验收项比对生效位置——验收项点名的生效层（写入路径内 / 独立旁路；源码层 / 脚本层 / 报告层）与交付物实际生效层。类别错配即验收未达成，即便交付物本身质量高。
- **执行侧镜像**：冻结验收的落地比预想重（要改源码 + 持久化）时，要么做全，要么 kanban_comment 提请改验收——禁止悄悄交付邻接替代物让卡「看起来完成」。

## 规则三：常驻回归集不是试验田——动共享验证基线后当场复跑

往常驻安全回归集（探针套件等共享验证基础设施）加探针/改判定代码，属于变更「所有后续任务的放行尺子」。

- **硬规则**：改动后必须立即复跑全套并看到预期 verdict（全绿/GUARDRAIL-EFFECTIVE）才能继续其他任务；出现 ANOMALY、探针报「无实现」、意外 SKIP 即停手先修基线。
- **机制**：带着自己刚弄坏的基线继续干活 = 用坏尺子放行后续交付，故障在无人察觉时扩散到每张经它验收的卡。
- **合入纪律**：新探针先在 scratch 副本里过全链（注册表、调用路径、fixture），确认可跑再合入常驻集并当场复跑全套。
