# 修复类交付的独立验收

触发词：验收修复卡 / 改引用 / 悬空引用清零 / 替换旧值 / 边界修复 / 顺手修复。

> 修「缺陷」的卡的验收目标与修「功能」不同：功能卡验「该干的干了」，修复卡验「缺陷类没了」。
> 本技能与 `worker-completion-independence-verification`（一般验收纪律）互补：那张管所有交付的通用核验，这张只管修复类交付特有的四项检查。

## When to Use

收到修复类交付的 done/自述：修 N 处悬空引用、替换过期值、改指向、修边界缺陷、批量清理。卡面验收常写成「N 处已修」「清零」「最小改动」——这类声明每一项都需要专门的验证手法。

## 四件套（按序执行，缺一即验收不完整）

### 1. 先定责，再处置

验收中发现的缺陷先归因：grep 本次交付的 patch 记录/差异，确认是**本次引入**还是**存量遗留**。

- 本次引入 → 打回本卡修
- 存量遗留 → 不阻塞本卡验收（不属本卡范围）；按「实用 gap 立即落地」走用户裁决 → 追加小卡，并回**原卡** comment 销号登记项
- 不归因就打回 = 把存量债误记到本次交付头上，worker 会徒劳返工本不属于它的缺陷

### 2. 扫全类，不只验点名的 N 处

修 N 处实例的任务，验收必须扫**全部同类位**：改 6 处引用 → 扫受影响集合内**所有**同类引用逐一 `ls`/`grep` 核实，不只验卡面列出的 6 处。同缺陷常是模式级复制产物，残余在没被点名的位点上；扩大扫描是「类清零」结论的唯一合法依据——没有扫描输出，验收结论只能写「N 处已修」，禁写「清零」。

### 3. 用结构不变量证明「最小改动」

对「单行替换 / 没动别的」类声明：对比 patch 前后 `grep -c '^##'` 节标题数一致、行数变化仅限被改行。文本文件里「只动了这一行」只能靠结构不变量机械证明——worker 自述与肉眼扫 diff 都不算证据。

### 4. 指向内容真实性抽查

「改为指向文件 X 的类目/小节 Y」类修复，X 存在还不够——对 Y 的名字 grep X 原文，命中数 >0 才算真指向，防「指对了文件、编了类目名」。

- 命中 0 → 先查语义迁移：内容可能实际落在另一份专域文件，且该文件已被工作流其他锚点强制引用（闭环不受影响）→ 备案为非阻塞偏差，不机械打回
- 迁移解释也立不住 → 返工

## 收尾

验收结论写 kanban_comment：逐项标注 ✅/⚠️/❌ + 证据命令原文。🔴 comment/complete 等所有 kanban_* 调用**显式带 `board=<slug>`**——漏传在非默认板报 "unknown task"，报错形似卡不存在，实为路由落错库；带参重发即过，别按「卡丢了」诊断。

## Pitfalls

- **把「N 处已修」当「类清零」**：点状验收漏掉未列出的同源位点；只写扫描结论支持的强度
- **把存量遗留打进本次交付**：先 grep 变更记录定责，再选处置
- **把 `ls 文件存在` 当「指向正确」**：目标文件存在 ≠ 引用的类目/小节在里面
- **「最小改动」靠自觉**：结构不变量（标题数/行数差）是唯一机械证明
