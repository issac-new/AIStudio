# 费曼式系统根因审视（Feynman Systems Autopsy）

> 2026-08-25 Hermes agent teams 全集群审视实战提炼：8 项问题修复 + 5 项根因解剖 + 6 张根治卡全链路。
> 核心准则：**「我不能重建的，我不理解」；重复出现的问题 = 从未被真正解决的问题。**

## When to Use

- 用户要求「审视系统/找根因/机制存在但没生效/为什么这个问题反复出现」
- 修复同一类故障第二次以上（漂移复发、cron 静默失败、协议违规重复）——复发即信号
- 大型修复收尾后要做根因层沉淀，而非停在擦屁股

## 方法论框架（用户指定组合，按序执行）

1. **第一性原理**：拆「系统职责的本质」——这个机制为什么存在？它的失效意味着什么？
2. **四个导向分级**：价值/目标/问题/结果——按 P0(职责失效)/P1(机制漂移)/P2(卫生) 三级金字塔分类
3. **MECE 分类**：问题清单互斥穷尽，每条必须有命令级证据（Toulmin：主张+根据+佐证）
4. **金字塔结构**：塔尖结论 → 分层论据 → 塔基证据
5. **麦肯锡七步**：界定问题→分解→优先级→计划→分析→综合→交付

## 假懂层识别（费曼检验）

对每个系统组件问：「如果让我从零重建，我能重建吗？」
- 能重建（机制透明、操作过、验证过）→ 真懂
- 只能照抄/只知道开关位置 → 假懂层

**假懂层的典型形态**（2026-08-25 实证）：
- 机制完备率很高，但**生效回路是断的**（watchdog 在报但没人看、fence 存在但种频>剪频）
- 自愈层自己不喊疼（失败通知复用 deliver 通道，deliver=local 的 watchdog 安静=静默故障）
- 规则管得住文档管不住行为（prompt 层规则对抗默认值胜率极低，~18%）
- 文件边界=来源边界而非职责边界（多波融合只增不删）

## 解剖卡设计（每项假懂层一卡，5 段结构）

每个解剖对象强制 5 段：**现象(命令/日志证据) → 机制(代码路径 file:line) → 根因(为什么这样设计/为什么失效) → 根治提案(具体改动点，禁"建议加强"空话) → 费曼检验(如果重建我会怎么设计)**。

方法论约束写进卡面：调研先行（先取证后结论）、证伪主义（不信组件自报，独立验证）、禁营销语言。

## 根治卡 F 分层模式

解剖报告出来后按「止血→根治→结构」三层派工：
- **止血卡**（最高优先级）：每天都在产生错误记账/静默故障的先修
- **根治卡**：消除振荡源/违规源
- **结构卡**：文档归并/标注降级，依赖前序卡的判定结果（用 kanban parents 挂依赖链）
- 每卡带 frozen 验收标准 + staged-action-proposal 强约束 + pytest 基线对比要求
- **重型/goal_mode 卡必设 max_runtime_seconds**（缺省 0s 立即超时）

## 验收纪律（orchestrator 侧）

- worker 自报完成 **必须独立核验**：grep file:line 证据、跑 watchdog 回归、查 DB/文件系统
- 修复后顺手检查涟漪：worker 长任务可能触发种子机制再漂移（复跑 inventory_watchdog）
- 结构卡的归并映射表必须先审批再动手（决策点拍板后 unblock）

## Pitfalls

1. **分类器语义混淆**：pid gone = crashed（真死，合理重试）；rc=0 无 terminal call = 可能是供应商熔断误报，重派前先查 run 时长分布（60-80s 连环死 = 环境故障非模型违纪）。
2. **修复≠理解**：当天清零的漂移 6 小时内可再生——没修种子机制的修复都是治标，必须在报告中标注「治标的搬运工」。
3. **审视报告不落地 = 白审**：解剖报告必须转成带依赖链的实施卡（parents 表达），否则两周后同样的问题再出现。
4. 委老实未竟项要记录并接受（如写入保护拦截的 patch），不可强求 100% 闭环而放宽验收。
