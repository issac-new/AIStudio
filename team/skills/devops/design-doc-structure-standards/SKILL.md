# 设计文档结构标准（结构层纠偏合流）

> 收录设计文档四类结构层纠偏的定稿口径。内容纪律（费曼/纯态/质量门）在
> `as-is-design-doc` 与 `document-writing-craft`（default profile，只读）——本 skill
> 管结构层：一节该怎么组成、全文怎么提纲、节该放哪章、多视图怎么画。

## When to Use

- 写/整改设计文档的章节结构时（与 as-is-design-doc 同时加载）
- 用户说「措施不能称为设计」「心智负担太重」「这是调度编排的内容啊」「投影关系要画出来，否则看不懂」「没有剥离干净，X 是 Y 的基础」

## 一、机制小节三层标准（措施 ≠ 设计）

用户判词：「当前说的措施只是标准的执行落地方法，不能称为设计，是技术实现而已」。

| 层 | 回答的问题 | 写法 |
|---|---|---|
| **标准** | 什么算合格？ | 可判定条款（阈值/必备件/禁令）——设计本体 |
| **闸门要点** | 怎么判定有效？ | 哪个环节、什么手段、看什么信号判达标 |
| **措施** | 标准怎么落地？ | 标注「执行〔标准名〕的措施」，不得裸奔成清单 |

每节措施段前插两张表（标准表 + 闸门要点表）；引言句改「执行〔X〕标准的三条落地措施（标准见下表）」。自查：把该节条目逐条问「判定条款还是执行方法？」——全是执行方法 = 实现汇总不是设计。

## 二、提纲挈领改写（纲举目张）

用户判词：「要提纲挈领 纲举目张的讲……理解起来心智负担太重了」。

- **每节一句纲**：「本域回答什么问题 · N 条机制名 · 实现落点 §X.X」；条目为目挂纲下，只读各节纲句即得全文骨架
- **禁双导语**：一节一套导语。「本域提纲」句 + 四段式引用块（它是什么/为什么需要/怎么运转/何时介入）并存 = 双导语，四段式删
- **论证降从句**：独立论证段（「为什么这样做」「为什么不是别的做法」）整段删，理由压成从句并入机制句；同一论证复现只留一处
- **同类条目收敛成表**；叙述段只留判断句
- 心智负担的来源是双导语与成段论证，不是信息量——瘦身不等于删机制

## 三、章节错位检查（迁移不删内容）

用户判词：「不知道为什么要在这里……这是属于调度编排的内容啊」。

每节必答「它为什么在这个章节」；答不上 = 错位（如链路级载体分工出现在典型岗位章）。处置：整节**零丢失迁移**到回答该问题的章，压缩为该章语境的一段 + 表；原章纲句写「X 见 §新落点」保可发现；禁顺手删。

## 四、多视孩子昵称（三视图/投影关系）

用户判词：「我要的是三视图……不是一个表格」「投影关系要画出来，否则看不懂」。

- **图 ≠ 表**：用户要「视图」时交付 mermaid 图（一张图 N 个 subgraph 纵向堆叠，C4 式），不是对应表
- **投影必须画出来**：共享编号 ≠ 投影关系。跨 subgraph 连线带标签：结构部件 `-.->|"投影"|` 机制域、机制域 `-.->|"承载"|` 承载者、机制域 `-->|"执行"|` 执行者；线型即语义（粗虚=投影/承载，粗实=执行落位），图下配投影读法表（每条线一行：落点+执行者）
- **编号跨视图全局唯一**：节点 ID 按视图加前缀（V1acc/V2S1/V3orch），复用 ID 渲染报错
- **堆叠面板 init**：`subGraphTitleMargin` 上下 8-10、`padding: 18-20`，防面板标题与入边束相撞
- **跨视图边使子图内 `direction` 失效**：一旦有节点连出 subgraph，内部 direction 被忽略，面板横向漂移（如第三面板偏左下）——渲染后接受轻微漂移，不追完美对齐
- **linkStyle 序号计全部边**：按声明顺序全局计数，留边界注释（`%% 视图内边 0-13，跨视图从 14 起`）防后续编辑错改
- **验收双通道**：先 SVG 源码断言（标题/边标签精确计数/dasharray 样式/节点在位），后一次 vision 终检（压字/遮挡/对齐——SVG 源码看不出的事）；一轮修完再渲染复验

## 五、写作事故防线（execute_code 大段手术）

- **裸索引切片 = 截断风险**：`text[a:b]` 替换大段起点算错，1336 行文档瞬间剩 354 行。切片后立即 `len()` 断言行数，差 >20% 即 `git checkout HEAD -- <doc>` 恢复重做；大段手术优先用两个唯一锚串的 `str.replace`，禁裸索引
- **用户报「内容丢了」先对账再动作**：三件套——章节+小节计数清单 / 关键句探针 grep（当前 vs 上一入库版逐项比对）/ `git diff` 定实际改动范围。磁盘完整 → 结论指向编辑器旧缓冲（外部改写后不自动 reload，让用户 Revert File），**禁盲目回填**（回填=制造双事实源）
- **留痕 comment 被拒先改内容再疑工具**：kanban_comment 报内部函数错（`no such function: kanban_write_sanctioned` 类）= body 内容触发写入审查，改写敏感表述后重发，不反复重试原文
- **图表渲染直调 subprocess 列表参数**：`subprocess.run(['mmdc','-i',fn,...])`；禁 `bash -c` 内嵌 `python -c`（markdown 反引号/引号经两层 shell 展开被吞，mmd 输入文件根本没写出来，rc=1 会被误判成渲染失败）

## 六、双节交叉剥离（「X 与 Y 没剥离干净，Y 是 X 的基础」类重构）

用户判词：「3.1 和 3.2 没有剥离干净……3.2 是 3.1 的调度编排基础……把流程和边界、逻辑讲清楚，可以画个完整的图」。

- **先病灶实锚，后动刀**：逐条列出交叉点并给行级证据。四类典型病灶——①同一机制两半写（两节各讲一遍、互相「见 §X」打乒乓）②总览图节点混入他域内容（图节点文字与总览表行矛盾）③悬空引用（多处引「§X 机制名」，目标节里根本没有该段——本体常在 `_shared/` 外部文件）④他章内容混入打断主线（节尾堆孤立小节，流程主线看不见）
- **剥离方向由依赖关系定**：被依赖节（上游）重排为**一条完整链**——每阶段固定写输入/出口/守门者，配一张全流程总图（用户点名要图时这是交付物不是可选项）；依赖节（下游）收敛为**前提机制清单**（它为流程提供什么判据）。两节接缝用**接口表**接线：上游每阶段 × 消费下游哪个机制/判据，一行一条；消费点行内标注「由 §Y 定义、本域只执行」——边界从 prose 变结构声明
- **孤立小节并入其支撑的阶段**，不留节尾；「一条消息的旅程」类叙事改为「全流程的实例化」图，图号顺延后全文扫旧图号引用
- **联动面清单**（内容搬家后逐处 grep 旧归属措辞）：总览表行、架构图节点文字、承载/盘点表、附录术语表——凡以旧归属口径描述该内容的行全部对齐，禁只改正文两节
- **验收五件（顺序固定）**：①开工先 `cp <doc> /tmp/doc-pre-<tag>.md` 快照 → ②完工 diff 快照逐行对账丢失行（逐条判有意/误删）+ 语义保全点抽验（关键机制句 grep 现文，20+ 项）③mermaid **全量**渲染（非只渲新图，防改 A 坏 B）④悬空终扫（旧机制名/旧节名 0 残留 + § 引用目标标题全存在）+ 纯度扫描（历史词/U+FFFD/`^||` 畸形表行）⑤diff 落点核对——工作区文件常本就领先 HEAD 多轮，`git diff --stat` 大 ≠ 本次改动大，用快照 diff 圈定本次落点、逐 hunk 核「只落计划面」
