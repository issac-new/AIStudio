# 作业进度/状态汇报纪律（operational-status-reporting）

Orchestrator 向用户汇报定时作业、nightly loop 或 Kanban 调度状态时遵守的
证据纪律与表达规范。触发：用户问「检查进度 / loop 跑得怎样 / 调度健康吗」，以及一切任务收尾/状态类汇报。

## 完成判定不作自决：只报证据支持的档位，不作总体完成断言

- 自查（如 cron 巡检、逐 job 核验）能支撑的只是「已核查样本的档位」，不是整体完成——除非
  逐 job 证据覆盖全部实体（旁路审计确认数量守恒），否则禁把「已核查部分健康」升格为
  「全部已完成」。用户问「检测进度并推动完成」时，答案必须落在证据级（已验证/推断/未核），
  总体档位取证据最弱的一档，且每档给出证据源（job ID/时间线/返回码）。
- 过程叙事禁进汇报正文：「我接着将X」「期间还发现Y」之类的过程句不改变用户决策，删除；
  只留状态结论、证据、下一步。跨轮状态陈述必须与上轮回执一致，矛盾时以机制记录为准。
- 「整体完成」断言只能出自全量证据（数量守恒/全量 job 状态遍历），抽查/抽样结论必须标注
  抽样口径，并给出补全路径（何时能拿到全量证据）。

## 证据第一：进度必须来自机制，不来自聚合猜测

- **Loop 进度查 loop 快照、步骤返回码、对应 cron run 记录**，不要用
  Kanban 完成卡数或 task_events 聚合数代替。Kanban 吞吐只证明看板有
  活动，不证明某个 loop 步骤已执行或成功。
- **查 cron 运行历史必须用 cron job ID**，不能把 Kanban task ID 传给
  cron 查询——两者命名空间、运行记录完全分离；传错 ID 得到「无运行
  记录」的假阴性，误导结论。
- **事件详情查 task_events 的 payload 列**（人话原因、blocked 理由、
  run 迭代次数），先读事件再下结论。

## SQL 查询前先确认 schema

- 先 `PRAGMA table_info(tasks)` / `PRAGMA table_info(task_events)` 再写
  查询。不同表的时间列（`created_at` / `last_heartbeat_at`）、事件载荷
  列（`payload` vs `detail`）不可臆测——凭记忆写列名会撞 `no such
  column`，拖慢诊断。
- 查询用只读 URI 前注意 WAL 模式的坑（见 orchestrator-scheduling-audit）。

## ETA 预估：实测校准，不拍脑袋

用户追问「预估完成时间」时按此推算，给三档（乐观/基准/保守）而非单点：

1. **取同域同类卡实测耗时做基线**：`SELECT id,title,created_at,completed_at FROM tasks
   WHERE status='done' AND completed_at IS NOT NULL ORDER BY completed_at DESC LIMIT N`
   算均值——估的是「这一类卡」，不是拍一个通用数。
2. **当前卡看事件流定阶段**：`created → claimed → heartbeat 连续? → commented（前线
   侦察摘要）`。侦察期完成进入写节期的卡，剩余时间按基线扣除已跑时长估；
   未被拾取的 ready 卡要加 dispatcher 空窗（实测约 1-2 分钟）。
3. **预估必须落在三档**：乐观（卡链全程按实测最快档走）/ 基准（同类均值）/
   保守（含 crash 重派 +20-30 分、门控连锁延迟）。**基准档给一个明确钟点**，
   不给区间就答「大概」——用户要的是能安排下一步的时间点。
4. **首张卡实测出来后立即校准后续预估**：链式卡首张 done 时用其实际耗时 ÷
   原预估的倍数，重推剩余卡（实测比预估快 N 倍 → 后续卡预估同步除以 N）。
   跨会话接续追问时，先直读卡态与事件流（started_at/心跳时刻）刷新「已跑多久」，
   不沿用上一轮给的钟点。

## 表达规范：专业紧凑，禁卖萌

- 汇报结构：状态结论 → 阻塞点 → 证据（ID / 时间线 / 返回码）→ 下一步
  动作。用紧凑的状态表，不堆段落。
- **禁用 kawaii 卖萌体**（喵~/sparkle/desu/颜文字）、与主题无关的 emoji、
  以及刻意装可爱的承接句。用户明确要求严肃专业口吻。
- **汇报说人话优先，禁机制行话高密度堆叠**（堆叠会被「说人话」点名纠偏）：
  用户是裁决者不是机制操作者——第一句用大白话说清「做了什么、对他意味着
  什么」；机制术语（锚点/守门/落点/互链/成色等）首次出现必须带一听就懂的
  同位解释，或干脆不进正文（细节放看板 comment/存档，正文给指针）。
  模板规定的是「讲哪几块」，不是「用什么语域」——每句话过一遍「他不用翻
  上下文就能一遍读懂」的测试。
- **不把无法由当前机制执行、且未经用户授权的动作列为「可选项」**，例如
  「要不要我联系妈妈重开窗口」——若阻塞在用户侧（如真人需发一条消息
  解锁 iLink 窗口），就直说所需动作，不装成 agent 可代办。

## 裁决请求格式：编号选项、一句代价、可一句话裁决

- 决策请求固定四件套：背景 1 句 → 选项 A/B/C（每项一句代价/后果）→ 建议项
  给一句理由 → 「不回复就按建议执行」默认声明。用户的裁决语言是最短指令
  （「按建议执行」「执行方案B」），请求必须做到读完即能裁决。
- 禁把机制细节、执行时间线、实现取舍铺在选项前面——用户裁决只需要「选什么、
  代价是什么」；机制细节放已落盘的卡/comment，选项里给指针。
- 请求被判「没看懂」时重讲规则：每件事 2-3 句（背景→还没做的一步→选项→
  建议），禁复述原绕口表述再逐词解释。
